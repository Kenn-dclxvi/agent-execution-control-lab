# C280・C282の結果待ち制御とC147の対応分析

2026-10-07。保存済みC280・C282の各70件を読み取り診断した。追加試験、再採点、Candidate作成は行っていない。

## 結論

C282の不改善から、結果待ちの影響範囲限定に削減余地がなかったとは判断できない。C147で閉じていた開始確認と本文読み取りの分離は、C280・C282の両方に残った。C282の追加文はC147の一部に対応するが、独立した呼び出しの共同発行と、検証の途中でモデルへ結果を返さない制約を再現していない。短い文の追加だけでは既存の処理分割を変えられず、他の経路の増加が集計値に現れた、という説明が今回の証拠に最も整合する。

これはC147の効果を今回のモデル・条件で証明するものではない。C147とC280・C282を同条件で今回測定した比較はない。過去のC147の数値を今回の差へ直接帰属させない。

## C147に含まれる内容との違い

[C147本文](../prompts/candidates/the-caption-3ce91a4-result-effect-scope-r1/files/AGENTS.md.txt)の`DECISION_BOUNDARY`は、結果が対象・許可・方法・停止条件を変え得る操作だけを停止対象にしたうえで、既知の独立した呼び出しを分割せず同じモデル処理から発行する。開始識別確認が変更と検証だけを止める場合、許可済みの読み取りは開始確認と共同発行することまで定める。

`VALIDATION_CLOSURE`と`VALIDATION_PLAN`は、順序付き検証を一回の外側呼び出し内で個別実行し、失敗時に後続を止める。全結果を受領してから一度だけ完了を判断する。`EVIDENCE_GATE`は、確定した判断を無関係な結果によって未確認へ戻すことと、実装方法の選択だけを理由とする追加探索も制限する。

C282は「影響しない作業は止めず、再判断しない」までを追加した。どの呼び出しを共同発行するか、結果をいつモデルへ返すか、検証途中の再入をどう閉じるかは明示していない。共同発行が明示されていないことと、モデルが実際にすべての操作を同時発行すべきことは区別する。必要な依存や停止条件がある検証の並列実行を要求する分析ではない。

rootの保存済み実行履歴から、初回識別確認と最初の対象・指示本文読み取りの外側ツール呼び出しを照合した。F01・F02・F03は各5件。

| 観測 | C280 | C282 |
| --- | ---: | ---: |
| 開始識別確認と初回本文読み取りが同じ外側呼び出し | 0 / 15 | 0 / 15 |
| 本文読み取りが開始確認とは別の外側呼び出し | 15 / 15 | 15 / 15 |

初回の`rg --files`による所在取得が開始確認と同じ呼び出しにあるrunはあるが、本文取得の共同発行とは数えていない。外側呼び出し件数をコマンド数やモデル処理回数と同一視しない。

過去の[C125–C147の研究記録](candidate125-candidate147-control-findings-synthesis.md)では、C145の開始確認と本文の分離に対し、C147はこの3ケース15件すべてで共同発行を実現した。今回、その局所的な差に対応する経路がC282へ戻っていないことを確認した。単にC147にある考え方を含むことと、同じ実行境界が成立することは別である。

## 増加の大きいF08

F08のrootの外側ツール呼び出しは、C280の中央値5回に対しC282は8回。8回の経路はC280で1 / 5件、C282で3 / 5件だった。8回の経路のトークンは両条件で約245–247千、5回の経路は約153–155千で、同じ呼び出し件数の経路では近い値になっている。

具体例はC280 `71751e85a1444029b95003e1c8878d2c`とC282 `ad1a5fa11cc044a8b163b6e4ded80ae2`。両方とも開始確認、指示と対象本文、補助的な所在確認、`case.json`の確認、同じ参照文の変更、最後の差分確認を行った。C282側では途中の所在確認が別呼び出しへ分かれ、変更後の`git diff --check`、内容差分、`git status`も3回の外側呼び出しへ分かれた。C280側は最後の確認を一回にまとめていた。

したがってF08の増加は、成果のために読む内容が大きく増えたという説明より、似た作業を細かく分けた経路の頻度が増えたという説明に合う。なぜ追加文でその頻度が変化したかは未確定であり、文の因果効果とランごとの実装選択の変動を分離していない。

## F04の検証境界

F04の外側ツール呼び出し中央値は9回から11回、プロセス結果待ちを含む呼び出し中央値は1回から3回に増えた。C282の反復1・3・5では`npm ci`、`lint`、`build`を個別の外側呼び出しから実行し、それぞれの途中結果を受けて待機を発行していた。これは必要な同期を含むため、3回すべてを無関係な待機とは呼ばない。

C147の検証制御は、必要な順序と失敗時停止を保ちながら、この途中のモデル再入をまとめる。C282の追加文は依存する検証を待つことを認めるので、この分割経路を直接閉じない。ここでも、影響範囲限定だけでC147の検証制御全体は再現されない。

## 判断の限界と残る原因

C280・C282とも70件すべて4点で、品質差はない。C282の全体中央値はトークン+3.50%、経過時間+4.53%。A02、F03、F07などには減少があり、一律の悪化ではない。

今回確認したのは、開始境界が両条件で維持されたことと、F04・F08で外側呼び出しの分割が増えたこと。追加文がモデル内部の再判断を何件防いだか、C147の他要素との相互作用がどれほど必要か、各時間差の実行時刻要因は未確定である。ここから「効果が出尽くした」「追加文に効果がない」「並列化すれば必ず減る」とは結論しない。
