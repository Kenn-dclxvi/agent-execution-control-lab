# Candidate317 C316に、完了の報告の形を加える

2026-10-12。利用者の依頼（C316の改善の余地を調べ、Sonnetの報告の長さから進める）を受けて、Candidate本文の作成前に固定する設計記録。[設計原則](prompt-control-design-principles.md)の全文を読み、「Candidateを作成する前の確認事項」の項目1〜9と「処理方法を指定できる条件」に対応させた。計測と記録は[計測と記録の基準r2](shared-instruction-evaluation-criteria-r2.md)に従う。この記録ではbundleを作成しない。

## 目的と役割

- 系列：実行環境を切り離し、負荷を見て次のrunを始める発行の条件（CPU使用率70%以下、間隔1秒）で測る系列。プールは`effective-v1`。
- ベースと直接の親：C316（`the-caption-3ce91a4-receive-form-file-read-range-r1`、2026-10-12にリリース・承認済み、本体へは未反映）。
- 計測の順序：Sonnet lowで測り、Solを測るかはその結果を見て決める（利用者の指示）。
- 評価は計測であり、達成目標を置かない（r2）。

## この一文で何をさせたいか

完了の報告を、依頼が示した条件ごとの結果と、実行した確認の結果だけにすること。実装の経緯の説明、開始時の状態の説明、許可されていない操作をしなかったことの列挙を、報告に書かないこと。

## 1. 比較の基準と、正常な最短経路

基準はC316の同じセルのN=5（[Sonnet low](../evaluations/results/c316-claude-sonnet55-low-standard14-n5_2026-10-12.md)）。正常な最短経路は[C309の設計記録](candidate309-c307-final-check-unit-design.md)の項目1のとおりで、最後の応答で、条件ごとの結果と確認の結果を報告して終える。

## 2. 保存traceで確認した問題経路

C316のSonnet low（累積N=20、280件）の費用は、1セットあたり0.626 USDのうち、キャッシュへの書き込みが0.375、出力が0.182、キャッシュ読み取りが0.069だった。出力の中で最も大きいのは最後の応答（完了の報告）で、1セットあたり約11,400字だった。同じ課題でSol Lowの最後の応答は約4,900字である。

C316のSonnet low N=5（70件）の報告の中身：

- 開始時の状態（HEAD、`git status --short`など）に触れる報告：66 / 70
- commit、push、PRなど、しなかった操作に触れる報告：45 / 70
- 実装の経緯（「元はこうだったので、こう変えた」）を条件ごとに説明する報告が多い

ケース別の報告の長さ（N=5の平均、字）：A01 334、A02 538、F01 877、F02 992、F03 1,016、F04 707、F05 428、F06 767、F07 666、F08 746、F10 1,627。

## 3. 開いている記述と、TaskSpec・正本で防げない理由

C316には報告の形についての記述がなく、報告に何をどれだけ書くかはモデルに任されている。TaskSpecは、停止時に「観測した事実と未完了のcriterion IDを報告する」ことを求めるが、完了時の報告の範囲は定めていない。リポジトリの正本も報告の形を定めていない。

採点（`outcome-terminal-state-evidence-claude-collector-v2`）では、報告の本文が品質に使われるのは、F10のレビューの指摘内容と、F05の確認事項だけである。ほかのケースは、変更の差分とコマンドの記録で判定される。A01は応答本文を判定に使わない。

## 4. 追加する条件の全件

C316の末尾に、次の一項目を加える。

> - 完了の報告は、依頼が示した条件ごとの結果と、実行した確認の結果だけを書く。

- 禁止ではなく、させたい形を書く（C312、C316と同じ書き方）。
- 「簡潔に」「必要な範囲で」のような、モデルの判断に頼る語を使わない。何を書くかを、依頼が示した条件と、実行した確認という事実で決める。
- 新しい操作の発行を求める文ではない。報告は最後の応答で必ず出るので、操作の数は変わらない見込み。
- F10のレビューの指摘とF05の確認事項は、「条件ごとの結果」そのものなので、この文の範囲に入る。停止時の報告（観測した事実と未完了の条件）も、条件ごとの結果として書ける。

## 5. 禁止行動、開放経路、閉じる境界、反証

| 項目 | 内容 |
| --- | --- |
| 閉じる経路 | 最後の応答で、条件ごとの結果と確認の結果以外の説明（開始時の状態、実装の経緯、しなかった操作の列挙）を出力する |
| 現在の開放経路 | 報告の範囲の定めがない |
| 閉じる境界 | 完了の宣言（最後の応答の本文）。保存traceでは最後の応答の字数と、開始時の状態・しなかった操作に触れる報告の数で観測する |
| 正常な処理の保持 | 条件ごとの結果（レビューの指摘、確認事項、未完了の条件を含む）と確認の結果は書ける |
| 反証する構成 | 実装の経緯を「条件の結果の説明」として書く構成は、文の上では違反と判定しにくい。この一文は、報告の範囲を事実で示すが、各文がどこに属するかの判定はモデルに残る。閉じた経路とは主張せず、字数で効果を観測する |

## 処理方法を指定できる条件との対応

| 条件 | 満たし方 |
| --- | --- |
| 1. 無条件である | すべての完了の報告に当てはまる |
| 2. 遵守を観測できる | 最後の応答の字数と、開始時の状態・しなかった操作への言及の有無で判定できる |
| 3. 遵守率を実証している | 未確認。この計測で最初に確かめる |
| 4. 正常経路を保持する | 項目5のとおり |
| 5. 汎用の形で書く | ケース、条件ID、期待値を書いていない |

## 6. 維持する正常経路

- 実装と確認：変わらない。
- F10（レビュー）：指摘の内容と根拠を、条件ごとの結果として書く。
- F05・A01（確認して終える）：確認したい事項を書く。
- 停止したとき：観測した事実と未完了の条件を書く（TaskSpecの要求）。

## 7. 新しく増える判断と、変更対象外への影響

- 新しい判断：報告の各文が、条件の結果か確認の結果に当たるか。
- 危険1：F10やF05で、必要な指摘や確認事項まで削り、品質が下がる。品質で観測する。
- 危険2：条件ごとに結果を書くことが新しい義務として読まれ、短い報告を出していたケースで長くなる。ケース別の字数で観測する。
- 見込みの大きさ：報告が3〜4割短くなると、1セットあたり約3,000トークン、約0.03 USDで、費用の約4〜5%。C316のSonnet lowの5反復の幅（0.6097〜0.6469）と同じ程度で、差が幅に埋もれる可能性がある。
- 固定分：一項目（113バイト）が加わる。

## 8. 評価ケース、比較単位、比較条件、記録する項目

- セル：Sonnet low、Standard14の全14ケースN=5の計70件。
- 比較条件：C316のSonnet low N=5のプロファイルと同じで、prompt identityだけを変える。
- 記録する項目（r2）：品質、処理の適切さ、費用、経過時間、生のトークン（参考）。
- 機序の診断（合否にしない）：最後の応答の字数（全体とケース別）、開始時の状態・しなかった操作に触れる報告の数、出力トークン、応答の数、C316で確かめた機序（状態の確認の置き場所、確認コマンドの受け取り方、ファイルの読み方）が保たれているか。

## 9. 停止条件

C302の設計記録の項目9のとおり。品質が下がった場合は、どの条件の結果が報告から欠けたかを保存traceで確かめる。

## 判断の限界

- 項目2の観測は、C316のN=5とN=20による。
- 採点で報告の本文を使うのはF10とF05だけなので、それ以外のケースで報告に欠けがあっても、品質の点数には表れない。報告の中身の妥当性は、診断として字数と言及の有無だけを見る。
- この記録は採用、release、本体反映を決めない。
