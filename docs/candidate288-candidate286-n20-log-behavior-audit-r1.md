# C286とC288の追加N=15で実際に起きた読み取り動作

2026-10-08。先の[累積N=20比較](candidate288-candidate286-standard14-n20-comparison-r1.md)は登録結果の数値とN=5の実行記録に基づいていた。ここでは、両条件の追加分各210件の保存rolloutを直接読み、指示の差と実際の操作の対応を調べた。生ログはリポジトリへ複製していない。

## 観測

C286のroot指示は、開始時の確認と名指しされたファイルの読み取りを一つの外側呼び出しへまとめるが、ファイル内の取得範囲は限定しない。C288は一般ファイルについて検索で位置を特定し、定義・節などの範囲を取得するよう指定する。C288では開始時の発行方法とMarkdown書式も同時に変更されているため、単一条項の効果を分離した比較ではない。

| 追加15件のケース | C286で見た動作 | C288で見た動作 | 変更前のツール結果量の平均 | 全エージェントトークンの平均 |
| --- | --- | --- | ---: | ---: |
| F04 Web監査列 | 最初の外側呼び出しで`App.tsx`全文を`cat`し、`package.json`とロックファイルも広く読む例が15 / 15件 | 最初の呼び出しで対象語を`rg`検索する例が15 / 15件。次の呼び出しで該当範囲を読む例が中心 | C286 57,905 → C288 28,022バイト | C286 176,429 → C288 116,058 |
| A02 v4経路 | `run.sh`、指示、実装、試験などを広く取得してから対象を読み直す例が多い | ファイル名・語句の検索と範囲指定を使う例が多い。ただし`run.sh`の広い範囲を読む例もある | C286 50,771 → C288 33,107バイト | C286 158,947 → C288 136,814 |
| F08 CLI参照 | 複数の対象ファイルを全文で取得する例がある | 最初の呼び出しで検索を行う例が15 / 15件で、次の範囲取得を組み合わせる | C286 43,225 → C288 18,233バイト | C286 130,539 → C288 108,894 |

F04のC288にも例外がある。run `9b3b3b101f864347bdfb27fd925ed2be`は最初の`rg`検索に`|^`を含め、実質的に広い範囲を返した。このrunは152,154トークンで、C288のF04追加分では唯一140,000トークンを超えた。`rg`を使ったというだけで範囲限定に従ったと数えない。C286のF04で全文取得した件数と、C288で意味上の必要範囲だけを取得した件数を、そのまま厳密な遵守率として比較することもしない。

減少しなかったケースにも、指示変更に沿う動作と追加コストが併存した。追加15件のログで平均した値は次のとおり。全エージェントトークン差とroot入力トークン差はC288−C286である。

| ケース | C286 → C288の外側呼び出し回数 | 変更前のツール結果量 | root入力トークン差 | 全エージェントトークン差 |
| --- | ---: | ---: | ---: | ---: |
| F03 原子的保存 | 3.00 → 4.00 | 14,406 → 13,759バイト | +18,782 | +18,819 |
| F06 空スナップショット | 3.00 → 4.00 | 17,359 → 14,462バイト | +18,584 | +18,620 |

| F01 重複資産キー | 3.13 → 4.07 | 27,784 → 18,722バイト | +10,778 | +10,682 |

F03とF06ではC286が最初の呼び出しで対象の試験や実装を読み、次の呼び出しで変更していた例に対し、C288は最初に対象内を検索し、次の呼び出しで該当範囲を取得してから変更していた。F10月次レビューでもC288は定義を検索した後、コミット時点の該当範囲を別の呼び出しで取得する例があり、C286より約1回多い。F01でも同じ探索・範囲取得の分割が見える。これら4ケースは取得結果が小さくなっても、後続の応答へ元の入力と新たな検索結果を持ち越す回数が増え、入力トークンの増加が総量をほぼ説明する。各追加呼び出しの因果寄与を厳密に分離した数値ではない。

追加210件を一反復相当に合算すると、最初の変更までのツール結果量はC286の348,906からC288の233,926バイトへ減った。一方、rootの入力トークンは1,301,560から1,281,774へ約19,786減、出力トークンは11,532から11,764へ約232増、外側呼び出しは39.40から44.47回へ約5.07回増えた。ツール結果のバイト数はモデルが受け取った正味の入力トークンと同じではなく、追加の検索・取得や後続応答での文脈再処理も含めて判断する必要がある。

## 判断の範囲

F04、A02、F08のトークン減少には、C288が求める取得範囲の限定と実際の読み方の変化が対応している。これは指示差が寄与したという説明を支えるが、ケース全体の正味差や個々の条項の因果効果を確定するものではない。C288でも広い取得の反例があり、F01・F03では検索と追加取得による費用増が見える。書式変更の独立効果は測っていない。

経過時間の登録値はC288のほうが長いが、この読み取り動作だけで時間差の原因を指示へ帰属できない。両追加試験は異なる時間帯に実施され、モデル応答の待ちと出力速度の寄与を同時刻の対照で分離していない。

根拠は[C286累積登録結果](../evaluations/results/bee75634efb749e58de759aaa0b2b848.json)、[C288累積登録結果](../evaluations/results/b1e352d14357403fbd8e3b4a66727ec3.json)と、両結果文書に記した非公開の`codex-homes/<run_id>/sessions/`内の保存rollout。N=5分と追加分は各N=5結果のrun ID集合で区別した。変更前のツール結果量は、最初の`apply_patch`を含む外側呼び出しより前の出力をJSON文字列化したUTF-8バイト数であり、実際にモデルへ届いた意味上の範囲を完全には表さない。
