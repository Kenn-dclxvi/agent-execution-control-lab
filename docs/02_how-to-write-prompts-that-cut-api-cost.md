# API料金を下げるプロンプトには、判断条件を書く

> 実務者向けExecution Controlシリーズ 2 / 8（2026-10-12改版）

## 結論

[前の記事](01_why-prompt-writing-changes-your-bill.md)では、6行の指示で、4つのAIすべてのAPI料金換算が11〜33%下がったことを紹介しました。

では、その6行には何を、どう書けばよいのでしょうか。

今回は、最新版の6行を1行ずつ見ながら、AIが無駄に動く場所の見つけ方と、そこへの書き方を説明します。

**AIが無駄に動く場所を作業記録から見つけ、そこで「どうするか」を、AIが迷わず当てはめられる事実で書きます。**

長く書けば安くなるわけではありません。前の版は約1万バイトありましたが、最新版は6行です。

## 料金が増える場所から逆算する

前の記事では、指示が曖昧なときに起きる無駄として、次の例を挙げました。

- どのファイルを見るか探し回る
- 念のための調査を始める
- 誰が作業するか考え直す
- 終わった後も確認や検証を繰り返す

このほかに、測ってみて分かった無駄がありました。

- コマンドの終了を短い間隔で何度も見に行く
- テストの出力やファイルの中身を、必要以上に全部受け取る

前の記事のとおり、料金を大きく動かすのは、作業中に新しく受け取る出力です。なので、何をどれだけ受け取るかも、プロンプトで決める対象になります。

## 最新版の6行

測った最新版（C316）の`AGENTS.md`は、次の6行です。

```text
- ユーザーが求める結果（作業後にどうなっているべきか）は、ユーザーが示した内容と、それが従うよう求めている指示や正本が直接定めている内容だけで決まる。既存の状態、候補を消去法で一つに絞れること、過去の例、テストの期待値、実装上の都合は、結果を決める根拠にならない。結果が決まっていない間は、依頼内容の確認と依頼で指定された事前確認だけを行い、調査・変更・テストやその他の操作を始めず、決まっていない結果だけを確認して終える。対象の場所や具体的な実施方法が未確認なだけなら、利用可能な情報や環境を確認し、自分で決めて進める。
- 事前調査は、対象と実施方法を一つに決めるために不足している情報だけに絞る。方針が決まった後は、念のための探索・再確認・履歴調査を追加せず、実行へ進む。
- 最後の変更の後、作業ツリーの状態の確認は、依頼や適用中の指示が求める確認のうち最後に実行するものと同じ応答で発行する。その応答の結果がすべて成功していれば、コマンドを発行せずに報告する。
- コマンドの実行とその終了待ちで、ツールの既定値より短い待機時間を指定しない。
- 確認のコマンドは、そのコマンド自身の終了コードと、判断に必要な部分の出力（末尾など）だけを受け取る形で実行する。
- ファイルの本文は、判断に必要な範囲だけを受け取る形で読む。
```

それぞれが止めている無駄は、次のとおりです。

| 行 | 判断する場所 | 止める無駄 | 書き方の要点 |
| --- | --- | --- | --- |
| 1 | 何を成果にするか | 結果が決まっていないのに、推測で編集やテストを始める | 結果を決めてよい根拠と、決めてはいけない根拠を列挙する。場所や方法が未確認なだけなら、自分で決めて進めてよいと書く |
| 2 | 何を調べるか | 方針が決まった後の、念のための探索や再確認 | 調査の範囲を、方針を決めるのに足りない情報だけに絞る |
| 3 | 何を確認したら終わるか | 終わった後の確認のやり直し | 状態の確認を、最後の確認と同じタイミングで出す。全部成功なら、それ以上コマンドを出さない |
| 4 | どう待つか | 短い間隔での様子見 | 待機時間を、ツールの既定値より短くしない |
| 5 | 確認の結果をどう受け取るか | テストの出力を全部受け取る | 終了コードと、判断に必要な部分だけを受け取る形で実行する |
| 6 | ファイルをどう読むか | 長いファイルを丸ごと読む | 判断に必要な範囲だけを受け取る形で読む |

## 書き方で分かったこと

この6行は、項目を一つずつ足したり外したりして、そのたびに4つのAIのうち2つ（Sol LowとSonnet low）で測り直して決めました。その中で、書き方について分かったことが5つあります。

### 1. 無駄が起きている場所は、作業記録から見つける

効いた項目は、どれもAIの実際の作業記録から見つけました。たとえば6行目は、Sol Lowが600行や1,000行を超えるファイルを毎回丸ごと読んでいることを記録から見つけ、そこを止めるために足しました。足した後は、300行を超えるファイルを丸ごと読む回数が16回から0回になりました。

反対に、記録で無駄を確かめないまま残っていた項目は、外しても変わらないことがありました（5で説明します）。

### 2. AIが迷わず当てはめられる事実で書く

3行目は「最後の変更の後」「最後に実行する確認と同じ応答で」と、作業の流れの中の事実で書いています。AIが「もう十分か」を自分で判断しなくても、当てはめられます。この形にしてから、Sol Lowでは確認の後にもう一度戻ってコマンドを出すことが、ほぼなくなりました。

### 3. 「するな」より、「こういう形でやる」と書く

ファイルの読み方は、最初は「1回で300行を超えて受け取らない」と禁止の形で書きました。すると、小さなファイルまで細かく分けて読むようになり、料金ははっきりとは下がりませんでした。「判断に必要な範囲だけを受け取る形で読む」と、させたい形で書き直したら、受け取る量が減り、料金が下がりました。5行目のテストの出力も同じ書き方です。

### 4. 新しい作業を求める文を足さない

「長いファイルは、検索で位置を確かめてから読む」のように、何かをするよう求める文は書いていません。こうした文は、AIの作業を一つ増やすことがあります。止めたい無駄だけを、受け取り方として書きました。

### 5. 効果の見えない項目は外す

前の版には「変更前に、必要な成果、変更箇所、直し方、維持する動作を一つの方針にまとめる」という項目がありました。外して測っても料金も品質も変わらなかったので、外しました。担当を分ける項目も、今回の課題ではAIが作業を分けることがなかったので、外しました。

一方で、2行目（調査を絞る）を外すと、変更前の読み取りが両方のAIで増えました。こちらは残しています。

## 自分のプロンプトに当てはめる

上の6行は、そのまま使える万能プロンプトではありません。今回の計測は、一つのリポジトリの14個の課題についてのものです。

自分の作業に当てはめるときは、次の順で考えてください。

1. AIの作業記録を見て、余計な呼び出しや、大きな出力を受け取っている場所を探す。
2. その場所で、AIにどうしてほしいかを決める（止めたいのか、受け取り方を変えたいのか）。
3. AIが自分で判断しなくても当てはめられる事実で、させたい形を書く。
4. 新しい作業を求める文になっていないか確かめる。
5. 書いた後も作業記録を見て、別の無駄（細かく分けすぎるなど）が出ていないか確かめる。

## これだけ覚えてください

長いプロンプトを書くこと自体が目的ではありません。

**AIが無駄に動く場所を作業記録から見つけ、そこで「どうするか」を事実で書く。**

成果、調査、完了、待ち方、受け取り方を順に確認すると、書くべき場所を見つけやすくなります。
