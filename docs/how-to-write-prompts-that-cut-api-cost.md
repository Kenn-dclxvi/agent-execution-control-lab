# API料金を下げるプロンプトには何を書くのか

## 結論

[前の記事](why-prompt-writing-changes-your-bill.md)では、AIへの指示を0バイトから10,772バイトに増やしたところ、API料金換算が39.95%下がった実測結果を紹介しました。

ただし、長く書けば安くなるわけではありません。

**AIが作業中に迷う場所へ、「進んでよい条件」と「止まる条件」を書きます。**

実際に採用されたプロンプトには、13の詳細な制御規則があります。この資料では規則を一つずつ解説するのではなく、普段のプロンプトを書くときに確認すべき内容を、作業の流れに沿って説明します。

## 料金が増える場所から逆算する

前の記事では、指示が曖昧なときに起きる無駄として、次の例を挙げました。

- どのファイルを見るか探し回る
- 念のための調査を始める
- 誰が作業するか考え直す
- 終わった後も確認や検証を繰り返す

これらを止めるには、ファイル名やコマンドを細かく指定するだけでは足りません。AIが判断をやり直す原因を先に閉じる必要があります。

## プロンプトに書く内容

成果、変更開始、担当と結果、調査と待機、完了について、次の条件を書きます。

| 判断する場所 | プロンプトに書く条件 | 止めたい無駄 |
| --- | --- | --- |
| 何を成果にするか | 利用者が決める結果と、AIが選べる実装方法を分ける。結果が不足している場合だけ質問する | 結果の勝手な推測、自分で調べられる方法についての質問 |
| いつ変更を始めてよいか | 必要な成果、変更箇所、直し方、維持する動作が一つの方針になってから変更する | 分かった場所から始める部分修正 |
| 誰のどの結果で完了とするか | 独立した作業を分ける場合だけ、作業、担当、判定対象、必要な結果を対応づける | 担当の決め直し、欠けた結果の自己補完 |
| 何を調べ、何を待つか | 未完了の成果を決める調査だけを行う。先の結果で対象、権限、方法、停止条件が変わる作業だけを待たせる | 念のための調査、決定済み事項の再確認、無関係な待機 |
| 何を確認したら終わるか | テスト、順序、失敗時の停止、実行中の待機、完了条件を先に決める | 成功後の追加確認、再実行、別作業への脱線 |

そのまま指示へ入れるなら、次のように書けます。

```text
- 利用者が決めるべき成果が不足している場合は、その成果だけを質問し、変更やテストを始めない。実装方法が未確認なだけなら、プロジェクト内の根拠から選ぶ。
- 必要な成果をすべて挙げ、変更箇所、直し方、維持する動作を一つの方針にできた場合だけ変更を始める。
- 独立した作業を分ける場合は、各作業の担当、判定対象、必要な結果を開始前に決める。欠けた結果を進捗報告や別作業の結果で補わない。
- 調査は未完了の成果を決めるものだけに絞る。先の結果で対象、権限、方法、停止条件が変わる作業だけを待たせ、影響を受けない調査はまとめて行う。
- 変更後は必要なテストと差分確認を先に一式決める。失敗したら後続を止め、実行中なら同じ結果を待ち、全結果がそろったら一度だけ完了を判断する。
```

## 実運用版が約10kある理由

[実際に採用されたプロンプト](https://github.com/Kenn-dclxvi/the-caption/blob/3119a91d3fad63180884f80ac6b742fbae328afe/AGENTS.md)は、10.5KBあります。

上の表と指示例は、プロンプトへ書く内容の入口です。実運用版では、「結果が決まった」「調査が必要」「作業が終わった」と判定する条件や例外を、AIが実行中に区別できるところまで具体化しています。

実運用版をそのままコピーしても、別のAIや別の仕事で同じ結果になるとは限りません。重要なのは文字数ではなく、自分の作業で判断が分かれる場所に、判定可能な条件があることです。

## この説明で分かっていることと、分からないこと

前の記事の料金約40%減は、13規則を含む実運用版全体と0バイト版を比べた結果です。上の短い記述だけで同じ削減率になることを示したものではありません。

したがって、上の文章は完成済みの万能プロンプトではありません。自分の作業で起きる無駄を見つけ、進行条件と停止条件を書くための出発点です。

## これだけ覚えてください

長いプロンプトを書くこと自体が目的ではありません。

**AIが判断をやり直す場所を見つけ、次へ進める条件と、そこで止まる条件を書く。**

成果、変更開始、担当と結果、調査と待機、完了を順に確認すると、必要な条件を見つけやすくなります。
