# C147の検証一括実行のSol Low遵守確認と原則改訂

2026-10-07。C147の検証側の処理方法の指定が、GPT-6.1 Sol Lowでどの程度守られているかを、保存済みtraceから確認した記録。あわせて、処理方法の指定を制御として扱う基準を[設計原則](prompt-control-design-principles.md)とルートの`AGENTS.md`で改訂した。新しいモデル実行、再採点、Candidate作成は行っていない。

## 改訂の理由

条件判断へ誘導する制御を避ける理由は、モデル自身がその条件に当たるかを判定する側にいるため、判定を誤れば保証が効かないことにある。ところが改訂前の原則は、この理由ではなく制御の形を基準にしていた。処理順の指定を一律に疑い、「望ましい処理順を直接指示しなければ成立しない案はCandidateを作成しない」「分割を新しい禁止行動へ昇格させない」と定めていた。

この基準のずれによって、[再判定r2](c280-c147-control-group-transfer-reassessment-r2.md)は、C147の「固定した検証を一つの外側呼び出しの中で実行する」という無条件の指定を、方式指定として移植対象から外した。その結果、[C283](candidate283-validation-result-permission-boundary-design.md)には、行為の目的や根拠をモデルに判定させる三項だけが残った。この三項が禁じる操作は、[基準側の監査](c280-c283-three-boundaries-baseline-trace-audit-r1.md)では確認されていない。

改訂後は、誤経路の回避がモデルの条件判断に依存するかで判定する。処理方法の指定は、適用が確定済みの事実だけで決まること、遵守を保存traceで観測できること、同じ比較条件で遵守率を実証していること、正常経路を保持すること、汎用の形で書くことの五条件を満たす場合に制御として扱う。条件の本文は設計原則の「処理方法を指定できる条件」を正本とする。

r2とr1の本文は当時の判断として保持する。r2のうち、単一呼び出しを不要な方式指定として外した判断は、この改訂後の基準では採用しない。一方、方式を指定しない三項が分割を閉じないというr2の反証は、引き続き有効である。

## 確認した対象

いずれもGPT-6.1 Sol Low、Standard14全14ケース、各N=5の保存済みrolloutである。

| --- | --- | ---: |
| C147 | 9月30日の[C147・C276・Control-Free比較](../evaluations/results/sol61-c147-c276-free-low-medium-standard14-n5-cli0159_2026-09-30.md)のlow | 45 |
| C276 | 同上のlow | 45 |
| C280 | result `794d02abe894456686eea22e9b6f0fed` | 45 |
| C283 | result `8f11b7122d6847a88e81a494c4480e99` | 42 |

C283は、rolloutが保存されていない3件（`99bc3496f3474ff89715c00a098a259c`、`74931e1d59b04e5cbcd7be1ecade6d16`、`f585826dd3e74d3e933b81afed00f24e`）を除いた。変更を伴わないA01、F05の2ケース、F10の2ケースは、検証側の指定の対象外である。

C147の該当規則は`VALIDATION_CLOSURE`と`VALIDATION_PLAN`である。変更後のrootの検証は、一つの外側呼び出しの中で、固定した順に個別に実行する。各終了コードを確認し、失敗なら後続を発行しない。未終了の結果には同じ呼び出し単位への待機だけを許す。

## 判定方法

rootのrolloutで、apply_patchを含む最初の外側呼び出しを変更とした。それより後の外側呼び出しを、コマンド実行を含むもの、待機だけのもの、再修正の三種に分けた。コマンド実行を含む外側呼び出しが1回以下で、待機だけの呼び出しと再修正がないrunを、検証を一括で実行したrunとした。数えるのは外側の呼び出しであり、呼び出しの内部で発行したコマンドの数ではない。

C147では抜き取りで中身も確認した。F04 `9e595c4510aa4348978616e0f90043df`では、`npm ci`、lint、buildを一つの呼び出しの中で順に実行し、未終了の間はその中で待機し、失敗なら停止する形だった。最後の差分と状態の確認も同じ呼び出しに含まれていた。F07の依存関係ケース `db76dba4128945b5a9332477349fb2e8`でも、静的検証と差分確認を同じ形で実行していた。

## 判断の限界

- 遵守率45 / 45は、C147の全文の中で指定が働いた結果である。この指定をC280へ移植したときに同じ遵守率になるかは、まだ確認していない。設計原則の条件3は、移植先の測定で改めて確認する。
- C147は9月30日、C280とC283は10月7日の別の待ち行列で測定した。トークン差をpromptだけの効果とは断定しない。経過時間は日付による変動が大きいため、ここでは比較しない。
- 変更を伴うrunは各条件で45件程度にとどまる。低い頻度の不遵守がないとは判断しない。
- 変更前の区間にも、C147の開始側の規則（`DECISION_BOUNDARY`）による呼び出し数の差がある（例：F06の中央値はC147が1回、C280が3回）。今回の改訂と移植の対象は検証側に限り、開始側は別の単位として扱う。

## 次の段階

C280を直接の親として、C147の検証側の指定を、設計原則の五条件を満たす汎用の形で移植するCandidateを設計する。作成前の設計記録には、閉じるコスト経路（固定済み検証の途中結果ごとのモデル再入）、遵守の判定方法、正常経路の保持を対応づける。評価はC280と同条件のSol Low・Standard14 N=5とし、品質、全エージェントトークン、経過時間で判定する。遵守率は条件3の確認と原因の診断に使い、独立した合否条件にはしない。
