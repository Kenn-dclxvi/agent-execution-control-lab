# 変更前の情報封鎖レビューによる修正契約仕様

> **位置づけ**: 仕様確定／候補未作成／評価ケース未設計／評価未開始
>
> 本文は、将来Candidate147へ組み込む機能の設計仕様である。候補、評価結果、採用、リリース、投影のいずれでもない。既存のCandidate147、Candidate164〜166、評価ケース、結果は変更しない。

## 1. 目的

修正作業を担当する`root`が、同じ判定条件について判断を歪め得る先行評価を受け取っている場合に、最初の成果物変更より前に、情報を封鎖した独立レビュー担当が修正の要否と修正後に満たす条件を判定する。

独立レビュー担当は差分を作らず、実装方法も指定しない。レビュー結果は、別の実行担当がC147の`implementation_bound`へ実装方法を結び付けるための「修正契約」として使用する。

この仕組みで防ぐのは、次の経路である。

```text
誤った先行評価
    ↓
同じ文脈を持つrootが修正方法と完了条件を決める
    ↓
誤った変更または不要な変更
```

変更後に常にレビュー担当を追加すること、独立レビュー担当に修正させること、レビューと自動再修正を際限なく繰り返すことは目的にしない。

## 2. 系譜と変更単位

- 採用済みの比較基準はCandidate147とする。Candidate147のリリースと投影をその場で書き換えない。
- 実装候補はCandidate166を直接の親とする。Candidate166が持つ`RESULT_ADMISSION`、同じ判定条件の先行評価だけを独立レビューへの切替条件にする境界、情報封鎖、`root`による代行禁止を維持する。
- 新しい候補で行う変更は一つに限る。修正操作に必要な独立レビュー結果を、変更後の終了判定だけに使うのではなく、最初の成果物変更より前に修正契約として結び付ける。
- 修正操作以外の品質レビューには、Candidate166の`REVIEW_ADMISSION`を引き続き適用する。修正操作では本仕様の`REPAIR_CONTRACT_ADMISSION`を先に適用し、同じ判定条件について品質レビューを重複して発行しない。

## 3. 用語と操作の識別

### 3.1 修正操作

`repair_operation_ready`は、次をすべて満たす一つの操作を表す。

```text
repair_operation_ready :=
    spec_ready
    ∧ TaskSpecが対象成果物の欠陥または意味不整合の是正を必須成果として要求する
    ∧ 対象の識別情報が結び付き済み
    ∧ 修正の判定条件が結び付き済み
    ∧ 権限と保持条件が結び付き済み
```

先行評価が存在するだけでは、修正を必須成果にしない。修正要求は、利用者の明示的な依頼、またはその修正を直接要求する一意なリポジトリ上の根拠から結び付ける。

### 3.2 修正の判定条件

修正の判定条件は、修正後の成果物が満たすべき正しさを判定する条件である。対象のパス、記号、見出し、規則IDなど、場所を示す情報は判定条件と分けて保持する。場所だけでは、修正の要否や修正後に満たす条件を決めない。

### 3.3 修正契約の状態

各修正操作は、最初の成果物変更より前に次のいずれか一つの状態を持つ。

```text
repair_contract_state :=
    not_applicable
    | unobserved
    | no_repair_required
    | ready
    | unavailable
```

- `not_applicable`: 必須の機械判定結果だけで、修正の要否と修正後に満たす全条件を決められる。
- `unobserved`: 人による意味判断に相当する判定が必要だが、受け入れ可能な結果がまだない。
- `no_repair_required`: 閲覧を許可された根拠が、現在の成果物は判定条件を満たしていると示す。
- `ready`: 受け入れ可能な修正契約が結び付き済みである。
- `unavailable`: 閲覧を許可された根拠だけでは、修正の要否または必要な修正後条件を確定できない。

## 4. 修正契約の受入判定

### 4.1 修正契約が必要となる条件

```text
repair_contract_required :=
    repair_operation_ready
    ∧ artifact_change_pending
    ∧ TaskSpecに結び付いた非機械的な修正判定が未完了
    ∧ 必須の機械判定結果だけでは修正判断または全修正後条件を確定できない
    ∧ 受け入れ可能な修正契約が存在しない
```

`repair_contract_required=false`なら、独立レビュー操作を作らない。機械的な根拠だけで閉じられる修正は、C147の既存の実装選択と検証へ進む。

### 4.2 同じ判定条件に対する先行評価

```text
relevant_prior_evaluation_received :=
    rootが修正契約の担当を決める前に評価を受領済み
    ∧ その評価が同じ修正判定条件を対象にする
    ∧ 指摘、処置判断、完了評価のいずれかを含む
    ∧ 現在の修正操作で受け入れ済みの修正契約ではない
```

次の事実だけでは、この条件を成立させない。

- `root`が成果物を実装または調査したこと。
- リポジトリ、差分、テスト結果を読んだこと。
- `TaskSpec`が正式に定めた必須成果または保持条件。
- 現在の操作ですでに受け入れた修正契約。
- 同じ対象であっても、別の判定条件に対して受け取った評価。

### 4.3 担当の選択

```text
repair_context_clean := ¬relevant_prior_evaluation_received

repair_contract_producer :=
    none                    if repair_contract_required=false
    root                    if repair_contract_required=true ∧ repair_context_clean=true
    independent_reviewer    if repair_contract_required=true ∧ repair_context_clean=false
```

実行担当は、最初の修正判定より前に一つだけ決める。同じ修正契約を`root`と独立レビュー担当へ並行または順次に割り当てない。担当を変更する場合は以前の結び付きを失効させ、新しい操作として扱う。

### 4.4 レビューを発行できる条件

```text
repair_review_consumer_ready :=
    repair_contract_required
    ∧ repair_contract_state=unobserved
    ∧ 修正判定条件と対象識別情報が結び付き済み
    ∧ 閲覧許可範囲と入力禁止情報が結び付き済み
    ∧ 要求する結果によってrepair_contract_stateを確定できる
```

独立レビュー担当は、`repair_review_consumer_ready=true`の場合だけ起動する。レビュー前に根拠が十分だと推測する必要はない。根拠が不足していた場合は`unavailable`として確定する。

## 5. 独立レビュー担当へ渡す情報

### 5.1 渡してよい情報

独立レビュー担当には、次の情報だけを渡す。

- 修正操作の識別情報。
- 修正の判定条件と、その条件の責任者。
- `TaskSpec`の該当範囲。
- 対象成果物の識別情報と現在の内容。
- 権限、閲覧許可範囲、保持条件。
- 適用中のリポジトリ上の根拠。
- 実行を許可済みの必須機械判定結果。
- 判定対象を中立に示す場所情報。
- 必要な結果形式。

中立な場所情報は、パス、記号、見出し、規則IDなど、判定対象を識別するだけの情報に限る。先行評価から場所情報を抽出するときも、合否、重大度、修正方法、評価理由を含めない。`TaskSpec`またはリポジトリ上の根拠へ結び付けられない評価文からしか対象を構成できない場合は、その評価文を渡さず`unavailable`とする。

### 5.2 渡してはいけない情報

次の情報は独立レビュー担当へ渡さない。

- 実行担当、`root`、他のレビュー担当が書いた指摘本文。
- 合否、重大度、処置判断、完了評価。
- 先行評価が提案した差分または修正方法。
- 実行担当による正誤の説明、実装・執筆の経緯、自己評価。
- 非公開の正解、期待する経路、期待する終了状態。
- 入力漏えいを検出するための標識。
- 現在の修正操作で受け入れていない過去の結果。

### 5.3 情報の十分性

渡した情報と閲覧許可範囲だけで判定できる場合は、不要な履歴を継承しない。履歴継承に用いる実行環境固有の引数名は、本仕様の不変条件にしない。必要十分な入力境界と、結果の生成元を確認できることだけを要求する。

## 6. 修正契約の結果形式

修正契約の担当は、次のいずれか一つだけを返す。

### 6.1 修正不要

```yaml
operation_identity: <修正操作の識別情報>
disposition: no_repair_required
criterion_ids: [<判定条件ID>]
direct_evidence:
  - <閲覧を許可された直接根拠>
preservation_constraints:
  - <保持条件>
```

閲覧を許可された根拠が、現在の成果物は修正判定条件を満たしていると示す場合に使用する。修正要求を無視するのではなく、修正不要という判断を直接根拠へ結び付ける。

### 6.2 修正契約を作成可能

```yaml
operation_identity: <修正操作の識別情報>
disposition: repair_contract_ready
criterion_ids: [<判定条件ID>]
direct_evidence:
  - <閲覧を許可された直接根拠>
required_postconditions:
  - <変更後に観測すべき条件>
preservation_constraints:
  - <保持条件>
permitted_target_scope:
  - <TaskSpecの権限内にある対象>
```

`required_postconditions`には、変更後に観測すべき状態を書く。具体的な差分、編集手順、ツール名、指定されていないコマンドを実装方法として固定しない。`permitted_target_scope`は`TaskSpec`が許可した範囲の部分集合に限り、独立レビュー担当は範囲を広げられない。

### 6.3 判定不能

```yaml
operation_identity: <修正操作の識別情報>
disposition: unavailable
criterion_ids: [<判定条件ID>]
missing_evidence:
  - <不足している根拠の識別情報>
reason:
  - <閲覧を許可された根拠だけでは確定できない境界>
```

必要な根拠が閲覧許可範囲に存在せず、修正不要と必要な修正後条件のどちらも確定できない場合に使用する。`unavailable`を`blocked`または欠陥確定へ読み替えない。

## 7. 結果の受入れと`root`による代行禁止

```text
repair_contract_admissible :=
    result.operation_identity == current_repair_operation.identity
    ∧ result.producer == repair_contract_producer
    ∧ root以外の担当では結果の生成元を担当の実行識別情報へ結び付けられる
    ∧ resultを第6節の形式へ結び付けられる
```

- 受け入れ可能な結果だけを`repair_contract_state`へ結び付ける。
- 先行評価は`relevant_prior_evaluation_received`を成立させられるが、修正判断、修正後条件、停止条件、実装方法には使わない。
- 独立レビュー担当を選んだ場合、`root`は結果を比較、統合、再採点、再生成、上書きしない。
- `root`は結果の識別情報と構造化された項目を後続操作へ渡せるが、新しい指摘や修正後条件を補わない。
- 結果形式または生成元を確認できない場合は`unavailable`とし、`root`が代行しない。

## 8. C147の実行過程への接続

### 8.1 変更開始

```text
repair_change_admissible :=
    repair_operation_ready
    ∧ (
        repair_contract_state=not_applicable
        ∨ repair_contract_state=ready
      )
    ∧ implementation_bound
```

`repair_contract_state`が`unobserved`または`unavailable`なら、成果物の変更を開始しない。`no_repair_required`の場合は修正差分を作らず、`TaskSpec`が要求する無変更確認だけを行って終了を判断する。

`repair_contract_state=ready`だけでは`implementation_bound=true`にしない。`root`または別の修正担当は、契約に含まれる全修正後条件と保持条件を、一つの実行可能な実装方法へ結び付けてから変更する。

### 8.2 結果が影響する範囲

```text
repair_contract_result_effect_scope := {
    implementation_binding,
    artifact_change,
    change_dependent_validation
}
```

レビュー結果の停止効果を作業全体へ広げない。すでに許可され、レビュー結果によって対象、権限、方法、停止条件が変わらない閲覧は停止しない。

### 8.3 検証

成果物を変更した後は、C147の`VALIDATION_PLAN`と`VALIDATION_CLOSURE`を維持する。修正契約から、指定されていない実行コマンドを追加しない。`TaskSpec`またはコマンド証拠手順が指定した必須検証と、既存の根拠から選んだ方法を一つの実行票へ結び付ける。

## 9. 変更後のレビュー

変更後のレビューは常時発行しない。

```text
postchange_review_required :=
    artifact_change_complete
    ∧ 修正契約の修正後条件に非機械的な判定が残る
    ∧ 必須の機械検証だけではその判定を確定できない
    ∧ 受け入れ可能な変更後レビュー結果が存在しない
```

`postchange_review_required=true`の場合だけ、修正担当とは別の新しい独立レビュー担当を一つ選ぶ。修正契約、変更後の成果物、リポジトリ上の根拠、必須の機械判定結果、閲覧許可範囲は渡してよい。修正担当の自己評価、先行レビューの処置判断、期待する終了状態は渡さない。

変更後のレビュー担当は修正しない。重大な不一致を返した場合は、そのレビュー操作を終了して停止する。同じ操作の中で自動修正へ戻らない。追加修正を行う場合は、新しい修正操作の識別情報、担当の結び付け、修正契約の状態から始める。

## 10. 終了条件

- `no_repair_required`: 直接根拠と、`TaskSpec`が要求する無変更確認がそろった場合だけ、修正操作を`completion_ready`にできる。
- `repair_contract_ready`: 修正契約を作る操作としては終了しているが、修正操作全体は未完了である。実装、検証、必要な変更後レビューが完了するまで、作業全体の完了に使わない。
- `unavailable`: レビュー操作と修正操作を`unavailable`で終了し、成果物の変更、代替レビュー、推測による修正、検証開始へ進まない。
- 変更後レビューの重大指摘: 現在の修正操作を`blocked`で終了する。自動再修正を開始しない。

## 11. 実行環境への依存境界

本仕様は、次の意味だけを要求する。

- 最初の判定より前に、実行担当を一つの実行識別情報へ結び付けられる。
- 結果の生成元を、その実行担当へ結び付けられる。
- 独立レビュー担当へ、必要十分な許可情報だけを渡せる。
- 入力を禁止した情報を配送しない。
- 終了していない実行を、同じ操作の識別情報で終了まで追跡できる。

特定の実行環境に固有のツール名、返却項目名、待機命令、履歴継承の引数名、実行識別子の項目名を仕様語にしない。実装候補では、現在のCodex互換条件で上記の意味を観測できる結び付けを使用する。Codexで成立したことだけから、他の実行環境でも成立すると主張しない。

## 12. 対象外

- Candidate147、Candidate166、既存の評価ケース、保存済み結果の上書き。
- 独立レビュー担当による差分作成または成果物変更。
- 独立レビュー担当による権限、対象範囲、必須成果の追加。
- レビュー、修正、再レビューの無制限な反復。
- 機械的な根拠だけで閉じられる修正へのレビュー担当の常時起動。
- 成果物の実装者であることだけを理由にした独立レビュー担当の起動。
- 実行環境、CLI、ツール接続層、実行時フック、外部ラッパーの変更。
- Codexでの成立から、他の実行環境への効果を一般化すること。

## 13. 本仕様の完了条件

本文では、評価ケースを設計するために必要な次の事項を固定した。

1. 修正操作と起動条件。
2. レビューを起動しない条件。
3. `root`と独立レビュー担当の選択。
4. 渡してよい情報と渡してはいけない情報。
5. `no_repair_required`、`repair_contract_ready`、`unavailable`の結果形式。
6. 結果の受入れと`root`による代行禁止。
7. `implementation_bound`、`result_effect_scope`、検証への接続。
8. 変更後レビューの限定条件と自動再修正の禁止。
9. 実行環境固有の語を不変条件へ含めない境界。

次に行うのは、この仕様に対する設計監査である。設計監査が通過する前に、候補一式、評価ケースの新しい版、評価集合、実行設定、事前照合記録、評価実行を作成または開始しない。
