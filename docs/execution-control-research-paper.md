## 0. 先に読む用語集

本文で使う言葉を、使う前にここでまとめて説明する。カッコ内は再現性のために残した原語である。

### 0.1 対象と登場人物

| 言葉 | 説明 |
| --- | --- |
| AIエージェント | 指示を受け取り、自分でファイルを読み、コマンドを実行し、コードを書き換えるAIのこと。本研究では、開発支援ツールCodex CLI上で動くAIを指す。 |
| 指示書（prompt） | エージェントに与える文書。本研究では、対象リポジトリの`AGENTS.md`などに置く常設の指示文を指す。人が毎回打ち込む依頼文ではない。 |
| 指示書一式（prompt set） | 比較の単位。root `AGENTS.md`という1ファイルではなく、対象リポジトリへ差し込むファイル群をまとめたひとまとまり（bundle）を指す。階層ごとの`AGENTS.md`だけでなく、用語集や手順索引などの参照文書、作業別のprompt file、シンボリックリンクも含む（C81の配布物は19 path）。本文で「Baselineの指示書」「C81の指示書」と書くときは、この一式全体を指す。 |
| `prompt_set_identity` | どの指示書一式を実行したかを指す論理的な名札。少なくとも名前（`name`）と、変更不可の版（`revision`）を持つ。名前だけでは結果を登録できない。 |
| `bundle_sha256` | 一式の中身そのものから計算するSHA-256のハッシュ値。`revision`の代わりに、または併記して使える。名札である`prompt_set_identity`とは別の値であり、こちらは中身が1バイトでも変われば変わる。 |
| root `AGENTS.md` | リポジトリの最上位に置く指示書。配下のすべての作業に共通して効く。指示書一式のうち、本研究で主に書き換えた1ファイル。 |
| 対象リポジトリ（target） | エージェントに作業させる実物のリポジトリ。本研究ではTHE-CAPTIONという一つのリポジトリに固定している。 |
| 実行制御 | 指示書を「読み物」ではなく「実行の進め方を決める規則」として扱う見方。具体的には、仕様をいつ確定するか、作業を誰にやらせるか、どこまで他のエージェントへ任せるか、どこで検証するか、どこで止めるか、という境界を決めることを指す。 |

### 0.2 比較する指示書の呼び名

| 言葉 | 説明 |
| --- | --- |
| Baseline | 比較の出発点として固定した、既存の指示書。 |
| Candidate（候補） | Baselineを改良する案として作った指示書。作った順にCandidate1、Candidate5…と番号を付ける。本文ではC5、C43のように略す。 |
| ControlFreeRepository | root `AGENTS.md`**だけ**を0バイト（空）にし、配下の階層別指示書4つはそのまま残した対照条件。「rootの制御文だけを外したらどうなるか」を測るための下限側の比較対象であり、改良案ではない。指示書をすべて空にした条件は別artifact（`the-caption-3ce91a4-control-free-generic-r1`）であり、本版の比較対象ではない。 |
| 条件 | 比較の一単位。ここではBaseline・ControlFreeRepository・各Candidateのそれぞれを指す。 |

### 0.3 測り方

| 言葉 | 説明 |
| --- | --- |
| 課題（case） | エージェントに解かせる一つの作業問題。実装、レビュー、確認して止まる判断など、種類が異なる14問を用意している。 |
| 標準14項目 | その14問をひとまとめにした、固定済みの評価課題集合（evaluation set）。 |
| 実行（run） | 1つの課題を1回解かせること。本研究では1課題あたり5回繰り返す（`N=5`）ので、1条件あたり14 × 5 = 70回になる。 |
| 作業指示（TaskSpec） | 各課題でエージェントへ渡す依頼文と成果条件。全条件で同一に固定する。 |
| 採点契約（rating contract） | 採点の基準を文書として固定したもの。版が変わると採点基準も変わるため、`v13`のように版で区別する。 |
| case score | 1課題1回ぶんの成果に付ける点数。求めた条件と禁止事項を満たしたかどうかを0〜4の5段階で採点する。 |
| `quality_score` | 比較に使う品質指標。上のcase scoreを直接使うのではなく、1回ぶんの反復に含まれる14課題のcase scoreを合計し、満点で割って0〜100に直したうえで、5反復ぶんの中央値を取る（`quality_score[i] = sum(case_score[i]) / (4 × 課題数) × 100`、その`1..N`中央値）。本文の`92.857`や`100.000`はこの0〜100の値である。 |
| token（トークン） | AIが処理した文章量の単位。同じmodelの中では処理量の代理指標として使える。本研究は使用量そのものを記録するだけで、料金への換算は行わない。 |
| all-agent token | 親エージェントと、そこから呼ばれた子エージェント全部を合計したtoken量。本研究のコスト指標。 |
| `elapsed_seconds` | 一連の実行にかかった実測の所要時間（秒）。 |
| 中央値 | 値を小さい順に並べたときの真ん中の値。平均値と違い、極端な外れ値に引きずられにくい。 |

### 0.4 実行条件

| 言葉 | 説明 |
| --- | --- |
| model | 使用するAIモデル。本研究では全期間`gpt-5.6-sol`に固定している。 |
| 推論の深さ（reasoning effort） | モデルがどれだけ考えてから答えるかの設定。本研究で測ったのは`low` / `medium` / `high` / `xhigh` / `max` / `ultra`の6水準で、主比較は`medium`に固定する。 |
| 並列上限（`M`） | 同時に走らせる実行の最大本数。本研究の主比較は`M=24`。 |
| 反復回数（`N`） | 同じ課題を繰り返す回数。本研究では`N=5`。 |
| 互換条件 | 「同じ土俵で比べている」と言うために一致していなければならない設定一式。課題・作業指示・採点契約・model・推論の深さ・実行環境・`M`・`N`などが含まれる。 |
| 互換キー（compatibility key） | 互換条件をまとめて一つの文字列に要約した指紋。キーが一致する結果どうしだけを同じ表で比べる。 |

### 0.5 エージェントの振る舞いを説明する言葉

以下は原因の説明に使う観察値であり、コスト・品質・時間の3指標には加えない。

| 言葉 | 説明 |
| --- | --- |
| 正本（authority） | ある値や手順について「ここに書いてあるものが正しい」と定めた出所。 |
| 未確定値の確認停止 | 成果に必要な値がリポジトリから確定できないとき、推測で埋めずに人へ確認して止まること。 |
| 委譲 | 親エージェントが作業を子エージェントへ渡すこと。 |
| モデル再入 | 一連の作業の途中で、モデルへの問い合わせが何度も往復すること。往復が増えるほどtokenと時間が増える。 |
| 必要な検証（required validation） | 変更後に必ず実行しなければならないテストやコマンドの集合。 |
| 1回で出し切れた率（1-step closure） | 必要な検証コマンドを、何度も往復せずに1回のまとまりとしてすべて発行できた割合。 |
| 診断値（diagnostic） | 原因の説明には使うが、優劣の判定指標には加えない観察値。 |

### 0.6 成果物の状態

評価が済んだことと、採用されたことは別である。ここでは「成果物そのもの」と「その成果物が置かれている状態」を分けて扱う。

まず、成果物の種類は次のとおりである。これらは互いに別のものとして扱い、一つにまとめない。

| 成果物 | 説明 |
| --- | --- |
| Baseline | 比較の出発点として固定した指示書一式（0.2節）。 |
| Candidate（候補） | Baselineを改良する案として作った指示書一式（0.2節）。 |
| 評価結果（evaluation result） | 測定と採点の記録。 |
| 配布物（release） | 配布できる形にまとめた指示書一式。**作ること自体が独立した手続き**であり、状態の一段階ではない。作っただけでは、採用も本体への反映も意味しない。 |

そのうえで、指示書一式の状態は次の6段階を区別する。段階は自動的に繰り上がらず、評価の成功、配布物の作成、承認、本体反映はそれぞれ別の関門として扱う。

| 状態 | 説明 |
| --- | --- |
| `draft` | 作成中。比較の判断には使わない。 |
| `evaluation_ready` | 一式の中身と評価条件を固定し、評価を開始できる。 |
| `evaluated` | 固定した設定で結果を取り終えた。採用はまだ判断していない。 |
| `release_candidate` | 評価の範囲と未解決のリスクを確認し、反映の候補として固定した。 |
| `approved_for_projection` | 対象リポジトリ本体へ反映してよい、と明示的に承認した。配布物を作ったことと同じではない。 |
| `projected` | 実際に本体へ取り込み、その取り込み先の識別子を記録した。 |

## 要旨

本研究は、AIエージェントへ与える指示書を、文章ではなく**実行制御**として扱う。すなわち、仕様の確定、作業の担当決め、委譲、検証、停止を、どの条件で進めるかという境界を定めるものとして扱う。

第2版では、過去の候補ごとの結果を時系列に並べることはしない。BaselineからCandidate81までのうち、課題集合・採点契約・model・推論の深さ・実行環境・作業指示・反復条件がすべて揃う7条件だけを主比較とする。

- Baseline
- ControlFreeRepository
- Candidate5
- Candidate35
- Candidate43
- Candidate71
- Candidate81

固定した条件は、採点契約Rating v13、推論の深さ`medium`、標準14項目、各課題`N=5`、全体を1つの待ち行列で捌く並列上限`M=24`である。各条件70回、合計490回の実行を比較する。7条件は同じ互換キーを持つ。

主要な結果は次の4点である。

1. **Baselineは7条件の中で、tokenも所要時間も最大だった。** all-agent tokenの中央値は`11,977,774`、所要時間の中央値は`3,568.742`秒、品質の中央値は`92.857`だった。
2. **rootの指示書を0バイトにするだけでコストは大きく下がったが、品質の欠陥は残った。** ControlFreeRepositoryはBaselineに比べてtoken中央値が`-70.80%`、所要時間中央値が`-64.97%`だった。しかし、確認して止まるべき課題A01では5回中5回が0点で、品質中央値は`92.857`にとどまった。
3. **Candidate43で品質の落ち込みがなくなり、Candidate71でコストがさらに下がった。** C43とC71はどちらも70回中70回が4点だった。C71はC43に比べてtoken中央値が`-29.19%`、所要時間中央値が`-10.59%`だった。
4. **Candidate81は効率の改善ではなく、検証の出し方を安定させた変更である。** C81は70回中70回が4点で、検証コマンドを複数必要とする課題で「1回で出し切れた率」をC71の`30 / 35`から`35 / 35`へ改善した。C71と比べるとtoken中央値は`-0.30%`だが、所要時間中央値は`+5.78%`、token合計は`+0.28%`だった。

つまり、C81までの到達点は「指示書を短くしてコストを下げた」ではない。**Baselineが呼び込んでいた不要な作業経路を取り除き、仕様が決まらないうちに作業を始めてしまう誤りをC43で止め、既知の検証をまとめてモデルの往復をC71で減らし、検証コマンドの出し方をC81で安定させた**と整理できる。

## 1. 第2版の比較境界

### 1.1 比較する問い

本版が扱う問いは一つである。

> 同じ14課題を、同じmodel・同じ実行環境・同じ採点条件で解かせたとき、BaselineからC81までの代表的な指示書は、成果品質・all-agent token・所要時間をどう変えたか。

評価指標は次の3つに限定する。

| 指標 | 意味 |
| --- | --- |
| `quality_score` | モデルから見える成果条件と禁止事項を満たしたか |
| all-agent `total_tokens` | 親と全子エージェントの最終使用量の合計 |
| `elapsed_seconds` | 一連の実行にかかった実測時間 |

モデルの思考ステップ数、ツール呼び出し回数、子エージェント数、コマンドの出し方、1回で出し切れた率は、原因を説明する診断値として扱い、上の3指標には加えない。

### 1.2 「BaselineからC81まで」の意味

Candidateの番号は、一本の親子関係を表しているわけではない。途中には、原因を調べるためだけの枝、そこで打ち切った枝、別の採点契約や別の推論の深さで測った結果が混ざっている。

そこで本版は、C1〜C81のすべてを同じ表に並べない。比較条件が一致していることを優先し、最新のRating v13・推論`medium`・標準14項目の結果を持つ7条件を代表点として選ぶ。

7条件の選定には、次の3基準をすべて使った。互換条件の一致は必要条件だが、それだけで主表に加えることはしない。

| 選定基準 | 内容 |
| --- | --- |
| 互換性 | 採点契約Rating v13、推論`medium`、標準14項目、`N=5`、`M=24`、実行環境、作業指示、互換キーが一致する |
| 比較上の役割 | あらかじめ固定した6条件比較の基準点であるか、同じ互換キーに接続されたC81という終点である |
| 解釈上の役割 | 出発点、0バイト対照、初期の完了条件制御、root中心の構造、品質の境界、コストの境界、安定性の境界のいずれかを、重複なく表している |

| 条件 | この比較で表す制御の段階 | root `AGENTS.md` |
| --- | --- | ---: |
| Baseline | 比較の出発点となる固定済み指示書 | 5,980 bytes |
| ControlFreeRepository | rootの制御を0バイトにし、配下ディレクトリごとの正本だけを残した対照 | 0 bytes |
| Candidate5 | Baseline系列に「完了条件に達するまで続ける」境界を追加 | 7,725 bytes |
| Candidate35 | rootの実行制御は残し、旧来の役割説明や手順説明は見出しだけの空の受け皿に置き換えた | 3,235 bytes |
| Candidate43 | 決まっていない成果値を推測せず、正本から確定できる場合だけ着手する | 3,980 bytes |
| Candidate71 | 判断の境界と、必要な検証のまとめ方を定めて、モデルの往復を抑える | 4,987 bytes |
| Candidate81 | 「順に」「個別に」という指定を、rootの一つのまとめ役の中での発行順として固定 | 5,525 bytes |

C41、C69、C78は重要な中間成果だが、この7条件と同じRating v13・推論`medium`・標準14項目の結果を持たないため、互換性の基準を満たさない。C78の保存済み標準14項目の結果は推論`high`で、互換キーは`7426ecd03421590549c30a4e16373722153ceefc00280bc305eedb1aa0955633`である。これはhigh側の6条件とは比較できるが、主表のmedium側キー`79ed04a45971db8ffc2287aea064af8b448008da510d27ceefd70862e0ad40d8`とは比較できない。したがってC78は、最初の互換性チェックの時点で主表の対象外になる。C78が索引ファイル仮説を検証して打ち切った別枝であることは、その評価状態の説明であって、主表から外す理由ではない。

この選定は、C41、C69、C78の評価価値を否定するものではない。**第2版の一つの表で何を比べるか**だけを限定している。各枝の系譜と状態は[`candidate-history.md`](candidate-history.md)を正本とする。

### 1.3 比較しないもの

本版は次を行わない。

- 採点契約の版や推論の深さが異なる過去の結果をつなげること
- Candidateの番号順を、そのまま因果の連鎖として読むこと
- 7条件以外のCandidateを、未評価または失敗とみなすこと
- 指標の差を、そのまま優劣・採用・配布・本体反映の判断に変換すること
- C81の標準14項目の結果を、測っていない課題や別のmodelへ一般化すること

## 2. 方法

### 2.1 固定した互換条件

| 条件 | 固定値 |
| --- | --- |
| 課題集合 | `the-caption-standard14-r1` revision `r1` |
| 課題集合の識別子 SHA-256 | `430d1d4b70b7e670d03048954c6ef1ec588da593d562cb832d58bd51ad7b11db` |
| 対象リポジトリ | `THE-CAPTION@3ce91a403f9e0c83f29d56bbe9e7b449b713445d` |
| 対象のツリー識別子 | `88eecfa29f7016b4d77061d3aabe3e7d176fea9b` |
| model / 推論の深さ | `gpt-5.6-sol` / `medium` |
| エージェント実行環境 | Codex CLI `0.144.0`、記憶機能は無効 |
| 権限設定 | `workspace-write`、承認要求は`never` |
| 採点契約 | `outcome-abstract-condition-preserving-owner-diagnostic-v13` |
| 反復 | 14課題 × `N=5` = 1条件あたり70回 |
| 実行スケジュール | 全体で1つの待ち行列、並列上限`M=24` |
| token集計 | all-agent方式 / `v1` |
| 互換キー | `79ed04a45971db8ffc2287aea064af8b448008da510d27ceefd70862e0ad40d8` |

7条件のあいだで意図的に変えたのは、指示書そのものだけである。課題、作業指示、テスト用ファイル一式、正解判定、必要な検証、採点契約、実行環境、`M`と`N`はすべて一致している。

### 2.2 推論の深さを`high`から`medium`へ移した経緯

前の版が参照していた主な過去比較は、推論`high`を中心としていた。第2版の7条件比較は、C79以降の通常の候補比較で採用した`medium`に全条件を揃えて**新たに実行し直した結果**である。`high`の結果を換算して作った表ではない。

C71以降の保存済み設定と結果を推論の深さで整理すると、次のようになる。modelは全期間`gpt-5.6-sol`である。表の「主な評価」は完了して保存されている結果の範囲を示し、設定だけ作って実行前に打ち切ったものは含めない。

| Candidate | 採点契約 | 推論の深さ | 主な評価 | 本版との関係 |
| --- | --- | --- | --- | --- |
| C71 | v10〜v13 | `high` | 絞り込み課題、標準14項目 | high系列の基準。v13のhighはC78と比較可能 |
| C71 推論水準の追試 | v13 | `low` / `medium` / `high` / `xhigh` / `max` / `ultra` | 各水準で標準14項目、`N=5` | 水準を移すための診断。水準ごとに互換キーが別 |
| C72〜C77 | v12 | `high` | 絞り込み課題または標準14項目 | high系列。採点契約がv12のため本版の主表とは比較不可 |
| C78 | v13 | `high` | 標準14項目 | high側6条件とは比較可能。medium主表とは比較不可 |
| C79〜C80 | v13 | `medium` | F04の絞り込み課題 | 通常の候補比較をmediumへ移した最初の枝 |
| C81 | v13 / v14 | `medium` | F04、標準14項目、A01、F10、D01、B20 | v13・medium・標準14項目だけを本版の主表に接続 |
| C82 | v13 | `medium` | F10、D01、標準14項目、B20 | C81より後の別候補であり、本版主表の範囲外 |

したがって、切り替え点はC71そのものではない。C71にはhighを含む複数水準の結果があり、C78まではhigh系列の候補評価が続いた。**新しい候補評価をmediumに固定した最初の条件はC79**である。以後のC79〜C93の保存済み結果はすべてmediumで、highへ戻していない。

C71の6水準の追試では、`medium`も`high`も70回中70回が4点だった。`medium`は`high`に比べてtoken中央値が`-9.73%`、所要時間中央値が`-14.86%`だった。さらにBaseline、ControlFreeRepository、C5、C35、C43、C71の6条件では、highでもmediumでもtokenと所要時間の順序が同じ`C71 → C43 → ControlFreeRepository → C35 → C5 → Baseline`になった。この観察を受けて、通常の比較を`medium`へ移した。

ただし、推論の深さは互換条件の一つである。highとmediumは互換キーが別なので、水準間の差はあくまで記述的な診断にとどまる。C81の同一条件の結果はmediumであり、**第2版の7条件表は、high上でC81がどう振る舞うかも、highからmediumへ移したことの因果的な効果も示さない。**

### 2.3 評価課題

標準14項目には、実装、レビュー、確認して止まる判断、リポジトリの正本から仕様を解決する作業が含まれる。

- F01〜F08: 実装・検証・依存関係・同期の境界
- F10: 一覧の棚卸しと月次レビュー

- A02: リポジトリの規則から一意に決まる正しい手順を選べるか

各条件を14課題 × 5回で実行した。有効な実行はすべて0〜4で採点し、「採点不能」は認めない。

## 4. 何がコストと品質を分けたのか

### 4.1 指示書のバイト数では説明できない

rootの指示書の静的なバイト数と、実行時のtoken量は一致しない。

| 条件 | rootのバイト数 | token中央値 |
| --- | ---: | ---: |
| ControlFreeRepository | 0 | 3,496,976 |
| Candidate35 | 3,235 | 4,920,365 |
| Candidate43 | 3,980 | 2,716,869 |
| Candidate71 | 4,987 | 1,923,688 |
| Candidate81 | 5,525 | 1,917,979 |
| Baseline | 5,980 | 11,977,774 |
| Candidate5 | 7,725 | 8,425,533 |

C43からC81にかけて、rootの指示書は`3,980 → 5,525 bytes`へ増えたのに、token中央値は`2,716,869 → 1,917,979`へ減った。BaselineはC81とバイト数がほぼ同じだが、token中央値は約6.25倍だった。

減らすべき対象は文字列そのものではなく、その文字列が呼び込む探索、委譲、モデルの往復、読み直し、検証のやり直しである。

### 4.2 0バイトは下限の対照であって、完成形ではない

ControlFreeRepositoryは、Baselineのrootの指示書が大きな実行時コストを呼び込んでいたことを示した。一方で、A01は5回中5回が0点だった。

この結果は、両極端な2つの解釈をどちらも否定する。

- 詳しい指示書を書けば品質が上がる、とは限らない。
- 指示書を削り切れば最適になる、とも限らない。

必要なのは、0バイトの条件に一般的な手順書を戻すことではない。残った具体的な欠陥に対して、正本・判断・停止の境界を最小限だけ足すことである。

### 4.3 C43は品質の転換点である

C35までの3条件とControlFreeRepositoryは、いずれもA01の5件を閉じられなかった。C43は、変更後の値を直接指定している正本がある場合だけ着手し、それ以外は編集や試験に入る前に確認する、という境界を固定した。

最新の互換比較で70回すべて4点だったのは、C43、C71、C81だけである。したがって本版ではC43を品質の転換点として扱う。

ただし、`N=5`で欠陥が0件だったことを、将来にわたる完全な保証へ一般化はしない。

### 4.4 C71はコストの転換点、C81は安定性と所要時間の引き換えを残した終点である

C71はC43と同じ点数分布を保ったまま、token中央値を`-29.19%`、所要時間中央値を`-10.59%`下げた。最新の互換比較で「品質を保ったままの明確なコスト差」はここにある。

C81はC71に比べてtoken中央値こそ`-0.30%`だが、token合計は`+0.28%`、所要時間中央値は`+5.78%`、所要時間合計は`+5.03%`だった。したがってC81を、さらなる効率改善として扱うことはしない。

C81の採用を判断するときは、F04を含む発行経路の`35 / 35`という安定化と、この所要時間の増加を、別々の判断軸として同時に扱う必要がある。両者は同時に観測された引き換えではあるが、因果関係は切り分けられていない。品質、コスト、指示書の安定性を、一つの勝敗判定にまとめてはならない。

## 6. 限界

1. **modelも実行環境も1種類だけである。** `gpt-5.6-sol`とCodex CLI `0.144.0`以外へは一般化しない。
2. **対象はTHE-CAPTIONの14課題に限る。** 別のリポジトリ、別の言語、収録していない課題での再現は未確認である。
3. **反復は各課題`N=5`である。** めったに起きない誤りが存在しない、とは主張しない。
4. **7条件は代表点であって、一本の直系ではない。** 表で隣り合う条件の差を、指示書の個々の一文が単独で生んだ効果に読み替えてはならない。
5. **採点契約Rating v13に固定した比較である。** v14を含む別の採点契約の結果を、採点し直したり混ぜたりしていない。
6. **highからmediumへの連続性は限定的である。** 6条件の順序は両水準で一致したが、推論の深さごとに互換キーは異なる。C81のhigh側の互換結果は、本版の7条件表には存在しない。
7. **中央値だけでは分布を表せない。** 点数分布と70件合計を併記し、C71とC81のように中央値・合計・所要時間で向きが食い違う点を隠さない。
8. **採点は独立した盲検の採点者ではなく、固定した契約による監査である。** 契約と集計側の欠陥が結論に影響し得る。
9. **C81の「1回で出し切れた率」は診断値である。** 3指標には加えず、測っていない課題の安定性へ一般化しない。所要時間の増加との因果関係も確定していない。

## 7. 結論

最新の互換条件でBaselineからC81までの代表7条件を整理すると、結論は次のとおりである。

1. Baselineは品質中央値`92.857`、token中央値`11,977,774`、所要時間中央値`3,568.742`秒で、7条件中もっとも高コストだった。
2. ControlFreeRepositoryはBaselineに比べてtoken中央値`-70.80%`、所要時間中央値`-64.97%`だったが、A01は5回中5回が0点だった。
3. Candidate43は決まっていない値についての正本の境界を閉じ、70回中70回の4点に到達した。
4. Candidate71は同じ点数分布を保ったまま、C43に比べてtoken中央値`-29.19%`、所要時間中央値`-10.59%`だった。
5. Candidate81は70回中70回の4点を保ち、検証を1回で出し切れた率を`30 / 35 → 35 / 35`へ改善した。
6. C81はC71に比べてtoken中央値`-0.30%`だが、所要時間中央値`+5.78%`、所要時間合計`+5.03%`、token合計`+0.28%`である。安定化とコスト増加を同時に観測したが、因果関係は切り分けられておらず、さらなる効率改善とは判断しない。
7. Baselineに比べてC81は品質中央値`+7.143`、token中央値`-83.99%`、所要時間中央値`-71.87%`だった。

この結果を一文でまとめる。

> **C81までの改善は、指示書を短くしたことではなく、不要な実行経路を取り除き、仕様の確定・モデルの往復・検証の発行という境界を順に閉じたことの結果である。**
