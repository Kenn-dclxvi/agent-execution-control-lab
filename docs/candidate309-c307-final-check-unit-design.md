# Candidate309 完了条件の確認を最後の確認と同じ応答で行い、その後は戻らない

2026-10-10。C298に由来する成功後の一文の狙いを、保存traceから定め直し、それに合う制御として置き換えるための設計記録。Candidate本文の作成前に固定する。[設計原則](prompt-control-design-principles.md)の全文を読み、「Candidateを作成する前の確認事項」の項目1〜9と「処理方法を指定できる条件」に対応させた。計測と記録は[計測と記録の基準r2](shared-instruction-evaluation-criteria-r2.md)に従う。この記録ではbundleを作成しない。

## 目的と役割

- 系列：実行環境を切り離し、負荷を見て次のrunを始める発行の条件（CPU使用率70%以下、間隔1秒）で測る系列。
- ベースと直接の親：C307（`the-caption-3ce91a4-taskspec-scoped-closure-output-trim-r1`）。比較の基準は、同じ条件で測ったC307とC301 `-r5`のSonnet low。
- 計測の順序：利用者の指示により、Sonnet lowで確立してからSolを測る。この一文はSolに向けた制御で、Sonnet lowでは、C301ですでに行っている形を書き写したものになる。Sonnet lowでは、何も壊さないことを確かめる。
- 評価は計測であり、達成目標を置かない（r2）。
- 変更対象：C307のroot `AGENTS.md`の、成功後の一項目だけを置き換える。他の項目と他の18対象はC307とバイト一致を保つ。

## この一文で何をさせたいか

最後の変更の後に、TaskSpecが求める確認と、完了条件の確認（許可外の変更がないことを、作業ツリーの状態で確かめる）を行い、その結果を受け取ったら、すぐに報告する。

閉じたいのは、確認の結果を受け取った後に、もう一度モデルへ戻ってコマンドを出すことである。完了条件の確認は、閉じる対象ではなく、させたい処理の一部である。

## 1. 比較の基準と、正常な最短経路

C301のSonnet lowが、この最短経路を行っている。最後の確認コマンドと同じ呼び出しで状態を確かめ（例：`bash scripts/dev/main_verify.sh > /tmp/verify.log 2>&1; echo "exit=$?"; tail -8 /tmp/verify.log; git status --short`）、その結果で報告していた。変更を伴う41件で、最後の変更の後に状態を確かめずに報告したrunは0件だった。

## 2. 保存traceで確認した問題経路

C301の、最後に成功したfull gateより後のコマンド（5反復の合計）：

| | Sol Low | Sonnet low |
| --- | ---: | ---: |
| 合計 | 51 | 17 |
| 状態・差分の確認 | 40 | 4 |
| `git diff --check`（F06・F07でTaskSpecが求める） | 10 | 10 |
| 読み取り・検索 | 1 | 3 |

- Sol Lowは、完了条件の確認を、最後の確認と別の呼び出しで行っていた。状態を確かめたrunでは、1件あたり約1.6回で、確認を重ねることもあった。確認を含む変更35件のうち10件は、状態を確かめていなかった。
- C298の一文（「必須の確認コマンドがすべて成功した結果を受け取った後は、コマンドを発行せずに報告する。」）と、その置き換え（C306、C308）は、成功後の確認そのものを止めた。Sonnet lowでは、最後の変更の後に状態を確かめずに報告したrunが、C302で8件、C306で15件、C307で13件、C308で12件になった（C301とC305は0件）。C308のF01（反復3）は、確かめずに「許可外の変更はありません」と報告した。

## 3. 開いている記述と、TaskSpec・正本で防げない理由

C307の一文は、止める側だけを書き、止める時点（すべて終わったか）をモデルの判断に委ねている。完了条件の確認をどこで行うかは、どこにも書かれていない。モデルが早めに終わったと判断すると、完了条件の確認は行われない。TaskSpecは完了条件を定めるが、それをいつ確かめるかは定めていない。

## 4. 追加・変更する条件の全件

C307の成功後の一項目を、次の一文に置き換える。

> - 最後の変更の後、作業ツリーの状態の確認は、TaskSpecが求める確認のうち最後に実行するものと同じ応答で発行する。その応答の結果がすべて成功していれば、コマンドを発行せずに報告する。

- 一文目は処理方法の指定である。完了条件の確認の置き場所を、最後の確認と同じ応答に固定する。状態の確認は読み取りだけで、ほかの確認と順序の依存がない。
- 二文目は閉じる文である。止める時点を「状態の確認を含む応答の結果を受け取った後」という、traceで判定できる事実で定める。
- 一文目は新しい操作の発行を求めるが、置き換える操作は、C301ですでに行われている状態の確認（Solでは別の呼び出しで1〜2回）である。追加ではなく、置き場所の固定と回数の上限になると見込む。

## 5. 禁止行動、開放経路、閉じる境界、反証

| 項目 | 内容 |
| --- | --- |
| 禁止する行動 | rootが、状態の確認を含む最後の確認の応答の結果をすべて成功で受け取った後に、コマンドを発行する |
| 現在の開放経路（C301） | 完了条件の確認の置き場所の定めがなく、Solでは別の呼び出しで確認し、重ねることもある |
| 現在の開放経路（C307） | 止める時点をモデルが判断し、完了条件の確認を省いて報告できる |
| 閉じる境界 | 操作の発行。止める時点は、状態の確認を含む応答の結果という事実で定める |
| 正常な処理の保持 | 確認が失敗した場合は、修正して、同じ形でもう一度確認できる。TaskSpecが求める確認の順序は変えない |
| 反証する構成 | 状態の確認を最後の確認と別の応答で行う構成は、一文目に違反する。状態の確認を含む応答の後に状態を重ねて確かめる構成は、二文目で禁止に当たる。状態の確認を省いて報告する構成は、一文目に違反する |

## 処理方法を指定できる条件との対応

| 条件 | 満たし方 |
| --- | --- |
| 1. 無条件である | 適用は「最後の変更の後」という事実で決まる。必要性の判断を介さない |
| 2. 遵守を観測できる | 最後の確認の応答に状態の確認が含まれるか、その応答の後にコマンドがないかを、保存traceで判定できる |
| 3. 遵守率を実証している | 未確認。この計測で最初に確かめる。Sonnet lowはC301で同じ形を行っていたが、指定としての遵守率は確かめていない |
| 4. 正常経路を保持する | 項目5のとおり |
| 5. 汎用の形で書く | 個別のコマンド名、ケース、期待値を書いていない |

C297は「状態の確認を、必須の確認と同じ応答で発行する」という発行を求める文だけを入れ、Sonnet lowで状態確認のコマンドが増え、閉じたかった応答も残った。今回は閉じる二文目と組にしている。同じことが起きないかを、最後の確認より後のコマンドの数で確かめる。

## 6. 維持する正常経路

- Claude Codeは、課題文の指定どおり、TaskSpecが求める確認を個別の`Bash`呼び出しで実行する。状態の確認は、最後の確認コマンドの後ろに付けるか、同じ応答の別の`Bash`呼び出しにする。C301のSonnet lowの形である。
- 変更を伴わないケース（A01、F05の二件、F10の二件）では「最後の変更の後」が生じず、適用されない。F10でTaskSpecが求める終了時の状態確認は、変わらない。

## 7. 新しく増える判断と、変更対象外への影響

- 新しい判断：TaskSpecが求める確認のうち、どれを最後に実行するか。モデルが実行の順を決める。後から別の確認を足すと一文目に反するので、trace上で判定できる。
- 危険1：Sonnet lowで、状態の確認を重ねる、または最後の確認より前に別に確かめる。状態確認のコマンドの数で観測する。
- 危険2：C307で出力を絞ってよいとした一文と組み合わさり、最後の確認の呼び出しが長くなる。費用で観測する。
- 固定分：置き換える文の差（改行を除き、135バイトから262バイト）。

## 8. 評価ケース、比較単位、比較条件、記録する項目

- セル：Sonnet lowのStandard14の全14ケースN=5の計70件。Solは、Sonnet lowで確立した後に測る。
- 比較条件：C307のSonnet lowと同じで、prompt identityだけを変える。
- 記録する項目（r2）：品質、処理の適切さ（完了条件を確かめてから報告したか）、費用、経過時間（内訳を含む）、生のトークン（参考）。
- 機序の診断（合否にしない）：
  - 遵守率：最後の確認の応答に状態の確認が含まれたrunの割合（変更を伴うrun）。
  - 最後の変更の後に状態を確かめずに報告したrunの件数。
  - 最後に成功したfull gateより後のコマンドの回数と種類。
  - F06とF07の`git diff --check`の成功件数。

## 9. 停止条件

C302の設計記録の項目9のとおり。遵守率が低く、閉じたい戻りも残る場合は、制御できないものとして、この一文をやめる判断を利用者とする。
