# AIにレビュー担当を増やす前に、判定条件を書こう

> 実務者向けExecution Controlシリーズ 5 / 8

## 結論

**守りたいのは「レビューを実行した」という工程ではなく、欠陥を見逃さず、必要な検証を終え、根拠のない完了を防ぐことです。**

レビュー担当を増やすと、その品質責務を守れる場合があります。しかし同時に、同じファイルを読み、同じ判断を繰り返し、差し戻し後に再び全体を確認する経路も増えます。

そこで、まず工程と責務を分けます。

| よくある工程 | 本当に守りたいこと | 研究の到達点での扱い |
| --- | --- | --- |
| プラン担当が草案を作る | 成果が決まる前に変更しない | 必要な成果値が明示入力または正本から確定するまで着手しない |
| 監査担当が契約準拠を確認する | 必須検証の省略や契約違反を防ぐ | 必須検証の発行・結果・完了条件の一部は条件へ移った。ただし独立した契約準拠監査は残っていない |
| レビュー担当が品質確認する | PRレビュー相当の品質を確認する | 対応する常設制御はない。非破壊レビュー能力を固定課題で確認することは、実装ごとのレビューを置き換えない |
| 指摘が消えるまで差し戻す | 指摘された欠陥を修正する | 対応する常設の自動再修正ループはなく、同等能力も直接確認していない |
| 4者の合意で完了する | 根拠のない完了を防ぐ | 必要な結果が揃った状態による完了判定へ移った |

## 「担当を消す」話ではない

独立したレビューには価値があります。別の視点、情報を分けた監査、専門家の判断が必要なら、別担当を置く理由があります。

問題は、「高品質にしたいからレビュー担当を置く」というだけで、担当が判定する対象や合格条件が決まっていない場合です。その状態では、役割の数だけ読み直しと判断が増えます。

別担当を置く前に、次を決めます。

1. その担当にしか出せない結果は何か
2. 何を根拠に合否を判断するか
3. その結果がなければ完了できないのか
4. 同じ判定を親や別担当がやり直さないか

答えられないなら、必要なのは新しい担当ではなく、既存の実行へ追加する判定条件かもしれません。

## 研究で何が変わったか

研究の出発点は、実装・監査・レビューを分け、指摘が消えるまで最大5回差し戻す構成でした。この構成は当時の評価範囲で一定の品質を出していました。

到達点では、仕様確定、必須検証、結果の受領、完了判定などの一部が、常設の担当工程から観測可能な条件へ移っています。一方、レビュー担当による品質確認のすべてが条件へ移ったわけではありません。工程から分離できた責務と、常設制御を持たない責務を分けて扱う必要があります。

ただし、レビューが完全に置き換えられたとは言えません。独立した契約準拠監査は常設されておらず、監査・レビュー指摘に基づく自動再修正ループと同等の能力も、現行の評価課題集合では直接確認していません。

工程と責務の対応、および未測定の範囲は、[技術報告の11.1節と11.2節](execution-control-measurement-report.md)を正本とします。

## これだけ覚えてください

**レビュー担当を増やす前に、その担当が守る品質責務を一文で書く。次に、その責務を判定条件で守れるか考える。**

工程が増えるとなぜ料金も増え得るのかは、[「AIの料金を増やすのは、文章量より実行経路」](06_execution-paths-drive-ai-cost.md)で説明します。
