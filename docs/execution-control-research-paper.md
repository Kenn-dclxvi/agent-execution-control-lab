# 実行制御としてのprompt設計 第3版

## AIエージェントへの指示書を書き替えると、成果の質と費用はどう変わるか

リポジトリに置く常設の指示書（`AGENTS.md`）を、文章ではなく**実行の進め方を決める規則**として設計し直し、他の条件をすべて固定したまま指示書だけを取り替えて、同じ14種類の作業を繰り返し解かせた記録である。丁寧に書いた指示書がコストだけを増やしていたこと、空にすると止まるべき場面で止まれなくなること、そのあいだにある「効く条件文」をどう見つけたかを扱う。

# 第I部 10分で読める版

## I-1. 何を調べたのか

AIエージェント（ここでは開発支援ツールCodex CLI上で動くAI）は、リポジトリに置かれた常設の指示書（`AGENTS.md`）を読んでから作業を始める。人が毎回打ち込む依頼文とは別に、「どう進めるか」の規則がリポジトリ側に置いてある。

この指示書は文章なので、良い文章を書けば良い結果が出そうに見える。しかし実際には、1文がエージェントの分岐を1つ増やし、子エージェントの起動を1体増やす。子1体ぶんの消費量は総量へ丸ごと乗るため、影響は非線形に伝播する。つまり指示書は**読み物ではなく、実行の進め方を決めるプログラムに近い**。

そこで本研究は、対象リポジトリ・課題・依頼文・採点基準・モデル・実行環境をすべて固定し、**指示書だけを取り替えて**、同じ14種類の作業を各5回ずつ解かせた。測るのは3つだけである。成果の点数、消費したtoken量（親と子の合計）、所要時間。

作業させる相手（対象リポジトリ）は、実務で運用している非公開のリポジトリ1件で、測定のあいだは状態を1点に固定してある。非公開なので第三者は中身を確認できない。その分を補うため、誰でも見られる公開リポジトリ（`pallets/click`）でも同じ枠組みを組み、同じ方向の結果が出るかを確かめている。

実際の指示書はこういう文で書かれている（現在採用中の版から一部を抜粋）。

> `spec_ready := required outcome valueが、明示user inputまたはそのvalueを直接要求する一意なrepository authorityへbind済み`。…`spec_ready=false`の間はproducer binding / predicate実行 / artifact変更 / testを開始せず、未固定のrequired outcome valueだけをclarification resultにする。

平たく言えば「作るものの値が、人の指示かリポジトリの正式な決定のどちらかで決まっていないなら、コードを触らず試験もせず、その値だけを質問して止まれ」である。本研究が扱う「制御」はこの種の条件文であり、心構えや注意書きではない。

## I-2. 分かったこと

**(1) 丁寧に書かれた指示書は、コストを増やすだけで品質を買っていなかった。** 出発点の指示書（5,980 bytes）は、同じ土俵で比べた7条件の中でtokenも所要時間も最大で、点数の分布も最も悪かった。

**(2) では空にすればよいのかというと、そうではない。** rootの指示書を0バイトにすると、tokenは約7割減った。ただし「決まっていない値があるときに、勝手に決めずに人へ確認して止まる」課題では5回中5回失敗した。**削るだけでは閉じない欠陥が残る。**

**(3) 短くすることと、速く安くすることは別の作業である。** 表面の文字数を1〜4割削った8件の候補のうち7件で、実行時のtokenは減らなかった（増えたものもある）。逆に、条件文を1つ足した候補はtokenを3割近く減らした。現在採用中の指示書は10,908 bytesで、出発点の約1.8倍の長さである。**減らすべきは文字ではなく、その文字が呼び込む探索・往復・やり直しである。**

**(4) 効く条件文は一度には見つからず、境界を順番に閉じることになった。** 実際にたどった順序は次のとおりである。

1. 決まっていない値があるなら、触る前に止まる（仕様の境界）
2. 変更後に必要な検証は、まとめて出して結果を全部受け取ってから一度だけ判断する（検証の境界）
3. その検証を「1コマンドずつ」と書いたとき、モデルへ何度も戻るのではなく、一つのまとめ役の中で順に出す（発行単位の境界）
4. 変更前に集める材料は、依頼文が指した範囲だけに限り、追加は原則禁止にする（材料の境界）
5. 「何を作るか」と「どうやって作るか」を別の状態として扱い、後者が決まった時点で材料集めを終わりにする（実装確定の境界）
6. 材料の取り直しは「あと1回」「あと何行」ではなく、「必要な条件を覆うまで」で区切る（取り直しの境界）

**(5) 同じ指示書でも、モデルを変えると成立しなかった。** 現在採用中の指示書のまま、同系列の別モデル2つで測ると、片方は70回中2回、もう片方は3回、成果条件を満たせなかった。とくに後者は「確認して止まる」課題で3回続けて失敗し、tokenも2倍以上になった。**指示書の制御は、モデルに依存しない保証ではない。**

## I-3. 「境界を閉じる」とは何をすることか

抽象的に見える3つの制御を、実際の文面と平たい意味で並べる。

| 閉じた境界 | 実際の文面（抜粋） | 平たい意味 | 観測されたこと |
| --- | --- | --- | --- |
| 仕様の境界 | 「`spec_ready=false`の間は…artifact変更 / testを開始せず、未固定のrequired outcome valueだけをclarification resultにする」 | 決まっていない値があるなら、コードを触らず試験もせず、その値だけ質問して止まる | 「確認して止まる」課題の失敗が5 / 5件から0件になった |
| 発行単位の境界 | 「『順に』『1 commandずつ個別』は、1回のwrapper内で全required validationを個別の`exec_command`として発行することを意味し、command resultをmodelへ返して次commandを別の呼び出しで発行することを意味しない」 | 「1つずつ順に実行せよ」を、モデルへ毎回戻ることではなく、一つのまとめ役の中で順に出すことと定義する | 検証を1回で出し切れた率が`30 / 35`から`35 / 35`になった |
| 取り直しの境界 | 「初回resultで変更criterionが未観測でも、…`continuation_scope_complete`なrequest identityを発行前にbindでき…た場合だけ、同じeditable targetへのcontinuation evidenceを一件許可する」 | 直す対象が1ファイルに収まっていて、必要な箇所が最初の読み取り範囲から外れていたときだけ、その定義全体を読み直す1回を許す。「あと1回」「あと620行」のような数では区切らない | 読める対象を「もう無い」と誤判定して止まる失敗が2件から0件になり、材料取得は1回で済んだままになった |

3つに共通するのは、**モデルが実行時に観測できる条件で書かれている**ことである。「慎重に確認せよ」「必要なら追加調査せよ」のような、モデル自身の判断を増やす書き方は、いずれも失敗した（次節）。

## I-4. 効かなかったこと

**(1) 「誰にやらせるか」の条件を細かくすること。** 子エージェントを起動する条件を時刻や状況で細分化しても、そもそも1つの作業を誤って2つに割っている問題は直らなかった。狙った1課題ではtokenが半分になったのに、14課題全体では増えた例もある。

**(2) 実行環境側の振る舞いを指示書に書くこと。** 「ツールの出力はこの形だけモデルへ渡す」「上限バイト数を超えたら切る」といった指定は成立しなかった。何をモデルへ返すかは、指示書ではなく実行環境が決めている。**指示書で制御できるのは、返ってきた結果をどう分類し次に何を選ぶかまでである。**

**(3) 抽象的な判断をもう一段増やすこと。** 「これは人の判断が必要か」「追加調査に価値があるか」を判定させる条文を足すと、正しく進める場面で余計に止まるようになった。5回試験では見えず、1,400回試験で出た失敗もある。

指示書だけを替えた7条件のうち、代表5つ（採点基準v13、14課題 × 5回、1条件70回）。

# 第II部 精密版

## 要旨

本研究は、AIエージェントへ与える指示書を、文章ではなく**実行制御**として扱う。すなわち、仕様の確定、担当決め、委譲、証拠集め、検証、停止を、どの条件で進めるかという境界の集合として扱い、指示書の差だけを変数にした反復測定を積み上げる。

対象は、実務で運用している非公開のリポジトリ1件である（本文では「対象リポジトリ」と呼ぶ。測定に使った固定点の識別子は`THE-CAPTION@3ce91a4`）。この対象へ与える指示書として、出発点からCandidate125までを派生させた。加えて、誰でも中身を確認できる公開リポジトリ`pallets/click`で同じ枠組みを再現した。modelは主比較を通じて`gpt-5.6-sol`、実行環境はCodex CLIに固定し、最後にmodelだけを変えた追試を加えた。

主要な結果は6点である。

1. **精緻に書かれたBaselineは、品質を買わずに実行時のコストを大きく増やしていた。** Rating v13・推論`medium`・標準14項目の7条件比較で、Baselineはall-agent token中央値`11,977,774`、所要時間中央値`3,568.742`秒と7条件中で最大であり、品質中央値は`92.857`にとどまった。
2. **rootの指示書を0バイトにするだけでコストは大きく下がるが、削除では閉じない品質欠陥が残る。** ControlFreeRepositoryはBaseline比でtoken中央値`-70.80%`だったが、確認して止まるべき課題A01で5回中5回が0点だった。「lean（無駄のない）」の最適点は0ではない。
3. **減らすべき対象は文字数ではなく、実行経路上の判断点である。** 表面のバイト数を`-1.43%`〜`-39.12%`縮めた8件は実行時tokenを`-2.33%`〜`+31.36%`へ動かして多くが悪化した一方、判定条件（「何を観測すれば真になるか」を書いた条件文。predicate）を1つ足した候補はtokenを`26`〜`30%`削減した。C43からC71では、rootを`3,980 → 4,987 bytes`へ増やしながらtokenが減っている。
4. **境界は一気に閉じられず、順番に閉じる必要があった。** C43が仕様確定の境界、C71が検証のまとめ方、C81が検証コマンドの発行単位を閉じた。C81は70回中70回が4点を保ち、検証を1回で出し切れた率をC71の`30 / 35`から`35 / 35`へ改善した。
5. **C82以降で効いたのは、抽象的な注意を増やすことではなく、証拠と状態遷移を実測可能な結果へ縛ることだった。** 委譲条件の細分化、tool出力の投影指定、meta的な判断の追加はいずれも安定しなかった。効いたのは、初期証拠集合の限定と追加の既定禁止（C104）、成果値と実装方法の分離（C116）、実装確定を変更前工程の終端結果（これを受け取ったらその工程は終わり、と定めた結果）にすること（C118）、そして「一つの編集対象が全変更条件を持つ場合だけ、条件を満たすまでの追加取得を一度許す」というC125である。C125は標準14項目で70 / 70件が4点、token中央値`1,401,225`で、C107の到達目標を`8.00%`下回った。
6. **同じ指示書でもmodelを変えると品質とコストは維持されなかった。** C125をTerraへ変えると68 / 70件、token`+23.81%`、Lunaへ変えると67 / 70件、品質中央値`-7.143`、token`+136.06%`だった。指示書の制御はmodel非依存の保証ではない。

加えて、保存済みの使用量を公開API単価へ換算すると、この差は費用の単位でも読める。14課題 × 5回ぶんで、出発点が`$91.6701`、rootを0バイトにした対照が`$25.1562`、C125 Solが`$15.5472`である。**必要な制御を足したC125は、削除の下限である0バイト対照より`38.20%`安く、しかも品質欠陥を閉じている。** これは指標ではなく派生表示であり、実請求額でもない（第7節）。

あわせて本研究は、採点契約そのものが結論を歪め得ることを実例で示し（抽象的な成果条件を採点側で特定コマンドへ具体化していた欠陥をv13で塞いだ）、これらの観測が2026年7月のOpenAI GPT-5.6 Sol指針およびAnthropic Claude Opus 5指針と同方向であること、そして両指針が語で混在させている「バイト削減」と「判断点削減」の区別、下限条件の測定、残余欠陥、効率向上の代償を実測で分離できることを述べる。

## 1. 問題設定と貢献

### 1.1 対象

測定の主対象は、実務で運用している非公開のリポジトリ1件である。以下ではこれを「対象リポジトリ」と呼び、測定に使った固定点を識別子`THE-CAPTION@3ce91a403f9e0c83f29d56bbe9e7b449b713445d`で指す。名前そのものに意味はなく、**指示書の効き方を測るために状態を固定した実在のコードベース**という位置づけである。対象リポジトリの実行は、root `AGENTS.md`とpath別の指示書によって制御される。本論文を置いているリポジトリは別物で、その指示書を設計・比較・評価し、反映可能な単位へ固定するための実験基盤である。本体のruntime変更は通常作業範囲に含めず、本体への反映は明示的な別作業として扱う（正本: [`repository-contract.md`](repository-contract.md)）。

### 1.2 問題

指示書の改善は通常、文章の読みやすさや網羅性で評価される。しかしエージェント実行では、1文がモデルの分岐を1つ増減させ、子セッションの起動を1体増減させる。子1体の使用量は総量へ丸ごと加算されるため、影響は非線形に伝播する。

したがって次の3つは別の量である。

- 指示書自体の文字数・token数（**静的量**）
- 実行時に消費されるtoken総量（**動的量**）
- 成果品質

本研究の問いは、**成果品質を維持したまま動的量を減らす制御は何か、そしてそれは静的量の削減と一致するか**である。

### 1.3 貢献

1. 実在コードベース上で、指示書の差だけを変数とした互換比較の基盤を構築した。
2. 効いた制御と効かなかった制御を、同一条件の反復測定として両方保存した（負の結果を破棄していない）。
3. 静的量と動的量の乖離を、方向が逆転する事例として定量化した。
4. 「証拠・成果値・実装方法・検証」を別の判定条件へ分解する必要があることを、失敗系列の積み上げから示した（第5節）。
5. 採点契約そのものの妥当性欠陥を検出・修正し、影響範囲を記録した（第8節）。
6. 指示書の制御がmodelに依存することを、同一条件でmodelだけを変えた測定で示した（第6節）。
7. 上記を2026年7月のベンダ公式指針と対照し、一致点・追加点・未検証点を分離した（第12節）。

## 2. 方法

### 2.1 評価基盤の4つのLayer

評価は4つのLayerに限定し、各Layerは自分の出力だけを作り、前段のartifactを変更しない。

1. **Evaluation set** — どの課題で測るかを固定する
2. **Execution** — 固定条件で指示書を実行し一次結果を保存する
3. **Quality rating** — 成果を0〜4で採点する
4. **KPI comparison** — 保存済み結果から比較viewを作る

扱う指標は3つだけである。`quality_score`（成果の点数を0〜100へ直した値）、all-agent token（親と全子エージェントの合計使用量）、`elapsed_seconds`（実測の所要時間）。保存した使用量を公開API単価へ換算した金額は、指標ではなく派生表示として第7節に置く。ツール呼び出し数、モデルの思考ステップ数、子セッション数、コマンドの出し方、1回で出し切れた率は診断値として確認し、指標へ昇格させない（正本: [`prompt-comparison-workflow.md`](prompt-comparison-workflow.md)、[`evaluation-loop-manual.md`](evaluation-loop-manual.md)）。

### 2.2 互換条件

2つの結果を比べてよいのは、課題集合の版、対象リポジトリのref、model、実行環境、作業指示、権限、テスト用ファイル一式、実行パラメータ、課題、反復条件、token集計版、採点契約が**すべて一致する**ときだけである。この一致を単一のハッシュ（互換キー）で表し、異なるキーの結果を同じ表へ混ぜない。

この規律には本論文にとって重要な帰結がある。**採点契約や推論の深さ、実行環境の版が異なる測定は連結できない。** 本文が「層」を分けて記述するのはこのためであり、層をまたいだ削減率の掛け算は示さない。

### 2.3 model-visible / private境界

課題は、実行役へ提示する情報（model-visible）と、採点用の正解・期待diff・確認コマンド（private）を厳密に分離する。**privateに確認コマンドが存在することと、それが実行役へ課された必須試験であることは別である。** 必須試験は作業指示または適用されるリポジトリ規則が要求するものに限られる。この区別の破れが実際に測定を歪めた事例を第8節で扱う。

### 2.4 基盤が出力しないもの

評価基盤は勝者、改善・悪化の断定、指標の優先順位、採用可否、配布判断、本体反映判断を出力しない。数値を並べるだけであり、採否は人が別に判断する。この分離は本論文の解釈全体に及ぶ（第9節）。

観測された効果量は、制御が触る対象の階層で決まった。

| 階層 | 制御対象 | 効果量 | 例 |
| --- | --- | --- | --- |
| 1 | 処理量そのもの（子セッション起動） | 最大 | C41: 合計`-50.02%`、起動ほぼ0 |
| 2 | モデル再入回数（判断・検証の一括化） | 大 | C69 / C71: `-26%`〜`-30%` |
| 3 | read回数と順序 | 中（局所的、課題横断で不安定） | C63: F10で`-52.90%`、全体では不安定 |
| 4 | 指示書の表面（バイト数、label数） | 有意差なし、しばしば悪化 | C32 / C65 / C66 |

この階層はall-agent tokenの合算構造から予測できる。子1体の起動は子セッションの使用量全体を加算するため階層1が支配的になり、以降はモデルのステップ数、ツール呼び出し数、静的入力量の順に寄与が小さくなる。

### 4.4 効率改善の代償は分布の裾に出る

最大規模の測定は、C69とC71を標準14項目・`N=5` × 18束（条件あたり1,260回、合計2,520回）で実行したものである。C71はC69比でtoken中央値`-26.14%`、合計`-27.93%`、ツール呼び出し`-30.16%`、モデルのステップ`-26.54%`、所要時間中央値`-12.44%`だった。18束すべてで方向が一致し、14課題中13課題でtoken合計が小さかった。

それでもC71は評価上`stopped`だった。理由は中央値ではなく分布の裾にある。保存記録の意味確認では、C71に採点偽陰性1件と実質欠落4件があり、C69比で実質的な低得点が3件多かった。うち1件は、変更後を対象とする検証のまとめ方の制御が、**非適用領域である仕様確定前へ流入した**失敗形である。

この非対称性は反復規模の設計に直結する。`N=5`（70回）では`4 / 1,260`の頻度の欠陥は観測されない可能性が高い。本基盤が絞り込み試験→標準評価→長期反復（B18、B20）という段階設計を採るのはこのためである。**低頻度の誤経路は少数反復で不在を証明しない。**

正本: [`C69 / C71 validation closure v12 標準14項目 B18`](../evaluations/results/candidate69-candidate71-validation-closure-v12-standard14-continuous-n5-b18_2026-07-22.md)。

## 5. 層C: C82以降で効いた制御と効かなかった制御

### 5.2 効かなかったもの（3系統）

**(1) 委譲条件の細分化（C82〜C89）。** 保存記録では、rootが同じ判定条件を処理しているのに独立した子セッションを起動する重複が確認された。起動の時刻条件を細かくしても、誤って二つに分けた工程の同一性は変わらなかった。C87は指定の子セッションを使うD01で親候補比token`-51.06%`を示したが、標準14項目全体ではC81比token`+6.09%`、所要時間`+1.35%`だった（正本: [`C81 / C87 標準14 N=5`](../evaluations/results/candidate81-candidate87-producer-local-invocation-wave-v14-medium-standard14-n5_2026-07-29.md)）。**局所経路の改善を全体コスト改善へ一般化できない。**

**(2) 実行環境側の性質を指示書で書く（C90〜C93、C96、C97）。** tool出力の投影、バイト上限、結果の分類を指示書で指定しても狙った形は安定せず、コストも下がらなかった。C96は成功した検証結果を識別子とコマンドと終了コードだけへ投影しようとしたが、成功時の標準出力は全5件でモデルへ返った。C97は検証成功後の追加判断を閉じようとしたが、全5件で成功後に別の`git status`を発行した。**モデルが選べる行動と、実行環境がモデルへ返すeventを混同してはならない。**

**(3) meta的な判断の追加（C94、C95）。** risk、担当者、判断の必要性を一つのmeta判定条件へまとめると、モデルへ新しい判断が増える。C95は`N=5`を通過したが、B20（1,400回）ではA02で不要な確認を返して停止した1件とF06で担当者を質問して必須変更を実行しなかった1件が残り、コストもC81比でtoken中央値`+4.49%`、所要時間`+5.53%`だった。対応する束の符号付順位検定をHolm補正した結果、両指標ともC81より有意に悪化していた（正本: [`C81 / C95 標準14 B20`](../evaluations/results/candidate81-candidate95-required-judgment-owner-boundary-v14-medium-standard14-continuous-n5-b20-cli0146_2026-07-30.md)）。この試験で、C81側は1,400 / 1,400件が4点だった。

### 5.3 効いたもの（4段）

**(1) 初期証拠の限定と追加の既定禁止（C104）。** C99〜C103は「何を記録するか」を増やしたが、モデルは正本、テスト用ファイル、開始条件などを新しい判断材料として追加できた。C104は初めて、初期証拠を作業指示・明示された開始状態・対象成果物・明示されたread-only path・適用中の指示に限定し、それ以外の追加を既定で禁止した。追加を開くのは、許可済みの結果が具体的な不足または矛盾を示した場合だけである。標準14項目は70 / 70件が4点で、C98比token中央値`-6.48%`、所要時間`-9.77%`だった（正本: [`C98 / C104 標準14 N=5`](../evaluations/results/candidate98-candidate104-staged-evidence-admission-v14-medium-standard14-n5-cli0146_2026-07-30.md)）。

**(2) 成果値と実装方法の分離（C116）。** C112〜C115は証拠の順序、正本の委譲、確定フェーズ、正本の場所をそれぞれ個別のラベルで制御したが、A01（確認して止まる）とA02（正本から一意に解決する）を一つの条件で安定分離できなかった。C116は状態を二つに分けた。求める成果値が確定しているか（required outcome）と、それを実現する方法がリポジトリの正本から解決済みか（implementation choice）である。これによりA01は成果値未確定のまま変更・試験へ進まず、A02は確定済みの成果値を実装へ変換できた。

**(3) 実装確定を変更前工程の終端にする（C118）。** 実装方法・対象・保持すべき制約・変更条件が確定した結果を、変更前の証拠工程の終端結果にした。A02を`N=20`で測ると20 / 20件が4点で、確定後から最初の成果物変更までのコマンド再入は0 / 20件だった（C116の同条件は5 / 20件）。一方、標準14項目のtokenはC116比`+7.44%`で、所要時間は`-14.37%`だった。**機構の成立とコスト改善は別である**（正本: [`C116 / C118 標準14 N=5`](../evaluations/results/candidate116-candidate118-implementation-bind-terminal-closure-v14-medium-standard14-atomic-reuse-n5-cli0146_2026-07-31.md)）。

**(4) 条件を満たすまでの一度の追加取得（C125）。** C119は必須の検証条件と、その実行方法（厳密なコマンド）を分けた。C121は証拠要求ごとに判定条件・対象・結果範囲・後続判断を結び付け、A02の変更前再入を0 / 5にしたが、F02では場所の特定と内容取得が二段階になりコスト目標を超えた。C122は「作業指示が列挙した厳密な対象集合が同じ判定条件を共同で決める場合だけ、内容の証拠を一度のまとまりで取り切る」形にしてF02のtoken中央値を`124,719`まで下げたが、F04の1件で、最初の取得範囲に必要箇所がなかっただけの読める対象を「もう手に入らない」と誤分類した。C123は結果の往復回数に上限を置き、正常な状態を未確定と誤分類した。C124は同じ対象への追加読み取りを一回だけ許したが、取得範囲が条件を覆わずF04の誤停止を2件出した。

C125は、この追加取得を**量ではなく意味の条件**へ結び付けた。すなわち、一つの編集対象が未解決の全変更条件を持ち、他の対象は検証能力または保持制約だけを決める場合に限り、未観測の条件へ直接つながる記号の文脈全体、または同じ対象の未取得部分の終端までを覆う継続を一度許す。

平たく言えば次のとおりである。直すべき箇所が1ファイルに収まっていて、他のファイルは「テストが動くか」「壊してはいけない約束」だけを決めているとする。このとき最初の読み取り範囲に必要な箇所が入っていなかったら、**その関数や定義の全体、または同じファイルの残り全部**まで読み直す1回だけを許す。「あと1回だけ追加で読む」「あと620行読む」のような量の上限では、必要な材料がそろったかどうかを定義できない、というのがC124までの失敗から得た点である。

結果は次のとおりである。

| token中央値 | `1,401,225` | C107（検証の待ち方を閉じた候補。外側の待ちの制約が守られず採用しなかったが、同じ固定条件で指示書の差だけにより到達したtoken水準を目標値として使う）の`1,523,137`を`8.00%`下回る、C118比`-18.47%`、C122比`-0.19%` |

### 5.4 C125が組み合わせた制御

C125は、この系列で別々に確認した次の制御を一つの指示書へまとめたものである。

1. C81: 必須検証全体を一つのrootのまとめ役として完了させる。
2. C104: 初期証拠を作業指示由来の範囲へ限定し、追加は既定で禁止する。

6. C122: 厳密な対象集合が同じ判定条件を決める場合に、内容の証拠を一度のまとまりへ閉じる。
7. C125: 一つの編集対象が全変更条件を持つ場合だけ、条件を満たすまでの追加取得を一度許す。

### 5.5 失敗候補を直系で継承しない

## 7. 料金換算で見た効果

本研究の主指標はtokenの使用量そのものである。ただし使用量は、通常入力・キャッシュ済み入力・キャッシュ書き込み・出力の4区分で単価が違うため、合計tokenだけでは費用の大小を読めない。そこで、保存済みの使用量を公開API単価へ換算した記述的な比較を置く（正本: [`Candidate125課金換算比較`](candidate125-billing-equivalent-cost-comparison.md)）。

**この節の数値は指標ではない。** 換算値であって、実際の契約プランに対する請求額でもない。また、出発点と0バイト対照は採点契約v13・Codex CLI `0.144.0`、C125はv14・`0.146.0`で測っており、同一互換キーではない。**同じ単価で換算して並べた記述的な費用比較**として読む。

### 7.1 換算方法

`input_tokens`はキャッシュ済み入力とキャッシュ書き込みを含むため、通常入力は差し引いて求めた。

```text
通常input = input_tokens - cached_input_tokens - cache_write_input_tokens
```

単価は100万tokenあたりの米ドルで、`gpt-5.6-sol`は通常入力`$5.00`、キャッシュ済み入力`$0.50`、キャッシュ書き込み`$6.25`、出力`$30.00`である。Terraはその`0.4倍`、Lunaは`0.04倍`の単価体系で、model内の区分間比率は共通である（キャッシュ済み入力は通常入力の`0.1倍`、キャッシュ書き込みは`1.25倍`、**出力は`6倍`**）。推論の出力は出力tokenへ含めた。長文割増が発生する要求はなかった。C125の使用量ではキャッシュ書き込みは`0`であり、旧schemaの2条件も`0`として扱った。

| C125 Sol | `$15.5472` | **0.62倍（`-38.20%`）** | 70 / 70件が4点 |
| C125 Terra | `$6.5447` | 0.26倍 | 4点は68 / 70件 |
| C125 Luna | `$0.9571` | 0.04倍 | 4点は67 / 70件、品質中央値`92.857` |

読み取れることは2点である。

第一に、**丁寧な指示書は0バイト対照の3.64倍を払って、品質は同じだった。** 第一版から一貫している観測が、費用の単位でも同じ向きに出る。

第二に、**必要な制御を足したC125は、0バイト対照より安い。** これは第4節で「削除の下限は完成形ではない」と述べた点の裏返しである。0バイト対照に残っていたA01の欠陥を閉じた版が、費用でも`-38.20%`下回った。少なくともこの保存結果では、**品質境界を閉じることと費用を下げることが引き換えになっていない。**

TerraとLunaは単価が低いため、生tokenが増えても換算額は小さくなる。ただし4点に到達しない件数はSolより多い。**価格だけでSolと同じ成果が得られたとは扱わない。**

### 7.4 キャッシュ率では費用を判断できない

キャッシュ率が最も高いのは出発点（`86.93%`）である。それでもキャッシュ済み入力の絶対量が5,506万tokenあり、通常入力と出力も大きいため、Solの中で最も高額になった。C125 Solのキャッシュ率は`73.64%`と低いが、3区分すべての絶対量が小さい。

さらに、出力は通常入力の6倍で課金される。C125 Solの出力は生tokenの約`2.05%`にすぎないが、換算額では約`27.11%`を占める。**費用を見るときは合計tokenだけでなく、出力の量を分けて見る必要がある。**

## 8. 測定装置そのものの妥当性（採点基準が結論を歪めた事例）

効率研究では、採点契約の欠陥が結論を反転させ得る。本研究はその実例を検出し、修正した。

### 8.1 A02で起きた「要求と採点のずれ」

A02は、一見あいまいだが実はリポジトリ規則で一意に決まる正しい手順を、質問せず解決して実装できるかを測る課題である。

- 実行役へ提示した成果条件は「shell構文、作業指示または適用される規則が要求する既存試験、最終差分の確認」という**抽象表現**であり、特定のコマンド名を含まない。
- 一方、採点側（private）には`git diff --check`という**特定コマンド**が置かれていた。
- 採点器はこの抽象条件を「そのコマンドの実行必須」と読み替え、未実行を欠落として減点した。
- しかしそのコマンドは末尾空白や競合markerの検査であり、A02の主眼である手順の解決とは別物である。

C71のB18でA02のscore 3は4件あり、意味確認により3件がこのずれ、1件が別の採点偽陰性と分かれた。すなわちその4件はいずれも本物の品質低下ではない。

### 8.2 契約の版で修正する

採点条件は版別に固定し、その場では書き換えない。結果を見た後の基準変更は必ず新しい版とする。

| 版 | 主眼 |
| --- | --- |
| v10 | 実行役に提示した成果境界だけを必須にする |
| v11 | F10の数値行の意味等価と位置診断を分離 |
| v12 | コマンド証拠の直列化を正規化 |
| **v13** | 提示した抽象的な成果条件を特定コマンドへ具体化して必須化することを禁じる |
| **v14** | 終端状態と証拠の観点を加えた現行契約（層Cが使用） |

v13がこのずれを塞いだ。C71のB18自体はv12で実施しており、v12契約とその結果はそのまま履歴として保持する。**過去の結果を新しい契約で再採点したようには扱わない。**

### 8.3 一般的な含意

この事例は外部比較にも及ぶ。ベンダ公式指針が報告する「eval scoreが10〜15%改善」のような主張は、その採点契約がmodel-visible境界を守っているかに依存する。抽象的な成果条件を採点側で特定手段へ具体化すれば、手段を変えた条件は実体のない減点を受ける。**効率化の測定では、効率化された側が「省略した」ように見えやすいため、この偏りは方向性を持つ。**

正本: [`a02-rating-divergence.md`](a02-rating-divergence.md)、[`research-backlog.md`](research-backlog.md)。

## 10. 統合した設計原則

第1版が定式化した収支の式は、層Cを経ても有効である。

```text
正味token差
= 制御文の読解cost
 + 追加された判断・確認cost
 - 回避できた探索・context継承・再読・再試行・手戻りcost
```

第3項が第1項・第2項を上回るときだけ、制御は正味で効く。C41・C69・C71は第3項が支配的だった。表面圧縮系（C32、C49、C54、C64〜C68）は第1項を減らしただけで第3項を動かせず、いくつかは第2項を増やして正味で悪化した。C94・C95は第2項を増やした典型である。

層Cを加えたうえで、現在の設計原則は次の9点である（正本: [`prompt-control-design-principles.md`](prompt-control-design-principles.md)、[`C81からC125までのprompt制御知見`](candidate81-candidate125-control-findings-synthesis.md)）。

1. **状態遷移を実測可能な結果へ縛る。** `ready`、`complete`、`owner`のようなラベルだけでは足りない。何を観測すれば真になるか、どの結果で次へ移るか、どの条件で失効するかを定める。
2. **成果値・実装方法・証拠・検証を混ぜない。** 利用者が求める成果値、リポジトリから決まる実装方法、変更前に必要な証拠、変更後に必要な検証は別の判定条件である。一つの正本判定やチケットへまとめない。
3. **証拠は量ではなく、それを使う判定条件で閉じる。** バイト数、行数、対象数、呼び出し数、往復回数は完了の代理値にすぎない。
4. **速い経路は適用条件を狭くする。** C122 / C125の一括取得は、厳密な対象集合・同一判定条件・単一の編集対象が成立する場合だけ有効であり、一般的な一括readへ広げない。
5. **モデルへ新しいmeta判断を増やさない。** 担当者の必要性、追加調査の価値、正本の利用可否を新しい抽象判断として重ねると、誤停止または探索拡大を起こす。
6. **指示書の層と実行環境の層を分ける。** 指示書が制御できるのは、返された結果をどう分類し次に何を選ぶかである。出力の変換、返却の時機、外側の待ち、adapterの原子性は指示書だけでは保証できない。実行環境の診断結果を、指示書候補の解決策へ昇格しない。
7. **機構・品質・コスト・安定性・採用を別の関門にする。** 局所機構の通過は全体コスト改善ではない。`N=5`の成功は長期安定性ではない。70 / 70件の4点は採用・配布・本体反映を意味しない。
8. **失敗候補を直系で継承し続けない。** 最後に成立した親へ戻り、成功した判定条件だけを別軸として再検証する。
9. **指示書の同一性だけでなく、modelの同一性も採用条件にする。** 同じ指示書でもmodel変更により停止境界、探索量、token、所要時間が変わる。指示書とmodelの組を評価・採用の単位とする。

なお第1版が指摘した「削除ではなく置換」という含意は残る。model世代が上がると、以前は必要だった足場（明示的な検証step、委譲の指示、徹底性の要求）がモデル自身の既定挙動と二重化し、経路を増やすだけになる。指針の「削除せよ」も本研究の「判断点を消せ」も、この二重化の解消を指す。ただし0バイト条件が残した欠陥は削除では閉じず、境界の判定条件で閉じた。

## 11. 別のリポジトリでも同じことが起きるか（公開target `click`）

制御が対象リポジトリ固有でないかを見るため、公開リポジトリ`pallets/click`へ同じ枠組みを移した。非公開の対象と違い、こちらは第三者が中身を確認できる。ここでの数値は課題も採点契約も別であり、対象リポジトリ側の層と連結しない。

- C81全文を推論`medium`・14課題・各`N=5`で測ると、control-free条件比でtoken中央値`-28.79%`、所要時間中央値`-12.62%`、品質は70 / 70件が4点だった。モデルのステップは`-35.06%`、キャッシュ済み入力は`-33.92%`で、**token削減はコマンド削減ではなくモデル再入とcontext再計上の削減に整合した**。
- ただし残余経路も見えた。C81では変更前の履歴探索（`git log` / `show` / `blame`）がcontrol-free条件の`0 / 10`に対して`4 / 10`だった。これは変更後を対象とする検証の制御の外側であり、**変更前の証拠範囲という別軸の仮説として分離した**。この仮説が層CのC98〜C104、C119〜C125へつながっている。
- 階層別指示書の効果は「置くだけ」では出なかった。rootを置かず`docs` / `src` / `tests`へ指示書を置いた条件では、70回の開始時点で本文が1件も読み込まれず、本文の読み取りを確認できたのは1課題の5 / 5件だけだった。したがって配置だけでは全課題へ水平適用されない。
- 一方、正本の有無で結果が分かれることは再現した。F10（棚卸し）を見直した版では、指示書なし条件は5 / 5件が「正本がない」として停止し（score `1`）、リポジトリ正本あり条件は5 / 5件が正本と3つのsourceを照合して完了した（score `4`）。C81と正本の併用でも、他13課題の品質を保ったままこの差だけが現れ、C81の削減方向は正本の有無どちらでも維持された。

正本: [`Click Control-Free / C81全文 Medium Std14 N=5`](../evaluations/targets/click/results/click-control-free-c81-full-reasoning-medium-standard14-n5_2026-07-27.md)、[`Click C81 Medium残余経路分析`](click-c81-medium-residual-analysis.md)、[`Click No-AGENTS / Repository sub-AGENTS`](../evaluations/targets/click/results/click-no-agents-repository-subagents-reasoning-medium-standard14-n5_2026-07-27.md)、[`Click C81 / C81 + Repository Authority Std14 r2`](../evaluations/targets/click/results/click-c81-repository-authority-reasoning-medium-standard14-r2-n5_2026-07-27.md)。

## 12. 2026年7月ベンダ公式指針との対照

2026年7月、両ベンダが指示書設計の指針を更新した。いずれも本研究の主要な結論と同方向である（外部資料は2026-07-25取得、末尾参照）。

### 12.1 指針の要点

**OpenAI GPT-5.6 Sol指針**: 内部testで「よりleanなsystem promptがeval scoreを約10〜15%改善し、総tokenを41〜66%削減した」。各指示は一度だけ述べる。関係するtoolだけを露出する。手順を規定せず、目標と成功条件、制約、承認境界を述べる（outcome-first）。安全なlocal操作は確認なしに実行し、外部書き込みや範囲の実質的拡大には確認を要する。旧世代向けに最適化した指示書は結果を悪化させ得る。

**Anthropic Claude Opus 5指針**: 明示的な検証指示（最終検証stepを含めよ、検証に子セッションを使え）は削除せよ。小さな作業へ委譲を適用するとコストと時間が増える。モデルが既に行う再確認を指示するな。包括的な既定を、的を絞った指示へ置き換えよ。独立したtool呼び出しは並列化する。推論の深さを第一のコスト調整手段とする。

### 12.2 対応表

| 本研究の制御（実測） | 実測効果 | 指針との対応 |
| --- | --- | --- |
| C41 委譲境界: 担当者を指す語が現れただけでは子セッションを起動せず、作業指示が独立した実行を明示した場合だけ委譲する | C35比token合計`-50.02%`、起動ほぼ0、60 / 60が4点 | Opus 5の「子セッション起動の制御」とほぼ同一 |
| C69 判断境界: 未発行の呼び出しの選択を変えない結果のあいだではモデルへ再入しない | 中央値`-26.21%`、ツール呼び出し`-26.60%` | Opus 5「approachを選んだらcommitせよ」の不変条件版 |

| 反例系列 C32 / C49 / C54 / C64〜C68: 表面のバイト圧縮 | 静的`-1.43%`〜`-39.12%`に対し動的`-2.33%`〜`+31.36%`（多数が増加） | 「lean」をバイト削減と読むと**反例**。判断点削減と読めば整合 |
| 反例系列 C90〜C97: tool出力の投影や上限、成功後の締めを指示書で書く | 狙った投影は成立せず、コストも下がらない | 両指針が扱っていない**層の境界**。本研究の追加点 |

### 12.3 本研究が追加する点

1. **削減対象の分離。** 両指針は「lean」「trim」「remove」で方向を示すが、バイト削減と判断点削減を区別していない。本研究は同一基盤上で、両者が逆方向の結果を出すことを示す。指示書を短くする作業と、実行経路を短くする作業は別の作業である。
2. **下限の測定。** 指針は「減らせ」と言うが、減らし切った状態を測っていない。0バイト対照によれば、削減余地の大部分は文面ではなく、文面が誘発する実行経路にあった。
3. **削除では閉じない品質欠陥。** 0バイト条件はA01を`0 / 5`で落とし、C41は`1 / 60`を残した。最適点は0ではなく、**control-free相当の効率＋最小限の境界判定条件**である。
4. **効率向上の代償の定量。** Opus 5指針は検証指示の削除を「品質を損なわずに」と述べるが、対応する制御（C71）は1,260回で実質欠落がC69比`+3`件だった。代償は分布の裾に現れ、中央値では見えない。
5. **指示書の層と実行環境の層の区別。** C90〜C97、C105〜C111が示すとおり、出力の投影、返却の時機、外側の待ちは指示書だけでは強制できない。指針の推奨を「指示書へ書けば実現する」と読むと外れる領域がある。
6. **測定装置の妥当性要件。** 抽象的な成果条件を採点側で特定コマンドへ具体化すると、手段を変えた効率化条件が実体のない減点を受ける（第8節）。効率化の主張では採点契約のmodel-visible境界を先に検証する必要がある。
7. **model同一性の採用条件化。** 同じ指示書でもTerra / Lunaでは品質とコストが維持されなかった（第7節）。指針の推奨は世代・系列を跨いで自動的に移らない。
8. **検証可能性の粒度。** 指針は推奨文と内部evalを示すが、課題別分布、反復間の方向一致、失敗形の分類は公開されていない。本研究は18束での方向一致（18 / 18）、課題別（13 / 14）、対別（935 / 1,260）まで開示している。

### 12.4 未検証点

- **単一model系列・単一実行環境。** 全評価結果は`gpt-5.6`系列 / Codex CLIである。Claude Opus 5での測定は**0件**である。12.2節の一致は「異なるmodel系列で同方向の結論が独立に得られた」ことを示すにとどまる。
- **API層の統制。** 出力の詳細度指定やプログラム的なtool呼び出しは指示書の層の外にあり、未測定である。本リポジトリの方針は「安定して効果が確認された機械的な制御は自然言語の指示書へ積み増さず、型付きの作業指示、権限gate、scheduler、検証の依存グラフなどの機構へ移す」ことであり、ベンダがAPIパラメータへ移した動きと同方向である（[`future-roadmap.md`](future-roadmap.md)）。

## 13. 限界

1. **modelは`gpt-5.6`系列、実行環境はCodex CLIだけである。** Claude系modelでの測定は0件であり、他CLIでの再現も未確認である。
2. **対象は非公開の対象リポジトリの14課題と、公開リポジトリ`click`の14課題に限る。** 別のリポジトリ、別の言語、収録していない課題での再現は未確認である。
3. **層をまたいだ連結ができない。** 採点契約はv1からv14まであり、推論の深さと実行環境の版も互換条件である。層A〜層Dの数値を掛け合わせた削減率は示さない。
4. **代表点は一本の直系ではない。** 表で隣り合う条件の差を、指示書の個々の一文が単独で生んだ効果に読み替えてはならない。
5. **反復規模の上限。** 条件あたり最大1,400回（B20）である。これ未満の頻度の誤経路について不在を主張しない。C125は標準14項目のB20が未実施で、`N=100`も未着手である。
6. **中央値だけでは分布を表せない。** 点数分布と合計値を併記し、C71とC81、C118とC122のように指標間で向きが食い違う点を隠さない。
7. **採点は独立した盲検の採点者ではなく、固定した契約による監査である。** 契約と集計側の欠陥が結論に影響し得る（第8節がその実例である）。
8. **効かなかった制御の方が多い。** 効率で明確に効いたのは、子セッション抑制と再入削減の2系統である。証拠削減系はC104とC125で成立したが、C121・C123・C124は失敗した。
9. **診断値を指標へ昇格しない。** 1回で出し切れた率、誤停止件数、再入件数、一括取得の成立数はいずれも診断値であり、測っていない課題の安定性へ一般化しない。
10. **料金換算は指標ではない。** 第7節の金額は、保存した使用量に公開API単価を掛けた換算値である。契約プランに対する実請求額ではなく、採点契約と実行環境の版が異なる条件を同じ単価で並べた記述的比較である。単価改定の影響も受ける。
11. **本論文自体の位置。** この文書は総説であり、いずれの状態についても正本ではない。

## 14. 結論

指示書を実行制御として定義し、指示書の差だけを変数とする互換比較を反復したところ、次が観測された。

1. 精緻に書かれたroot指示書は実行時コストを大きく増やし、その超過は品質を買っていなかった（層Bでtoken中央値がC81の約6.25倍、層AでC41比`+278.40%`）。
2. rootを0バイトにするだけで大幅な削減が得られたが（層Bで`-70.80%`、層Aで`-74.06%`）、確認して止まる課題の欠陥は残った。**「lean」の最適点は0ではない。**
3. 削減対象は文字数ではない。静的量を減らした8件は動的量を悪化させ、判定条件を足した候補はtokenを`26`〜`30%`削減した。効果量の階層は、子セッション起動 ＞ モデル再入 ＞ read経路 ＞ 表面圧縮の順である。
4. 境界は順番に閉じる必要があった。C43が仕様確定、C71が検証のまとめ方、C81が発行単位、C104が証拠の受け入れ、C116が成果値と実装方法の分離、C118が実装確定の終端、C125が条件を満たすまでの追加取得を閉じた。C125は標準14項目で70 / 70件が4点、token中央値`1,401,225`である。
5. 効かなかったのは、委譲条件の細分化、実行環境側の性質の指定、meta的判断の追加、量による証拠の打ち切りである。**指示書の層で強制できることと、実行環境の層でしか強制できないことを分ける必要がある。**
6. 効率改善の代償は分布の裾に現れる。1,260回で4件の実質欠落が採用の関門を分け、C95は`N=5`を通過してB20で落ちた。
7. 採点契約そのものが結論を歪め得る。抽象的な成果条件を採点側で特定コマンドへ具体化する欠陥を検出し、v13で塞いだ。この偏りは効率化された側を不利にする方向を持つ。
8. 同じ指示書でもmodelを変えると品質とコストは維持されなかった。**指示書とmodelの組を評価・採用の単位とする。**
9. 公開API単価へ換算すると、出発点は0バイト対照の`3.64倍`を払って品質は同じであり、C125 Solは0バイト対照より`38.20%`安く70 / 70件が4点だった。**品質境界を閉じることと費用を下げることは、この保存結果では引き換えになっていない。** 出力は入力の6倍で課金されるため、合計tokenだけでは費用を読めない。

この到達点を一文でまとめる。

> **BaselineからC125までの改善は、指示書を短くしたことではない。不要な実行経路を取り除いたうえで、仕様の確定・モデルの往復・検証の発行・証拠の受け入れ・実装の確定という境界を、モデルが実行時に観測できる条件へ順に閉じたことの結果である。**

最後に、本基盤が一貫して分離してきた区別を再掲する。**評価は観測であり、採用は判断である。** 基盤は勝者も採否も出力しない。C71が評価上`stopped`のまま反映され、C125の一次結果が`adoption_not_decided`のまま別状態で採用・反映されている事実は、この分離が運用上も維持されていることを示す。

## 付録A. 用語解説

本文で使う言葉をまとめて説明する。カッコ内は再現性のために残した原語である。

### A.1 対象と登場人物

| 言葉 | 説明 |
| --- | --- |
| AIエージェント | 指示を受け取り、自分でファイルを読み、コマンドを実行し、コードを書き換えるAIのこと。本研究では開発支援ツールCodex CLI上で動くAIを指す。 |
| 指示書（prompt） | エージェントへ与える常設の文書。本研究では対象リポジトリの`AGENTS.md`などに置く指示文を指す。人が毎回打ち込む依頼文ではない。 |
| 指示書一式（prompt set / bundle） | 比較の単位。root `AGENTS.md`という1ファイルではなく、対象リポジトリへ差し込むファイル群のひとまとまりを指す（本研究の配布物は19 path）。 |
| `bundle_sha256` | 一式の中身から計算するSHA-256。中身が1バイトでも変われば変わる。論理的な名札である`prompt_set_identity`とは別の値である。 |
| root `AGENTS.md` | リポジトリ最上位の指示書。配下すべての作業に共通して効く。本研究で主に書き換えた1ファイル。 |
| 対象リポジトリ（target） | エージェントに作業させる実物のリポジトリ。主対象は実務で運用している非公開リポジトリ1件（固定点の識別子`THE-CAPTION@3ce91a4`）で、公開対象として`pallets/click`を併用する。 |
| 実行制御 | 指示書を「読み物」ではなく「実行の進め方を決める規則」として扱う見方。仕様をいつ確定するか、誰にやらせるか、どこまで任せるか、どこで検証するか、どこで止めるかという境界を決めることを指す。 |

### A.2 比較する指示書の呼び名

| 言葉 | 説明 |
| --- | --- |
| Baseline | 比較の出発点として固定した、既存の指示書。 |
| Candidate（候補） | Baselineを改良する案として作った指示書。作った順に番号を付ける。本文ではC5、C125のように略す。 |
| ControlFreeRepository | root `AGENTS.md`**だけ**を0バイトにし、配下の階層別指示書4つはそのまま残した対照条件。「rootの制御文だけを外したらどうなるか」を測る下限側の比較対象であり、改良案ではない。 |
| 条件 | 比較の一単位。Baseline・ControlFreeRepository・各Candidateのそれぞれを指す。 |

### A.3 測り方

| 言葉 | 説明 |
| --- | --- |
| 課題（case） | エージェントに解かせる一つの作業問題。実装、レビュー、確認して止まる判断など種類が異なる。 |
| 標準14項目（Standard14） | その14問をひとまとめにした、固定済みの評価課題集合（evaluation set）。 |
| 実行（run） | 1つの課題を1回解かせること。1課題あたり5回繰り返す条件（`N=5`）なら1条件70回になる。 |
| 反復束（B20など） | 同じ`N=5`を20束繰り返す長期試験。1条件1,400回になる。めったに起きない誤りを見るための規模である。 |
| 作業指示（TaskSpec） | 各課題でエージェントへ渡す依頼文と成果条件。全条件で同一に固定する。 |
| 採点契約（rating contract） | 採点基準を文書として固定したもの。版が変わると基準も変わるため`v13`、`v14`のように区別する。 |
| case score | 1課題1回ぶんの成果に付ける0〜4の点数。 |
| `quality_score` | 比較に使う品質指標。1反復に含まれる14課題のcase scoreを合計し満点で割って0〜100へ直し、その反復間の中央値を取る。本文の`92.857`や`100.000`はこの値である。 |
| all-agent token | 親エージェントと、そこから呼ばれた子エージェント全部を合計したtoken量。本研究のコスト指標。指標としては使用量のまま扱い、料金は指標に含めない（換算は第7節の派生表示）。 |
| `elapsed_seconds` | 一連の実行にかかった実測の所要時間（秒）。 |
| 中央値 | 小さい順に並べたときの真ん中の値。極端な外れ値に引きずられにくい。 |

### A.4 実行条件

| 言葉 | 説明 |
| --- | --- |
| model | 使用するAIモデル。主比較は`gpt-5.6-sol`（本文ではSol）に固定し、最後の追試で`gpt-5.6-terra`（Terra）、`gpt-5.6-luna`（Luna）へ変えた。 |
| 推論の深さ（reasoning effort） | モデルがどれだけ考えてから答えるかの設定。`low`〜`ultra`の6水準を測り、通常比較は`medium`に固定する。 |
| 並列上限（`M`） | 同時に走らせる実行の最大本数。本研究の通常試験は`M=24`。 |
| 互換条件 | 「同じ土俵で比べている」と言うために一致していなければならない設定一式。課題・作業指示・採点契約・model・推論の深さ・実行環境・`M`・`N`などが含まれる。 |
| 互換キー（compatibility key） | 互換条件をまとめて一つの文字列に要約した指紋。キーが一致する結果どうしだけを同じ表で比べる。 |
| 単発実行（atomic run） | 1課題1回を独立した単位として登録し、足りないぶんだけ追加実行する方式。既存の実行を再利用でき、後半の系列で使っている。 |

### A.5 エージェントの振る舞いを説明する言葉

以下は原因の説明に使う観察値（診断値）であり、コスト・品質・時間の3指標には加えない。

| 言葉 | 説明 |
| --- | --- |
| 正本（authority） | ある値や手順について「ここに書いてあるものが正しい」と定めた出所。 |
| 未確定値の確認停止 | 成果に必要な値がリポジトリから確定できないとき、推測で埋めずに人へ確認して止まること。 |
| 委譲 | 親エージェントが作業を子エージェント（worker）へ渡すこと。子1体の使用量は総量へ丸ごと加算される。 |
| モデル再入 | 一連の作業の途中で、モデルへの問い合わせが何度も往復すること。往復が増えるほどtokenと時間が増える。 |
| 判定条件（predicate） | 「何を観測すれば真になるか」を書いた条件文。指示書の1見出し（label）が1つのpredicateを持つように整理する。 |
| 必要な検証（required validation） | 変更後に必ず実行しなければならないテストやコマンドの集合。 |
| 1回で出し切れた率（one-step closure） | 必要な検証コマンドを、何度も往復せずに1回のまとまりとしてすべて発行できた割合。 |
| 変更前の証拠（pre-change evidence） | 変更に着手する前に集めるファイル内容や履歴などの材料。ここが広がるとtokenが増える。 |
| 終端結果（terminal result） | 「これを受け取ったらその工程は終わり」と定めた結果。次の工程へ進むための区切りになる。 |
| 誤停止（false stop） | 本当は読める・進められるのに、材料が足りないと誤判断して止まること。 |
| 一括取得（one-wave） | 必要なファイル内容を二段階に分けず、一度のまとまりで取り切ること。 |

### A.6 成果物の状態

評価が済んだことと、採用されたことは別である。成果物の種類は次のとおりで、互いに別のものとして扱う。

| 成果物 | 説明 |
| --- | --- |
| Baseline / Candidate | 出発点の指示書一式と、その改良案（A.2節）。 |
| 評価結果（evaluation result） | 測定と採点の記録。 |
| 配布物（release） | 配布できる形にまとめた指示書一式。**作ること自体が独立した手続き**であり、状態の一段階ではない。 |

そのうえで、指示書一式の状態は次の6段階を区別する。段階は自動的に繰り上がらない。

| 状態 | 説明 |
| --- | --- |
| `draft` | 作成中。比較の判断には使わない。 |
| `evaluation_ready` | 中身と評価条件を固定し、評価を開始できる。 |
| `evaluated` | 固定した設定で結果を取り終えた。採用はまだ判断していない。 |
| `release_candidate` | 評価範囲と未解決riskを確認し、反映の候補として固定した。 |
| `approved_for_projection` | 本体へ反映してよい、と明示的に承認した。配布物を作ったことと同じではない。 |
| `projected` | 実際に本体へ取り込み、取り込み先の識別子を記録した。 |
