# プロンプトで制御できること・できないこと

> 実務者向けExecution Controlシリーズ 4 / 8

## 結論

**本研究で試した条件では、プロンプト単独で安定して制御できたのは、返された結果の分類と後続行動の選択まででした。AIへ結果が届く前の仕組みは、試したプロンプト条件では保証できませんでした。**

この境界を知らないと、効かない指示を何度も言い換えることになります。

| 本研究で確認できたprompt側の判断 | 試したprompt条件では保証できなかった挙動 |
| --- | --- |
| 返された結果をどう分類するか | tool出力をどの形へ変換するか |
| 返された結果から次に進むか、停止するか | tool結果を返すタイミング |
| 成功・失敗の分類後にどの行動を選ぶか | modelの外側にある待機 |
| 必要な結果が揃った後に完了するか | adapterが複数処理を原子的に扱うか |

## 迷ったら「AIから見えるか」で分ける

例えば、テスト結果がAIへ返った後なら、次の条件を書けます。

```text
必須テストがすべて成功したら完了とする。
一件でも失敗したら後続の検証を止める。
```

AIは終了コードや結果を観測して、次の行動を選べます。

一方、次のような指定は別です。

```text
成功したテストの標準出力はAIへ返さない。
複数のtool結果を一つの原子的な結果として返す。
```

これは、AIが結果を読む前の配送方法を変えようとしています。プロンプトに書いても、tool adapterやexecutorが対応していなければ保証できません。

## 効かない指示を書き直し続けない

境界を見分ける質問は一つです。

> その条件を判断する時点で、AI自身が必要な値を観測できるか？

- 観測できるなら、本研究で成立した条件と同様に、進行・停止・後続行動の候補として書く
- 観測できないなら、promptで制御できたことにせず、このリポジトリでは未解決として停止する

プロンプトで解決できない問題へ自然言語を重ねても、制御が強くなるとは限りません。このリポジトリでは、runtime、executor、tool adapterなどrepository外の変更へ作業を広げません。

## 研究で確認できた範囲

研究で試した条件では、プロンプト単独で安定して扱えたのは、返された結果の分類と後続行動の選択まででした。tool出力の変換、返却の時機、外側の待ち、adapterの原子性は保証できませんでした。

これは「どんなモデルでも原理的に不可能」という証明ではありません。少なくとも、プロンプトを書けば実現したと扱ってはいけない境界が観測された、という結論です。

試した条件と境界の限定は、[技術報告の8.3節と11.3節](execution-control-measurement-report.md)にまとめています。

## これだけ覚えてください

**本研究でpromptから安定して制御できたのは、返された結果の分類と後続行動の選択までです。それより前の仕組みをpromptで保証できたことにはしません。**

品質のためにレビュー工程を増やしている場合は、次の[「AIにレビュー担当を増やす前に、判定条件を書こう」](05_review-roles-vs-decision-conditions.md)へ進んでください。
