# Candidate284 変更後の検証を一つの呼び出しで実行する指定

2026-10-07。Candidate作成前に固定する設計と計測条件。

## 目的と役割

C147の削減の主な出どころである検証側の処理方法の指定を、改訂後の[設計原則](prompt-control-design-principles.md)の「処理方法を指定できる条件」を満たす形でC280へ移植する。比較基準と直接の親はC280（result `794d02abe894456686eea22e9b6f0fed`）。C147は制御原文の参照と遵守率の根拠に限り、直接の親にしない。C283は、目的や根拠で禁止を定める文では分割を閉じられないことを示す反例であり、その三項は引き継がない。実行担当はroot。root以外の18対象とC280の既存本文をバイト一致で維持する。

## 追加原文

root `AGENTS.md`の「実行制御」の末尾へ、次の三項を追加する。

- 変更後に行う検証と確認のコマンドは、rootがすべて一つの外側のツール呼び出しの中で、発行前に決めた順に一件ずつ実行する。実行するコマンドは、受け取った依頼・適用中の指示・対象の情報から、呼び出しの前に決めておく。
- その呼び出しの中で各コマンドの終了を待ち、終了コードを個別に確認する。失敗または実行不能なら後続のコマンドを実行しない。`&&`や`;`で複数のコマンドを結合して一つの終了コードにまとめない。途中の結果をモデルへ返して、次のコマンドを別の呼び出しで発行してはならない。
- 呼び出しが終了前に返った場合は、その呼び出しの終了を待つ操作だけを行い、進捗報告や別の操作を先に行わない。全結果を受け取った後に一度だけ完了を判断する。失敗時の修正は依頼が許可した範囲と回数に従い、修正後の検証と確認も同じ形で実行する。

## 作成前の確認事項

設計原則の「Candidateを作成する前の確認事項」の各項に対応させる。

1. **比較基準と正常な最短経路。** 基準はC280。正常経路は、成果を固定し、必要な情報から変更し、要求された全検証と確認の結果を受け取って一度だけ完了を判断することである。
2. **保存traceで確認した問題経路。** C280のSol Low・Standard14 N=5では、変更を伴い再修正のない44件のうち38件で、変更後の検証と確認が複数の外側呼び出しへ分かれていた。変更を伴う45件のうち29件には、待機だけの外側呼び出しがあった。途中結果ごとにモデルの推論が再開し、蓄積した履歴を入力として繰り返し処理する。C147との変更後区間のrootトークン差は約265万で、変更を伴うrunの差全体の約94%を占める（[遵守確認](c147-sol-low-validation-call-compliance-audit-r1.md)）。これは利用者要求違反ではなく、コストを生む経路である。
3. **既存の記述やTaskSpecでは防げない理由。** C280の三項とTaskSpecは、検証の項目と順序を定めているが、外側呼び出しの分け方を定めていない。「順に」「個別に」は、別々の呼び出しで一件ずつ発行する形でも満たせる。C283の三項は目的や根拠で禁止を定めており、分割は規則に違反せず実行できた（C283でも、変更を伴い再修正のない40件のうち27件が分割）。
4. **追加する条件の全件。** 上記の三項だけである。開始側（C147の`DECISION_BOUNDARY`による開始確認と読み取りの同時発行）は別単位とし、今回は追加しない。担当、ラベル、新しい判断項目は追加しない。
5. **禁止行動、開放経路、閉じる境界と反証。** 禁止行動は、変更後の検証と確認のコマンドを複数の外側呼び出しへ分け、途中結果をモデルへ返して次を発行することである。開放経路は、呼び出しの分け方が実装方法としてモデルに任されていることである。追加文は、変更後のコマンドを一つの呼び出しに限定し、途中結果をモデルへ返す辺を閉じる。適用場面は「変更後」という確定した事実だけで決まり、必要性や目的の判定を介さない。順序、ラベル、目的の言い換えで分割しても規則違反になる。プロンプトは実行を物理的に強制しないため、不可分性は主張しない。
6. **維持する正常経路。**
   - 各コマンドの結果は、呼び出しの中で個別に確認でき、最後にまとめてモデルへ返る。失敗時の停止もその中で行う。
   - 長いコマンド（F04の`npm ci`など）は呼び出しの中で終了まで待つ。外側の呼び出しが終了前に返った場合は、その呼び出しへの待機だけを許す。
   - 再修正はTaskSpecの`machine_rework_max`に従い、修正後の検証も一つの呼び出しで実行する。修正のたびに一つの呼び出しが増えるのは正常経路である。
   - F02、F04、F07のように、結果の静的確認や独立確認がある場合は、差分の取得を同じ呼び出しに含め、受け取った出力からモデルが一度だけ判断する。独立確認を別担当へ委ねる場合はC280の担当対応を適用し、この指定の対象外とする。C280のSol Low・Standard14では委任は0件だった。
   - F04の`node_modules/`と`dist/`の後片付けは試験基盤の担当であり、モデルの呼び出しへ含めない。
   - 変更を伴わない経路（A01、F05の2ケース、F10の2ケース）には適用されない。
7. **新しく増える判断と対象外への影響。** 新しい判断は、呼び出しの前に実行するコマンドの一覧を決めることだけである。これはC280の「作業前に実施方法を一つの方針にまとめる」と同じ範囲にある。コマンドが未指定の場合でも、受け取った情報から決め、コマンド選びのための追加探索は行わない（C280第3項）。変更を伴わない経路への新しい分岐は生じない。C147ではSol Lowの全70件が品質4であり、検証の一括実行と品質低下の関係は観測していない。
8. **評価ケースと比較条件。** C283のN=5用profile（`c283-sol61-low-standard14-n5-cli0159-isolated-20261007-r1`）からprompt identityとprofile IDだけを変える。GPT-6.1 Sol Low、Standard14全14ケース各N=5の計70件、Rating v14、CLI 0.159.0、Python 3.14.5、固定Layer 1、fixture、TaskSpec、個人指示の隔離、M24、固定executor、全エージェントのトークン計上を再利用する。主比較はC280。品質、全エージェントトークン、経過時間の3 KPIで判定する。原因の診断として、遵守確認と同じ方法で、変更後のコマンド実行呼び出しの数、待機だけの呼び出し、再修正、変更前後のrootトークンを集計し、設計原則の条件3の遵守率をこのCandidateについて確認する。
9. **停止条件。** 互換条件の不一致や未確認があれば、一件目の発行前に停止する。外部失敗だけ同じ枠で固定上限内に再試行し、有効な失点は保存する。70件を完了して判断し、自動で追加反復しない。品質を維持し、トークンと経過時間がともに減った場合だけコスト改善の方向とする。片方でも増えた場合は、その指標の退行として記録する。遵守率は独立した合否条件にしない。採用、本体反映、方式の修正による再試験は行わない。
