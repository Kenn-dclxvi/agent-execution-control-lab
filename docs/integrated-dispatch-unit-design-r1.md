# 検証と読み取りの発行単位を統合する設計（r1）

2026-10-08。Candidate本文の作成前に固定する設計記録。[要素の抽出の検討（r5）](c291-improvement-review-r5.md)で決めた方針のうち、検証と読み取りの二つを一つの実装に統合する。[設計原則](prompt-control-design-principles.md)の全文を読み、「Candidateを作成する前の確認事項」の項目1〜9に対応させた。Candidateのbundleはこの記録では作成しない。

## 目的と成果物の関係

- 系列：汎用指示の改善系列。比較の基準かつ親はC280（汎用の到達点）。
- 必要な効果：C281以降で効いた要素（検証を一つの外側呼び出しにまとめる、確定した読み取りを同じ応答にまとめる、検索と本文取得を同じ呼び出しで返す）が閉じていた経路を残し、実装を一つに統合して、固定コストを減らす。Sol LowとClaudeに同じ本文を渡す。
- 保持するもの：全件4点の品質、C280の本文、Solの削減、C291の終了コードの一文が果たす役割、モデル別の本文を作らないこと。
- 関係：C284〜C291は制御原文の供給源であり、親ではない。C291の本文を出発点にしない。ルート本文の非取得（C290）は、Solのコストに結びついていないため対象に含めない。範囲の一項（C285）は別の辺（リポジトリ外の読み取り）を閉じるため、統合せず、原文のまま全文に残す。
- 変更対象：root `AGENTS.md`だけ。成果と担当（C280の本文）、範囲の一項（C285の原文）、事前調査の一項（C280の原文）は文言を変えず、読み取りと検証の6項目を下の4項目に置き換える。他の18対象はC280とバイト一致を保つ。

## 1. 比較の基準と、正常な最短経路

基準はC280（result `794d02abe894456686eea22e9b6f0fed`が属するSol Low、およびClaude各モデルのC280保存結果）。正常な最短経路は、成果を固定し、必要な情報を集め、変更し、要求された検証をすべて受け取って、一度だけ完了を判断することである。

## 2. 保存traceで確認した問題経路

- **検証の分割。** C280のSol Lowでは、検証を含む40実行のうち30で、検証の呼び出しが2回以上あった。C284でこれが10/45、C289で7/45に減り、検証を一つのループにまとめた実行は3/40から44/45に増えた。途中結果ごとにモデルが再入し、蓄積した履歴を入力として処理し直す経路が、C280とC147の差の約94%を占めていた（C284の設計記録）。
- **読み取りの再入。** C289の設計記録のとおり、検索の位置だけを返して本文取得を次の応答へ送る経路で、C288のF03とF06などが外側呼び出しを増やし、root入力トークンを一件平均で約10,800〜19,300増やした。
- **固定コスト。** 統合の対象とする現行の6項目（C291）は3,905バイトで、Opus lowの1反復あたり約73,000トークンの固定分にあたる。Claudeの増加の大きな部分を占める。

## 3. 問題経路を許している記述と、TaskSpec・正本で防げない理由

C280は、これらの再入を定めていない。TaskSpecは検証の項目と順序を定めるが、呼び出しの分け方を定めない。C284、C288、C289は、同じ辺（確定した事実だけで次の操作が決まるのに、結果をモデルへ返して再入すること）を、検証、開始時の読み取り、検索と本文の取得に分けて、別々の文で閉じていた。同じ辺を複数の箇所で閉じていることが、固定コストの増加につながっている。

## 4. 追加・変更・削除する条件の全件

C291の読み取り3項目と検証3項目（計3,905バイト）を、次の4項目（2,262バイト）に置き換える。案文を下に固定する。

> - 依頼と適用中の指示だけで確定している操作は、結果をモデルへ返さず続けて発行する。読み取りは同じ応答の中にまとめ（呼び出しは分けてよい）、検索とその一致箇所を含む定義・節の本文取得、および変更後の検証と確認のコマンドは、それぞれ一つの外側のツール呼び出しの中で順に実行する。これ以外の、先行結果によって対象・範囲・許可が決まる読み取りは、その結果を受け取ってから発行する。
> - 開始時の確認と、依頼が名指しした対象の読み取りは、最初にツールを呼び出す応答で発行する。読み取りには、本文の取得範囲を特定する検索とその範囲の本文、および適用される指示ファイルの取得を含める。確認前の読み取りを禁じる依頼では、一つの呼び出しの中で確認を先に実行し、停止条件に当たれば読み取らずに結果を返す。成果が決まっていない間の調査は、この指定で許可されない。
> - 適用される指示ファイルと、全文取得が指定された資料は全文を読む。それ以外の本文は、指定された範囲、名前・語句の検索一致箇所を含む定義・節、およびそれらの直接の参照先に限って取得する。定義・節をその呼び出し内で特定できない場合は、一致箇所と直接関わる限定した周辺本文を返す。検索結果にも同じ範囲の制限を適用し、実質的に全文を返さない。追加取得は未取得の範囲に、再取得は変更で失効した範囲に限る。
> - 変更後に行う検証と確認のコマンドは、呼び出しの前に決める。その呼び出しの中で各コマンドの終了コードを個別に確認し、失敗または実行不能なら後続を実行しない。呼び出し自体は、全て成功した場合は0、止めた場合は止めたコマンドの終了コードで終える。呼び出しが終了前に返ったときは、その終了を待つ操作だけを行う。全結果の受領後に一度だけ完了を判断し、修正後の検証と確認も同じ形で実行する。

### 指示全文の構成（統一した表記）

指示全文は、次の構成で一つの書式に統一する。追加分だけが別の表記にならないよう、C280から引き継ぐ文も同じ書式で並べる。

### 反証する構成

- 検証を2回の外側呼び出しに分けて実行する：第1項と第4項に違反する。保存traceの外側呼び出しの数と内容で観測できる。
- 検証を`&&`でつなぐ：禁止されない。ただし、第4項の「終了コードを個別に確認」「止めた場合は止めたコマンドの終了コード」に従う必要がある。失敗を隠した結合は、呼び出し全体の終了コードが結果と一致しなければ違反になる。
- 検索を発行し、位置だけを返す：第1項と第3項に違反する。

### 残る穴（既知）

- 第1項の「先行結果によって対象・範囲・許可が決まる読み取りは、受領後に発行する」は、C289から引き継ぐ例外である。モデルが、依頼で確定している読み取りを「先行結果で決まる」と分類して再入する構成を、完全には防げない。これは分類を要する判断であり、閉じた経路とは主張しない。この穴は、開始時の読み取りの観測（第2項の対象を最初の応答で発行した割合）で診断する。

- Claudeの検証コマンドの出力の形（絞るか否か）は、プロンプトでは強制できない。未解決のまま残す。

## 6. 維持する正常経路

- 検証：各コマンドの結果は、呼び出しの中で個別に確認でき、最後にまとめてモデルへ返る。失敗時の停止もその中で行う。長いコマンドは呼び出しの中で終了まで待ち、外側の呼び出しが終了前に返った場合は、その呼び出しへの待機だけを許す。再修正は、修正後の検証を同じ形で実行する。
- 読み取り：指示ファイルと全文指定の資料は全文を読める。検索一致なしの結果、出力の欠落、直接の参照先が読んだ範囲から初めて分かる場合の後続の取得は、受領後に発行できる。確認前の読み取りを禁じる依頼では、確認を先に実行して停止できる。
- 変更を伴わない経路（A01、F05、F10）：検証の項目は適用されない。読み取りの項目は、これらの経路でも最初の応答のまとめ発行と範囲限定として働く。

## 7. 新しく増える判断と、変更対象外への影響

- 新しい判断は増えない。「確定している」かどうかは、依頼、適用中の指示、検索結果の機械的な参照関係から決まる。この判断は、C288、C289がすでに持っていたものと同じ範囲にある。
- 変更対象外への影響：成果と担当、調査の範囲（C285）、他の18対象は変えない。統合によって文の関係が変わるため、読み取りの束の挙動が変わる可能性がある。これは診断として観測する。
- 固定コストは、指示全文でC291より1,627バイト減る（置き換える6項目では1,643バイト減る。ルート本文の非取得の約270バイトを含む）。Opus lowの固定分で、1反復あたり約30,600トークンにあたる見積もり。

## 8. 評価ケース、比較単位、比較条件

- 比較単位：Standard14の全14ケース、各N=5の計70件を、モデルごとに1条件とする。
- 基準：各モデルの保存済みC280結果（Sol Low、Opus 5.5 low、Sonnet 5.5 low、Haiku 5.5 low）。参考として、保存済みのC289・C291の結果を並べる。
- 比較条件：Sol Lowは、C289・C291と同じ固定Layer 1、CLI 0.159.0、個人指示の隔離、全エージェントトークン計上。Claudeは、C280・C291のlow N=5と同じClaude Code 2.1.288、評価コード、権限、tool集合。変えるのは、prompt identityだけとする。発行前に、基準結果との互換条件の完全一致を示すpreflight receiptを保存し、不一致があれば一件も発行しない。
- 測定の順序：まずSol Lowで、削減が保たれるかを確かめる。保たれた場合に、Opus low、Sonnet low、Haiku lowの順に、固定コストの減少がClaudeの増加を減らすかを確かめる。
- 判定：品質を維持し、全エージェントトークンと経過時間がともに減った場合だけ、cost改善の方向とする。一方でも増えた指標はcost退行として記録する（設計原則）。モデルごとに分けて判定し、相殺しない。
- 診断（合否にしない）：検証を一つの外側呼び出しにまとめた実行の割合、最初の応答で読み取りをまとめた割合、検索と本文を同じ呼び出しで返した割合、検索の窓の大きさの中央値、検証の出力の大きさ。
- 「ばらつきを超える」の基準：未決。N=5の標準誤差（Claudeで約20,000〜32,000トークン）を使うか、再現性の基準（N=5・20・50）に従って反復を増やすかを、実行前に決める。

## 9. 停止条件

- 互換条件の不一致、未確認があれば、一件目の発行前に停止する。
- invalid、採点不能、品質の低下は、有効な改善として扱わない。外部失敗だけ、同じ枠で固定上限内に再試行する。
- 70件で判断し、自動で追加反復しない。採用、release、本体反映は別の判断とする。
- 診断値（遵守の割合）だけで、追加Nや比較を停止しない。

## 判定

項目1〜9を満たす記録を固定した。Candidateのbundle作成は、この記録の範囲で可能である。ただし、次の点は結果で確かめるまで主張しない。

- 統合した文が、Solの検証のループ化（44/45）と、開始時のまとめ読みを保てるか。責務名での言い換えが機序を回復しなかった過去の例（C191〜C193、C204、C205）がある。
- 固定コストの減少（約1,600バイト）が、Claudeのトークンの増加を、ばらつきを超えて減らすか。減少量はOpus lowの合計の約4%で、N=5では検出できない可能性がある。

## 判断の限界

- 案文はこの記録で固定し、結果に合わせて書き換えない。変更する場合は新しい版とする。
- 固定コストの見積もりは、C280→C291の実測比（1バイトあたり約18.8トークン/反復、Opus low）を使った推定である。
- この記録は採用、release、本体反映を決めない。
