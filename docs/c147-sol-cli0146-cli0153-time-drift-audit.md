# C147 Solの旧環境と再計測の時間増加

C147 Solの852.543秒から1,178.039秒への増加は、モデルの作業量増加だけではない。中央値の差325.496秒のうち、初期入力が記録されるまでの区間とroot実行記録の外側で227.185秒増えており、約69.8%を占めた。ツール呼び出し区間が72.200秒、残りの区間が26.111秒増えた。

比較対象は過去N=5の`f7baeadc5bd44399ac13cc0e0a8aff48`と、9月5日のN=5再計測`1dc4feb4282e42bdac2f19ddb6e80eaf`である。C147 bundle、Sol、medium、14ケースと採点は同じで、登録compatibilityの差はCLI 0.146.0→0.153.3。実行時期も異なる。CLI版だけの因果効果を測定する実験ではない。Astraは対象外である。

## 中央値の差を分解した結果

各条件で登録中央値を実際に構成する14runを選んだ。旧結果はselection iteration 2、新結果はiteration 1。両者の14ケース合計を、重複しない時刻区間へ分けた。ケース別中央値の合計や平均値への置き換えは行っていない。

| 区間 | 旧結果秒 | 再計測秒 | 増加秒 |
| --- | ---: | ---: | ---: |
| root開始から最初のuser入力記録まで | 40.692 | 156.718 | 116.026 |
| root記録の外側（開始前・完了後） | 85.841 | 197.000 | 111.159 |
| ツール呼び出しから結果返却まで | 39.453 | 111.653 | 72.200 |
| 上記以外のroot区間 | 686.557 | 712.668 | 26.111 |
| 合計 | 852.543 | 1,178.039 | 325.496 |

root区間は`task_started`から`task_complete`。入力準備区間は最初のuser messageの記録時刻までであり、内部の具体的な処理をすべて識別したものではない。ツール区間は外側callとoutputの時刻差の和で、重複は除外した。最後の行の前の残余区間には応答生成、通信、待機などを含むため、純粋な推論時間とは呼ばない。中央値を構成するrunの選択は異なるため、この分解を各runの因果寄与と混同しない。

## 終了後に増えた待ち

実行アダプタはCLI subprocessの終了後に`codex-events.jsonl`を保存し、その後にusageを集計する。保存済みファイルの更新時刻を補助証拠に用いて、root完了からこの保存までと、保存からusage保存までを分けた。更新時刻にはファイル保存時間も含まれるため、精密な内部計測ではない。

範囲外deployを断って終了するF05の各N=5では、次の差を確認した。

- root完了からCLI実行ログ保存まで: 旧約0.6秒、再計測約17.6秒。
- 実行ログ保存からusage保存まで: 旧約0.3秒、再計測約0.4秒。
- root開始から最初のuser入力記録までの中央値: 2.889→17.233秒。
- 作業の外側call数と推論応答回数の中央値: 両者1回・2回。

従って、このケースでは追加作業やusage集計の重さだけでは説明できず、CLIが戻るまでの終了処理付近と初期準備が増加箇所である。取得できた旧55runではroot完了後の中央値1.038秒、新70runでは6.389秒だった。旧15runの終了前後メタデータは今回の抽出元に含まれず、この補助比較へ入れていない。全140runのroot時刻分解自体は取得できている。

## 今回だけ観測したエラー

再計測70runのうち39runで、`codex_models_manager::manager`が`failed to refresh available models: timeout waiting for child process to exit`を記録した。旧stderrを取得できた55runでは0件だった。モデル一覧更新の子プロセス終了待ちのタイムアウトという具体的な環境事象は確認できた。

ただし、タイムアウト記録のない新31runでも初期区間は長く、新結果内の中央値はタイムアウトあり11.691秒・なし9.840秒だった。タイムアウトを325.496秒すべての原因とは断定しない。接続関連エラーも少数あったが、基準と同じ採点・実行契約で70件は有効として記録されている。

## 特定できた範囲と残る限界

大部分の増加が初期準備とroot記録外の時間にあり、そのうち終了後の待ちがCLI subprocess終了付近で発生していることを特定した。C147 Solのトークンは1.45%減少しており、モデルの作業増加が全体時間増加の主因という説明は成立しない。ツール区間の増加も存在するため、環境側の一種類の待ちだけへ全差を帰属することもできない。

一方、CLI内部のどの終了処理が待ったか、モデル一覧更新タイムアウトと初期・終了待ちの因果関係、サービス側負荷とローカル負荷の寄与は保存済みログでは分離できない。CLI新版そのものが原因という確定まではしていない。外部runtime、設定、評価基盤の変更や新規評価は実施していない。

[140runの時刻・数値・SHA-256](c147-sol-cli0146-cli0153-time-drift-audit.json)を一次診断に用いる。旧55runのメタデータは既存のexecution-evidence.tar.zstから`/tmp`へ必要部分のみ展開し、残り15runはresultのrun IDに一致する保存rolloutを参照した。run原本と履歴結果は変更していない。
