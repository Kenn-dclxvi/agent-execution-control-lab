# 共通の指示文を改善する判定基準と、変更を考える範囲（r1）

2026-10-09。C281以降の検討で、判定の基準が「作った規則（機序）をモデルに守らせること」へずれ、試験が何を見ているかから変更を考えていなかったことを、利用者の指摘を受けて正した記録。以後のCandidateの設計と判定は、この記録の基準に従う。[設計原則](prompt-control-design-principles.md)の「制御の価値と評価順序」と、[`evaluations/AGENTS.md`](../evaluations/AGENTS.md)の3 KPIを、この系列へ当てはめたものであり、新しい基準を作るものではない。

## 何がずれていたか

- C293〜C296とその判定表の追記では、機序（変更前に戻る回数、検証の一括化、位置だけの検索）が両方のセルで「成立するか」を、残す・外すの基準にしていた。機序は、3 KPIの差の原因を調べる診断であり、目標ではない（設計原則）。
- [Sonnet lowの検証の分割の分析](sonnet-low-validation-split-cause-r1.md)の後に、検証をまとめる規則を、Claudeの課題文の指定と両立する別の形で通す案（同じ応答に並べる）を出した。Claudeの課題文が「必須の確認コマンドは1つずつ別々の`Bash`呼び出しで実行する」と指定しているのは、品質の判定で、必須コマンドごとの終了状態を証拠として取るための、試験の条件である。試験の条件と食い違う規則を、形を変えて守らせる案は、この基準では検討の対象にしない。この案は撤回する。

## 判定の基準

1. **品質を保つ。** 各セルで、有効な4点未満を増やさない。4点未満は中央値で相殺しない。
2. **主なセルの両方で、C280よりトークンと経過時間を増やさない。** 主なセルはGPT-6.1 Sol LowとClaude Code Sonnet 5.5 lowとする。全エージェントの`total_tokens`と`elapsed_seconds`の中央値で、C280（各セルの保存済み結果）と比べる。両方が減った場合だけコスト改善の方向とし、一方でも増えた指標はコスト退行として記録する。セルの間で相殺しない。
3. **機序の指標は、3 KPIの差の原因を調べる診断に限る。** 機序が成立したことを、残す理由にも外す理由にもしない。

## 試験の条件

- 課題文、TaskSpec、評価の仕組みがモデルへ渡す指定（必須コマンドの実行方法、開始時の確認など）は変えない。変える場合は、プロンプトの比較ではなく評価条件の変更となり、利用者が明示的に依頼する別作業とする（`PROMPT_ONLY_COMPARISON`）。
- 指示文に、試験の条件と食い違う指定を書かない。たとえば、Claude Codeで必須の確認コマンドを一つの`Bash`呼び出しにまとめさせる指定は書かない。
- Standard14のTaskSpecが求める操作は、開始時の確認（`pwd`、ブランチ、`HEAD`、`git status --short`）、許可された対象の変更、必須の確認コマンド（focused gateとfull gate）、既存の正本・対象の実装・試験を必要な範囲で読むこと、である（例：[F01のTaskSpec](../evaluations/cases/TC-F01-DOMAIN-DUPLICATE-ASSET-KEY/r3/trial-prompt-input.json)）。

## 変更を考える範囲

- 試験の条件を守ったうえで、プロンプトで減らせるトークンと時間がどこにあるかを、各セルの保存traceから特定し、そこから考える。
- 進め方：まず、C280の各セルのトークンを、TaskSpecが求める操作（開始時の確認、変更、必須の確認コマンド）と、それ以外（読み取り、探索、必須以外の確認、やり取りの回数）に分ける。求める操作以外で、両方のセルに共通して大きな部分を、次の設計の対象にする。
- 片方のセルでしか減らせない部分を、もう片方のセルを悪化させてまで減らさない。

## 既存の記録との関係

- C281〜C296の結果、判定表、各設計記録は、当時の記録として保持し、書き換えない。この記録は、以後の判定の基準を固定する。
- この記録は採用、release、本体反映を決めない。
