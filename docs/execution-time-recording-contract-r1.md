# 実行時間の記録規則 r1

2026-09-05に記録規則を固定した。これは評価基盤の時間診断の契約であり、実装・導入済みという宣言ではない。現行の3 KPI、`elapsed_seconds`、採点、比較条件、採用条件は変更しない。レイヤー境界は[評価基盤の正本](prompt-comparison-workflow.md)、実行手順は[評価実行手順](evaluation-loop-manual.md)に従う。

## 1. 何を残すか

総所要時間を必ず保持し、その内訳として開始付随時間、作業時間、終了付随時間を記録する。作業時間にもモデル応答待ち、通信、ツール実行、子エージェント待機を含める。「純粋な推論時間」「モデル速度」とは呼ばない。

現行の`elapsed_seconds`は、評価基盤がアダプタのsubprocessを起動する直前から、同processが戻るまでの単調時計による計測値である。キュー投入から開始まで、fixture準備、採点、集計はこの値に含まれない。従って利用者の依頼受付から完了までの全待ち時間とも区別する。この区間を今回の規則のために取り直したり、補正した値で上書きしたりしない。

| 記号・記録名 | 境界の意味 |
| --- | --- |
| `t0 / execution_started` | 現行elapsed計測開始。アダプタ起動直前 |
| `t1 / initial_input_delivered` | 対象runの初回推論へ必要な初期入力一式が渡された境界 |
| `t2 / response_completed` | 対象runの最後の回答が確定した境界。最初の出力・commentary・中間turnの終了を使わない |
| `t3 / execution_ended` | 現行elapsed計測終了。アダプタprocessが戻った直後 |

- `startup_seconds = t1 - t0`
- `work_seconds = t2 - t1`
- `shutdown_seconds = t3 - t2`
- 同じ時計で全境界が得られれば、3区間の和は`elapsed_seconds`と一致する。

`t1`は最初のuser messageの記録時刻ではない。初期system・developer・repository instruction・TaskSpec・評価用protocolなど、当該runtimeが初回入力へ含める全要素の配送が完了したことを、runtime別の対応表で確認する。動的な入力取得を作業開始後に行うruntimeでは、その取得も作業に含め、後からt1を移動しない。最初の応答受信までを開始付随時間に入れて、応答待ちを除去してはならない。

`t2`はプロトコル上の回答完了であり、成果品質の合格ではない。回答後の子process残存・終了待ち・usage集計は終了付随時間に残し、未完了の子実行を別に記録する。品質やrun有効性は従来の契約で判定する。複数turnがあるrunは初回入力から最終回答までの一つの区間とし、途中の待ちを差し引かない。回答完了を観測できない中断・失敗ではt2を推測しない。

## 2. 証拠と時計

実装時には、runtime・CLI・collectorの版ごとに、各境界に対応するイベント、発行主体、run／thread／turnとの結び付け、時計の種類と分解能を実行前に固定する。ファイル名やイベント名の類似だけで、別runtimeへ同じ意味を当てはめない。

| 証拠区分 | 扱い |
| --- | --- |
| `direct` | 境界の意味が確認済みで、同一の単調時計により取得。正式な内訳として記録可能 |
| `reconstructed` | 保存イベントから再構成。イベントの意味、時計の対応・精度が確認できる範囲で診断に使用 |
| `proxy` | 最初のuser記録、ファイル更新時刻などの代用。別名の診断区間としてだけ表示 |
| `unavailable` | 必要境界・対応・時計の根拠が不足。該当時間はnull |

各区間へ証拠区分を付け、弱い境界を含む区間は強い区分にしない。UTC時刻は照合用に残すが、異なるprocessの単調時計値を直接減算しない。同一時計への変換が必要なら、対応証跡と最大誤差を記録する。時計補正や精度の根拠がない場合、正式な内訳は欠測とする。

負の時間、逆転、境界の重複、run不一致、重複した完了イベントの解決不能は`invalid_timeline`とし、丸め・0への切り上げで修復しない。区間和と総所要時間の差は未丸め値で保存する。許容誤差は結果を見る前に時計の分解能と変換誤差から定める。許容範囲外なら内訳を無効にし、現行elapsed自体の有効性は従来契約で別に判定する。

## 3. 保存単位と必須情報

一つの実行attemptにつき、既存runとは別の変更不可の診断記録を作る。想定保存先は`EVAL_EXTENSION_DIR/execution-time/`。この規則だけを理由に既存schemaやコードへ新しい必須項目を追加しない。

記録は少なくとも次を含む。

- 記録ID、契約版`execution-time-recording/r1`、collector版・内容hash。
- result ID（登録後の結び付けは別記録）、run ID、attempt ID、case ID、selectionとの対応、prompt identity、model、reasoning、runtime／CLI identity、実行日時・並列条件。
- 総所要時間の値と正本参照、t0〜t3の未丸め値、イベントIDまたは行位置、時計情報、各証拠区分。
- 3区間の値、境界の欠測理由、時間軸の状態、区間和の差と許容誤差。
- 根拠ファイルのSHA-256、保存先参照。非公開生ログや入力本文は公開用記録へ複製しない。
- 終了状態、子実行の終了確認状態、観測したタイムアウト・接続エラーの件数と発生区間。エラーと時間差の因果を未確認のまま結び付けない。

生イベントと対応表は既存のseal対象へ含め、workspace削除前に参照可能性を確認する。欠測は0にせず、未取得、未対応runtime、切断、時計不一致など理由を残す。再試行はattemptごとに保持し、成功attemptへ失敗attemptの時間を加算しない。キャンペーン全体の運用費用を示す場合は、全attemptを含む別集計と明示する。

## 4. 追加の診断区間

必要なら、root開始、CLI process終了、ログ保存、usage保存、個別ツールcallとresultの境界を追加する。ただしt0〜t3と混ぜて別の作業時間を作らない。

ツール時間は作業区間と交差するcall〜result区間の和集合とし、並列callや子実行の時間を二重加算しない。子エージェントの経過時間をroot時間へ加算しない。ツール時間を作業時間から引いた残りも、純粋なモデル推論時間とは呼ばない。ツール結果欠落時には、該当内訳を欠測にする。

ファイル更新時刻はログ保存の代理観測であり、CLI終了時刻の直接証拠に昇格させない。今回のSol監査で使った「最初のuser記録まで」「root完了からログ保存まで」はこの代理診断に当たり、本契約のt1・CLI終了へ読み替えない。

## 5. 集計・比較・表示

比較前に基準result ID、対象result ID、selection IDとrun集合、契約版、各境界の対応表を固定する。CLIや実行日時が異なる場合は差を明記し、比較相手を説明なく差し替えない。

通常の集計は既存と同じく、sampleごとに全caseの値を合計し、そのN sampleの中央値を取る。個々のcase中央値を足して全体中央値と呼ばない。診断値にも件数、対象case、N、欠測数、証拠区分を併記する。

- 全体の作業時間中央値は、必要な全sample・全caseに同じ定義の区間がある場合だけ主比較として出す。
- 欠測があれば全体の内訳は未完了とする。観測済み共通部分を示す場合は対象集合を固定し、部分比較と明示する。欠測caseを黙って落とした中央値を全体値と比較しない。
- 総所要時間の中央値の内訳を説明する場合は、実際にその中央値を構成するsampleの各区間を使う。偶数Nは中央2 sampleの区間平均とする。同値の選択規則はsample ID順へ固定する。
- 各区間を独立に中央値化した表では、区間の中央値の和が総所要時間中央値と一致するとは限らない旨を明記する。
- 異なる証拠区分・境界定義の値を同じ母集団へ混ぜない。作業時間が短くても、現行elapsedの増加を相殺してコスト合格へ変更しない。

## 6. 過去結果と導入

過去のresult、elapsed、採点、採用判断は上書きしない。保存ログの再解析は、新しいIDを持つ診断として追記し、取得できたイベントをその証拠区分で記録する。旧ログに正式な境界がなければ、代理区間のまま保持する。

本規則の固定は文書だけを対象とする。次の実装で境界が取得できるか検証するまで、作業時間を取得済みとは扱わない。導入検証には、通常終了、無ツール終了、並列ツール、子実行待ち、中断・タイムアウト、欠測・時計逆転、複数turnを含め、区間の意味と非重複性を確認する。

当面の内訳は診断であり、第4のKPIではない。計測実装によってruntimeやexecutor挙動が変わる場合は別の評価系列とし、旧結果との差をprompt効果へ帰属しない。将来work_secondsをコスト判定に採用する場合は、KPI・比較・停止条件を別途改訂し、導入前後を別系列として扱う。本規則だけでその変更を許可したことにはしない。

根拠となった問題は[C147 Solの時間増加監査](c147-sol-cli0146-cli0153-time-drift-audit.md)に保存している。記録の定義と、個別監査から推定した原因は分けて扱う。

## 実装追記

記録契約の固定後、`scripts/execution_time_recording.py`による診断保存をLayer 2の既存実行記録確定後へ追加した。`execution-time/diagnostic.json`は総所要時間と欠測理由、根拠hash、代理区間を別記録として保存する。アダプタは`execution-time/adapter-clock.json`へCLI subprocessの起動・復帰を同一processの単調時計で記録する。これらは既存extensionsとともに保存対象となる。

CLI 0.146.0／0.153.3のpersisted記録についてrootのturn・threadを照合するが、初期入力全配送の境界と単調時計との対応は未観測である。このため正式な3区間はnullを維持する。root区間・最初のuser記録まで・ツール区間は明示的なproxyとしてだけ出力し、子usageの存在を子実行完了の証拠にしない。未対応runtime、中断、欠落、時計逆転は診断の欠測または無効として保存する。今回の導入に伴う新規モデル評価は行っていない。
