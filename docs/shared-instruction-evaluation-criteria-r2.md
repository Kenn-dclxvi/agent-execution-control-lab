# 共通の指示文を改善する計測と記録の基準（r2）：トークンの数え方を料金の重みへ改める

2026-10-09。利用者の依頼（評価を見直す機会に、KPIの使い方と種類を見直し、試算してから続ける）を受けて、[判定基準r1](shared-instruction-evaluation-criteria-r1.md)のうち、トークンの扱いと、計測の記録の仕方を改めたもの。r1は当時の記録として保持し、書き換えない。r1の「試験の条件」と「変更を考える範囲」の考え方は、この版でも引き継ぐ。評価基盤への反映は、後述のとおり同日に実施した。

## 適用する範囲

- [実行環境を切り離した新しい評価系列](agent-runtime-venv-isolation-record-r1.md)（`shell_environment.revision: fixed-path-workspace-venv-r1`）に適用する。この系列の基準は[C301](candidate301-c280-uniform-markdown-design.md)（[計測記録](../evaluations/results/c301-sol61-low-sonnet55-low-standard14-n5-shellenv_2026-10-09.md)）。
- 旧系列（C280〜C300）の結果と判定は、当時の基準（r1）による記録として保持し、書き換えない。

## 改める理由

[試算](../evaluations/results/kpi-cost-weighting-trial_2026-10-09.json)では、全エージェントのトークンの約85%が、キャッシュから読み直した文脈だった。この読み取りの単価は通常の入力の20分の1（$0.10 / 100万トークン）であり、生のトークン数は、実際にかかる費用とずれている。

| セル | 条件（C280比） | 生のトークン | 費用 |
| --- | --- | ---: | ---: |
| Sol Low | C298 | −10.4% | +2.6% |
| Sol Low | C299 | −11.7% | +6.4% |
| Sol Low | C300 | −20.9% | −5.7% |
| Sonnet low | C298 | +3.1% | +1.6% |
| Sonnet low | C299 | −1.8% | −1.4% |
| Sonnet low | C300 | +2.1% | −2.1% |

- Sol Lowの削減は、主に安いキャッシュ読み取りの削減だった。キャッシュを使わなかった入力（単価が20倍）は、C298で+9%、C299で+19%増えており、生のトークンで「改善」だったC298とC299は、費用では増加になる。
- Sonnet lowでは、C300の増減の向きが逆になる。
- Sonnet lowでは、費用で数えると反復の間の揺れが小さくなる（C280の反復の幅は、生のトークンで約16%、費用で約3.5%）。Sol Lowは、どちらで数えても約10%揺れる。

この表は旧系列の結果の数え直しであり、当時の判定のやり直しではない。

## KPIの種類

1. **品質（`quality_score`）**：r1と同じ。各セルで、有効な4点未満を増やさない。4点未満は中央値で相殺しない。
2. **費用（新設、トークンの主な指標）**：全エージェントの使用量を、版を固定した単価表で米ドルに換算した値。
3. **経過時間（`elapsed_seconds`）**：r1と同じく、記録するが参考の扱いにする。
4. **生のトークン（全エージェントの`total_tokens`、参考）**：従来のKPI。引き続き各試験で算出して記録し、試験の間で比べる値として表に並べる。ただし、取り組みの成否（改善か、退行か）の判定には使わず、参考として扱う。

旧系列の結果資産にある生のトークンは、記録としてそのまま残す。新しい系列の値と比べる相手にはせず、参考情報として扱う。

## 費用の数え方

### 単価表（版`api-standard-2026-10-09`）

単位は米ドル / 100万トークン（Standard料金）。利用者が示した2026-10-09時点の公表料金による。

| 項目 | GPT-6.1 Sol | Claude Sonnet 5.5 |
| --- | ---: | ---: |
| 入力 | 2.00 | 2.00 |
| キャッシュ読み取り | 0.10 | 0.10 |
| キャッシュ書き込み（Solは最低30分、Sonnetは5分） | 2.50 | 2.50 |
| キャッシュ書き込み（1時間） | — | 4.00 |
| 出力 | 10.00 | 10.00 |
| 1リクエストの入力が272K超の場合（Sol、リクエスト全体） | 入力4.00、出力15.00 | 割増なし |

- 単価表は版として計測の条件の外に固定し、費用の結果には使った版を記録する。料金が変わったら新しい版を作り、過去の結果を新しい版で上書きしない。比べる結果同士は、同じ版で計算する。（2026-10-10追記）単価表は計測の条件ではなく、比較のときに選ぶものとする。比べる両方を、同じ単価表で各runの使用量の内訳から数え直せば比べられ、版の違いを理由に測り直さない（`compare-analyses --price-table --registry`、[`evaluations/AGENTS.md`](../evaluations/AGENTS.md)の「3 KPI」）。
- Batch、Fast、Ultrafastの料金は、評価の実行で使わないため対象にしない。

### 使用量から費用への換算

- Claude Code：transcriptのリクエストごとの使用量（重複を除いたもの）から、通常の入力、キャッシュ書き込み（1時間と5分を分ける）、キャッシュ読み取り、出力に単価を掛ける。C301では、書き込みはすべて1時間だった。
- Codex：各セッションの使用量から、キャッシュを使わなかった入力（入力−キャッシュ入力）、キャッシュ入力、出力に単価を掛ける。推論の出力は出力に含まれる。Codexはキャッシュ書き込みの量を報告しないため、キャッシュを使わなかった入力は通常の入力（2.00）として数える。すべてを書き込み（2.50）として数えた値も記録するが、主な値には使わない。報告の形が変わったら、数え方の版を上げる。
- リクエストごとの入力が272Kを超えたSolのリクエストは、その全体を割増の単価で数える。試算の範囲では、最大は47,149トークンで、該当はなかった。
- runの費用を合計し、1反復（14ケース）の合計を5反復分集計した中央値を比べる。これは従来の生のトークンと同じ集計方法である。

## 計測と記録の仕方

評価は計測であり、Candidateごとに目的や達成目標を宣言して、その成否を判定するものではない。どのCandidateも同じ項目を同じ方法で計測して記録し、残すかどうかは、その記録を見て利用者が判断する（評価基盤は`winner`や採用可否を出さない、[`evaluations/AGENTS.md`](../evaluations/AGENTS.md)）。

### 計測して記録する項目

主なセル（Sol LowとSonnet low、r1と同じ）ごとに、次を記録する。セルの間で相殺しない。

1. **品質**：各セルの点数の分布。有効な4点未満は中央値で相殺せず、件数で示す（r1と同じ）。
2. **処理の適切さ**：保存traceを、[処理の適切さの分類](c280-c300-processing-appropriateness-audit-r1.md)と同じ方法（TaskSpecが明示する確認を、最後の変更より後に成功させてから報告したか）で分類した件数を、ケースごとに示す。分類の方法は計測の前に固定し、結果に合わせて変えない。
3. **費用**：費用の中央値と、同じ系列の基準（C301）との差。差は、基準の揺れの幅と比べて「幅より下」「幅の中」「幅より上」のどれかで記録する。
4. **生のトークンと経過時間**：中央値と、基準との差。表に並べて試験の間で比べるが、成否の結論には使わない。
5. **費用の内訳**：キャッシュを使わなかった入力、キャッシュ書き込み、キャッシュ読み取り、出力、応答の回数。費用と生のトークンの向きが違う場合は、その原因（読み取りの増減か、新しく文脈へ入る内容や出力の増減か）を記す。
6. **機序の指標**：指示文が作ろうとした機序の観測は、上の差の原因を調べる診断に限る（r1と同じ）。

### 揺れの幅

- 幅は、基準のN=5の反復の最小と最大とする。結果を見る前に固定する。
- C301の費用の幅は、Sol Lowが$0.857〜1.007、Sonnet lowが$0.645〜0.714だった（[試算](../evaluations/results/kpi-cost-weighting-trial_2026-10-09.json)）。同日、#361の経路でC301を[測り直した](../evaluations/results/c301-singlepath-sol61-low-sonnet55-low-standard14-n5_2026-10-09.md)。以後の比較の基準はこの測り直しとし、費用の幅はSol Lowが$0.9261〜1.0331、Sonnet lowが$0.6656〜0.7005である。さらに同日、この測り直しは同時実行がホストの上限24を超えていたため、両セルを一つの待ち行列で[測り直した](../evaluations/results/c301-onequeue-sol61-low-sonnet55-low-standard14-n5_2026-10-09.md)。基準はこの計測へ移し、費用の幅はSol Lowが$0.8704〜0.9324、Sonnet lowが$0.6380〜0.6878、経過時間の幅はSol Lowが567.79〜617.29秒、Sonnet lowが283.87〜301.27秒である。

### 記録を読む順序

1. 品質。
2. 処理の適切さ。不適切な処理がどのケースで増えたか、減ったかを先に見る。
3. 費用。処理の適切さの変化と並べて、費用が幅の中か、幅を超えたかを見る。
4. 生のトークン、経過時間、内訳、機序は、上の差の原因を説明する情報として読む。

処理の適切さ（TaskSpecが求める処理を行ったか）と、指示文が作ろうとした機序は、別のものとして扱う。

## 指示文の固定分の見方

- 指示文を足したときに必ず増える費用（固定分）は、主に各セッションの最初の書き込みとして生じる。C301のSonnet lowでは、100バイトあたり1反復の費用の約0.3%だった（生のトークンでも約0.26%で、ほぼ同じ）。
- 費用で数えても、指示文の固定分の重さはほとんど変わらない。一方で、大きな出力の読み込みや不要な読み取り（書き込みとして費用に効く）を減らす変更は、費用ではっきり差が出る。設計の対象を選ぶときは、この違いを使う。

## 評価基盤への反映

2026-10-09、利用者の依頼で、評価基盤へ次を反映した。あわせて、実行の前に比較の相手を要求していた経路を置き換えた（[`evaluations/AGENTS.md`](../evaluations/AGENTS.md)の「試験の実行前ゲート」）。

- [`evaluations/AGENTS.md`](../evaluations/AGENTS.md)の「3 KPI」を、`quality_score`、`cost_usd`、`elapsed_seconds`に改めた。`total_tokens`は参考値として記録を続ける。
- 単価表を版として置く場所（[`evaluations/price-tables/`](../evaluations/price-tables/api-standard-2026-10-09.json)）と、使用量の内訳と費用を扱う`scripts/usage_components.py`を加えた。CodexとClaude Codeのアダプタは`token-usage/v3`で内訳を報告し、`record-result`、`aggregate-selection`、`register-selection-result`は単価表を受け取って費用を集計する。比較（`compare`、`compare-effective`、`compare-analyses`）は、同じ単価表のものだけを受け付け、費用の差と、基準の反復の幅に対する位置（`cost_band`）を記録する。
- 既存のresult、互換キー、比較viewは書き換えず、費用を持つ新しいschemaとして追加した。

## 利用者が決めたこと（2026-10-09）

- 揺れの幅は、基準のN=5の反復の最小と最大で取る。反復を増やす判断は、[再現性の判断の方針](reproducibility-decision-policy.md)に従う。
- 処理の適切さを、費用より先に見る。
- 評価の目的は計測である。Candidateごとに目的や達成目標を決めて成否を判定しない（同日、#359でいったん入れた「Candidateの目的を設計記録で先に決め、目的ごとに判定する」節は、この決定で取り下げた）。

## 決めていないこと

- Codexのキャッシュを使わなかった入力に、書き込みの割増がかかるか（主な値では通常の入力として数える）。
- 採用、release、本体反映。
