# Candidate307 C306に、確認コマンドの出力を絞ってよいとする一項目を加える

2026-10-09。ベースのC306の弱点（Sonnet lowのF01で費用が増える）を潰すため、Candidate本文の作成前に固定する設計記録。[設計原則](prompt-control-design-principles.md)の全文を読み、「Candidateを作成する前の確認事項」の項目1〜9に対応させた。計測と記録は[計測と記録の基準r2](shared-instruction-evaluation-criteria-r2.md)に従う。この記録ではbundleを作成しない。

## 目的と役割

- 系列：実行環境を切り離し、負荷を見て次のrunを始める発行の条件（CPU使用率70%以下、間隔1秒）で測る系列。
- ベースと直接の親：C306（`the-caption-3ce91a4-taskspec-scoped-success-closure-and-wait-time-r1`）。比較の基準は、同じ条件で測ったC306のSonnet low。
- 文の出所：C293のV2の一句（「各コマンドの出力は絞って表示してよいが、確認する終了コードは、そのコマンド自身のものとする」。C294〜C296も引き継いだ）。C293は親ではない。
- 利用者の指示により、Sonnet lowで確立するまでSolは測らない。
- 評価は計測であり、達成目標を置かない（r2）。
- 変更対象：C306のroot `AGENTS.md`の末尾に一項目を加える。C306の本文と他の18対象はC306とバイト一致を保つ。

## 1. 比較の基準と、正常な最短経路

基準はC306。変更を伴うケースの正常な最短経路は、開始時の確認と読み取り → 変更 → TaskSpecが求める確認（すべて） → 報告である。確認では、各コマンドの終了状態と、失敗した場合はその内容を受け取れば足りる。

## 2. 保存traceで確認した問題経路

- C306のSonnet lowで、C301 `-r5`比の費用の増加（+5.09%）は、ほとんどがF01だった（ケースの中央値で+$0.055）。F01の5件中4件で、TaskSpecが求める個別のテスト（`.venv/bin/python -m pytest tests/unit/test_market_units_snapshot.py -v`）を出力を絞らずに実行し、約19,000字（約8千トークン）を一度に受け取っていた。この1回のリクエストが1件あたり約$0.04で、増加の大半を占める。C301 `-r5`は5件中1件だった。
- `main_verify.sh`を出力そのままの形で実行した件数は、C301が20件中4件、C298だけのC303とC299だけのC305がそれぞれ7件、二つの文がそろったC302とC306が12〜14件だった。二つの文がそろうと、確認コマンドを加工せずに実行する形が増える。
- C301の短くする形（`| tail -15; echo "exit=${PIPESTATUS[0]}"`や、ファイルへの書き出しと`tail`）は、評価の仕組みで必須の確認として受け付けられ、課題文の指定に反する実行（`command_protocol_violations`）には数えられていない（C301 `-r5`で0件）。

## 3. 開いている記述と、TaskSpec・正本で防げない理由

TaskSpecは確認のコマンドを指定するが、その出力をどれだけ受け取るかは定めていない。C306の二つの文は、確認の成功と、コマンドの実行を強く意識させる。その結果、確認コマンドを指定どおりに加工せず実行し、全出力を受け取る形が増えたと読める。出力を絞ってよいかを定めた記述がないため、全出力を受け取る経路が開いたままになる。

旧系列でも同じ現象があった。C284以降、Sonnet lowは検証の出力を絞らなくなった（検証のコマンドで出力を絞ったものが、C280は54件中44件、C284は56件中37件）。C293で出力を絞ってよいとする一句を加え、C294〜C296もそれを引き継ぐと、出力を絞った実行がC280の水準以上に戻った（C295は59件中57件、C296は55件中53件、[C296の計測](../evaluations/results/c296-sol61-low-sonnet55-low-standard14-n5_2026-10-09.md)）。この一句は、当時の設計記録で「保存traceに直接の裏づけがない仮説」とされていたが、その後の計測で裏づけられた（[判定表の追記](mechanism-establishment-table-r1.md)）。

## 4. 追加する条件の全件

C306の末尾に、次の一項目を加える。

> - TaskSpecが求める確認のコマンドは、出力を絞って実行してよい。確かめる終了コードは、そのコマンド自身のものとする。

- 一文目は、確認コマンドの出力を絞ることを許す文で、新しい操作の発行を求めない。絞らずに実行しても違反にはならない。
- 二文目は、出力を絞る形で終了コードを取り違える経路を閉じる文である。`| tail`の終了コードではなく、確認コマンド自身の終了コードを確かめる。
- 文の文字は、C293のV2の一句を、C306の「TaskSpecが求める確認」という言葉に合わせて書き直した。

## 5. 禁止行動、開放経路、閉じる境界、反証

| 項目 | 内容 |
| --- | --- |
| 閉じたい経路 | rootが、確認コマンドの全出力を受け取り、終了状態の判断に使わない大量の出力を以後の文脈へ持ち越す |
| 現在の開放経路 | 出力の扱いの定めがなく、二つの文がそろうと加工しない実行が選ばれる |
| 閉じる境界 | 結果の受け取り。ただし、この一項目は禁止ではなく許可であり、全出力の受け取りを規則違反にはしない。一文目は、モデルが加工を避ける理由を外す試みである |
| 正常な処理の保持 | 終了状態は、コマンド自身の終了コードで確かめる（二文目）。失敗した場合の内容も、絞った出力か、必要なら追加の読み取りで受け取れる |
| 反証する構成 | 一文目は許可なので、全出力を受け取る構成は規則に違反しない。この一項目は、全出力の受け取りを閉じたとは主張しない。効果は、出力を絞った実行の割合として観測する |

この一項目は、設計原則の「処理方法を指定できる条件」に当たる指定（出力を絞る実行）を、義務ではなく許可として書く。遵守を求めないため、遵守率の実証は要件にならない。効果は、出力を絞った実行の割合と、F01の費用で観測する。

## 6. 維持する正常経路

- Claude Codeは、課題文の指定どおり、確認のコマンドを1コマンドずつ個別の`Bash`呼び出しで実行する。出力を`tail`で絞る形は、評価の仕組みで必須の確認として受け付けられている。
- 終了状態は、`${PIPESTATUS[0]}`やファイルへの書き出しと`$?`など、コマンド自身の終了コードで確かめる。
- Codexの経路では、出力の上限（`max_output_tokens`）の指定がすでにあり、この一項目で変わらないと見込む。

## 7. 新しく増える判断と、変更対象外への影響

- 新しい判断：出力を絞るか、絞らないか。どちらも規則に違反しない。
- 危険1：出力を絞った結果、失敗の内容が見えず、追加の読み取りが増える。全件が成功した場合は起きない。
- 危険2：終了コードを取り違える。二文目で閉じる。取り違えは、評価の仕組みのコマンドの記録と報告の食い違いで観測する。
- 固定分：一項目のバイト数。Sonnet lowでは、キャッシュ読み取りの単価で、費用ではごく小さい。

## 8. 評価ケース、比較単位、比較条件、記録する項目

- セル：Sonnet lowのStandard14の全14ケースN=5の計70件。
- 比較条件：C306のSonnet lowと同じで、prompt identityだけを変える。
- 記録する項目（r2）：品質、処理の適切さ、費用、経過時間（内訳を含む）、生のトークン（参考）。
