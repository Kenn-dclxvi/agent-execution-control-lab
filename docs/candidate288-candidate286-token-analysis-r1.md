# C288がC286より少ないトークンを使った部分

2026-10-08。GPT-6.1 Sol LowのC286とC288について、保存済みStandard14 N=5の登録結果とrootのrolloutを比較した。両条件は同じ互換キーを持ち、各70件が有効で全件4点だった。新しいモデル実行や採点はしていない。

## 結論

C288の全エージェントトークン中央値は1,304,022で、C286の1,313,998より9,976（0.76%）少ない。ただし減少は全体に均一ではない。F04の5件平均が70,241、A02が30,707トークン減り、この2ケースの減少を、ほかのケースの増加がほぼ打ち消した。14ケース中、C288のケース別平均が減ったのは5ケース、増えたのは9ケースである。

各ケース5件の平均を14ケースで合算すると、C286の1,309,238からC288の1,304,691へ、一反復相当で4,548トークン減った。5つの反復の合計値は3回で減り、2回で増えた。したがって、全体で安定して大幅に減るという結果ではなく、F04とA02に偏った小幅な正味差である。中央値の9,976減と、この平均差の4,548減を混同しない。

## ケースごとの寄与

各行は5件の平均のC288−C286で、負値がC288の削減である。小さい変化を含む全14ケースの値と各runの識別子は[機械可読の分析](../evaluations/results/c288-c286-token-decomposition_2026-10-08.json)に保存した。

F04のC286は初回の呼び出しで`App.tsx`、`package.json`、`package-lock.json`をまとめて`cat`し、その後`App.tsx`の一部を読み直していた。C288は`App.tsx`内の関連語を検索し、指示・`package.json`とロックファイルの限定した項目を読み、次の呼び出しで該当するコード範囲を取得した。F04では変更前のツール結果量が1件平均約59,300バイトから約27,400バイトへ減り、5件すべてでトークンが約66,000〜75,000減った。読み取る量を狭めたこととトークン減少が、このケースでは直接対応している。

A02でも、C286は`README`、指示ファイル、実装、試験を広く`cat`した後に対象を読み直していた。C288は名前や語句の検索から対象を絞り、範囲を指定して読み、変更前のツール結果量が1件平均22,766バイト減った。5件ともトークンは減ったが、差はケース内でも変動する。F08とF02にも取得量の減少とトークン減少が見える。一方、F01やF06は変更前の取得量が減っても総トークンが増えているため、「読む量を減らせば全ケースでコストが下がる」とは言えない。

## 全体で相殺された理由

変更前の外側ツール結果量は、一反復相当でC286の341,871バイトからC288の240,144バイトへ、約30%減った。しかしrootの入力トークンは1,297,771から1,292,433へ5,337減っただけで、出力トークンは11,468から12,258へ790増えた。rootの応答も一反復相当で53.4回から58.6回へ5.2回増えた。両条件の70件すべてでrootの最終トークンと全エージェントの登録トークンが一致した。

ツール結果のバイト数はモデルが実際に取り込んだトークン数と同一ではない。同じ内容の後続応答での再処理、検索・追加取得の応答、新しい指示本文やケース別の作業差も総量に入る。実行記録は、F04での大きな削減経路を具体的に示すが、全体の正味差4,548トークンを単一の変更条項だけへ厳密に割り付けるものではない。書式統一を単独の節約効果として認定もしない。
