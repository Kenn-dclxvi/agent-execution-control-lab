# Candidate269・Candidate147 ケース別KPI原因分析

## 結論

C147からC269へのtoken差を、自然語の長さまたは表現差の費用として説明してはいけない。BaselineからC147までの系列では、prompt本文を追加しながら、不要なworker、read、判断およびmodel再入へ至る経路を閉じることで、Baseline比token `-89.38%`、同じ品質分布のCandidate43比でも`-54.06%`を記録している。KPIを決めたのは自然語量ではなく、制御が作った実行経路である。

今回の中心問題は、C147までに成立した経路を自然語だけで同じ費用水準へ再現できないのか、それとも必要なpermission・dependency関係をC269へ正しく移植できていないのかである。model応答回数の差だけでは両者を区別できない。保存traceを各runの上振れ経路まで確認すると、経路未適用二つに加え、C269の現在の文が`result`の対応先をpredicateから発行済みinvocationへ広げ、carrierを過大化したKPI原因を一つ特定した。

第一は、F03のstart-only 1件である。開始確認と影響を受けないreadを同じmodel stepへ載せる既知の共同発行境界を安定して再現できていない。第二は、F01の5件中3件である。C269は必須validationと完了判定用のdiff・statusを一つの実行票へ載せたが、大量のcommand outputと完了判定用resultを区別せず、同じmodel-visible carrierへ連結した。diff・statusの文字列が一部のcarrier内に存在していても、必要な完了resultとして安定してbindできず、2件は最終証拠を別応答で読み直し、1件は同じrequired commandを含む後段を再発行した。C147 F01の保存済みN=20では、検証後にこの理由で完了証拠を再取得したrunは0 / 20だった。

第三はF02の中央値境界である。C269の自然語carrierは二重待機を閉じたが、「発行済みの全result」を一度に返す現在の文に従い、raw validation outputまで保持・配送した。中央値境界runでは、C147よりwait resultが112,548文字大きく、完了判断のmodel入力が15,624 token増えた。これは自然語一般の費用ではなく、C269が追加した機序の現在の書き方が効率を悪くした原因である。

C269で増えたvalidation待機は、nonterminalな外側実行を待つ正常な同期である。観測した9件すべてが同じcellのterminal resultへ正しく依存していたため、待機そのものを上の移植不良と混同しない。ただし、待機後に返った一回のcarrier resultへ完了判定用resultが残らず、追加取得を要した経路は別である。

- F10: C147の安い3 runは、必要な`src/AGENTS.md`結果を待たず配下readまで同時に発行していた。C269は必要なresult依存を保持するため、その未達経路と単純比較しない。N=20では通常18件の中央値が113,562.5 token、発行分割2件が138,586 / 156,075 tokenだった。
- F02: N=20でもC269中央値は167,606 tokenで、C147の134,960に対して`+24.19%`だった。差32,646 tokenのうち16,117.5 tokenは、C147では中央値を通常routeと一回待機routeが構成したのに対し、C269では両方が一回待機routeへ入った配置差である。残る16,528.5 tokenは対応する通常routeと一回待機route自体の費用差である。一回待機routeでは、C269のcarrierが大量のvalidation outputを返し、完了判断のmodel入力を増やした。
- F01: N=5で3 / 5件だった完了result欠落はN=20で3 / 20件となり、追加15件では再発しなかった。ただし別の限定read 1件とvalidation分割1件を含めると上振れrouteは5 / 20件である。C269中央値は118,667.5 tokenまで下がったが、C147比はなお`+10.89%`だった。
- F03: start-onlyはN=20でも1 / 20件で、追加15件では再発しなかった。別に最終証拠の追加取得2件とvalidation分割1件があり、待機との和集合では上振れrouteが9 / 20件だった。中央値は109,342.5 token、C147比`+10.73%`である。

validation出力のtruncation回数だけを見ると、F01が各run 1回、F02が2回、F03が1回、F10が0回で、C147とC269が全20 runで同じだった。しかし、この一致からtruncationを原因外へ置くことはできない。F01では、C147は必要な終了状態を外側resultとして利用できたのに対し、C269は5件中3件で完了判定用resultを大量のraw outputと同じcarrierへ載せ、必要なbind済みresultとして安定利用できなかった。原因として見るのはtruncationの存在や文字列の有無ではなく、完了判定に必要な値がraw outputから独立したresultとしてbindできたかである。

## ケース間比較の目的

ケース同士のtoken量を比べる目的は、F01とF02のどちらが優れているかを判定することではない。各ケースは読むsource、test、検証command、出力量が違うため、tokenの大小をそのまま横比較できない。

ケース間比較で見るのは、C147までの効率leverが全ケースで共通に失われたのか、特定ケースの経路だけで移植が不安定なのか、新しい目的のために必要な依存が増えたのかである。自然語の入力費用を独立原因として探す比較ではない。

## N=20で確定した基礎差と上振れの分離

N=5では一件が20ポイントを占め、中央値が通常routeと上振れrouteのどちらへ入るかが容易に反転した。このため、C269だけを各ケースN=20へ追加し、既存C147 N=20と比較した。通常routeは、待機がなく、変更前または検証後の追加outer callもないrunに限定する。

| ケース | C147通常route中央値 | C269通常route中央値 | 通常route純差 | C269上振れroute | 読み取れること |
| --- | ---: | ---: | ---: | --- | --- |
| F01 | 106,758 | 115,549.5 | `+8.23%` | 5 / 20件。完了result欠落3、限定追加read 1、validation分割1 | N=5の`+52.30%`は上振れ3件が中央値を動かした過大推定だった。N=20全体差は`+10.89%` |
| F02 | 123,675 | 131,556 | `+6.37%` | 11 / 20件。待機9、追加outer call 5で3件重複 | 通常route純差だけで`+24.19%`を説明できない。上振れが過半数となり中央値側へ残った |
| F03 | 98,127 | 105,698 | `+7.72%` | 9 / 20件。待機6、追加outer call 4で1件重複 | start-onlyは1件だけだが、別の最終証拠取得とvalidation分割も上側を作った。N=20全体差は`+10.73%` |
| F10 | 目的未達runを混ぜるためN=20通常値は使わない | 113,562.5 | C147 N=5の目的達成済み通常run比`+4.71%` | 2 / 20件。instruction後listing分割1、開始identity逐次分割1 | N=5の`+30.92%`は目的未達の安いC147中央値との比較だった。C269 N=20全体差は`+11.19%` |

通常route同士では、自然語側の純差が約5〜8%に収まった。これは自然語本文を含む入力構成の差と整合するが、純粋な自然語上乗せとは断定しない。自然語側が別の処理または出力を省く分も相殺された後の純差だからである。

原因を探す中心は引き続き上振れ側に置く。ただしN=20によって、F01・F03・F10のN=5中央値は上振れ頻度を過大に反映していたと分かった。F02は、C147の上側群10 / 20件とC269の11 / 20件を同程度として打ち消してはいけない。一件の違いが中央値を通常routeとの境界から一回待機route内へ移すためである。比較対象を実際の10件目・11件目へ固定し、route配置と各route内費用を分ける。

## F02 N=20中央値差の正体

F02のN=20を昇順に並べると、C147は10件目128,236 tokenと11件目141,684 tokenの平均が中央値134,960になる。C269は10件目166,758 tokenと11件目168,454 tokenの平均が中央値167,606になる。中央値差32,646 tokenは、C269の通常route中央値が6.37%高いことに加え、C269では診断済み上振れrouteが11件となり、中央値を構成する二件がとも上振れ側へ入ったことで拡大した。

中央値差32,646 tokenは二つに分かれる。C269に通常routeがもう一件あり、実測上の通常群上端136,219 tokenと一回待機群下端166,758 tokenが中央値を構成した場合は151,488.5 tokenになる。実測中央値167,606との差16,117.5 tokenが、11件目も上側へ入った配置差である。残りのC147中央値との差16,528.5 tokenは、C147の境界二件128,236 / 141,684 tokenに対して、C269の対応境界を136,219 / 166,758 tokenとした場合のroute内費用差である。

ここまでの保存済み20件で、中央値差を作ったrunと量は特定できた。さらにNを増やして比率だけを精密化しても、carrierがなぜ大きいresultを返したかは分からない。したがって現時点では追加Nを発行せず、中央値境界runのmodel入力とvalidation carrier内容を直接比較する。

C147は待機6 / 20件、計10回で、うち4件が二重待機だった。C269は待機9 / 20件、計9回で、全件が一回待機である。C269は待機run数を3件増やした一方、二重待機を4件から0件へ、validation分割を1件から0件へ閉じた。変更前追加readもC147の7 / 20件からC269の3 / 20件へ減った。最終証拠の別取得は2 / 20件から3 / 20件へ一件増えた。

C269の自然語`VALIDATION_CLOSURE`は二重待機とvalidation分割を閉じたが、効率まで保持できていない。機序が機能的に成立したことと、その機序がC147と同じ費用で成立したことを分ける。今回のKPI原因は、途中resultを返さないために作った一回のcarrierが、必要な終了状態だけでなくraw validation outputまで大量に保持・配送したことである。

中央値境界の一回待機runを直接比較すると、C147 141,684 tokenの`wait`は`max_tokens=2,000`で8,358文字を返し、完了判断の最終model入力は32,778 tokenだった。C269 166,758 tokenの`wait`は`max_tokens=30,000`で120,906文字を返し、最終model入力は48,402 tokenだった。両runの差25,074 tokenのうち、完了判断の一回だけで15,377 token、61.3%を占める。最終model入力自体は15,624 token増えている。

この選択は偶然の待機やtest出力量の差だけでは説明できない。中央値境界runの内部出力は、C147がfocused 23,550文字・full 158,709文字、C269がfocused 23,634文字・full 158,840文字で、ほぼ同量だった。C147 wrapperは内部commandのoutputを生成しながら、外側carrierを`max_output_tokens=2,000`へ制限し、制御本文でも完了条件を「全result bind済み」としていた。C269 wrapperは各outputを配列へ保持し、外側上限を固定せず、最後に全件のraw outputを個別の`text`として返した。

この分岐に対応する現在のprompt差は明確である。C147は「完了済みの全resultを一度だけmodelへ返す」「全件successかつ全result bind済みならterminalを判断する」として、返却resultをvalidation predicateの完了へ対応づけていた。C269はこれを「発行済みの全resultをwrapperが終了した時に一度だけ返す」「必要な結果がすべてそろった後に完了を判断する」へ変えた。`発行済み`を主語にしたため、各invocationが生成したraw outputまで全件返す実装が現在の文へ直接準拠するようになり、`bind済み`を局所完了条件から外したため、完了判断に必要なresultだけへcarrierを限定する根拠が弱くなった。文言だけではなく、実際にC269が`evidence.push(... output ...)`後に全outputを再放出したtraceを合わせて、この現在差を原因とする。

C147でも大きなcarrier resultが一切なかったわけではない。F02の一回待機route 2件のうち1件は80,595文字を返している。したがってC147がraw output配送を禁止していた、または外側上限を常に一定にしていたとは扱わない。C147で起きていないのは、C269のように一回待機route 6件すべての最終入力が約48,400〜49,700 token帯へ寄り、F02中央値を押し上げた分布と、F01で完了resultを3件再取得・再発行した現象である。絶対禁止の有無ではなく、C269の現在の局所文が過大配送を正規routeへしたことを疑う。

## F01・F02をつなぐC269現在文の境界

C269が固定したのは、途中resultをAIへ返さず、外側実行の終了時に一度だけ返すという返却時点である。その際、C147の`完了済み`と`bind済み`を保持せず、`発行済みの全result`へ広げた。必須commandの終了状態、完了判定に必要なdiff・status、成功時のraw stdoutが、発行したinvocationのresultとして同じcarrierの同格要素になっている。このため、C269ではraw stdout全量を運ぶことが現在文に準拠した正常routeになり、完了判定はそのcarrier内から必要値をもう一度解釈することへ依存した。

この一つの境界が、出力量の異なるF01とF02で逆向きに現れた。

- F02の中央値境界runでは、外側carrierの上限を30,000 tokenまで許し、120,906文字を返した。必要な終了状態は届いたが、raw outputも同時に届いたため、完了判断のmodel入力がC147比15,624 token増えた。
- F01の上振れ2 runでは、wait resultが70,096文字と71,783文字になった。その後に完了証拠を別取得している。別の1 runではvalidation後段を再発行した。carrier内にdiff・statusの文字列が含まれる場合でも、raw outputと区別された完了resultとして安定してbindできなかったことが追加応答に現れている。

したがって、単に外側carrierの上限をC147と同じ値へ下げることは原因解消にならない。C147でも上限値はrun間で一定ではなく、tool outputのprojectionや成功stdout抑制を直接指定したC90〜C93・C96も成立しなかった。C147の成功runで使われた上限値やtool順を次案へ転記せず、C269が現在の局所文で変えたresultの対応関係を先に戻す必要がある。

原因となるpermission・dependencyの辺は、C269が返却対象をpredicateへbindされた完了resultではなく、発行済みinvocationの全resultへ置き換えたことである。次の設計へ進む前に固定すべき分析要件は、C147と同じく、各validation predicateへ対応づけて確定したresultが全件そろったことを完了条件へ戻すことである。成功stdoutの非配送、byte上限、wrapperのtool順はこの要件へ含めない。これは新しいoutput制御ではなく、C269が現在の文で失ったC147のresult bindingの復元である。

## 固定prompt入力差の位置づけ

最初のmodel応答のinput tokenには、C147で約18,100と約19,400、C269で約19,200と約20,400という二つの入力群があった。同じ入力群同士を比べると、C269は約1,000 input token多い。この直接入力差は、同じ経路でも生じる自然語側の基礎費用と考えるのが妥当である。

## 今回の調査で原因から外れたもの

- 自然語の長さまたは表現差だけを、各ケースのKPI差全体の原因とすること。通常routeの約5〜8%には対応するが、上振れ分までは説明しない。
- F03の待機だけを、全ケース共通のtoken増加原因とすること。
- nonterminal wrapperの完了待ちを、C69・C71が閉じた不要なmodel再入と同一視すること。
- validation出力のtruncationが存在すること自体をC269固有原因とすること。問題は回数や文字列の有無ではなく、完了判定に必要な値がraw outputから独立したbind済みresultとして利用できたかである。
- F02の中央値`+30.04%`だけから、F02全体が悪化したと判定すること。

## 追加試験による頻度訂正

N=5からN=20へ広げた結果、上振れrouteの頻度は次のように確定した。

| ケース | N=20の待機 | N=20の追加outer call | 原因内訳 | 中央値への影響 |
| --- | ---: | ---: | --- | --- |
| F01 | 6 / 20 run、7回 | 5 / 20 run | 完了result欠落3、限定追加read 1、validation分割1 | N=5では上振れが3 / 5で中央値を占めたが、N=20では通常routeへ戻った |
| F02 | 9 / 20 run、9回 | 5 / 20 run | 最終証拠の別取得3、変更前追加read 3。追加outer call 5件のうち3件は待機とも重複 | 和集合11 / 20で中央値の両側が一回待機routeへ入り、carrier配送量がroute内費用も増やした |
| F03 | 6 / 20 run、7回 | 4 / 20 run | start-only 1、最終証拠の別取得2、validation分割1 | 和集合9 / 20となり、中央値は通常route側へ戻った |
| F10 | 0 | 2 / 20 run | instruction後のlisting・本文分割1、開始identityの逐次分割1 | 通常route18 / 20で中央値は安定した |

追加試験は必要だった。C269 N=5だけなら、F01、F03、F10の中央値悪化を安定差として過大評価し、F01の完了result欠落3 / 5やF03 start-only 1 / 5を実際より高い発生率として扱っていた。F02では中央値`+24.19%`が残り、その境界runを特定できた。原因は、上側routeが11件になった配置差16,117.5 tokenと、carrierのraw output配送を含むroute内費用差16,528.5 tokenである。

この追加NはC269を採用候補へ戻す試験ではない。品質80 / 80 Score `4`と分布精度を保存したが、C147比token `+11.15%`、elapsed `+2.77%`は残る。新しい一律Gateは設定しない。F02について追加Nは不要だが、分析優先順位は下げない。次に詰めるのは、C269で`完了済みかつbind済みのresult`を`発行済みの全result`へ変えた現在差である。F01の完了result再取得も同じ変更後に発生したため、両ケースを一つのresult対応関係の問題として扱う。

経過時間のrun別原因分解は、このtoken経路調査では確定していない。
