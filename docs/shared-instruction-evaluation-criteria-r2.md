# 共通の指示文を改善する判定基準（r2）：トークンの数え方を料金の重みへ改める案

2026-10-09。利用者の依頼（評価を見直す機会に、KPIの使い方と種類を見直し、試算してから続ける）を受けて、[判定基準r1](shared-instruction-evaluation-criteria-r1.md)のうち、トークンの扱いを改める改訂案。r1は当時の記録として保持し、書き換えない。r1の「試験の条件」と「変更を考える範囲」の考え方は、この版でも引き継ぐ。この記録は改訂案であり、評価基盤の変更（後述）を実施していない。

## 適用する範囲

- [実行環境を切り離した新しい評価系列](agent-runtime-venv-isolation-record-r1.md)（`shell_environment.revision: fixed-path-workspace-venv-r1`）に適用する。この系列の基準は[C301](candidate301-c280-uniform-markdown-design.md)（[計測記録](../evaluations/results/c301-sol61-low-sonnet55-low-standard14-n5-shellenv_2026-10-09.md)）。
- 旧系列（C280〜C300）の結果と判定は、当時の基準（r1）による記録として保持し、書き換えない。

## 改める理由

[試算](../evaluations/results/kpi-cost-weighting-trial_2026-10-09.json)では、全エージェントのトークンの約85%が、キャッシュから読み直した文脈だった。この読み取りの単価は通常の入力の20分の1（$0.10 / 100万トークン）であり、生のトークン数は、実際にかかる費用とずれている。

| セル | 条件（C280比） | 生のトークン | 費用 |
| --- | --- | ---: | ---: |
| Sol Low | C298 | −10.4% | +2.6% |
| Sol Low | C299 | −11.7% | +6.4% |
| Sol Low | C300 | −20.9% | −5.7% |
| Sonnet low | C298 | +3.1% | +1.6% |
| Sonnet low | C299 | −1.8% | −1.4% |
| Sonnet low | C300 | +2.1% | −2.1% |

- Sol Lowの削減は、主に安いキャッシュ読み取りの削減だった。キャッシュを使わなかった入力（単価が20倍）は、C298で+9%、C299で+19%増えており、生のトークンで「改善」だったC298とC299は、費用では増加になる。
- Sonnet lowでは、C300の増減の向きが逆になる。
- Sonnet lowでは、費用で数えると反復の間の揺れが小さくなる（C280の反復の幅は、生のトークンで約16%、費用で約3.5%）。Sol Lowは、どちらで数えても約10%揺れる。

この表は旧系列の結果の数え直しであり、判定のやり直しではない（後述）。

## KPIの種類

1. **品質（`quality_score`）**：r1と同じ。各セルで、有効な4点未満を増やさない。4点未満は中央値で相殺しない。
2. **費用（新設、主な判定に使う）**：全エージェントの使用量を、版を固定した単価表で米ドルに換算した値。
3. **経過時間（`elapsed_seconds`）**：r1と同じく、記録するが参考の扱いにする。
4. **生のトークン（全エージェントの`total_tokens`、参考）**：従来のKPI。引き続き各試験で算出して記録し、試験の間で比べる値として表に並べる。ただし、取り組みの成否（改善か、退行か）の判定には使わず、参考として扱う。

旧系列の結果資産にある生のトークンは、記録としてそのまま残す。新しい系列の値と比べる相手にはせず、参考情報として扱う。

## 費用の数え方

### 単価表（版`api-standard-2026-10-09`）

単位は米ドル / 100万トークン（Standard料金）。利用者が示した2026-10-09時点の公表料金による。

| 項目 | GPT-6.1 Sol | Claude Sonnet 5.5 |
| --- | ---: | ---: |
| 入力 | 2.00 | 2.00 |
| キャッシュ読み取り | 0.10 | 0.10 |
| キャッシュ書き込み（Solは最低30分、Sonnetは5分） | 2.50 | 2.50 |
| キャッシュ書き込み（1時間） | — | 4.00 |
| 出力 | 10.00 | 10.00 |
| 1リクエストの入力が272K超の場合（Sol、リクエスト全体） | 入力4.00、出力15.00 | 割増なし |

- 単価表は版として計測の条件の外に固定し、費用の結果には使った版を記録する。料金が変わったら新しい版を作り、過去の結果を新しい版で上書きしない。比べる結果同士は、同じ版で計算する。
- Batch、Fast、Ultrafastの料金は、評価の実行で使わないため対象にしない。

### 使用量から費用への換算

- Claude Code：transcriptのリクエストごとの使用量（重複を除いたもの）から、通常の入力、キャッシュ書き込み（1時間と5分を分ける）、キャッシュ読み取り、出力に単価を掛ける。C301では、書き込みはすべて1時間だった。
- Codex：各セッションの使用量から、キャッシュを使わなかった入力（入力−キャッシュ入力）、キャッシュ入力、出力に単価を掛ける。推論の出力は出力に含まれる。Codexはキャッシュ書き込みの量を報告しないため、キャッシュを使わなかった入力は通常の入力（2.00）として数える。すべてを書き込み（2.50）として数えた値も記録するが、判定には使わない。報告の形が変わったら、数え方の版を上げる。
- リクエストごとの入力が272Kを超えたSolのリクエストは、その全体を割増の単価で数える。試算の範囲では、最大は47,149トークンで、該当はなかった。
- runの費用を合計し、1反復（14ケース）の合計を5反復分集計した中央値を比べる。これは従来の生のトークンと同じ集計方法である。

## 判定の使い方

1. **品質を保つ。**（r1と同じ）
2. **主なセルの両方で、基準より費用を増やさない。** 主なセルはSol LowとSonnet low（r1と同じ）。費用の中央値で、同じ系列の基準（C301）と比べる。セルの間で相殺しない。
3. **揺れの幅を、結果を見る前に固定する。** 各セルの基準の反復の幅（最小と最大）を記録し、比べる試験の中央値がその幅の中にある場合は、改善とも退行とも判定せず「揺れの範囲内」と記録する。C301の費用の幅は、Sol Lowが$0.857〜1.007、Sonnet lowが$0.645〜0.714だった（[試算](../evaluations/results/kpi-cost-weighting-trial_2026-10-09.json)）。
4. **生のトークンと経過時間は、表に並べて試験の間で比べるが、判定の結論にしない。** 費用と生のトークンの向きが違う場合は、その原因（読み取りの増減か、新しく文脈へ入る内容や出力の増減か）を診断として記す。
5. **機序の指標は診断に限る。**（r1と同じ）
6. **費用の内訳は診断として残す。** キャッシュを使わなかった入力、キャッシュ書き込み、キャッシュ読み取り、出力、応答の回数を、セルごとに並べる。

## 指示文の固定分の見方

- 指示文を足したときに必ず増える費用（固定分）は、主に各セッションの最初の書き込みとして生じる。C301のSonnet lowでは、100バイトあたり1反復の費用の約0.3%だった（生のトークンでも約0.26%で、ほぼ同じ）。
- 費用で数えても、指示文の固定分の重さはほとんど変わらない。一方で、大きな出力の読み込みや不要な読み取り（書き込みとして費用に効く）を減らす変更は、費用ではっきり差が出る。設計の対象を選ぶときは、この違いを使う。

## 評価基盤への反映（別作業）

この改訂案を使うには、評価基盤の変更が要る。評価基盤の保守は、利用者が明示的に依頼する別作業とする。

- [`evaluations/AGENTS.md`](../evaluations/AGENTS.md)の「3 KPI」は、全エージェントの`total_tokens`をKPIとしている。費用を主な判定に使うには、この規則の改訂が要る。
- 単価表の版を置くアーティファクト、使用量から費用を計算する処理（両エージェント）、比較のview、それぞれの単体テスト。既存の結果、互換キー、比較viewは書き換えず、費用は別のschemaとして追加する。KPIの数え方が変わるため、`tests/test_kpi_revision_guard.py`の考え方に従って版を分ける。
- 反映までの間は、保存済みの使用量の記録から、試算と同じ方法で費用を計算して記録する。

## 決めていないこと

- Codexのキャッシュを使わなかった入力に、書き込みの割増がかかるか（判定には通常の入力として数える）。
- 揺れの幅をN=5の最小と最大で取ることが十分か。反復を増やす判断は、[再現性の判断の方針](reproducibility-decision-policy.md)に従う。
- 採用、release、本体反映。
