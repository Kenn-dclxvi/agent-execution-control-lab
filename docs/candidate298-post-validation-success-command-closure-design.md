# Candidate298 必須の確認がすべて成功した後のコマンドを禁止する

2026-10-09。Candidate本文の作成前に固定する設計記録。[設計原則](prompt-control-design-principles.md)の全文を読み、「Candidateを作成する前の確認事項」の項目1〜9に対応させた。判定は[判定基準の記録](shared-instruction-evaluation-criteria-r1.md)に従う。根拠は[C280に加える短い閉鎖文の候補の洗い出し](c280-short-closing-sentence-candidates-r1.md)の候補1a（推奨）であり、[C297の設計](candidate297-post-change-status-with-validation-design.md)の誤り（閉じる文のつもりが状態確認を発行する新しい義務になった）を直した形である。この記録ではbundleを作成しない。

## 目的と役割

- 系列：汎用指示の改善系列。比較の基準かつ直接の親はC280（`the-caption-3ce91a4-execution-control-outcome-binding-r1`）。C297は親にせず、発行を求める文が操作を増やした反例として使う。
- 主なセル：GPT-6.1 Sol LowとClaude Code Sonnet 5.5 low。
- 必要な効果：品質を保ち、両セルでC280よりトークンを増やさない。経過時間は保存済みC280との比較を参考として記録する。
- 対象：必須の確認コマンドがすべて成功した結果を受け取った後に、状態・差分の確認などのコマンドを出す応答（C280で1反復あたりSonnet low 2.4回、Sol Low 5.4回）。
- 変更対象：root `AGENTS.md`の末尾に一項目（132バイト）を加えるだけ。C280の本文は文言も書式も変えない。他の18対象はC280とバイト一致を保つ。全文は1,602バイト（C280は1,470）。

## 1. 比較の基準と、正常な最短経路

基準はC280。変更を伴うケースの正常な最短経路は、開始時の確認と読み取り → 変更 → 必須の確認 → 報告である。TaskSpecの完了条件（「required validationがpassし、許可外driftがない状態をdoneとする」、例：[F01のTaskSpec](../evaluations/cases/TC-F01-DOMAIN-DUPLICATE-ASSET-KEY/r3/trial-prompt-input.json)）は、状態確認をいつ行うかを定めていない。採点の証拠は評価の仕組みが取る終了時の差分の記録（`final_drift_manifest`）、コマンドの記録、終了状態であり、モデル自身の最後の`git status`は採点の証拠に含まれない。

## 2. 保存traceで確認した問題経路

C280の保存trace（Sol Low `794d02ab…`、Sonnet low `c84fd227…`、各70件）で、最後に必須の確認を含んだ応答より後の応答を種類で分けた（[記録](../evaluations/results/c280-short-closing-sentence-candidates_2026-10-09.json)）。

| 応答の種類 | Sonnet low | Sol Low |
| --- | ---: | ---: |
| 状態・差分の確認だけ | 2.4 | 4.8 |
| 状態の確認と開始時の確認 | 0 | 0.6 |
| 必須の確認の終了を待つ待機（状態確認を含む／含まない） | 0 | 1.6 / 4.8 |
| 保存された必須コマンドの出力ファイルの読み取りを含む | 1.2 | 0 |

必須の確認がすべて成功した結果を受け取った後に、もう一度コマンドを出してモデルへ戻る流れが、両セルに共通してある。この一回の戻りで、次のリクエストの固定分と、それまでの文脈の再処理が生じる。待機と出力ファイルの読み取りは、成功の結果を受け取る前の操作であり、対象ではない。

## 3. 開いている記述と、TaskSpec・正本で防げない理由

C280は、必須の確認が成功した後の操作を定めていない。TaskSpecは必須の確認コマンドと完了条件を定めるが、成功後に追加のコマンドを出すことを禁止していない。このため、成功後の状態確認は、完了条件の確認や報告の準備として、モデルの判断で発行できる。

## 4. 追加する条件の全件

C280の末尾に、C280の箇条書きと同じ書式（`*`）で、次の一項目を加える。

> * 必須の確認コマンドがすべて成功した結果を受け取った後は、コマンドを発行せずに報告する。

- この文は、既存の操作の発行を禁止する文である。新しい操作の発行を求める部分を含まない（設計原則の確認事項5）。
- 「報告する」は、作業の終わりにもともと行う最終応答を指し、新しい操作ではない。
- `git status`や`git diff`を名指ししない（候補1b）。名指しによって状態確認が目立ち、C297のように回数が増える危険を避ける。

## 5. 禁止行動、開放経路、閉じる境界、反証

| 項目 | 内容 |
| --- | --- |
| 禁止する行動 | rootが、必須の確認コマンドがすべて成功した結果を受け取った後に、コマンドを発行する |
| 現在の開放経路 | 成功後の操作が定められておらず、状態確認などをモデルの判断で発行できる |
| 閉じる境界 | 操作の発行。対象は「必須の確認コマンドがすべて成功した結果を受け取った後に発行するコマンド」という、保存traceの応答の並びと終了状態で機械的に判定できる事実で定める。コマンドの目的や位置づけ（完了条件の確認、報告の準備）では定めない |
| 正常な処理の保持 | 状態確認そのものは禁止しない。変更の応答や必須の確認と同じ応答で行える。必須の確認が失敗した場合の調査、修正、再実行は「すべて成功した結果を受け取った後」に当たらず、妨げない |
| 反証する構成 | 成功後の状態確認を「完了条件の確認」と位置づけても、成功後に発行したコマンドなので禁止に当たる。必須の確認を一部だけ受け取った段階での状態確認は禁止に当たらないが、それは成功後にモデルへ戻る応答を生まない。成功後に必須の確認を再実行する構成も禁止に当たる |

## 6. 維持する正常経路

- Claude Code：必須の確認コマンドは、課題文の指定どおり個別の`Bash`呼び出しで実行する。この項目はその指定に触れない。
- Codex：必須の確認の実行と待機は、成功の結果を受け取る前の操作であり、対象ではない。
- Sonnet lowで、必須コマンドの出力が大きく、Claude Codeがファイルへ保存した場合の読み取りは、成功を確かめる前の操作であり、対象ではない。
- F04では、必須コマンドが作る`node_modules/`と`dist/`の後始末を試験基盤が担当するとTaskSpecが定めており、成功の後に後始末のコマンドが必要になる経路はない。
- 必須の確認コマンドを持たないケース（A01、A02、F05、F08、F10。評価条件の`required_command_groups_by_case`に含まれない）では、「必須の確認コマンドがすべて成功した結果を受け取った後」が生じないため、適用されない。

## 7. 新しく増える判断と、変更対象外への影響

- 新しい判断：どのコマンドが「必須の確認コマンド」かの特定。TaskSpecとClaudeの課題文が必須コマンドを列挙しており、確定した事実から決まる。
- 危険1：必須の確認コマンドを持たないケースで、文を「すでにすべて成功している」と読み、開始時の確認や読み取りまで省く。F10は終了時の`git status`による確認をTaskSpecが求めており、省けば品質に影響しうる。品質と、変更を伴わないケースの要求数で観測する。
- 危険2：A02やF08のように、TaskSpecが検証の内容を述べるが必須コマンドを列挙しないケースで、モデルが自分で選んだ確認を必須とみなし、その後の状態確認を省く。採点の証拠は評価の仕組みが取るため、品質への影響は小さいと見込むが、品質で観測する。
- 危険3：Sonnet lowで、状態確認が変更と必須の確認の間の独立した応答へ移る。この場合は削減が生じず、固定分だけ増える。
- 固定分：132バイト。Sonnet lowで1反復あたり約2.8千トークン、Sol Lowで約3.9千トークンの見積もり。
- 見込み：閉じる応答がなくなれば、Sonnet lowで約4.2万トークン（C280中央値の約5.0%）、Sol Lowで約16.0万トークン（約7.7%）の削減。上限側の見積もりである。Sonnet lowでは、閉じる応答の約7%が減れば固定分を回収できる。

## 8. 評価ケース、比較単位、比較条件

- セル：Sol LowとSonnet low、各Standard14の全14ケース各N=5の計70件。
- 基準：各セルの保存済みC280（Sol Low `794d02abe894456686eea22e9b6f0fed`、Sonnet low `c84fd22753d248e588e586cb8022ea1e`）。
- 比較条件：C293〜C297と同じ。Sol LowはC289の保存済み登録結果を基準にした比較互換preflight、Sonnet lowはC280・C291のSonnet lowと同じClaude Code 2.1.288、評価コード、権限、tool集合。変えるのはprompt identityだけ。発行前にpreflight receiptを保存し、不一致があれば一件も発行しない。
- 判定：品質を保ち、各セルで全エージェントトークン中央値がC280より減った場合を主な判定とする。経過時間の増減は記録するが、計測の時間帯の影響と区別できないものとして参考に扱う。セルの間で相殺しない。
- 診断（合否にしない）：最後に必須の確認を含んだ応答より後の応答の種類と数（候補の洗い出しと同じ方法）、1反復あたりの要求数、変更を伴わないケースの要求数。遵守率は、この計測で初めて確かめる。

## 9. 停止条件

- 互換条件の不一致、未確認があれば、一件目の発行前に停止する。
- invalid、採点不能、品質の低下は、有効な改善として扱わない。外部失敗だけ、同じ枠で固定上限内に再試行する。有効な4点未満は削除、相殺、再実行しない。
- 各セル70件で判断し、自動で追加反復しない。結果に合わせてこの記録と案文を書き換えない。
- 結果がばらつきと区別できない場合の追加反復は、[再現性の判断方針](reproducibility-decision-policy.md)に従って、利用者と判断する。

## 判断の限界

- 応答の種類の判定は、コマンド文字列による簡易なものである。
- 見込みの大きさは、C280の保存traceからの上限側の概算で、モデルが別の応答で代わりの操作を行う分を差し引いていない。
- この記録は採用、release、本体反映を決めない。
