# AIプロンプトに書かなくてよかった7つのこと

> 実務者向けExecution Controlシリーズ 3 / 8

## 結論

プロンプトがうまく動かないと、さらに詳しい説明を足したくなります。

しかし、説明を足すほどAIが新しい分類や確認を始め、かえって実行量が増えることがあります。今回の研究でも、効かなかったのは説明不足だけではありません。**書いたことで新しい判断を増やした条件**がありました。

まず、次の7つを無条件に足さないでください。

| 書きたくなること | 起きやすい問題 | 代わりに書くこと |
| --- | --- | --- |
| 参照先の索引を増やす | 索引を読んだ後も探索が続き、読む量だけ増える | その情報で探索を終えてよい条件 |
| 見出しや重複を機械的に削る | 文字数は減っても、判断に必要な局所条件まで遠くなる | 削除後も残す判断条件 |
| 委譲条件を細かく列挙する | 「委譲すべきか」という分類自体が増える | 独立した結果が本当に必要な場合だけ分ける条件 |
| toolやexecutorの内部動作を頼む | プロンプトから見えない層は保証できない | 返された結果を受けて何をするか |
| 「適切に」「必要に応じて」と書く | 適切かどうかを判断する仕事が一つ増える | 観測できる進行条件と停止条件 |
| 行数や回数で調査を打ち切る | 必要な証拠が揃う前に止まる | 何が確認できたら調査を終えるか |
| 調査や結果待ちを一律に禁止する | 必要な確認まで止まり、誤停止や再試行が増える | 許可する対象と、待つと判断が変わる結果 |

## 「書かない」は、短くすることではない

ここで言う「書かない」は、文章を短くすることではありません。

例えば、ファイルの在り処を教えるだけでは、そのファイルを読んだ後に探索を続けるかどうかが残ります。

```text
設定は config.toml にあります。
```

これでは、AIが`config.toml`を読んだ後、ほかの設定も探すかもしれません。終わりまで書くと判断が減ります。

```text
設定値は config.toml を正本とする。
対象の値を確認できたら、ほかの設定ファイルを探索しない。
```

追加したのは情報量ではなく、探索の終了条件です。

## 研究ではどうだったか

静的量の削減を主眼にした7条件と、中核を全文複製した対照1条件の計8条件では、7条件で実行時tokenが増え、残る1条件も実質的には変わりませんでした。また、「適切に判断する」型の抽象条件は小規模試験を通過しましたが、1,400回の比較では参照条件よりtoken中央値が`4.49%`増え、低得点も2件出ました。

一方で、これらは同じ理由で失敗したわけではありません。品質で止まった条件、狙った機構が成立しなかった条件、プロンプトとは別の層に属していた条件が混ざっています。したがって、7項目を永久に禁止するのではなく、**何の判断を減らすのか説明できないまま足さない**という使い方をしてください。

比較条件と数値の詳細は、[技術報告の8節と11.6節](execution-control-measurement-report.md)を正本とします。

## これだけ覚えてください

**プロンプトへ何かを足す前に、その一文が消す判断を一つ言えるか確認する。**

言えないなら、その一文はAIの仕事を減らす説明ではなく、AIに新しい判断を依頼している可能性があります。
