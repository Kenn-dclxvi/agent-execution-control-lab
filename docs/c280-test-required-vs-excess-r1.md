# C280のトークンを、試験が求める操作とそれ以外に分ける（r1）

2026-10-09。[判定基準の記録](shared-instruction-evaluation-criteria-r1.md)の「変更を考える範囲」に従い、GPT-6.1 Sol LowとSonnet 5.5 lowのC280（基準）の保存traceから、試験が求める操作と、それを超える操作を分けた記録。[設計原則](prompt-control-design-principles.md)の全文を読んだうえで、読み取り専用で分析した。新しいモデル実行はしておらず、Candidateは作成しない。

## 結論

- **Sonnet lowのC280は、試験が求める最小の流れに近い。** 14ケースのリクエスト数（中央値）の和で、最小の流れより10回多い（1ケースあたり約0.7回）。Sol LowのC280は41回多い（約2.9回）。C281以降の取り組みでSol Lowだけが大きく減ったのは、この差による。
- **両セルに共通する超過は、変更前の読み取りの追加回、変更後の必須以外の確認、変更後の読み取りである。** Sol Lowだけの超過として、長いコマンドの待機の呼び出しがある。
- Sonnet lowで減らせる余地は、1反復あたりリクエスト10回前後と、その持ち越しに限られる。指示文1バイトは、Sonnet lowで1反復あたり約21トークン（0.3247トークン/バイト×64.6リクエスト）の固定分になる。1,000バイトの指示は約2.1万トークンで、超過のリクエスト約1.5〜2回分に当たる。指示を加える場合は、加える文の固定分を上回って、この超過を減らす必要がある。

## 方法

- 対象：Sol Low C280（result `794d02abe894456686eea22e9b6f0fed`）、Sonnet low C280（result `c84fd22753d248e588e586cb8022ea1e`）、各70件。
- 応答ごとの使用量（Codexは`token_usage_record`、Claudeはtranscriptの`usage`）を使った。リクエスト単位の合計は、両セルとも70件すべてで登録値と一致した。
- 操作の種類は、コマンド文字列による簡易な判定である。`;`や`&&`でつないだコマンドは部分ごとに分けた。必須の確認は、評価条件の`required_command_groups_by_case`と一致するコマンドとした。
- 試験が求める最小の流れは、各ケースのTaskSpecから置いた。
  - 変更を伴わないケース（A01、F05の2ケース）：開始時の確認と依頼の確認 → 報告（2回）。
  - 読み取りだけのレビュー（F10の2ケース）：開始時の確認（ずれがあればレビューを始めない） → 読み取りと終了時の状態確認 → 報告（3回）。
  - 変更を伴うケース：開始時の確認と読み取り → 変更 → 必須の確認 → 報告。必須の確認は、Claudeでは課題文の指定により必須コマンドの数だけ（各コマンドを別の`Bash`呼び出しで、結果を受けて次へ進む場合）、Codexでは1回とした。
  - 読み取りの2回目（最初の読み取りで初めて分かる参照先）は、最小の流れに含めていない。このため、超過は上限側の見積もりである。

## 最小の流れを超えた応答の種類（A01・F05を除く、1反復あたり）

| 余分な応答 | Sonnet low | Sol Low |
| --- | ---: | ---: |
| 変更前の読み取りの追加回 | 7.4 | 20.0 |
| 開始時の確認だけの応答 | 2.2 | 1.0 |
| 変更の追加回 | 1.4 | 0.2 |
| 変更後の読み取り | 2.4 | 5.2 |
| 変更後の確認（必須以外：`git diff`、`git status`、`git diff --check`など） | 3.4 | 7.0 |
| 待機（長いコマンドの終了待ち） | 0 | 9.2 |

- 変更前の読み取りの追加回には、最初の読み取りで初めて分かった参照先の取得（試験が求める範囲）が含まれる。全部を減らせるわけではない。C288〜C295では、この回数を減らすために開始時のまとめ読みを指示し、Sonnet lowでは名指しされたファイルの全文`Read`が増えた（[C295の設計](candidate295-start-search-not-read-design.md)）。
- 変更後の確認（必須以外）には、TaskSpecの完了条件（許可外の変更がないこと）を確かめる終了時の`git status`が含まれる。これは試験が求める確認であり、減らせるのは、それを独立した応答として行う回数である。
- 待機は、Codexで長いコマンドが呼び出しより先に返った場合の待ちの呼び出しで、Sonnet lowでは起きていない。

## 次の設計の対象

判定基準（品質を保ち、両セルでC280よりトークンと経過時間を増やさない）のもとで、次の設計の対象になりうるのは、両セルに共通する超過のうち、試験の条件の内側で減らせるものである。

1. 変更後の必須以外の確認を、独立した応答として行う回数（Sonnet low 3.4、Sol Low 7.0）。終了時の状態確認そのものは試験が求める。
2. 変更前の読み取りの追加回のうち、最初の読み取りで分かっていた対象を後から読む回数。最初の読み取りで初めて分かった参照先の取得は除く。この区別は、保存traceの読み取り対象と、それより前の結果に現れたパスの対応で判定する必要がある。

どちらも、Sonnet lowで減らせる量は1反復あたり数回のリクエストにとどまる。加える文は、その固定分を上回る効果が見込める短さに限る。

## 追記：二つの対象の内訳（同日）

「次の設計の対象」の二つについて、減らせる部分を保存traceで確かめた（[機械可読の記録](../evaluations/results/c280-sol61-low-sonnet55-low-excess-response-detail_2026-10-09.json)）。A01とF05を除き、1反復あたりの回数で示す。

### 変更後の必須以外の確認だけの応答

| 直前の応答 | Sonnet low | Sol Low |
| --- | ---: | ---: |
| 必須の確認 | 2.2 | 2.6 |
| 変更 | 1.0 | 0.4 |
| その他（Solでは待機の後など） | 0.2 | 4.0 |
| 合計 | 3.4 | 7.0 |

- 必須の確認の直後に、`git status`や`git diff`だけを独立した応答として出す流れが、両セルに共通して2回強ある。この確認は、作業ツリーの状態を見るもので、必須の確認の結果には依存しない。
- 終了時の状態確認そのものはTaskSpecの完了条件（許可外の変更がないこと）が求める。減らせるのは、それを必須の確認の結果を受け取ってから別の応答で出す回数である。Claude Codeでは、必須のコマンドを個別の`Bash`呼び出しで実行する課題文の指定を守ったまま、状態確認を別の`Bash`呼び出しとして同じ応答に含められる。Codexでは、必須の確認と同じ外側の呼び出しに含められる。

### 変更前の読み取りの追加回

| 追加の読み取りの対象 | Sonnet low | Sol Low |
| --- | ---: | ---: |
| 一部を読んだファイルの追加取得（検索の後に範囲を読む、など） | 5.2 | 0.2 |
| 課題文で名前が出ていた対象 | 2.2 | 0 |
| 前の結果で初めて分かった対象 | 1.8 | 4.0 |
| 全体を読んだファイルの読み直し | 0.6 | 2.8 |
| その他 | 1.0 | 0.4 |
| 合計 | 10.8 | 7.4 |

- 内訳がセルで大きく異なる。Sonnet lowの主な部分は、検索で位置を確かめた後に範囲を読む、という同じファイルへの段階的な取得である。Sol Lowの主な部分は、前の結果で初めて分かった対象の取得（試験が求める範囲）と、全体を読んだファイルの読み直しである。
- 両セルに共通して減らせる部分は小さい。Sonnet lowの段階的な取得は、C289（検索と同じ呼び出しで本文まで返す）が狙った経路であり、C289〜C295ではSonnet lowで文脈つき検索の窓や全文の取得が増えた。Sol Lowの読み直しは、Sonnet lowでは0.6回にとどまる。
- この表の合計は、上の「最小の流れを超えた応答の種類」の表の値（Sol Low 20.0）と一致しない。こちらは読み取り対象のパスを取り出せた応答だけを数えており、パスを取り出せない読み取り（Codexの`python`による読み取りなど）を含まないためである。

### 判定

両セルに共通して、試験の条件の内側で減らせるのは、必須の確認の直後に独立した応答で出す状態確認（Sonnet low 2.2回、Sol Low 2.6回）である。変更前の読み取りは、セルごとに内訳が異なり、共通の対象にならない。

## 判断の限界

- 操作の種類と最小の流れの判定は、コマンド文字列とTaskSpecの読みによる簡易なものである。読み取りの2回目を最小に含めていないため、超過は上限側の見積もりである。
- 各セルN=5の1系列であり、ケースごとの中央値には5回のばらつきがある。
- この記録は採用、release、本体反映を決めない。
