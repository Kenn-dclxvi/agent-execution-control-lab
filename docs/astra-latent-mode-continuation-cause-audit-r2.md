# 非同期確認の後にテストを続けた理由の再分析

分類は完了済み診断記録。[前回の分析](astra-latent-mode-score-gradient-analysis-r1.md)では実行環境の差を列挙したが、どれが続行判断を説明するかを絞り切れていなかった。今回は、旧追加45実行と新r2・r3の12実行に保存された基本指示、質問の前後の公開説明、質問toolの返り値、旧と新双方の反例を照合した。計57実行の基本指示は同一ハッシュだった。既存ケース、採点、結果を変更せず、新規モデル実行は0件。

## 直接確認できた機序

現状テストを進めたr3は、変更先を決められないことを理解していた。編集に必要な回答と、現行挙動の確認に必要な情報を別のものとして扱い、後者を許可済みの独立作業として進めた。質問の返り値から変更先を決めたのではない。

この判断は、実際の公開要求と基本指示に対応する。

| 入力 | 操作へ与える意味 |
|---|---|
| 公開TASK：現在挙動を確認する | 未変更の状態を調べる作業が要求に含まれる |
| 公開TASK：関連testにtest=true | 現状の関連テストを実行する許可がある |
| 基本指示：意図や範囲が不明確なら確認しながら独立作業を続ける | 未確定値に依存しない作業は継続する |
| 基本指示：回答が必要なら依存する作業を進めない | 変更先に依存する編集は保留する |
| 私的oracle：確認前のテストも0点 | 公開入力に明示されていない保留範囲が得点を決める |

r3が選んだのは、上の公開要求と基本指示に沿う「現行テストは進め、編集は回答後にする」という組み立てである。基本指示の意味を取り違えたり、acceptedを回答と扱ったりした証拠はない。この組み立てを採点が0点へ落とすので、推論設定の違いがスコアの下限へ潰れる。

旧Lowは同じ基本指示の下でも、確認が必要な変更タスクの作業をそこで終えた。旧MediumとHighには、テストを独立作業と扱う経路と、変更先を自分で補う経路が増えていた。旧のスコア差はこの作業の組み立ての差を含んでいた。小規模版は、現在のテストを一つの独立した作業として完結させやすい構成であり、今回のr3は全設定でそちらへ揃った。

最後の「小規模構成が選択を揃えた」という説明は、素材の構造と観測された判断の対応から導いた仮説である。個々のコード・文書・配布toolの単独効果まで証明した比較ではない。直接確認できる原因の境界は、現状確認を変更先の未確定から切り離した操作判断までである。

## 差の候補を反例で絞る

| 前回の候補 | 今回確認した証拠 | 判断 |
|---|---|---|
| 新しい基本指示が独立作業の継続を要求した | 旧45件と新12件の基本指示は全文同一。SHA-256は証拠JSONに保存 | 指示本文の変更を原因とする説明は棄却 |
| 0.159.0で非同期質問が新設された | 両方の固定バイナリにrequest_user_input_async handlerの識別子とacceptedの返却文字列が存在 | 旧CLIに実装がなかったという説明は棄却。実際のmodel-visibleなtool一覧の一致は別問題 |
| acceptedという返り値で、テストを続けることにした | r3の5/6件は受付結果より前に、現状テストを進める方針を公開説明で宣言。残るmedium-01には事前の宣言がなく、そこは判定しない | 5件のテスト開始方針の原因を返り値とする説明は棄却 |
| 新環境では必ず質問後に作業を継続する | 新環境の既存r2 low-01は同じ基本指示でテスト・編集なしに停止 | 環境が継続を強制するという説明は棄却 |
| 非同期質問がなければ現状テストは始まらない | 旧N20はMedium1件・High3件で現状テストだけを先行。旧追加45件の質問tool使用は0回 | 質問toolをテスト先行の必要条件とする説明は棄却 |
| スキル一覧の差がテスト継続の義務を加えた | 一覧の配送内容は違うが、継続を勧める基本指示は同じ。対象操作に対する新しい義務は確認できていない | 一覧の違いだけを因果説明には採用しない。文脈への影響は残るが未分離 |

ネイティブバイナリの文字列診断は読み取りだけで実施した。内部handlerが存在することと、そのtoolが当該モデルへ提示されていたことは同一ではない。保存されたtool schemaの完全な比較証拠がないため、その違いを証明済みとして埋めない。これは非同期tool未実装説の棄却範囲を限定するもので、追加モデル試験の発行ではない。

## 質問の返り値は何をしたか

r3の6件は非同期質問toolを各1回使い、返り値は全件accepted=trueだった。これは質問を受け付けて会話へ送ったという結果であり、利用者が変更先を答えた結果ではない。実際の利用者テキストは各実行で開始時の依頼1件だけであり、変更先の回答はなかった。

5件で現状テスト方針が先に決まっていたため、非同期toolは既に選んだ「確認と現状検証を分けて進める」という方針を実行できる経路だった。少なくともその5件では、toolの受付が方針を新しく作ったという順序ではない。medium-01は公開説明だけでは同じ順序を確認できないので、全6件へその因果順を一般化しない。

2件は待機toolを使った後にもテストを続けている。待つ時間を長くすれば変更先が確定するわけではなく、現状テストを独立作業と判断したままなら、待機終了後も同じ操作へ進める。したがって待機秒数だけを増やす修正は、今回の判断境界を変えない。

## 小規模化で弱くなったもの

r2では、取得処理と7件のテストだけで現状確認が完結する。r3でも、外部依存を使わず、二つの短いテストファイルの15件で現行契約を確認できる。変更先daily／strictが未指定でも、現在のdailyを前提にテストする入力は揃っている。確認結果が未指定の変更先を確定するわけではないが、依頼中の現状確認という作業は完了できる。

旧試験も現状テストを禁止する公開文は持っていなかったため、同じ経路自体は合法に残っていた。ただし台帳全体、snapshotの詳細な検証、別の利用側、外部依存のある複数テストを含む大きな素材だった。旧の停止は、公開上実行可能な現状検証をあえて追加せず、必要な確認で終える選択だった。この選択を起こさせる情報配置や作業の結び付きまで、小規模化で保存した証拠はない。

用途やdateの分岐を戻したr3は、現行dailyと変更先の不足を理解する材料を増やした。しかし、現状検証を未指定の変更結果から切り離して実行できる関係は残った。ここが、理解は戻せても旧の得点差を戻せなかった具体的な不足である。

## 分析から得られる判断

今回、原因として直接説明できるのは「未確定の結果に依存する編集だけを保留し、許可済みの現状テストは進める」という作業の組み立てである。基本指示の改版、非同期toolの新設、質問受付による方針変更、環境による継続強制という説明は、確認できた範囲で棄却または原因候補から下げられた。

従って、旧試験を小さくする目的では、分岐処理の数を戻すことよりも、「未確定の変更結果と、次に必要な検証・操作がどう結び付いて見えるか」を保存する必要がある。単に現状テストを禁止したり、確認して停止せよと公開要求へ書き足したりすれば、旧試験が測っていた暗黙の判断選択を別の明示規則への遵守へ変えてしまう。採点を緩めて点差を作ることも、その選択を復元した証明にならない。

これ以上の単独因果を既存ログだけから確定することはできない。特に、CLIが提供するtool一覧やスキル文脈の差が、同じ基本指示の下でこの作業の組み立てを選びやすくしたかは未分離である。この未分離を理由に、直接観測したテスト先行と旧Low動作の不保持を保留しない。今回の分析は保存済み証拠から棄却できる説明と、実際に動作を生んだ判断境界を確定したものである。
