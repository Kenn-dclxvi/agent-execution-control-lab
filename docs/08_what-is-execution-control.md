# AIへの「依頼」とExecution Controlは何が違うのか

> 実務者向けExecution Controlシリーズ 8 / 8

## 結論

AIへの依頼は、してほしい仕事を伝えます。

Execution Controlは、その仕事を**いつ始め、何を根拠に進み、どこで止まり、何をもって完了するか**を決めます。

```text
依頼: この不具合を直してください。

制御:
- 期待する変更後の動作が確定するまで変更しない
- 対象と方法を決めるために必要な証拠だけ調べる
- 変更後に必要な検証を先に固定する
- 全結果が揃ったら一度だけ完了を判断する
```

## Prompt Engineeringとの違い

Prompt Engineeringは、AIへ意図を伝え、望む出力を得るための広い技術です。Execution Controlが見るのは、その中でも作業エージェントの実行中に生じる判断です。

| 依頼で伝えること | Execution Controlで決めること |
| --- | --- |
| 作ってほしい成果 | 成果が十分に確定した状態 |
| 守ってほしい制約 | 違反を検出したときの停止 |
| やってほしい作業 | 着手してよい条件 |
| 期待する品質 | 必須検証と合格条件 |
| 参考情報 | 調査を終えてよい条件 |

つまり、詳しい依頼文を作るだけではなく、実行経路の分岐と終端を設計します。

## 最初に決める5つ

難しい仕組みから始める必要はありません。

1. **成果** — 利用者が決める結果は何か
2. **着手** — 何が決まるまで変更しないか
3. **調査** — 何を確認したら探索を終えるか
4. **検証** — 何を実行し、失敗したらどう止まるか
5. **完了** — どの結果が揃ったら終わるか

これらが曖昧な場所では、AIが推測、探索、再読、再検証を始めます。条件が閉じていれば、次の行動を選び直す回数を減らせます。

## プロンプトで扱えない層を見分ける

プロンプトで扱えるのは、AIが観測できる値に基づく判断です。tool結果の配送、外側の待ち、並列上限、scheduler、cache、adapterの原子性などは、実行環境側の挙動です。

ただし、このリポジトリはruntime、executor、tool adapterの変更を解決策として提案または実装する範囲ではありません。問題が外部の層でしか強制できない場合は、promptだけで制御できたことにせず、ここでは未解決として停止します。

したがってExecution Controlは、長い万能プロンプトを作ることではありません。

- AIが判断できる条件はプロンプトへ置く
- AIが観測できない挙動を、自然言語の追加で強制できたことにしない
- promptの範囲外にある問題は、外部対応へ作業を広げず未解決として分ける
- 品質責務と、それを守る工程を分ける
- 実行結果を測り、効かなかった条件を積み増さない

## この研究から言えること

今回の研究では、単一の対象リポジトリ、特定のモデル系列、固定した課題集合の範囲で、判断条件と実行経路を繰り返し比較しました。到達点では、0バイトのFree条件より品質が高く、実行tokenも小さい結果が得られました。

ただし、同じ条件が別モデルや別リポジトリでも同じ品質・コストになるとは限りません。実行経路を閉じることも、効率化の十分条件としては確認されていません。Execution Controlは万能則ではなく、**品質責務を固定したまま、不要な判断経路を測って減らすための設計と評価の方法**です。

測定条件、一次artifact、解釈上限は、[Execution Control技術報告](execution-control-measurement-report.md)を正本とします。

## これだけ覚えてください

**AIへ仕事を頼むだけでなく、進行・停止・完了を観測可能な条件で制御する。**
