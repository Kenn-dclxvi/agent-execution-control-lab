# AIの料金を増やすのは、文章量より実行経路

> 実務者向けExecution Controlシリーズ 6 / 8

## 結論

同じ仕事でも、AIがモデルへ戻って判断し直す回数が増えると、読み直すcontextと出力が増えます。

```text
読む → 判断する → 追加で読む → 判断し直す → 確認する → 再び判断する
```

これを、必要な経路へ収束させます。

```text
成果を確定 → 必要な証拠を取得 → 変更 → 固定済みの検証 → 終了
```

**短くしたいのはプロンプトではなく、同じ成果へ到達するまでの実行経路です。**

## 文書が置いてあるだけでは料金は増えない

研究では、工程仕様やロール別プロンプトを残したまま、それらを呼び出す最上位の経路だけを外した条件を測りました。最上位から呼び出されなければ、文書が存在していても、その工程の実行量は生じませんでした。

逆に、短い指示でも次のような経路を起動すれば実行量は増えます。

- 追加調査のたびにモデルへ戻る
- 担当を増やし、同じ証拠を読み直す
- 検証を一件ずつ判断しながら発行する
- 完了後に念のための確認へ再入する

料金を見るときは、静的プロンプトの文字数だけでなく、tool call、モデルへの往復、子エージェントを含む全tokenを確認する必要があります。

## 実行経路を短くする4つの質問

| 場所 | 確認すること |
| --- | --- |
| 着手前 | 未確定なら止まる値は何か |
| 調査中 | どの証拠が揃えば探索を終えられるか |
| 検証前 | まとめて発行できる既知の検証は何か |
| 完了前 | どの結果が揃えば追加確認なしで終われるか |

経路を減らすために、必要な確認まで削ってはいけません。品質を落としてtokenが減った場合、それは効率化ではなく省略です。

## 研究から言える限界

表面的な短文化を主眼にした8条件では、静的量の低下は実行時tokenの低下へ対応しませんでした。一方、着手条件、探索の停止、検証のまとめ方、終端条件などは、複数の比較で実行量の低下と同時に観測されました。

ただし、「経路を閉じれば必ず安くなる」とは言えません。経路を閉じる側に分類された候補でも、多くが品質、機構またはコストのgateで停止しています。実行経路は設計に有用な軸ですが、効率の十分条件や一般的な因果法則として確認されたものではありません。

実行経路という解釈軸の根拠と限界は、[技術報告の6〜8節と11.4節](execution-control-measurement-report.md)を正本とします。
