# C291の改善の検討 C290・C291を外す余地（r3）

> **訂正（同日）**：この記録は、C291を親にして縮める・外す検討として書いたが、目的は「C281以降の取り組みから効く要素を抽出すること」であり、現行Candidateの維持や最小化ではない。ここに記した事実（Solの構造、Claudeでの観測、字句を縮める量の見積もり）は参考として残し、検討の枠組みは[要素の抽出の検討](c291-improvement-review-r5.md)で置き換える。

2026-10-08。[r2の検討記録](c291-improvement-review-r2.md)に続く検討である。[設計原則](prompt-control-design-principles.md)の全文を読んだうえで、保存済みの結果だけを読み取り専用で再分析した。新しいモデル実行はしておらず、Candidateは作成しない。

## 検討の目的

- 系列：C280 → C284 → C285 → C288 → C289 → C290 → C291
- 必要な効果：Codex（Sol Low）とClaudeの両方で効く共通の本文を、C280を基準に、全エージェントトークンと経過時間を増やさない方向へ最適化する。モデル別に本文を分ける案は、目的外として扱わない。
- 保持するもの：全件4点の品質、Sol Lowで得ている削減、閉じた経路。
- この記録の問い：C290とC291は、Sol Lowでコストが増えている。両方を外した形（C289）を、共通の本文の最適化の出発点にできるか。

## 事実

### Sol Low：コストは増えているが、ケース別には一貫していない

| 条件 | 4点 | トークン中央値 | 経過時間中央値 |
| --- | ---: | ---: | ---: |
| C289（N=5） | 70 / 70 | 1,263,739 | 582.11秒 |
| C290 | 70 / 70 | 1,281,263（+1.39%） | 701.01秒（+20.43%） |
| C291 | 70 / 70 | 1,318,762（+4.35%） | 632.10秒（+8.59%） |

C289の累積N=20（280件、全件4点）のトークン中央値は1,262,119で、N=5の値とほぼ同じである。

ケース別のトークン中央値で、C291とC289の差を並べると、減るケースと増えるケースが混在する（千トークン、A02 −6、F01 −4、F04 −4、F06 −3、F08 −2、F05 −1、A01 0、F02 +1、F03 +2、F10 +3、F07 +9）。合計はほぼ相殺しており、+4.35%は、どのケースにも一貫して現れた増加ではない。経過時間は計測した時刻が異なり、本文だけの因果効果と断定できない（結果記録の注記どおり）。

### C290の閉じる経路は、Solでトークンに結びついていない

C290はルートの本文の再取得を59件から0件にしたが、トークンは減っていない。ルートの指示ファイルは5,372バイト（C289）から5,828バイト（C291）へ456バイト増えた。C291で閉じる対象の事象（検証の呼び出しの終了コードのずれ）は、Sol LowのC289で0件だった。

### Claude：C291の一文は、品質の上で役割を持っている

| 結果 | 4点未満 |
| --- | --- |
| Opus 5.5 medium C289 | A02の2件（70件中）。どちらも、検証を一つの`Bash`呼び出しにまとめ、その呼び出し全体が終了コード1を返した。個々のコマンドは成功していたが、採点は終了コード1の呼び出しに含まれた`pytest`を試験証拠に数えなかった |
| Opus 5.5 medium C291 | 0件（70件すべて4点） |
| Sonnet 5.5 low C289 | A02の1件 |
| Sonnet 5.5 low C291 | A02の1件。理由は終了コードのずれではなく、試験を実行していなかったこと。終了コードのずれの候補は0件 |
| Opus medium C280・C286 | 0件 |

Opus mediumで、C289の2件の減点（終了コードのずれ）がC291で0件になった。N=5のため、C291の一文が原因とは断定しないが、C291が閉じる対象と減点の理由が一致している。

### Claudeのコスト：C289とC291で一貫した差はない

- Sonnet 5.5 low：C289が1,057,055、C291が1,081,993で、C291が+2.4%（約25,000トークン）。C289とC291の差の標準誤差（約32,200）の内にある。ケース別では、F02が+70千、F03が+39千と増え、F01が−27千、A02が−13千と減る。増加は検証の出力が多いケースに偏る。
- Opus 5.5 medium：C291はC289より、トークン中央値が−10.28%、経過時間中央値が+10.19%だった。ただし、この結果は、利用上限による別アカウントへの切り替えを含む。

## 判断

- **C290とC291を外すことは、単独では出発点にならない。** 外せば、Solで得られる見込みは+1.4〜4.4%の削減だが、ケース別には一貫しておらず、5回のばらつきと区別できない。Claudeでは、トークンの差に一貫した向きがなく、Opus mediumのA02の減点（終了コードのずれ）を再び開く可能性がある。固定コストの減少は、456バイト（Opus lowで1反復あたり約8,600トークン、約1.2%）にとどまる。
- **C290は、閉じる経路がSolのコストに結びついていない。** C290を外す案は、Solでのトークン、経過時間を悪化させる証拠がなく、Claudeでの再取得（Opus lowで1→8/70件）も閉じていない。C291の一文と分けて、外す案を残す。ただし、効果はノイズの範囲内であり、見込みが小さい。
- したがって、共通の本文の最適化で動かせる大きさは、別の箇所にある。Solの削減の約7割はC284の検証の三項で、Sonnetの増加の大半も、C284の三項と、C289から広がった文脈つき検索にある。

## 次に行う作業

1. **C284の検証の三項（S33〜S42）を、共通の形で最小化する案を設計する。** Solの削減を支える文と、Claudeの増加を生む文を分ける。C291の一文（S37）は、Claudeの品質に役割があるため、維持する前提で扱う。
2. **C290の単独の除去を、2の設計に含めるか判断する。** 単独では見込みが小さいため、他の変更と同じ比較単位に入れない。

どちらも、設計の確認事項（項目1〜9）を満たす記録を作ってから、Candidateを作る。

## 判断の限界

- 各条件はN=5（C289のSolのみN=20）の1系列である。Sol Lowの経過時間は、計測した時刻が異なる。
- Opus mediumのC291は、アカウントの切り替えを含む。
- Opus lowとHaiku lowでは、C289を測っていない。
- この記録は採用、release、本体反映を決めない。
