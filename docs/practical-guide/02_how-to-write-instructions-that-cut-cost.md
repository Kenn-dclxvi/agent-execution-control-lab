# 料金を下げる指示の書き方

> 実務ガイド 2 / 3

[前の記事](01_why-instructions-change-your-bill.md)では、指示ファイルに6行足しただけで、AIの料金が1〜3割下がったことを紹介しました。

この記事では、その6行を1行ずつ見ていきます。どの無駄を止めているのか、そしてなぜその言い方なのか。最後に、書かないほうがよいことと、指示では扱えないことも説明します。

## 1行目：やることが決まるまで、始めない

> ユーザーが求める結果（作業後にどうなっているべきか）は、ユーザーが示した内容と、それが従うよう求めている指示や正本が直接定めている内容だけで決まる。既存の状態、候補を消去法で一つに絞れること、過去の例、テストの期待値、実装上の都合は、結果を決める根拠にならない。結果が決まっていない間は、依頼内容の確認と依頼で指定された事前確認だけを行い、調査・変更・テストやその他の操作を始めず、決まっていない結果だけを確認して終える。対象の場所や具体的な実施方法が未確認なだけなら、利用可能な情報や環境を確認し、自分で決めて進める。

**止めたい無駄：** 「どうなっていればいいか」が依頼から決まらないのに、推測で作業を始めてしまうこと。Freeで満点にならなかった実行は、4つのAIすべてで、これが原因でした。

**書き方のねらい：** 長い行ですが、言っていることは三つです。

1. 結果を決めてよいのは、ユーザーが示したことだけ。
2. 「今のコードがこうだから」「テストがこう期待しているから」は、結果を決める理由にならない。
3. ただし、場所ややり方が分からないだけなら、自分で調べて進めてよい。

3がないと、AIは何でも質問するようになります。止めたいのは「結果の推測」だけで、「調べること」まで止めたくはないからです。

## 2行目：方針が決まったら、調べるのをやめる

> 事前調査は、対象と実施方法を一つに決めるために不足している情報だけに絞る。方針が決まった後は、念のための探索・再確認・履歴調査を追加せず、実行へ進む。

**止めたい無駄：** 方針が決まった後の「念のため」の調査。

**書き方のねらい：** 調べる範囲を「足りない情報」に限っています。試しにこの行を外してみたら、変更を始める前のファイルの読み取りが、2つのAIとも1〜2割増えました。

## 3行目：最後の確認は一度だけ

> 最後の変更の後、作業ツリーの状態の確認は、依頼や適用中の指示が求める確認のうち最後に実行するものと同じ応答で発行する。その応答の結果がすべて成功していれば、コマンドを発行せずに報告する。

**止めたい無駄：** 作業が終わった後に、確認をもう一度やり直すこと。

**書き方のねらい：** 「十分に確認したら終える」とは書いていません。それだと「十分か」をAIが毎回考えます。代わりに、「最後の変更の後」「最後の確認と同じタイミングで」と、作業の流れの中で決まる事実で書いています。AIは考えなくても当てはめられます。

この形にする前のSol Lowは、確認を終えた後にもう一度コマンドを出すことが、5回の計測で19回ありました。この形にしてからは、ほぼ0回です。

## 4行目：待つときは、普通に待つ

> コマンドの実行とその終了待ちで、ツールの既定値より短い待機時間を指定しない。

**止めたい無駄：** コマンドの終了を短い間隔で何度も見に行くこと。一回見に行くたびに、一手が増えます。

**書き方のねらい：** 「適切な間隔で」ではなく、「ツールの既定値より短くしない」と、比べられる基準で書いています。この行を入れる前のSol Lowは、短い待機時間を5回の計測で52回指定していましたが、入れた後は0回です。

## 5行目：テストの結果は、必要な分だけ受け取る

> 確認のコマンドは、そのコマンド自身の終了コードと、判断に必要な部分の出力（末尾など）だけを受け取る形で実行する。

**止めたい無駄：** テストの出力を何百行もそのまま受け取ること。

**書き方のねらい：** 「出力を受け取るな」ではなく、「こういう形で実行する」と書いています。たとえば、次のような違いです。

```text
書く前： pytest -q
        （全部の出力を受け取る）

書いた後： pytest -q > /tmp/test.log 2>&1; echo "exit=$?"; tail -n 5 /tmp/test.log
        （成功か失敗か（終了コード）と、最後の5行だけを受け取る）
```

終了コードは、コマンドが成功したか失敗したかを表す数字です。成功していれば、細かい出力は読まなくても判断できます。

## 6行目：ファイルは、必要な範囲だけ読む

> ファイルの本文は、判断に必要な範囲だけを受け取る形で読む。

**止めたい無駄：** 長いファイルを丸ごと読むこと。Sol Lowは、600行や1,000行を超えるファイルを毎回まるごと読んでいました。

**書き方のねらい：** 最初は「1回で300行を超えて読まない」と、禁止の形で書いていました。すると、短いファイルまで細かく分けて読むようになり、料金ははっきりとは下がりませんでした。

「必要な範囲だけを受け取る形で読む」と、させたい形に書き直したら、300行を超えるファイルを丸ごと読む回数が16回から0回になり、料金が約1割下がりました。

## 書かないほうがよいこと

6行を作る途中で、書いても効かない、あるいは逆効果になる書き方も分かりました。

**「適切に」「必要に応じて」と書く。** 「適切か」を判断する仕事が、AIに一つ増えます。代わりに、作業の流れの中で決まる事実で書きます（3行目、4行目）。

**数字の上限で禁止する。** 「300行まで」のような上限は、関係のない場面まで縛ります（6行目）。代わりに、させたい形を書きます。

**新しい作業を求める。** 「長いファイルは、検索で場所を確かめてから読む」のように書くと、検索という一手が増えることがあります。止めたいことだけを書き、やり方はAIに任せます。

**効果の分からない項目を残す。** 前の版には「作業前に方針を一つにまとめる」という項目がありました。外して測っても、料金も品質も変わらなかったので外しました。

## 指示で扱えること、扱えないこと

最後に、指示だけでは変えられないことがあります。

見分けるには、**「それは、AIが自分で選ぶ行動か」**と考えます。

- **AIが選ぶ行動：** どのコマンドを、どんな形で実行するか。ファイルのどこを読むか。どれだけ待つか。いつ終えるか。これらは指示で変えられます。5行目と6行目は、この範囲です。
- **AIが選ばないこと：** ツールが結果をどんな形で返すか。複数の処理をまとめて返すか。これらはツールの側で決まるので、指示に書いても変わりません。

効かない指示を何度も言い換える前に、この見分けをしてみてください。

## 自分の指示に当てはめるには

この6行は、そのまま使える万能の指示ではありません。自分の作業に合わせるときは、次の順に考えてください。

1. AIの作業記録を見て、余計な一手や、大きな出力を受け取っている場所を探す。
2. そこで、AIにどうしてほしいかを決める。
3. AIが考えなくても当てはめられる事実で、させたい形を書く。
4. 書いた後も作業記録を見て、別の無駄（細かく分けすぎるなど）が出ていないか確かめる。

## これだけ覚えてください

**無駄が起きている場所を作業記録から見つけ、そこで「どうするか」を、AIが考えなくても当てはめられる事実で書く。**

人と仕事を分担するときの考え方を、AIにどう移すかは、[「人間の開発工程を、AIに移すとき」](03_moving-human-processes-to-ai.md)で説明します。
