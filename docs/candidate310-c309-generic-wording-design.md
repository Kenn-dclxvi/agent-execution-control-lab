# Candidate310 C309の「TaskSpec」を、実際の使い方でも通じる言葉にそろえる

2026-10-12。利用者の指摘（「TaskSpec」は試験でしか通用しない）を受けて、Candidate本文の作成前に固定する設計記録。[設計原則](prompt-control-design-principles.md)の全文を読み、「Candidateを作成する前の確認事項」の項目1〜9に対応させた。計測と記録は[計測と記録の基準r2](shared-instruction-evaluation-criteria-r2.md)に従う。この記録ではbundleを作成しない。

## 目的と役割

- 系列：実行環境を切り離し、負荷を見て次のrunを始める発行の条件（CPU使用率70%以下、間隔1秒）で測る系列。
- ベースと直接の親：C309（`the-caption-3ce91a4-final-check-unit-output-trim-r1`）。比較の基準は、同じ条件で測ったC309。
- 計測の順序：Sonnet lowで、C309と変わらないことを確かめてから、Sol Lowを測る。
- 評価は計測であり、達成目標を置かない（r2）。
- 変更対象：C309のroot `AGENTS.md`のうち、「TaskSpec」を使う二つの項目の、その言葉だけを置き換える。他の項目と他の18対象はC309とバイト一致を保つ。

## 1. 比較の基準と、正常な最短経路

基準はC309。正常な最短経路は[C309の設計記録](candidate309-c307-final-check-unit-design.md)の項目1のとおり。

## 2. 確認した問題

「TaskSpec」は、評価の仕組みがモデルに渡す課題の書式の名前である（Claude用の課題文は「以下のTaskSpecに従って作業してください」と書く）。THE-CAPTIONの実際の使い方は、リポジトリを開いてCodexやClaude Codeに直接指示する形で、TaskSpecに当たるものは、利用者の依頼と、リポジトリの指示（`AGENTS.md`など）である。C309の二つの項目は、実際の使い方では、何が「求める確認」なのかを決められない。C309の前半の4項目（C301から引き継いだもの）は、すでに「ユーザーが示した内容と、それが従うよう求めている指示や正本」「依頼」「適用中の指示」という言葉を使っており、試験では課題文が依頼に当たる。

## 3. 開いている記述

この変更は、新しい経路を閉じるものではない。C309で閉じた経路と保つ処理は変えず、確認の範囲を指す言葉を、試験と実際の使い方の両方で同じものを指す言葉にそろえる。

## 4. 追加・変更する条件の全件

C309の二つの項目の「TaskSpecが」を「依頼や適用中の指示が」に置き換える。

> - 最後の変更の後、作業ツリーの状態の確認は、依頼や適用中の指示が求める確認のうち最後に実行するものと同じ応答で発行する。その応答の結果がすべて成功していれば、コマンドを発行せずに報告する。
> - 依頼や適用中の指示が求める確認のコマンドは、出力を絞って実行してよい。確かめる終了コードは、そのコマンド自身のものとする。

## 5. 禁止行動、開放経路、閉じる境界、反証

C309の設計記録の項目5のとおり。「求める確認」の範囲は、試験ではTaskSpec（依頼）とリポジトリの指示、実際の使い方では利用者の依頼とリポジトリの指示になる。試験では、適用中の指示（`AGENTS.md`）が確認のコマンドを定める場合に、それも「求める確認」に含まれる点が、C309と違いうる。

## 6. 維持する正常経路

C309の設計記録の項目6のとおり。

## 7. 新しく増える判断と、変更対象外への影響

- 新しい判断：適用中の指示が求める確認があるか。リポジトリの指示ファイルに書かれた事実から決まる。
- 危険：リポジトリの指示ファイル（`tests/AGENTS.md`など）が求める確認を、依頼が求めていない場合にも実行し、確認が増える。最後の確認の後の応答の数と、確認コマンドの種類で観測する。
- 固定分：置き換える言葉の差（2か所、各「TaskSpecが」から「依頼や適用中の指示が」へ）。

## 8. 評価ケース、比較単位、比較条件、記録する項目

- セル：Sonnet low、続けてSol Low。各Standard14の全14ケースN=5の計70件。
- 比較条件：C309の同じセルのプロファイルと同じで、prompt identityだけを変える。
- 記録する項目（r2）：品質、処理の適切さ、費用、経過時間、生のトークン（参考）。
- 機序の診断（合否にしない）：C309と同じ数え方で、状態の確認の置き場所の遵守率、状態を確かめずに報告したrun、最後の確認の後の応答・呼び出し、F06とF07の`git diff --check`の成功件数、確認コマンドを出力そのままで実行した件数。Sol Lowは、短い待機時間の指定と待機だけの呼び出しも数える。
