# Candidate286 Standard14 累積N=20の追加計測

2026-10-07。利用者の指示に従い、C286の品質と3 KPIを累積20件で確認する。[再現性の方針](reproducibility-decision-policy.md)のN=5からN=20への拡張は、利用者が求める追加確認に当たる。発行前に、観測対象、開始時の累積N、追加理由、追加上限、判定条件、停止条件を次のとおり固定する。

## 開始時の状態と追加理由

C286のGPT-6.1 Sol Low・Standard14 N=5は、全14ケース各5件の計70件がすべて有効で品質4だった。登録resultは`d6fb28dbcef44caebc516591fd720eaa`である（[結果](../evaluations/results/c286-sol61-low-standard14-n5_2026-10-07.md)）。C285比で、トークンは-7.18%、経過時間は-9.09%だった。

追加する理由は二つある。

1. **採用の判断に進む前に、品質4の保持を累積20件で確かめる。** C280からC286までの系列は、各段階がN=5で判断されている。
2. **N=5のコスト削減が保たれるかを確かめる。** C283では、N=5で見えたC280比のトークン削減が、累積N=20では保たれなかった（[C283 N=20](../evaluations/results/c283-sol61-low-standard14-n20_2026-10-07.md)）。C286でも同じことが起きないかを確認する。

## 観測対象と判定

| 観測対象 | 判定 |
| --- | --- |
| 品質4の保持 | 累積280件のうち、有効な4点未満が一件でもあれば、その条件での全件保持は不成立とする。追加分だけの分布も記録する。低得点を削除、相殺、再実行しない |
| コストの水準 | 累積N=20のトークン中央値と経過時間中央値を記録する。保存済みC285・C284・C280の各N=5との差は、標本数と実行時期が異なる参考差としてだけ記す |
| 機序の維持（診断） | 名指しされたファイルを2回目以降の呼び出しで初めて読んだrun、リポジトリの外を読んだrun、変更後の検証の一括実行を、C286 N=5と同じ方法で集計する。独立した合否条件にしない |
| 副作用の頻度（診断） | N=5で見えたA02のトークン増（最初の呼び出しの出力増）と、F05範囲外ケースの`README.md`読み取りの頻度を、ケース別に記録する |

累積N=20の判断は、品質の全件保持と、累積値の水準で行う。比較相手とNが異なるため、C285などとの差をprompt単独の因果効果やコスト改善の確定とは扱わない。

## 計測条件

- **追加枠**：既存の70件を保持し、同じatomic poolへ各ケース15件、計210件だけを追加する。既存の70件は再実行しない。
- **固定する条件**：C286の本文とhash、全14ケース、fixture、TaskSpec、Rating v14、GPT-6.1 Sol Low、CLI 0.159.0、Python 3.14.5、個人指示の隔離、M24、固定Layer 1と実行コード、executor parameter、全エージェントのトークン計上を変更しない。
- **事前照合**：保存済みのC286 N=5 resultに対する互換照合を、210枠の発行前に保存する。発行用profileは元のN=5の互換条件を保持し、追加数と枠はatomic dispatch planへ固定する。累積集計用には、N=20を宣言する別profileを保存する。
- **比較相手**：C285・C284・C280は保存済みN=5を再利用し、新規実行しない。
- **実行担当**：root。

## 診断の集計方法

C286 N=5と同じ方法を使う。ただし、N=5で見つかった数え漏れを次のように補う。旧方法の値も並べて記録し、N=5の結果と比べられるようにする。

- **変更の有無**：`apply_patch`の有無に加え、許可されたパスへ書き込むコマンド（Pythonの`write_text`・`write_bytes`、`sed -i`、リダイレクトなど）でも判定する。N=5では、F07の依存関係ケースの2件がPythonで書き換えており、変更として数えられていなかった。
- **名指しされたファイルの読み取り**：`cat`などのコマンド名に加え、Pythonの`read_text`や、`for`による繰り返しの中の読み取りも数える。N=5では15件が「観測できない」に分類されていた。

この補正は診断の数え方だけを変える。品質、トークン、経過時間の算出方法と採点は変えない。

経過時間は[経過時間の分解](c284-elapsed-time-decomposition-r1.md)と同じ方法で区間に分け、応答1回あたりの待ちの中央値と、実行時間帯を記録する。

## 停止条件

- 互換条件の不一致や未確認があれば、210枠の一件目の発行前に停止する。
- 外部失敗だけ、同じ枠で固定上限内に再試行する。認証失敗などで待ち行列が分かれた場合は、それぞれの実行時間帯と件数を記録する。
- 指定した210件の採点を終えてから、累積N=20で判断する。N=50へは自動延長しない。
- 採用、本体反映、release、PR、マージはこの計測に含めない。

## 判断の限界

追加分は、比較相手と別の時間帯・待ち行列で測る。経過時間の差には、[経過時間の分解](c284-elapsed-time-decomposition-r1.md)で確認した時間帯による応答速度の差が含まれ得る。同じ時間帯での比較が必要になった場合は、この計測とは別の計画として固定する。この計画は結果に合わせて改訂しない。
