# C291の改善の検討 検証の出力とルートの置き場所の切り分け（r2）

2026-10-08。[r1の検討記録](c291-improvement-review-r1.md)、[文ごとの台帳](c291-sentence-ledger-r1.md)、[Sonnet 5.5 lowの段階別の比較](../evaluations/results/claude-sonnet55-low-c284-c288-c289-standard14-n5-cli2288_2026-10-08.md)に続く検討である。[設計原則](prompt-control-design-principles.md)の全文を読んだうえで、保存済みのtranscriptを読み取り専用で再分析した。新しいモデル実行はしていない。Candidateは作成しない。

## 検討の目的

r1と同じ系列を続ける。目的は変えていない。

- 系列：C280 → C284 → C285 → C288 → C289 → C290 → C291
- 必要な効果：C280を基準に、全エージェントトークンと経過時間を増やさず、減らす方向へ近づける。評価対象はSol LowとClaude（Opus、Sonnet、Haiku）で、ルートの指示ファイルは全モデルで同じ本文を使う。
- 保持するもの：全件4点の品質、C290が閉じたルートの本文の再取得、C291が閉じた検証の呼び出しの終了コードのずれ、Sol Lowで得ている削減。
- 関係：C291を直接の親とする。

この記録で扱う未完了の項目は、段階別の比較で唯一、5回のばらつきを超えていたC284の増加（Sonnet lowで+15.8%）の原因と、その原因を閉じる辺がリポジトリ内にあるかどうかである。

## 確かめた事実

### C284の増加は、三項を足しただけの差である

C280とC284の本文の差は、ルートの指示ファイルに検証の三項を足した部分だけである（他の18対象はバイト一致）。したがって、Sonnet lowの+115,337トークン（5回の1反復合計の平均）は、この三項をまとめた効果として扱える。ただし、三項のどの文が効いたかは、この差からは分からない。

### 検証コマンドの出力を絞る書き方が減った

C280とC284の70件ずつ（Sonnet 5.5 low、変更を伴わないケースを含む）で、`pytest`または`main_verify`を含むBashのコマンドの書き方を、コマンド文字列から数えた。

| 書き方 | C280 | C284 |
| --- | ---: | ---: |
| 出力を絞らず、`; echo "exit=$?"`で終了コードを出す | 8 | 19 |
| `| tail`で絞り、`; echo`で終了コードを出す | 22 | 28 |
| 出力をファイルへ書き出し、`; echo`と`tail`で見る | 13 | 7 |
| `| tail`で絞り、`&&`でつなぐ | 7 | 0（`;`と`&&`の併用が2） |
| `| tail`だけで、終了コードを出さない | 2 | 0 |
| 絞りも結合もない | 2 | 0 |

同じ試験を実行する場面での変化は、さらにはっきりしている。`test_market_units_snapshot.py`を実行した10件は、C280では10件すべてが`-v 2>&1 | tail -N; echo "exit=${PIPESTATUS[0]}"`だった。C284では、同じ10件のうち6件が`tail`を外し、`-v; echo "exit=$?"`で全文を受け取っている。F03の試験（`test_atomic_save.py`）は、絞らない書き方の実行が、C280で4件、C284で5件あり、ほとんど変わっていない。

- `;`の使用そのものは減っていない。絞らない書き方でも`; echo "exit=$?"`を使っている。r1の「`;`でつなぐ書き方が消えた」という読みは、`;`を禁じる文が`tail`を外させた理由としては支持されない。
- 変わったのは、パイプで絞る前提が外れた点である。パイプを使うと、`$?`は`tail`の終了コードになり、試験自体の終了コードは`${PIPESTATUS[0]}`でしか取れない。三項の「終了コードを個別に確認する」が、この区別を意識させた可能性はあるが、transcriptには説明文も思考も残っておらず、理由は観測できない。

### 検証の出力が持ち越されたトークン

検証コマンドの結果を、後続のリクエストが何回数え直したかで見積もった（1バイトあたり0.30トークンと仮定し、結果の位置から終了までのリクエスト数をかけた。1反復＝14ケース合計）。

| 段階 | 検証の結果のトークン | 後続のリクエストでの持ち越しを含む |
| --- | ---: | ---: |
| C280 | 約5,100 | 約11,400 |
| C284 | 約12,500 | 約33,200 |
| C288 | 約10,700 | 約25,400 |
| C289 | 約11,800 | 約31,500 |
| C291 | 約15,200 | 約42,800 |

C280→C284の増加+115,337トークンのうち、検証の出力の持ち越しは約21,700（約19%）と見積もれる。ルートの指示ファイルの大きさによる固定分が47,519（41%）、出力が2,640である。残りの約43,000（約38%）は、検証の出力では説明できない。読み取りの持ち越しに入っているが、三項が検証の規則であるため、原因は特定できていない。

### Sol Lowは検証の出力の経路が違う

Sol Lowの検証は、`tools.exec_command`を呼び出すJavaScriptのループで実行され、呼び出しごとに`max_output_tokens`を指定できる（C284の保存rolloutで確認）。`-m pytest`または`main_verify`を含む呼び出しは、C280で73件、C284で45件あり、`tail`で絞った呼び出しは両方で0件だった。`max_output_tokens`を指定した呼び出しは、C280で69件、C284で36件である。Claudeの`Bash`で`| tail`と`PIPESTATUS`を使う書き方は、Solの経路には対応しない。

ルートの指示ファイルは全モデルで同じ本文のため、Claudeの`Bash`の書き方に合わせた文は、Solにとって意味を持たないか、別の意味に読まれる。

### Opus lowとHaiku lowでは、同じ変化が起きていない

台帳の出力量の分析では、検証コマンドの出力を絞った割合は、Opus lowで86%→84%、Haiku lowで17%→18%だった。出力を絞らなくなった変化は、Sonnet lowに限られる。

## 検証の出力を絞る案の成立性（案5）

r1の案に続く案として、「検証コマンドの出力を、終了コードを保ったまま絞る」処理方法の指定を、Candidateとして置くかを検討した。

| 設計原則の項目 | 内容 |
| --- | --- |
| 禁止する行動 | rootが、検証コマンドの全文の出力をそのままモデルへ返すこと |
| 現在の開放経路 | 出力の形を定める文がない。C284の三項は、終了コードの確認を求めるが、出力の形は定めない |
| 閉じる境界 | 検証コマンドの結果として受け取る出力の範囲 |
| 維持する正常な処理 | 失敗時に原因を読める出力、各コマンドの終了コードの個別確認、後続の停止 |
| 反証する構成 | 絞る形の定義をずらした書き方（絞る範囲を広くとる、複数のコマンドへ分ける）で、規則に違反せず全文を受け取れるか |

判定は、次のとおり成立しない。

- **強制できない。** ツール結果の量の上限は、プロンプトでは強制できない（設計原則の「どの層で制御するか」）。処理方法として書いても、絞る形の定義（行数の上限）を示せば、その数が境界になり、示さなければ、どこまで絞れば遵守かを保存traceから機械的に判定できない（処理方法を指定できる条件の2）。
- **成功したrunの書き方の転記になる。** 閉じる辺が`| tail -N; echo "${PIPESTATUS[0]}"`という、C280で観測された書き方と一致する。設計原則は、成功動作を実行手順へ転記することを避けるよう求める。操作の種類の水準で書くと、行数の上限が決まらず、境界にならない。
- **Solの経路に対応しない。** 上のとおり、Solは別の出力の制限を持つ。共通の本文に入れると、Sol Lowで得ている削減を保てるかが未確認になる（設計原則の項目6）。
- **見込みが小さい。** 約150バイトの文を足すと、固定分が1反復あたり約3,200トークン増える（0.3247トークン/バイト×64.8リクエスト）。回復できる上限は約21,700で、固定分を差し引くと約18,500、Sonnet lowに限られる。Sonnet lowの+249,377（C291）の約7%にあたり、5回の差の標準誤差（約32,200）より小さい。N=5では、効果と区別できない。

結論：**案5は`candidate_not_created`とする。** 問題が解決したという意味ではなく、Sonnet lowで検証の出力が増えた原因は未解決である。

## ルートの置き場所を変える案（案4）

r1が示した固定コストの64%（Opus low）は、ルートの指示ファイルがすべてのリクエストで数え直されることによる。そこで、適用範囲が事実で決まる規則（検証の十文など）を、局所の指示ファイル（`tests/AGENTS.md`など）へ移す案を検討した。適用される局所の指示ファイルは、対象のパスで決まり、モデルの判断を介さない。

- 変更を伴うケース（70件のうち55件）は、すべて検証を行うため、規則を使う。規則を局所へ移しても、読み取った本文は同じように持ち越されるため、固定コストは減らない。
- 規則を使わないのは、変更を伴わない15件（3ケース×5回、r1で示した値）だけである。C291のSonnet lowで、`Edit`と`Write`を使わなかった27件のリクエスト数は平均2.6で、変更した43件の平均5.9より少ない（Bashで変更した実行を含むため、変更しない実行の上限に近い）。検証の十文（1,239バイト、約400トークン/リクエスト）を負担しなくなる分は、3ケース×2.6リクエスト×約400トークンで、1反復あたり約3,000トークンにとどまる（Opus lowのC280の合計の約0.4%）。
- 変更を伴うケースでは、規則を取得するために、指示ファイルを読む応答が必要になる。F06のように、存在確認と取得を別の応答に分ける実行が増えれば、リクエスト数が増える。
- 規則を複数の局所の指示ファイルへ置くと、触れた対象の数だけ本文が重なる。

結論：**案4も`candidate_not_created`とする。** 減る分が変更を伴わないケースに限られ、見込みが小さい。

## 残っている未解決の課題

- **Sonnet lowの読み取り側の増加（約43,000トークン、C284の増加の約38%）の原因。** 検証の三項で、検証の出力以外の読み取りが増えた理由は、特定できていない。5回のばらつきの内にある可能性も残る。
- **Sonnet lowで、C289から広がった前後の文脈つき検索。** C291で10KB以上の検索結果は8件で、開始時のまとめ読みの呼び出し（複数のファイルの全文取得を含む）と、試験ファイルへの`-B2 -A8`と`head -300`が主である。この広がりは、C289の「検索と同じ呼び出しで本文まで返す」が許している「取得して返す範囲」の大きさと関係しうるが、範囲の上限を示す辺は、まだ特定できていない。
- **固定コストの大半は、ルートの指示ファイルの大きさにある。** 台帳の結論のとおり、意味を保って縮められる量は141バイトで、規則の削除はSol Lowで閉じた経路を再び開く。この制約の内側で動かせる辺は、見つかっていない。

これらは、解決済みにも、検討終了にもしない。

## 次に行う作業

Candidateを作らず、読み取り専用の分析で、次の二点の辺を特定する。

1. **C284の読み取り側の増加の内訳。** C280とC284のSonnet lowの70件ずつについて、読み取り系のコマンド（`cat`、`sed`、`grep`、Read）の種類別に、結果の大きさと持ち越しを比べる。三項と、この増加を結びつける経路が観測できるかを確かめる。観測できなければ、ばらつきの内とみなし、この項目は保留する。
2. **前後の文脈つき検索の発生場所。** C289で窓の大きさが2行から10行へ広がった検索を、ケースごとに分け、どの場面（開始時、変更前の調査、検証の前）で発行されたかを調べる。許している記述が特定できれば、その辺を狭める案を、設計の確認事項（項目4〜7）の形で書く。

どちらも新しい計測を発行しない。結果が出た時点で、この記録は書き換えず、別の記録に追記する。

## 判断の限界

- Sonnet 5.5 lowのみ、各段階N=5の1系列である。書き方の変化は、コマンド文字列からの判定で、規則の文との因果は観測できない。
- 持ち越しのトークンは、1バイトあたり0.30トークンの仮定と、リクエスト数の数え直しによる見積もりである。利用量の記録とは直接照合していない。
- Sol Lowの検証の書き方は、C280とC284の絞り方の有無を数えただけで、文ごとの効果は分けていない。
- この記録は採用、release、本体反映を決めない。
