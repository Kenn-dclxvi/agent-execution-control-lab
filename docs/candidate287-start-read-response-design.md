# Candidate287 開始時の読み取りを最初の応答で発行し、読み方を縛らない

2026-10-07。Candidate作成前に固定する設計と計測条件。

## 目的と役割

C286の開始側の指定は、GPT-6.1 Sol Lowではトークンと経過時間を減らした（累積N=20、全280件が品質4）。一方、Claude Code Opus 5.5 mediumではC280比でトークンが+25.56%増えた（[結果](../evaluations/results/claude-opus55-c286-standard14-n5-cli2288_2026-10-07.md)）。C286の指定から、Opusでコストを増やした部分を取り除き、Sol Lowで効いた部分を残す。

C286を親にして修正を重ねず、最後に両方の条件で問題を起こしていないC285（`the-caption-3ce91a4-repository-read-scope-r1`）を直接の親とする。C286の三項は追加せず、その代わりに下記の三項を追加する。C286はSol Lowでの効果とOpusでの反例を示す参照として扱う。実行担当はroot。root以外の18対象とC285の既存本文をバイト一致で維持する。

## Opusでコストが増えた経路

C280とC286のOpus 5.5の保存transcriptを比べた（[分析の記録](../evaluations/results/c286-opus55-start-read-volume-analysis_2026-10-07.json)、各70件）。

| 変更前の区間（70件の合計） | C280 | C286 |
| --- | ---: | ---: |
| モデルの応答 | 249回 | 172回 |
| ツール結果の量 | 650KB | 1,137KB |
| 範囲を指定した読み取り | 39回 | 18回 |
| 同じファイルの読み直し | 12回 | 18回 |
| 切り詰められた出力の保存ファイルの参照 | 2回 | 13回 |

C286の指定によって、変更前の応答は31%減った。開始時の確認と読み取りを最初の応答に集める部分は、Opusでも働いている。増えたのは読み取る量である。C280のOpusは`sed -n`などで範囲を絞って読んでいた。C286のOpusは、「一つの呼び出しの中で読む」という指定に従い、名指しされたファイルを一回の`Bash`でまとめて`cat`した。Claude Codeは大きな`Bash`出力を切り詰めて保存ファイルへ回すため、モデルは保存ファイルを参照したり、同じファイルを`Read`で読み直したりした（例：F02 `c514fd95b6fe4e0dac73e5e99b792778`では、4ファイルを`cat`した後、同じ4ファイルを`Read`で読み直した）。Claude Codeでは、読み込んだ内容がその後のすべての応答でキャッシュとして再処理されるため、変更前に増えた量がトークン全体を押し上げた。

Sol Lowでも、A02で最初の呼び出しの出力が約3倍になり、トークンが増えていた。読み取りを一つの呼び出しに詰め込む形は、モデルによらず読み取り量を増やす方向に働く。

## 追加原文

root `AGENTS.md`の「実行制御」の末尾へ、次の三項を追加する。

- 依頼が名指ししたファイルやコミットを変更前に読む場合は、開始時の確認と同じ、最初にツールを呼び出す応答の中でその読み取りを発行する。読み取りは同じ応答の中で複数のツール呼び出しに分けてよく、ファイルのどの範囲を読むかは指定しない。それらのファイルがあるディレクトリと上位のディレクトリの指示ファイル（`AGENTS.md`）も、存在するものを同じ応答の中で読み、存在を確かめるためだけに応答を分けない。
- 依頼が開始時の確認より前の調査や操作を禁じている場合は、開始時の確認と読み取りを一つの呼び出しにまとめ、確認を先に実行する。結果が依頼の停止条件に当たる場合は、読み取りを実行せずに結果を返す。
- 前の二項は読み取りを新しく許可しない。成果が決まっていない間に調査を始めない規則は、そのまま適用する。最初の応答の結果を見て初めて決まる読み取り対象は、次の応答でまとめて読んでよい。

## C286からの変更点

| 項目 | C286 | C287 |

## 作成前の確認事項

1. **比較基準と正常な最短経路。** 直接の親はC285。正常経路は、依頼が指定した開始時の確認と、名指しされたファイルと指示ファイルの読み取りを最初の応答で発行し、方針を固めて変更し、検証と確認を一つの呼び出しで終えることである。
2. **保存traceで確認した問題経路。** 二つある。一つは、C285のSol Lowで、名指しされたファイルを2回目以降の呼び出しで初めて読んだrunが47 / 55件あったこと（[分析](../evaluations/results/c285-start-read-split-analysis_2026-10-07.json)）。これはC286で3 / 55件まで減った。もう一つは、C286のOpusで、まとめて読むために読み取り量が75%増え、切り詰めと読み直しが増えたことである（上表）。
3. **既存の記述やTaskSpecでは防げない理由。** C285までの本文とTaskSpecは、開始時の確認を最初に行うことと読み取りの範囲を定めているが、読み取りを発行する応答の位置を定めていない。C286の指定は応答の位置を定めたが、呼び出しの単位まで固定したため、読み方を変えてしまった。
4. **追加する条件の全件。** 上記の三項だけである。既存の文は変更しない。担当、ラベル、新しい判断項目は追加しない。
5. **禁止行動、開放経路、閉じる境界と反証。** 禁止行動は、名指しされたファイルを変更前に読むとき、その読み取りを最初にツールを呼び出す応答より後に回すこと、または指示ファイルの存在確認だけのために応答を分けることである。適用場面は「名指しされたファイルを変更前に読む」という観測できる事実で決まる。呼び出しの分け方、読む範囲、ツールの種類は指定しないため、Claude Codeで`Read`を並べる形も、Codexで一つの呼び出しにまとめる形も、どちらも違反にならない。第二項の「依頼が確認前の調査や操作を禁じている」は、TaskSpecの停止条件の文言で決まる（F10の2ケースの「調査せず停止」、F05の2ケースの「追加操作せず停止」）。TaskSpecが変更や必須コマンドだけを禁じている場合（F01〜F04、F06〜F08）には、第二項は適用されない。プロンプトは実行を物理的に強制しないため、不可分性は主張しない。
6. **維持する正常経路。**
   - 成果が未確定の経路（A01）と、範囲外として変更しない経路（F05の2ケース）には、第三項によって読み取りを持ち込まない。
   - 確認前の調査を禁じる依頼（F10の2ケース、F05の2ケース）では、第二項により、停止条件に当たれば読み取りを実行しない。
   - 名指しされたファイルの内容から初めて決まる読み取り（A02で正本の記述から正規の対象を決める場合など）は、次の応答で行える。
   - 読む範囲を絞ることも、ファイル全体を読むことも妨げない。大きな出力を避けるために呼び出しを分けることもできる。
   - C284の変更後の検証の指定と、C285のリポジトリの範囲の指定は、そのまま維持する。
7. **新しく増える判断と対象外への影響。** 新しい判断は、第二項の適用を依頼の停止条件の文言から決めることだけである。これは依頼を読む段階で既に必要な判断であり、モデルの必要性の判定には当たらない。F05の範囲外ケースで、名指しされた`README.md`を読むrunがSol LowのC286で20件中16件あった。第三項はこれを禁じないため、この副作用は残り得る。
8. **評価ケースと比較条件。** 二つのモデル条件で、それぞれStandard14全14ケース各N=5の計70件を測る。

   品質、全エージェントトークン、経過時間の3 KPIで判定する。原因の診断として、変更前のモデルの応答、変更前のツール結果の量、範囲を指定した読み取り、同じファイルの読み直し、切り詰められた出力の参照を、[Opusの分析](../evaluations/results/c286-opus55-start-read-volume-analysis_2026-10-07.json)と同じ方法で両モデルについて集計する。名指しされたファイルを最初の応答より後に初めて読んだrunを、Codexはrolloutの応答単位、Claude Codeはassistant messageの単位で数える。C284とC285の診断（変更後の検証の一括実行、リポジトリの外の読み取り）も続ける。Claude Codeでは評価基盤が必須の検証コマンドを個別の`Bash`で実行するよう指示しているため、C284の指定はOpusでは基盤の指示と衝突したままである。この衝突は今回の変数に含めない。
9. **停止条件。** 互換条件の不一致や未確認があれば、各モデル条件の一件目の発行前に停止する。外部失敗だけ同じ枠で固定上限内に再試行し、待ち行列が分かれた場合は実行時間帯を記録する。各70件を完了して判断し、自動で追加反復しない。品質を維持し、トークンと経過時間がともに減った場合だけコスト改善の方向とする。片方でも増えた場合は、その指標の退行として記録する。二つのモデル条件の結果を合算せず、相殺もしない。採用、本体反映、方式の修正による再試験は行わない。

## 判断の限界

Sol Lowでは、C286が一つの呼び出しにまとめたことで得た削減の一部が、呼び出しを分けてよくしたことで失われる可能性がある。Opusでは、まとめて読む形が減っても、変更前の応答が増えて削減分が相殺される可能性がある。比較相手のOpus 5.5のC280は2026-10-06の測定であり、時間帯による応答速度の差を分離していない。この設計は作成後に結果へ合わせて改訂しない。
