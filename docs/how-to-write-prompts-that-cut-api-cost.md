# AIの無駄足を止める4つの判断ルール

## 結論

AIへの指示で大切なのは、細かい手順を全部書くことではありません。

**AIが迷いやすい4つの場面で、「進んでよい条件」と「止まる条件」を書きます。**

まず、考え方の核はこの4文です。

```text
- 人が決める結果がないなら、聞いて止まる。
- 直し方が全部そろうまで、変更しない。
- 未完了の成果を決める調査だけをする。
- 確認を先に決め、結果がそろったら終わる。
```

もう少し具体化して、そのまま指示へ入れられる形にすると、次の4文です。

```text
- 仕様を決めるとき: 利用者が決めるべき結果が書かれていないなら、コードやテストを調べず、その結果だけを質問する一方、ファイルの場所や実装方法が分からないだけなら、プロジェクト内の情報から自分で決めて進める。
- 変更を始めるとき: 必要な成果をすべて挙げ、それぞれをどこでどう直し、何を壊さず残すかまで一つの方針にできた場合だけ変更を始め、どれか一つでも分からないなら変更しない。
- 調べるとき: 調査は未完了の成果を決めるために必要なものだけに絞り、先の結果で調べる内容が変わらないものはまとめて行い、実装方法探し・決定済み事項の再確認・念のため・報告用には行わない。
- 作業を終えるとき: 変更後は必要なテストと差分確認を先に一式決めて順に実行し、失敗したらそこで止まり、すべての結果が揃ったら一度だけ完了を判断して追加確認しない。
```

先に限界も言っておきます。

**この4文だけで、AIが毎回そのとおりに動くわけではありません。**

指示なしとの比較では、「人に結果を聞く」と「調査を絞る」は実際に選ばれ方が変わりました。一方、「全部分かってから直す」と「確認を決めて終わる」は指示なしでも同じ動きが出る場面があり、4文だけの効果とは言い切れません。

後者の2文は、単独比較では追加効果を判別できませんでした。ただし、指示に意味がないと確認できたわけでもなく、ほかのルールと組み合わせた効果は未検証です。

つまり、これは完成済みの万能プロンプトではなく、AIの判断を望ましい方向へ動かすための最小形です。

## 4文なのに、実運用版はなぜ約10kあるのか

[実際に採用されたプロンプト](https://github.com/Kenn-dclxvi/the-caption/blob/3119a91d3fad63180884f80ac6b742fbae328afe/AGENTS.md)は、10.5KBあります。

これは実例であり、そのままコピーしても、別のAIや別の仕事で同じ挙動になるとは限りません。

4文は、実運用版を短くしたものではありません。**何を書けばAIの判断が動くのかを理解するための、考え方の骨組みです。**

| 4文の役割 | 実運用版で追加しているもの |
| --- | --- |
| 人が決める結果と、AIが調べる方法を分ける | 誰が値を決めるか、何を根拠に確定するか、未確定中に何を禁止するか |
| 全成果を決めてから変更する | 成果、変更箇所、維持条件、担当、複数作業の関係を別々の状態として管理する仕組み |
| 必要なことだけ調べる | 調査を許可する条件、結果が影響する作業、追加調査を認める例外 |
| 確認を決めてから終える | テスト順、失敗時の停止、実行中の待機、再確認を認める条件、復旧回数 |

約10kの正体は、説明を水増しした文章ではありません。4文だけでは曖昧な「決まった」「必要」「終わった」を、実行中に判定できる条件へ分解したものです。

短い4文は、まず行動を動かすための入口です。実運用版は、たまに起きる勝手な推測、部分修正、調査の再開、成功後の追加確認まで制御対象にするための契約です。

要するに、こういうことです。

**人にしか決められないことは聞く。全部分かってから直す。必要なことだけ調べる。終わったら終わる。**

## この4文で何が変わるのか

| 判断する場面 | よくある無駄足 | 4文を入れた後の動き |
| --- | --- | --- |
| 仕様を決めるとき | AIが色や表示内容まで勝手に決める。または、ファイルの場所まで利用者へ質問する | 人が決める結果だけを質問し、実装方法はAIが調べる |
| 変更を始めるとき | 分かったファイルから直し始め、関連する変更を落とす | 必要な成果と変更方針が全部そろってから直す |
| 調べるとき | 念のための検索、同じファイルの再読、決定後の方法探しを続ける | 未完了の成果を決める調査だけを行う |
| 作業を終えるとき | テストが通った後も、確認や再実行を思いつくたびに追加する | 必要な確認を先に決め、結果がそろったら一度で終了する |

## 1. 仕様を決めるとき

利用者が決めることと、AIが調べて決めることを分けます。

たとえば「ボタンを赤と青のどちらにするか」は利用者が決めます。一方、「どのCSSファイルを直すか」はAIがプロジェクト内を調べて決めます。

この区別がないと、AIは利用者の好みを勝手に推測したり、逆に自分で調べられることまで質問したりします。

## 2. 変更を始めるとき

一部だけ分かった状態で、編集を始めさせないためのルールです。

たとえば「画面表示、保存処理、テスト」の3か所を直す仕事なら、3か所の直し方と残す動作を先に決めます。一つだけ分かった段階では、まだ変更しません。

これで、「画面だけ直して完了」といった部分的な修正を減らしやすくします。

## 3. 調べるとき

調査を始める前に、「この結果で、まだ終わっていない何が決まるのか」を考えさせます。

答えがないなら、その調査はしません。前の調査結果を待っても次に調べる内容が変わらないなら、最初からまとめて調べます。

これで、念のための検索、決定済み事項の再確認、報告を厚くするだけの読み直しを減らしやすくします。

## 4. 作業を終えるとき

変更が終わってから、確認方法を一つずつ思いつかせないためのルールです。

必要なテストと差分確認を先に決めます。途中で失敗したら止まり、全部の結果がそろったら一度だけ完了を判断します。

これで、「もう終わっているのに、念のためもう一回」を減らしやすくします。

## 普段の作業に当てはめる

| 作業の場面 | 使う判断ルール |
| --- | --- |
| 依頼を読み、足りない情報を確認する | 仕様を決めるとき |
| 修正する場所と方法を決める | 変更を始めるとき |
| ファイル、仕様、テストを調査する | 調べるとき |
| テストし、完了を判断する | 作業を終えるとき |

この表は、どこで各ルールを思い出すかを示したものです。

実際には工程名ではなく、AIがいま何をしようとしているかで判断します。変更後でも、修正結果を確かめるための確認は必要です。変更前でも、答えが決まった後の念のため検索は不要です。

## これだけ覚えてください

長いプロンプトを書くこと自体が目的ではありません。

**AIが迷う場面に、進む条件と止まる条件を一文ずつ置く。**

これが、品質を落とさずにAIの無駄足を減らす、具体的なプロンプトの書き方です。
