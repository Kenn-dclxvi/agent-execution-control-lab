# C284の開始側の経路分析と移植の単位

2026-10-07。[経過時間の分解](c284-elapsed-time-decomposition-r1.md)で、C284とC147の応答回数の差が最初の変更より前の区間に残ることを確認した。この区間の外側呼び出しを、C147（9月30日）、C280、C284のGPT-6.1 Sol Low・Standard14 N=5の保存rolloutで比較した。新しいモデル実行は行っていない。

## 結論

変更前の区間の差（C284とC147で35回）は、性質の異なる二つの経路でおおよそ半分ずつ説明できる。リポジトリの外を読む呼び出しが18回、それ以外の差が17回である。

1. **作業対象のリポジトリの外を読む経路。** 意図しない操作であり、許可の境界で閉じる対象である。
2. **開始時の確認と、依頼が名指ししたファイルの読み取りが、別々の外側呼び出しに分かれる経路。** コストを生む経路であり、C147の開始側（`DECISION_BOUNDARY`）に対応する。

二つは独立に変更でき、別のCandidateとして扱う。設計原則の最優先に従い、意図しない操作を閉じる1をCandidate285とし、2はその結果を受けてCandidate286として固定する。

## 経路1：リポジトリの外の読み取り

リポジトリの外を読んだrunは、C147が0 / 70件、C280が12 / 70件、C284が9 / 70件だった。すべてF06、F07の正規runner、F08で、これらのTaskSpecは「runnerのstart-identity gateがfailedなら停止」と定めている。

どのrunも同じ流れをたどった。最初の呼び出しで`*identity*`や`*gate*`の名前のファイルを検索し、見つからないと親ディレクトリを一覧して、試験基盤の`../case.json`を読んだ。例として、C284 F08 `9daebfe428e4499c8f765af897d4835b`は呼び出し2で`ls -a ..`、呼び出し3で`cat ../case.json`を発行してから変更へ進んだ。C280 F08 `694346e9c773454fa2aa1dd4b3d0f560`も同じである。`case.json`の中身は依頼と同じTaskSpecとfixtureの識別情報で、採点の正解は含まない。モデルは新しい情報を得ずに、2〜3回の呼び出しと応答を追加していた。

この操作を許しているのは、C280第1項の「対象の場所や具体的な実施方法が未確認なだけなら、利用可能な情報や環境を確認し、自分で決めて進める」である。確認してよい範囲が依頼とリポジトリに限られていないため、依頼が触れている外部の判定を探しに行ける。C147は証拠の取得を既定で禁止しており（`EVIDENCE_GATE`）、外を読んだrunは0件だった。

閉じ方は、情報を確認してよい範囲を、依頼、適用中の指示、作業対象のリポジトリへ限定することである。コマンドの実行（`node --version`など環境の能力の確認を含む）は読み取りと区別し、制限しない。詳細は[Candidate285の作成前設計](candidate285-repository-read-scope-design.md)に記す。

## 経路2：開始時の確認と読み取りの分割

C147は、開始時の確認（pwd、HEAD、status）と、依頼が名指ししたファイルや適用される指示ファイルの読み取りを、最初の一つの呼び出しで行うことが多い。F06の中央値はC147が1回、C284が4回、F01はC147が1回、C284が2回だった。C284 F01 `it1`では、呼び出し1で開始時の確認とファイル検索を行い、呼び出し2で指示ファイルと対象ファイルを読んでいる。対象のパスはTaskSpecに書かれているため、検索の結果を待つ必要はない。

この経路は意図しない操作ではなく、分割は規則に違反しない。設計原則の「処理方法を指定できる条件」に沿って、無条件で観測可能な指定として扱う。次の点を守る。

- 読み取りの許可を新しく与えない。成果が未確定の間に調査を始めないC280第1項は維持し、A01・F05の経路へ読み取りを持ち込まない。
- 開始時の確認の結果が依頼の停止条件に当たる場合（未コミットの変更など）は、同じ呼び出しの中で読み取りを実行せずに返す。F10のように、確認前の調査を禁じる依頼にも反しない形にするためである。
- 名指しされたファイルの結果を見てから決まる追加の読み取り（正本の記述から次の対象を決める場合など）は、別の呼び出しで行ってよい。
