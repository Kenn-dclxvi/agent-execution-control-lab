# C280〜C300の処理の適切さの分類（r1）

2026-10-09。C300のSonnet low累積N=20の結果を受けて、利用者から「安い高いを基準にせず、適切に判断・処理させることが目的」と指摘された。これを受けて、C280・C297・C298・C299・C300の保存traceを、トークンではなく、TaskSpecが求める処理を適切に行ったかで分類し直した記録。新しいモデル実行はしておらず、Candidateは作成しない。採用、release、本体反映は決めない。

## 結論

- **不適切な処理の大部分は、Sonnet lowのA02に集中しており、C280の時点からあった。** A02のTaskSpecは既存testでの確認を求めるが、Sonnet lowは多くの実行で、テストを成功させないまま報告していた（C280で5件中4件）。
- **その主な原因は、確かめていない環境の制約を理由に、求められた確認をやめたことである。**
  - 最初に`python`でテストを実行し、`python`がない、またはpytestが入っていないという結果から、「pytestがこの環境にない」と結論して報告していた。
  - 実際にはリポジトリに`.venv`があり、`.venv/bin/python`でテストは通る。
  - C300の1件は、`sed`の失敗で後ろの`.venv/bin/python`のテストが一度も動かなかったのに、「`.venv`もない」と報告していた。
- C298の一項目（「必須の確認コマンドがすべて成功した結果を受け取った後は、コマンドを発行せずに報告する。」）を含む条件では、テストを通してから報告する実行が増えた（C298で5件中5件、C300で20件中12件）。ただしC300でも7件は、同じく確かめていない環境の制約で確認をやめていた。
- Sol Lowでは、TaskSpecが求める確認を終えずに報告した実行は見つからなかった。Sol Lowの不適切な処理は、短い待機時間での待機の繰り返しと、確認の成功後の状態確認であり、これらはC299とC300で閉じた。
- **訂正：** C298とC300の診断では、F06とF07正規ランナーで必須の確認の後に出した`git diff --check`と変更pathの確認を、「成功後の状態・差分の確認だけの応答」と数えていた。F06のTaskSpec（F06-C3）とF07正規ランナーのTaskSpec（F07-C3）は、これらを確認として明示的に求めており、余分な操作ではない。

## 方法

- 対象：Sonnet lowのC280、C297、C298、C299（各70件）、C300（累積280件）。Sol LowのC280、C297、C298、C299、C300（各70件）。
- 各ケースについて、TaskSpecの`validation_conditions_and_non_machine_risk`が、確認するコマンドとして明示しているものを、モデルが実行すべき確認とした。「変更pathの確認」「最終diff」のように、評価の仕組みでも判定できるものは除いた。

| ケース | モデルが実行すべき確認 |
| --- | --- |
| A02 | `bash -n run.sh`、既存test |
| F01、F02、F03 | focused gate、full gate |
| F04 | `npm ci`、`npm run lint`、`npm run build` |
| F06 | 二つのpytest、`git diff --check` |
| F07正規ランナー | `bash -n run.sh`、`main_verify.sh`、`git diff --check` |
| F07出所の対 | 指定の`python3 -c`、`git diff --check`、`git diff --name-only` |
| F08 | `git diff --check` |
| F10の2ケース | 終了時の`git status` |
| A01、F05の2ケース | なし（変更しない） |

- 確認は、最後の変更より後に成功した場合だけ「完了」とした（`npm ci`は依存の導入なので変更前でもよい）。成功の判定は、pytestでは「N passed」があり失敗の表示がないこと、`bash -n`では構文エラーの表示がないこと、などの簡易な文字列判定である。
- Sol Lowは、待機の対象を変数に保存して待つ実行や、ループの変数経由で実行するコマンドがあり、結果をコマンドに結びつけられないことがある。評価条件の必須コマンドの組は、採点が成功を確かめている（全件4点）ため、Sol Lowでは採点が見ていない確認だけを数え、「未完了」と判定された実行は実物を確かめた。

## 結果

### TaskSpecが求める確認を終えずに報告した実行

| 条件 | Sonnet low | Sol Low |
| --- | --- | --- |
| C280 | A02 4 / 5 | 0 |
| C297 | A02 4 / 5 | 0 |
| C298 | 0 | 0 |
| C299 | A02 4 / 5 | 0 |
| C300 | A02 8 / 20、F10 3 / 40 | 0 |

- Sol LowのA02で「未完了」と判定された実行（C280で3件など）は、実物を確かめると、いずれも変更後に「326 passed」を確認してから報告していた。集計の取りこぼしである。
- Sonnet lowのF10の3件（C300）は、終了時の`git status`を実行していなかった。C280では0件だった。

### Sonnet lowのA02の内訳

| 条件 | 変更後にテストを通した | 環境の制約を理由に確認をやめた | 変更前にだけテストした |
| --- | ---: | ---: | ---: |
| C280 | 1 | 3 | 1 |
| C297 | 1 | 4 | 0 |
| C298 | 5 | 0 | 0 |
| C299 | 1 | 4 | 0 |
| C300（累積20） | 12 | 7 | 1 |

- 「環境の制約を理由に確認をやめた」実行は、いずれも報告でテストを実行できなかったことを正直に書いている。誤りは報告の正直さではなく、制約の結論にある。`python`がない、pytestが入っていないという一つの実行方法の失敗から、テストを実行できないと結論し、リポジトリの`.venv`を確かめていない。
- 最初の実行方法の誤り（`python`の未検出、pytestの未導入）は、条件によらず多くの実行で起きていた（C280で5件中3件、C300で20件中17件）。Sonnet lowが最初に読み込む指示ファイルはルートの`CLAUDE.md`だけで（A02の20件すべて）、テストの実行方法を書いた`tests/AGENTS.md`は読み込まれていない。同ファイルの記述（`pytest tests/ -v`）も、仮想環境を有効にした前提である。

### 確認の成功後のコマンド

TaskSpecが求める確認をすべて成功させた後に、コマンドや読み取りを出した応答は、1反復あたり、Sonnet lowでC280 1.4回、C297 2.2回、C298 0.6回、C299 0.4回、C300 0.5回、Sol LowでC280 9.2回、C297 7.2回、C298 4.2回、C299 6.6回、C300 0.6回だった。Sol Lowでは、C298とC299の一項目をともに含むC300で最も少なかった。F06とF07正規ランナーの`git diff --check`はTaskSpecが求める確認であり、ここには含めていない。

## 次の設計の対象

1. **Sonnet lowのA02：確かめていない環境の制約を理由に、求められた確認をやめる経路。** モデルは、一つの実行方法の失敗を、確認を実行できないことの根拠として報告できる。閉じるべきなのは、この失敗から「実行できない」へ進む許可である。テストを通すまで続ける行動ではない。
2. **最初の実行方法の誤り。** 実行方法を確かめずに試行へ進む経路。1を閉じれば、誤った方法の試行は確認の途中の一段階になるが、正しい方法を最初から選べるかは、実行方法の情報がどこからモデルへ届くかによる。テストの実行方法を書いた指示ファイルは、A02では読み込まれていない。
3. Sonnet lowのF10で、終了時の確認をしなかった実行（C300で3件）。C298の一項目の「コマンドを発行せずに報告する」が、確認の前に報告へ進ませた可能性がある。

これらを閉じる案は、[設計原則](prompt-control-design-principles.md)の作成前の確認事項に従って、別の設計記録で検討する。

## 追記：A02の確認の中断の位置づけ（同日）

利用者と相談し、次のとおり扱う。

- Sonnet lowがA02で最初に実行したテストのコマンドは、`.venv`を使わない`python -m pytest`が多かった（C298とC300で25件中21件、C280とC299で10件中6件）。AIは、仮想環境が有効か、`python`とpytestがそのまま使える環境を前提に、最初のコマンドを実行する。
- 評価環境では、その前提が成り立たない。Sonnet lowの実行では、PATHに`python`がなく、`python3`にはpytestが入っておらず、`.venv`も有効になっていなかった。F01〜F06はTaskSpecが`.venv/bin/python`を明示しているため問題にならず、実行方法を指定しないA02でだけ現れた。
- したがって、A02の確認の中断は、主に評価環境に由来するものとして扱い、プロンプトの設計対象（次の設計の対象の1と2）から外す。環境の欠けをプロンプトで埋めることはしない。
- 確かめずに「実行できない」と結論する判断の誤り（`sed`の失敗で`.venv`のテストが動かなかったのに「`.venv`もない」と報告した件など）は、環境とは別の問題として記録に残す。ただし、環境が整えば、この判断が試される場面はほとんどなくなるため、優先度は低い。
- 評価環境の見直しは、このプロンプト比較とは別の作業とする。見直した場合は、保存済みの結果と比較できない新しい評価系列として、基準から測り直す。

### CodexとClaude Codeで`.venv`の扱いが違う理由（同日の確認）

- THE-CAPTIONには`configs/zsh/the-caption.zsh`がある。冒頭に「`~/.zshenv`から、シェルがこのリポジトリに入るたびに読み込む」とある。このファイルは、`python`、`python3`、`pip`、`pytest`を`.venv`のものへ振り向ける関数を定め、`.venv/bin/activate`を読み込む。
- 計測に使ったMacの`~/.zshenv`には、作業ディレクトリのリポジトリにこのファイルがあれば読み込む処理がある。`.zshenv`は、zshが対話でなくても必ず読む設定ファイルである。
- Codexは、計測の実行プロセスの環境をそのまま引き継いで起動しており（`SHELL=/bin/zsh`）、コマンドをzshで実行する。このため、`python3 -m pytest`は`.venv`のPythonで動き、A02でも成功していた（Sol LowのC280・C300のA02で、`python3 -m pytest`がそのまま「326 passed」）。この経路は、ログからの推定を含む。
- Claude Codeは、評価用の起動処理（`scripts/run_claude_evaluation.py`の`minimal_environment`と、計測の条件の`process_environment`）が、PATHを`/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin`、シェルを`/bin/bash`に固定して起動している。bashは`.zshenv`を読まないため、`.venv`は有効にならず、`python3`は`/opt/homebrew/bin/python3`（pytestなし）になる。
- したがって、A02の確認の中断がSonnet lowだけに現れたのは、モデルの違いだけでなく、二つのエージェントの実行環境の違いによる。Codexの環境は、計測したMacの個人のシェル設定に依存しており、その点で隔離されていない。
- どちらに揃えるか（Claude Codeもzshと`.zshenv`で起動するか、両方とも個人のシェル設定から切り離して`.venv`を明示的に有効にするか）は、評価環境の変更であり、別の作業として扱う。

## 判断の限界

- 確認の成否は、コマンドの出力の簡易な文字列判定による。Sol Lowは、変数経由の待機や実行を結びつけられないことがあり、「未完了」と判定された実行を実物で確かめて除いた。
- TaskSpecの確認のうち、評価の仕組みでも判定できるものを除いた。その線引きは、この記録での判断である。
