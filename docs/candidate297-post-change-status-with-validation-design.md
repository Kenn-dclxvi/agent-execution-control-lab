# Candidate297 変更後の状態と差分の確認を、必須の確認と同じ応答で発行する

2026-10-09。Candidate本文の作成前に固定する設計記録。[設計原則](prompt-control-design-principles.md)の全文を読み、「Candidateを作成する前の確認事項」の項目1〜9に対応させた。判定は[判定基準の記録](shared-instruction-evaluation-criteria-r1.md)に従う。根拠は[C280のトークンを試験が求める操作とそれ以外に分けた分析](c280-test-required-vs-excess-r1.md)である。この記録ではbundleを作成しない。

## 目的と役割

- 系列：汎用指示の改善系列。比較の基準かつ直接の親はC280（`the-caption-3ce91a4-execution-control-outcome-binding-r1`）。
- 主なセル：GPT-6.1 Sol LowとClaude Code Sonnet 5.5 low。
- 必要な効果：品質を保ち、両セルでC280よりトークンと経過時間を増やさない。両方が減れば、コスト改善の方向とする。
- 対象：両セルに共通して、試験の条件の内側で減らせると分かった一点、すなわち、必須の確認の直後に、作業ツリーの状態と差分の確認だけを独立した応答として出す流れ（1反復あたりSonnet low 2.2回、Sol Low 2.6回）。
- 変更対象：root `AGENTS.md`に一項目を加えるだけ。C280の4項目は文言も書式も変えない。他の18対象はC280とバイト一致を保つ。全文は1,758バイト（C280は1,470）。

## 1. 比較の基準と、正常な最短経路

基準はC280。変更を伴うケースの正常な最短経路は、開始時の確認と読み取り → 変更 → 必須の確認（状態と差分の確認を同じ応答に含める） → 報告である。TaskSpecは、完了条件として、許可外の変更がないことを求める（例：[F01のTaskSpec](../evaluations/cases/TC-F01-DOMAIN-DUPLICATE-ASSET-KEY/r3/trial-prompt-input.json)の「required validationがpassし、許可外driftがない状態をdoneとする」）。終了時の状態確認は、この完了条件の確認として、試験が求める操作に含まれる。

## 2. 保存traceで確認した問題経路

C280の保存trace（Sol Low `794d02ab…`、Sonnet low `c84fd227…`、各70件）で、最初の変更より後に、必須以外の確認（`git status`、`git diff`、`git diff --check`など）だけを含む応答を数えた（[記録](../evaluations/results/c280-sol61-low-sonnet55-low-excess-response-detail_2026-10-09.json)）。

| 直前の応答 | Sonnet low | Sol Low |
| --- | ---: | ---: |
| 必須の確認 | 2.2 | 2.6 |
| 変更 | 1.0 | 0.4 |
| その他 | 0.2 | 4.0 |

必須の確認の結果を受け取ってから、状態と差分の確認だけのために、もう一度モデルへ戻る流れが、両セルに共通してある。状態と差分の確認は作業ツリーを見るもので、必須の確認の結果には依存しない。この一回の戻りで、次のリクエストの固定分と、それまでの文脈の再処理が生じる。

## 3. 開いている記述と、TaskSpec・正本で防げない理由

C280は、変更後の確認の発行のしかたを定めていない。TaskSpecは、必須の確認コマンドと完了条件を定めるが、状態の確認をどの応答で出すかを定めない。Claudeの課題文は、必須の確認コマンドを1つずつ別の`Bash`呼び出しで実行し、まとめないよう指定している（`scripts/run_claude_evaluation.py`）。状態と差分の確認を、必須の確認コマンドとは別の呼び出しとして同じ応答に含めることは、この指定に反しない。

## 4. 追加する条件の全件

C280の末尾に、C280の箇条書きと同じ書式（`*`）で、次の一項目を加える。

> * 変更後の作業ツリーの状態と差分の確認は、必須の確認コマンドと同じ応答の中で、それとは別のコマンドとして発行する。必須の確認の結果を受け取ってから、状態と差分の確認だけを別の応答で発行しない。

- 第1文は、発行する応答を定める。「それとは別のコマンドとして」は、必須の確認コマンドと一つのコマンドにまとめないことを示し、Claudeの課題文の指定と、品質の判定（必須コマンドごとの終了状態）を保つ。
- 第2文は、閉じる経路（結果を受けてから、状態確認だけのために戻る）を禁止の形で書く。C284とC292の経験から、閉じる経路を名指しする文を省かない。

## 5. 禁止行動、開放経路、閉じる境界、反証

| 項目 | 内容 |
| --- | --- |
| 禁止する行動 | rootが、必須の確認の結果を受け取った後、作業ツリーの状態と差分の確認だけのために、別の応答を発行する |
| 現在の開放経路 | 変更後の確認の発行のしかたが、モデルに任されている |
| 閉じる境界 | 状態と差分の確認を、必須の確認コマンドと同じ応答で発行する。適用は、変更を行い、必須の確認を発行するという確定した事実で決まり、必要性の判定を介さない |
| 正常な処理の保持 | 終了時の状態確認（完了条件）は行われる。必須の確認コマンドは個別に実行され、それぞれの終了状態が残る。必須の確認が失敗して修正した場合は、修正後の必須の確認と同じ応答で、状態と差分の確認を再び発行できる |
| 反証する構成 | 必須の確認の後に、状態と差分の確認だけの応答を出す構成は、第2文に違反し、保存traceの応答の並びで観測できる。必須の確認コマンドと状態確認を一つのコマンドにまとめる構成は、第1文に違反する |

## 6. 維持する正常経路

- Claude Code：必須の確認コマンドは、課題文の指定どおり個別の`Bash`呼び出しで実行する。状態と差分の確認は、同じ応答の別の`Bash`呼び出しとして加える。
- Codex：必須の確認と同じ外側の呼び出しの中で、別のコマンドとして実行できる。
- 必須の確認が失敗した場合の原因の調査（失敗の出力や関連ファイルの読み取り）は、この項目の対象ではない。状態と差分の確認とは別の操作であり、結果を受けてから行える。
- 変更を伴わないケース（A01、F05、F10）には適用されない。

## 7. 新しく増える判断と、変更対象外への影響

- 新しい判断はない。
- 必須の確認が失敗した場合、同じ応答に含めた状態確認は、結果として使われない可能性がある。その費用は、状態確認一回分の出力（小さい）である。
- 必須の確認が複数あり、Claudeで1つずつ別の応答で発行する場合、状態確認をどの応答に含めるかは、モデルに任される。どの応答に含めても、状態確認だけの応答は生じない。
- 固定分：288バイト増える。Sonnet lowで1反復あたり約6千トークン（288×0.3247×64.6）の見積もり。
- 見込み：状態確認だけの応答がなくなれば、Sonnet lowで1反復あたり約2.2回、Sol Lowで約2.6回のリクエストが減る。Sonnet lowでは、作業の終盤の文脈（1件あたり1.5万トークン前後）で、約3万トークン（C280の約4%）にあたる。固定分を差し引くと、約2.4万トークン（約3%）である。これは5回の1反復合計の標準誤差（約2.3万トークン）と同じ程度で、N=5の一回の計測では、ばらつきと区別できない可能性がある。

## 8. 評価ケース、比較単位、比較条件

- セル：Sol LowとSonnet low、各Standard14の全14ケース各N=5の計70件。
- 基準：各セルの保存済みC280（Sol Low `794d02abe894456686eea22e9b6f0fed`、Sonnet low `c84fd22753d248e588e586cb8022ea1e`）。
- 比較条件：C293〜C296と同じ。Sol LowはC289の保存済み登録結果を基準にした比較互換preflight、Sonnet lowはC280・C291のSonnet lowと同じClaude Code 2.1.288、評価コード、権限、tool集合。変えるのはprompt identityだけ。発行前にpreflight receiptを保存し、不一致があれば一件も発行しない。
- 判定：品質を保ち、各セルで全エージェントトークンと経過時間の中央値がともにC280より減った場合だけ、コスト改善の方向とする。一方でも増えた指標は、コスト退行として記録する。セルの間で相殺しない。
- 診断（合否にしない）：必須の確認の直後に状態と差分の確認だけを出した応答の数（両セル）、1実行あたりの要求数、変更を伴うケースの要求数と最小の流れとの差。遵守率は、この計測で初めて確かめる。
- 経過時間：計測した時間帯の影響が大きい（C296で、変更を伴わないケースまで遅くなった）。二つのセルを同じ時刻に発行し、C280との差を本文だけの因果効果と断定しない。

## 9. 停止条件

- 互換条件の不一致、未確認があれば、一件目の発行前に停止する。
- invalid、採点不能、品質の低下は、有効な改善として扱わない。外部失敗だけ、同じ枠で固定上限内に再試行する。有効な4点未満は削除、相殺、再実行しない。
- 各セル70件で判断し、自動で追加反復しない。結果に合わせてこの記録と案文を書き換えない。
- 結果がばらつきと区別できない場合の追加反復は、[再現性の判断方針](reproducibility-decision-policy.md)に従って、利用者と判断する。

## 判断の限界

- 状態と差分の確認の分類は、コマンド文字列による簡易な判定である。
- 見込みの大きさは、C280の保存traceからの概算である。
- この記録は採用、release、本体反映を決めない。
