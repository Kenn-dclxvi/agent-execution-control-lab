# Candidate254 部分read残存経路監査

## 結論

Candidate254で残った1 / 5件は、相互に影響しない確認を意図的に分けた経路ではなく、一回目のread resultだけでは必要な観測値を確定できない範囲を先に発行し、その不足を受けて続きを発行した経路だった。

対象run `342cf77221a14660908dbb7e6cf6cc27`は、開始確認と`App.tsx` 1〜260行のreadを共同発行した後、261〜620行をreadし、そのresultを受け取ってから621〜980行を別model stepでreadした。二つの後続readは同じartifact上の同じ変更判断を満たすための連続取得であり、途中resultで対象、許可、方法、停止条件は変わっていない。

## 既存境界で残った理由

Candidate254の一般則は、結果で次の作業が変わらないと既に分かっている複数確認を同一model stepへ閉じた。しかし、最初から一回では不足する部分readを選べるpermissionは閉じていない。そのため、後半の必要性を前半resultで初めて知ったという解釈を作れる。

Candidate253由来の`EVIDENCE_GATE`には「取得する結果だけでその状態を確定できる場合に限る」とあるが、`一回のresult`と`現在欠けている観測値`の対応が一文内で固定されていない。部分readごとに局所的な未確認状態を作る解釈が残る。
