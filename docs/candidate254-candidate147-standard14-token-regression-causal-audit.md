# Candidate254とCandidate147のStandard14 token退行原因監査

## 結論

Candidate254 Standard14 N=5は70 / 70件でScore `4`を維持したが、Candidate147比でall-agent総token中央値が`+6.29%`、経過時間中央値が`-4.26%`だった。token増加を品質または必要な正常処理の対価とは認めず、`unjustified_token_regression`とする。Candidate254の正式採用を承認せず、追加制御の根拠を調べる側へ進む。

後続のN=20同数比較ではtoken `+9.33%`、経過時間`-6.48%`となった。[制御群別原因分解](candidate254-candidate147-standard14-n20-control-group-causal-decomposition.md)は、F02・F03の追加AI経路だけでなく、F07等でAI応答回数と主要tool経路が同じまま増えたmodel-visible入力の固定費と、A01で不要な開始確認を削減した境界を分離した。さらにC147で出現しなかった経路から逆向きに監査し、F03の開始確認とreadの分離には、C147のoperation class別`result_effect_scope`を復元する根拠があると訂正した。本監査のN=5事実は保持し、現在の改善方向はCandidate254全体のrevertではなく、C147の成立関係の復元と意味保持圧縮を組み合わせた選択的な再構成とする。

増加の中心は、必須試験を発行した処理が完了前にAIへ返り、AIが同じ処理の完了を待つためだけに再度動いた経路である。F03の2 / 5件には、開始状態の確認と、その結果で対象も許可も変わらないreadを別のAI判断へ分けた追加経路もあった。ここでいうAIの再実行とは、途中のtool resultを受け取った後、同じ会話内容とそれまでの結果を入力としてAIがもう一度応答を生成することである。

ただし、途中返却の頻度差をCandidate254のprompt差分へは帰属しない。Candidate147にも同じ途中返却はあり、Candidate254の正本本文も、途中返却後は同じ処理の完了だけを待つ境界を持つ。今回確定したのは追加tokenの直接の使用先であり、その発生頻度を変えたprompt上の原因ではない。

## 調査件数の判断

現時点ではNを増やさず、保存済みの実行結果で原因調査を続ける。ここでいうNは、各ケースを独立に実行した件数である。現在はCandidate254とCandidate147について、F02とF03を各5件ずつ保持している。

N=5では、完了待ちや開始確認後の不要な再判断が将来どの割合で起きるかを精密には推定できない。一方、現在必要なのは発生率の精密化ではなく、観測済みの追加tokenへ対応する、prompt内で新しく閉じられるpermissionまたはdependencyがあるかの特定である。同じpromptの実行件数だけを増やしても、この因果関係は確定しない。

現在結果だけで、次の事実はすでに確定している。

- Candidate254は70 / 70件でScore `4`を維持したが、正式採用のcost条件を満たさない。
- F02とF03の完了待ちは新しい成果または品質を生まず、追加tokenの直接使用先である。
- F03には完了待ちも開始確認後の分離もない104,287 tokenのScore `4` runがあり、追加costが品質に不可欠ではない。
- F03の開始確認とreadの分離へ同じ行動条件を追加しても経路は閉じられない。ただし、C147ではoperation class別`result_effect_scope`が分離を0 / 15件にしており、C254で省かれたこの関係の復元は別の改善候補になる。
- 完了前返却はCandidate147にもあり、発生頻度の差をCandidate254のprompt差分へ帰属できない。

過去のCandidate107 F03 100件でも、cell ID付きの完了前返却は6件発生し、その6件はすべて同じ処理の完了待ちへ進んだ。件数を100まで増やすことで完了前返却の存在と頻度は詳しくなったが、特定の待ち時間をpromptへ追加して一回で完了させる十分条件は得られなかった。また、Candidate125とCandidate145のF01 / F02 / F03各5件では、開始確認とcontent readを別のAI判断へ分けたことが共通のtoken増加と対応していた。今回のF03にある約20,000 tokenの追加再判断は、この既存証拠と同じ構造である。

したがって、今Nを増やすと「同じ不安定な経路が何件増えるか」は分かるが、「どの追加制御が正しいか」は分からない。Candidate254の不採用判断もすでに変わらないため、追加実行のtokenと時間を使う合理性がない。

N追加を再検討するのは、保存traceの調査から次の全条件がそろった場合に限る。

1. Candidate254本文に従ったまま到達できる不要な経路を一つ特定する。
2. その経路へ至るpermissionまたはdependencyと、必要な正常経路を壊さず閉じるprompt差分を固定する。
3. 追加Nで観測する値と、その値によって採用、棄却または設計選択が変わる境界を実行前に固定する。
4. Candidate147とのKPI比較が必要なら、prompt以外の条件を事前照合し、同じ評価範囲を比較可能な形で発行する。

現在状態は`current_trace_investigation_selected / n_extension_not_authorized / prompt_controllable_route_not_yet_bound`とする。

F03の内訳は、完了待ちによる大きなtoken使用と、2 / 5件での不要な開始確認後の再判断で説明できる。どちらも追加品質を生んでおらず、完了待ちも開始確認後の再判断もなかったCandidate254 runがCandidate147中央値と同じtoken水準でScore `4`を達成している。F03はCandidate254固有の品質コストではなく、同じpromptから実行経路が安定して再現されなかったことによる退行である。

Candidate254で開始確認とreadを同じAI応答から発行したiteration 2は、4回のAI応答で104,287 tokenだった。Candidate147中央値iteration 3も同じ4回で104,320 tokenだった。

この組ではCandidate254のprompt本文が長くても、同じ経路全体のtokenはCandidate147と同水準である。F03の退行をCandidate254の固定prompt costでは説明できない。

Candidate254 iteration 1と3は、開始確認と対象readを分離した。分離した二つのAI応答の合計から、共同発行したCandidate254 iteration 2の最初のAI応答19,695 tokenを差し引くと、分離による純増は次のとおりになる。

この差引き値は、実際にそのtoken数で完了したと主張するKPIではない。観測済みtokenを、完了待ち、開始確認とreadの分離、それ以外へ分けた診断である。比較方法によって残差は`-33`から`+1,957`の範囲になるが、実測中央値78,625 token、75.37%の退行とは規模が異なる。大きな退行が品質に必要な変更や検証ではなく、この二つの余分なAI再判断へ集中していることを示す。

F03の完了待ちからは追加制御候補は生じない。同じ実行の未完了返却に対する同期であり、特定の待ち時間や実行方法をpromptへ固定してもterminal返却を保証できない。一方、開始確認とreadの分離からは、同じ禁止の追加ではなく、C147で15 / 15件成立したoperation class別`result_effect_scope`の復元候補が生じる。これは成功runの処理順を転記する案ではなく、先行結果が影響しないreadを待機対象へ入れられる依存関係を閉じ直す案である。
