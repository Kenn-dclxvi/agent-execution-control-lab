# 人間の開発工程を、そのままAIへ移植しない

> 実務者向けExecution Controlシリーズ 7 / 8

## 結論

設計、実装、監査、レビュー、差し戻し。

人間のチームで機能する工程を、そのままAIエージェントの実行順にすると、品質責務と役割の数が一体化します。**人間の工程を捨てるのではなく、守りたい責務を取り出して、AIが観測できる条件へ変換します。**

## 人間の工程は、良い出発点になる

人間の職種を使うと、誰が何を確認するかを理解しやすくなります。最初の導入方法として、プラン担当、実装担当、監査担当、レビュー担当へ分けるのは自然です。

しかし運用を続けると、次の違いが効いてきます。

| 人間の工程で使う考え方 | AI向けに置き換える観点 |
| --- | --- |
| 職種ごとに役割を分ける | 失敗の種類と必要な結果を分ける |
| 経験や所感で確認する | ファイル、差分、終了コードなどの証拠へ結び付ける |
| 情報は自然に共有される | 見せるcontextと見せないcontextを設計する |
| 上位者へ順番にエスカレーションする | 独立した既知の検証はまとめて発行する |
| 全員の合意で完了する | 必要な結果が揃った状態を完了条件にする |

## 役職ではなく、壊れ方から設計する

例えば「監査担当を置く」だけでは、何を防ぐのかが分かりません。

- 必須テストの省略を防ぐ
- 対象外ファイルの変更を防ぐ
- 失敗しているのに完了と報告することを防ぐ
- 実装経緯に引っ張られた迎合的なレビューを防ぐ

これらは別の失敗です。必要な証拠、情報境界、停止条件も異なります。一人の「監査担当」という箱へ戻す前に、失敗ごとの条件へ分解します。

独立した担当が必要な責務は残します。別主体の判断そのものが必要なら、プロンプト上の条件だけで同等とは扱えません。

## 研究の位置づけ

研究の出発点にある人間組織の枠組みは、無自覚な設計ミスではありません。既知のノウハウで短期導入し、そこからAI固有の規律へ移るために意図的に使われていました。研究では、工程仕様の空ファイル化、着手条件への置換、実装確定の終端化などが、個別のcandidateとして記録・測定されています。

ただし、「どの工程がどの判定条件へ移り、どの責務が残ったか」という全体の対応は、複数のcandidateとartifactから技術報告が事後的に構成した解釈です。工程単位の変換全体を一つの計画として設計・測定した記録ではありません。

したがって結論は「人間の開発工程は間違い」ではありません。

**導入のための比喩を、毎回支払う実行経路として固定しない。**

出発点の二層構造と変換後の対応は、[技術報告の3節と11.1節](execution-control-measurement-report.md)を正本とします。

## これだけ覚えてください

工程を一つ追加するときは、「誰を増やすか」ではなく「何が壊れるのを防ぐか」から決めてください。
