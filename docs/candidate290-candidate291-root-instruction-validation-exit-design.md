# Candidate290・Candidate291 ルート指示の再取得と検証呼び出しの終了コードを閉じる

2026-10-08。Candidate本文の作成前に固定する設計記録。[設計原則](prompt-control-design-principles.md)の全文を読んだうえで、C289の保存traceから二つの局所的な経路を特定した。経路ごとにCandidateを一つずつ作り、C290はC289を、C291はC290を直接の親とする。

## 二つのCandidateに分け、試験をまとめる理由

二つの経路は、本文の別の節（開始時の読み取りと変更後の検証）にあり、片方だけを変えても中間状態は不整合にならない。そのため`prompts/AGENTS.md`の規則に従い、一つのCandidateへまとめない。

一方、Opus 5.5の計測はコストが高いため、利用者の判断でOpus 5.5ではC291だけを測る。C291とC289の差は二段階の変更を合わせた差であり、3 KPIの差を各段階へ因果分解しない。これはC286のOpus 5.5計測をC280からの三段階の差として扱ったのと同じである。二つの機序は、別々の観測で診断できる（後述）。

## 基準と正常な最短経路

基準は[C289](../prompts/candidates/the-caption-3ce91a4-scoped-first-return-r1/manifest.json)（`the-caption-3ce91a4-scoped-first-return-r1`）である。正常な最短経路は、最初のツール呼び出しで開始時の確認、名指しされた対象の限定取得、ルート以外の適用される指示ファイルの取得をまとめて行い、変更後は一つの呼び出しで検証を終える経路である。ルートの指示ファイルは、どちらの実行環境でも作業開始時に文脈へ渡されている。

## C290：ルートの指示ファイルを再取得する経路を閉じる

### 保存traceで確認した経路

- Sol LowのC289 N=5では、70件すべての最初の文脈にルートの`AGENTS.md`の本文が入っていた。そのうち59件で、同じ本文がツール結果にも現れた。
- Opus 5.5のC289 N=5では、48件で同じ本文がツール結果に現れた（C280では10件）。[トークン差の分析](claude-opus55-c289-c280-token-analysis-r1.md)では、この重複が、序盤に取り込んだ内容が後続のリクエストへ持ち越される分を押し上げていた。

### 開いている文と、既存の入力では防げない理由

C289の読み取りの節にある二つの文が、ルートの指示ファイルを取得の対象に含めている。

- 「対象のディレクトリからリポジトリのルートまでにある適用される指示ファイルの取得を含める」
- 「適用される指示ファイル…は全文を読む」

TaskSpecは指示ファイルの読み取りを許可しているだけで、取得の対象を定めていない。F10月次も、ルートの`AGENTS.md`を読める範囲として挙げているだけである。採点はルートの指示ファイルの取得を参照しない。したがって、重複取得はC289の本文が要求する操作として残っている。

### 閉じる境界

| 項目 | 内容 |
| --- | --- |
| 禁止する行動 | rootが、ルートの指示ファイル（`AGENTS.md`と、同じ本文を指す`CLAUDE.md`）の本文をツールで取得する |
| 現在の開放経路 | 上の二文が、ルートの指示ファイルを取得対象と全文取得の対象に含めている |
| 閉じる境界 | 取得対象を「ルート以外の適用される指示ファイル」に限定し、ルートの指示ファイルの本文をツールで取得しないと定める。適用は、そのファイルがルートの指示ファイルであるという確定した事実だけで決まり、必要性の判定を介さない |
| 正常な処理の保持 | ルートの本文は作業開始時に文脈へ渡されている。`src/`、`tests/`、`docs/`などの指示ファイルは自動では渡されないため、従来どおり最初の呼び出しで全文を取得する |
| 反証する構成 | `find`の`-exec`、ディレクトリ単位の`cat`、検索などで、ルートの本文を結果に含める構成。いずれも「本文をツールで取得しない」に違反し、ツール結果に本文が現れることで観測できる |

### 変更する文

- 読み取りの節の第3項：「…および対象のディレクトリからリポジトリのルートまでにある適用される指示ファイルの取得を含める。」を「…および対象のディレクトリからリポジトリのルートまでにある適用される指示ファイルのうち、ルートの指示ファイル以外のものの取得を含める。」へ置き換える。
- 読み取りの節の第4項の冒頭：「適用される指示ファイルと、依頼や指示が全文取得を指定した資料は全文を読む。」を、次の二文へ置き換える。「リポジトリのルートの指示ファイル（この文書。`CLAUDE.md`は同じ本文を指す）は作業開始時に渡されているため、その本文をツールで取得しない。ルート以外の適用される指示ファイルと、依頼や指示が全文取得を指定した資料は全文を読む。」

他の文は変えない。

## C291：検証の呼び出しの終了コードと各コマンドの結果のずれを閉じる

### 保存traceで確認した経路

Opus 5.5のC289 N=5で、A02の2件が`a02_abstract_test_evidence_missing`で3点になった。2件とも、試験を含む検証の呼び出しの中で、各コマンドは成功していた（`pytest`は8件成功）。しかし、各コマンドの終了コードを確かめるループの最後の`[ $rc -ne 0 ] && break`が、全コマンド成功時に1を返し、呼び出し全体が失敗として返った。試験を含む呼び出しのうち、こうして0以外で終わったのは、C289で68回中2回、C280で68回中0回、C286で64回中0回だった。

### 開いている文と、既存の入力では防げない理由

C284以降の検証の節は、各コマンドの終了コードを一つの呼び出しの中で個別に確認し、`&&`や`;`で一つの終了コードにまとめないことを求めている。しかし、呼び出し自体の終了コードを定めていない。そのため、成功を失敗として返す形も、失敗を成功として返す形も、規則に違反せずに構成できる。採点は呼び出しの終了コードで成功を判定しており、包み方の不具合と本当の失敗を区別できない。これは採点規則の欠陥ではないため、採点は変更しない。

### 閉じる境界

| 項目 | 内容 |
| --- | --- |
| 禁止する行動 | rootが、各コマンドの結果と一致しない終了コードで検証の呼び出しを終える |
| 現在の開放経路 | 呼び出し自体の終了コードが規則の外にあり、ループや判定式の書き方次第で決まる |
| 閉じる境界 | 呼び出し自体は、全コマンドが成功した場合は0で終え、途中で止めた場合は、止める原因となったコマンドの終了コードで終える。適用は、検証の呼び出しを発行したという確定した事実だけで決まる |
| 正常な処理の保持 | 各コマンドの終了の待機、終了コードの個別確認、失敗時の後続停止、一つの呼び出しでの実行は維持する |
| 反証する構成 | 末尾に`\|\| true`や判定式を置き、呼び出しの終了コードを結果と切り離す構成。いずれも新しい文に違反し、呼び出しの終了コードと各コマンドの出力を照らして観測できる |

### 処理方法を指定する条件の確認

- 無条件である：検証の呼び出しを発行した場合に必ず適用する。
- 遵守を観測できる：Claude Codeではツール結果のエラー状態、Codexでは終了コードを、各コマンドの出力と照らす。各コマンドの結果が出力に現れない呼び出しは、判定不能として別に数える。
- 遵守率：未測定である。C291の計測で最初に確認し、静的な文面だけで制御の成立を宣言しない。
- 正常な経路を保持する：上表のとおり。
- 汎用の形で書く：特定のコマンド、ケース、モデル名を本文へ入れない。

### 変更する文

検証の節の第2項の「失敗または実行不能なら後続のコマンドを実行しない。」の直後へ、次の一文を加える。「呼び出し自体は、全コマンドが成功した場合は終了コード0で、途中で止めた場合は止める原因となったコマンドの終了コードで終える。」

他の文は変えない。

## 増える判断と、変更対象外への影響

C290は判断を増やさない。対象の一つがルートかどうかは、パスで決まる。C291も判断を増やさないが、検証の呼び出しの書き方に一つの制約が加わる。ルートの本文はC289の5,372バイトから、C290で5,644バイト、C291で5,828バイトに増え、最初の文脈が増える。両案とも、成果の決め方、担当、変更前の調査範囲、それ以外の読み取りの規則は変えない。

## 評価と停止条件

- 固定済みのStandard14、Layer 1、TaskSpec、採点契約を再利用し、prompt identityだけを変える。発行前にprompt identity以外の互換条件を機械照合し、一項目でも不一致があれば一件目を発行しない。
- Sol Low：C290とC291を、C289のSol Low N=5と同じ条件で各N=5測り、保存済みのC289と比べる。
- Opus 5.5 medium：C291だけをN=5で測り、保存済みのC289（`d5001b92579f486da96a886ad23a3742`）と比べる。
- 3 KPIで判定する。品質の中央値が100でも、3点以下を相殺しない。品質を維持し、トークンと経過時間がともに減った場合だけ、コスト改善の方向とする。
- 機序の診断：C290は、ツール結果にルートの本文が現れたrunの数（目標0）と、ルート以外の指示ファイルの取得が維持されているか。C291は、検証の呼び出しの終了コードと各コマンドの結果がずれた呼び出しの数（目標0）と、A02の試験証拠不足の件数。機序の診断値は3 KPIを置き換えない。
- C291が閉じる事象は、Opus 5.5で70件中2件という低い頻度である。N=5で0件だったことだけを理由に、解消したとは判断しない。再現性の判断は[再現性の判断方針](reproducibility-decision-policy.md)に従う。
- invalid、採点不能、互換条件の不一致、品質の低下があれば有効な改善として扱わない。正常終了に必要な指示ファイルの本文が届かないrunが出た場合は、C290の境界の反証として記録する。
- 採用、release、本体反映はこの評価に含めない。
