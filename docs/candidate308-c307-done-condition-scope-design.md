# Candidate308 C307の成功後の一項目に、完了条件の確認を含める

2026-10-10。ベースをC307に移して弱点を洗い出した結果、成功後の一項目が完了条件の確認を省かせていたため、Candidate本文の作成前に固定する設計記録。[設計原則](prompt-control-design-principles.md)の全文を読み、「Candidateを作成する前の確認事項」の項目1〜9に対応させた。計測と記録は[計測と記録の基準r2](shared-instruction-evaluation-criteria-r2.md)に従う。この記録ではbundleを作成しない。

## 目的と役割

- 系列：実行環境を切り離し、負荷を見て次のrunを始める発行の条件（CPU使用率70%以下、間隔1秒）で測る系列。
- ベースと直接の親：C307（`the-caption-3ce91a4-taskspec-scoped-closure-output-trim-r1`）。比較の基準は、同じ条件で測ったC307のSonnet low。
- 利用者の指示により、Sonnet lowで確立するまでSolは測らない。
- 評価は計測であり、達成目標を置かない（r2）。
- 変更対象：C307のroot `AGENTS.md`の、成功後の一項目だけを置き換える。他の項目と他の18対象はC307とバイト一致を保つ。

## 1. 比較の基準と、正常な最短経路

基準はC307。変更を伴うケースの正常な最短経路は、開始時の確認と読み取り → 変更 → TaskSpecが求める確認と、完了条件の確認 → 報告である。TaskSpecは完了条件を明示している（例：F01の`F01-C3`「required validationがpassし、許可外driftがない状態をdoneとする」、F03の`F03-C3`、F04の`F04-C3`も同じ形）。許可外の変更がないことは、変更の後の作業ツリーの状態で確かめる。

## 2. 保存traceで確認した問題経路

変更を伴うケース（各計測45件）で、最後の変更の後に作業ツリーの状態の確認（`git status`、`git diff --name-only`など）をせずに報告したrunを数えた。

| C301 `-r5` | C305 | C302 `-r2` | C306 | C307 |
| ---: | ---: | ---: | ---: | ---: |
| 0件 | 0件 | 8件 | 15件 | 13件 |

- 成功後の一項目（C298とその置き換え）を含む計測だけで起きている。
- C307のF01（反復5）は「実行後の`git status --short`は確認していません」、F04（反復1）は「許可外の変更が無いことは未確認です」と報告した。完了条件の一部を確かめずに報告している。点数は4点だった（差分の記録は評価の仕組みが自分で取る）。

## 3. 開いている記述と、TaskSpec・正本で防げない理由

C306で置き換えた一文「TaskSpecが求める確認がすべて成功した後は、TaskSpecが求めていないコマンドを発行せずに報告する。」の「TaskSpecが求める確認」を、モデルは列挙された確認コマンドだけと読んだ。完了条件（許可外の変更がないこと）を確かめる操作は、コマンドとして列挙されていないため「求めていないコマンド」と判断され、止められた。C298を設計したときは、成功後の状態確認を閉じる対象としていたが、それは完了条件の確認も止める。

## 4. 追加・変更する条件の全件

C307の成功後の一項目を、次の一文に置き換える。

> - TaskSpecが求める確認（完了条件の確認を含む）がすべて成功した後は、TaskSpecが求めていないコマンドを発行せずに報告する。

- 「TaskSpecが求める確認」に、TaskSpecの完了条件の確認を含めることを明示した。完了条件はTaskSpecに書かれた事実である。
- 止める時点は、完了条件の確認を含むすべての確認が成功した後になる。それより後の、求められていない追加のコマンドは引き続き禁止する。
- 既存の操作の発行を禁止する文であり、新しい操作の発行を求めない。

## 5. 禁止行動、開放経路、閉じる境界、反証

| 項目 | 内容 |
| --- | --- |
| 禁止する行動 | rootが、TaskSpecが求める確認と完了条件の確認がすべて成功した後に、TaskSpecが求めていないコマンドを発行する |
| 現在の開放経路（C307） | 「求める確認」が列挙されたコマンドだけと読まれ、完了条件の確認まで止まる。止める時点が早まり、完了条件を確かめずに報告する経路が開いている |
| 閉じる境界 | 操作の発行。止める時点と禁止の対象は、TaskSpecの確認の列挙と完了条件という、モデルに見える入力で定める |
| 正常な処理の保持 | 完了条件の確認（許可外の変更がないことの確認）は、止める時点より前に行える。確認の失敗後の修正と再実行は妨げない |
| 反証する構成 | 完了条件の確認を済ませた後に、状態確認を重ねて発行する構成は、TaskSpecが求めていないので禁止に当たる |

## 6. 維持する正常経路

C306とC307の設計記録の項目6のとおり。Claude Codeは、求められた確認を個別の`Bash`呼び出しで実行する。状態の確認は、確認コマンドと同じ呼び出しに含めても、別の呼び出しにしてもよい。

## 7. 新しく増える判断と、変更対象外への影響

- 新しい判断：完了条件を確かめる操作がどれか。TaskSpecの完了条件の記述から決まる。
- 危険1：完了条件の確認として、状態確認を複数回行う。2回目以降は禁止に当たる。成功後のコマンドの回数で観測する。
- 危険2：Codexの経路で、成功後の状態確認がC302より増える。完了条件の確認として1回に収まれば、正常な処理である。Solは今回測らない。
- 固定分：置き換える文の差（改行を除き、135バイトから171バイト）。
