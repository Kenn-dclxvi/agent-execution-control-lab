# Candidate299 既定値より短い待機時間を指定しない

2026-10-09。Candidate本文の作成前に固定する設計記録。[設計原則](prompt-control-design-principles.md)の全文を読み、「Candidateを作成する前の確認事項」の項目1〜9と「処理方法を指定できる条件」に対応させた。判定は[判定基準の記録](shared-instruction-evaluation-criteria-r1.md)に従う。根拠は[C280に加える短い閉鎖文の候補の洗い出し](c280-short-closing-sentence-candidates-r1.md)の候補2（待機）であり、文はこの記録で確かめたツールの既定値に合わせて書き直した。この記録ではbundleを作成しない。

## 目的と役割

- 系列：汎用指示の改善系列。比較の基準かつ直接の親はC280（`the-caption-3ce91a4-execution-control-outcome-binding-r1`）。C298（候補1）とは別の経路を閉じるため、C298を親にせず、別のCandidateとして測る。
- 主なセル：GPT-6.1 Sol LowとClaude Code Sonnet 5.5 low。
- 必要な効果：品質を保ち、両セルでC280よりトークンを増やさない。経過時間は保存済みC280との比較を参考として記録する。
- 対象：Sol Lowで、実行中のコマンドの終了を、短い待機時間の呼び出しを繰り返して待つ応答（C280で待機だけの応答が1反復あたり9.2回）。
- 変更対象：root `AGENTS.md`の末尾に一項目（117バイト）を加えるだけ。C280の本文と他の18対象はC280とバイト一致を保つ。全文は1,587バイト（C280は1,470）。

## 1. 比較の基準と、正常な最短経路

基準はC280。変更を伴うケースの正常な最短経路は、開始時の確認と読み取り → 変更 → 必須の確認 → 報告である。必須の確認コマンドの所要時間は、記録上、`main_verify.sh`が中央値5.3秒・最大22.3秒、`pytest tests/`が中央値6.4秒・最大27.7秒である。

## 2. 保存traceで確認した問題経路

C280のSol Low（result `794d02abe894456686eea22e9b6f0fed`、70件）で、待機（空入力の`write_stdin`）だけの応答は1反復あたり9.2回（反復ごとに7〜12回）あった。待機の呼び出しはすべて`yield_time_ms`を1000（1秒）に指定しており、待たれたコマンドを発行した`exec_command`の多くも`yield_time_ms`を1000に指定していた（[候補の洗い出しの機械可読記録](../evaluations/results/c280-short-closing-sentence-candidates_2026-10-09.json)）。1秒で途中まま返った結果を受けてモデルへ戻り、再び1秒の待機を発行する流れが繰り返されていた。Sonnet lowでは待機は0回である。

## 3. 開いている記述と、TaskSpec・正本で防げない理由

この記録で、計測に使うCodex CLI 0.159.0の実行ファイルに含まれるツール説明を確かめた。

- `exec_command`の`yield_time_ms`は「出力を待ってから返すまでの時間」で、既定値は10000ミリ秒（10秒）である。
- 空入力の`write_stdin`（終了の待機）は、既定で5000〜300000ミリ秒待つ。
- ツール説明は、待つときは長い待機時間を使うよう述べている。

既定値のままでも、コマンドが先に終われば結果はその時点で返る。Sol Lowの保存trace（C280〜C298）で、`yield_time_ms`を指定しなかった`exec_command`のうち、終了した3,362回は、すべて10秒未満で終了と同時に返っていた。1秒の待機時間は、モデルが自分で指定した値である。C280、TaskSpec、課題文のいずれも待機時間を定めておらず、短い値の指定を禁じていない。

## 4. 追加する条件の全件

C280の末尾に、C280の箇条書きと同じ書式（`*`）で、次の一項目を加える。

> * コマンドの実行とその終了待ちで、ツールの既定値より短い待機時間を指定しない。

- この文は、既存の呼び出しのパラメータを限定する文である。新しい操作の発行を求めない（設計原則の確認事項5）。待機時間を指定しないこと（既定値を使うこと）でも、既定値以上を指定することでも満たせる。
- 「短い」はモデルの感覚ではなく、ツールの既定値との比較という、ツール説明と保存traceの値で判定できる事実で定めた（候補2aの「短い」を直した）。候補2bの「30秒以上」のような、試験の環境の所要時間から選んだ数値は使わない。
- `yield_time_ms`やツール名を名指ししない。Claude Codeの`Bash`の`timeout`にも同じ文が当たり、Sonnet lowは`timeout`を既定値（120秒）より長い600000ミリ秒にすることがある（C280で70件中8回）だけなので、禁止に当たらない。

## 5. 禁止行動、開放経路、閉じる境界、反証

| 項目 | 内容 |
| --- | --- |
| 禁止する行動 | rootが、コマンドの実行またはその終了待ちの呼び出しで、ツールの既定値より短い待機時間を指定する |
| 現在の開放経路 | 待機時間がモデルに任されており、1秒を指定して、途中まま返った結果ごとにモデルへ戻れる |
| 閉じる境界 | 操作の発行時のパラメータ。対象は、保存traceの`yield_time_ms`（Claudeでは`timeout`）の値とツールの既定値の比較で機械的に判定できる |
| 正常な処理の保持 | コマンドが先に終われば結果はその時点で返るため、短いコマンドの待ちは増えない。既定値の待機で終わらない長いコマンドは、既定値以上の待機の呼び出しで待てる。失敗の検出、出力の確認、待機の継続は妨げない |
| 反証する構成 | 待機時間を指定せずに、待機の呼び出しを繰り返す構成は禁止に当たらないが、各待機が既定値（`exec_command`で10秒、待機で5秒以上）まで待つため、必須の確認の所要時間（最大27.7秒）に対して繰り返しの回数は限られる。完全な閉鎖ではなく、回数を減らす限定である |

### 処理方法を指定できる条件との対応

1. 無条件である：コマンドを実行する、または待つという確定した事実だけで適用され、必要性の判定を介さない。
2. 遵守を観測できる：保存traceの`yield_time_ms`の値と待機の呼び出しの数で判定できる。
3. 遵守率：未確認。この計測で初めて確かめる。
4. 正常経路を保持する：上表のとおり。
5. 汎用の形で書く：ツール名、コマンド、ケースを名指ししない。

## 6. 維持する正常経路

- Codex：コマンドの実行と待機は従来どおり行える。既定値のまま、または長い待機時間で待つ。
- Claude Code：`Bash`は既定で終了まで待つ。`timeout`を長くする指定は禁止に当たらない。必須の確認コマンドを個別の`Bash`呼び出しで実行する課題文の指定に触れない。
- 必須の確認が失敗した場合の調査、修正、再実行を妨げない。

## 7. 新しく増える判断と、変更対象外への影響

- 新しい判断：ツールの既定値を知ること。Codexではツール説明に既定値が書かれている。
- 危険1：Sonnet lowが`timeout`の指定をやめる、あるいは新たに指定するなど、`Bash`の呼び出し方を変える。品質と`timeout`の指定回数で観測する。
- 危険2：Sol Lowが長い待機時間で待つ間に、失敗の早期発見が遅れる。待機はコマンドの終了で返るため、遅れは生じないと見込む。
- 固定分：117バイト。Sonnet lowで1反復あたり約2.5千トークン（117×0.3247×64.6）、Sol Lowで約3.5千トークン（117×0.34×88.0）の見積もり。Sonnet lowでは減る経路がないため、固定分だけ増える（C280中央値の約0.3%）。この増加は反復間の揺れの中にあるが、判定基準のもとではコスト退行として記録される。
- 見込み：Sol Lowで、待機だけの応答（9.2回/反復）がなくなれば、上限で約29.9万トークン（約14.4%）の削減。同じ文面に近いC297では待機が4.4回だったため、C280の9.2回は揺れの上側にある可能性があり、見込みは上限側である。

## 8. 評価ケース、比較単位、比較条件

- セル：Sol LowとSonnet low、各Standard14の全14ケース各N=5の計70件。
- 基準：各セルの保存済みC280（Sol Low `794d02abe894456686eea22e9b6f0fed`、Sonnet low `c84fd22753d248e588e586cb8022ea1e`）。
- 比較条件：C293〜C298と同じ。Sol LowはC289の保存済み登録結果を基準にした比較互換preflight、Sonnet lowはC280・C291のSonnet lowと同じClaude Code 2.1.288、評価コード、権限、tool集合。変えるのはprompt identityだけ。発行前にpreflight receiptを保存し、不一致があれば一件も発行しない。
- 判定：品質を保ち、各セルで全エージェントトークン中央値がC280より減った場合を主な判定とする。経過時間の増減は記録するが、計測の時間帯の影響と区別できないものとして参考に扱う。セルの間で相殺しない。
- 診断（合否にしない）：Sol Lowの待機だけの応答の数、`yield_time_ms`の指定値の分布、1反復あたりの応答数。Sonnet lowの`timeout`の指定回数と応答数。

## 9. 停止条件

- 互換条件の不一致、未確認があれば、一件目の発行前に停止する。
- invalid、採点不能、品質の低下は、有効な改善として扱わない。外部失敗だけ、同じ枠で固定上限内に再試行する。有効な4点未満は削除、相殺、再実行しない。
- 各セル70件で判断し、自動で追加反復しない。結果に合わせてこの記録と案文を書き換えない。

## 判断の限界

- ツールの既定値は、実行ファイルに含まれるツール説明の文字列から確かめたもので、実装の動作そのものは保存traceの返り方でだけ確かめた。
- 見込みの大きさは、C280の保存traceからの上限側の概算である。
- この記録は採用、release、本体反映を決めない。
