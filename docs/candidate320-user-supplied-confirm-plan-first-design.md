# Candidate320 利用者が示した「先に計画を出して確認を取る」プロンプトをそのまま測る

2026-10-30。利用者が示したプロンプトを、本文を変えずにrootの指示として置き、THE-CAPTIONのStandard14（STD14）をClaude Code Opus 5.5 lowとSonnet 5.5 lowで各N=5測るために、Candidate本文の作成前に固定する設計記録。

このCandidateは、保存traceの分析から導いた制御ではない。[作成前の確認事項](prompt-control-design-principles.md#candidateを作成する前の確認事項)のうち、traceに由来する項目（2、3、5）は該当なしとし、その理由を記す。この扱いは利用者の判断（2026-10-30、「それで進めて」）による。

## 目的と役割

- ベース：Free（`the-caption-3ce91a4-control-free-repository-r1`、rootの`AGENTS.md`が空）。
- 変更：rootの`AGENTS.md`（Claude Codeでは`CLAUDE.md`がこれを指す）を、利用者が示した本文に置き換える。ほかのファイルはFreeと同一。
- prompt identity：`the-caption-3ce91a4-confirm-plan-first-r1`
- 本文の要点：役割を「簡潔 / 厳格 / 先に確認する」とし、いきなり成果物を出さずに問題の理解・修正方針・影響範囲を整理して確認を取る。監査・確認・照合はそのまま実施し、作成・修正・書き換えはまず計画だけを出して、承認があるまで書き換えない。計画・実施・監査の出力の見出しを定める。

## 1. 比較の基準と、正常な最短経路

- 比較の基準は、同じエージェント・同じモデル・同じ評価セットで測った保存済みのFree（2026-10-10）とC319（2026-10-15）とする。試験の実行には比較の相手を要求せず、比較は保存したanalysis同士で後から行う。
- 正常な最短経路は課題ごとにSTD14が定める。F課題は作業指示どおりに変更と必須の確認を終えて報告し、A01は求める値が決まらないので確認して止まり、A02はリポジトリの規則から決まる修復を行って確認する。

## 2. 保存traceで確認した問題経路

該当なし。このCandidateは、保存traceで確認した問題経路を閉じるために作るものではなく、利用者が示したプロンプトの表れ方を測るために作る。

## 3. 開いている記述と、TaskSpec・正本で防げない理由

該当なし（2と同じ理由）。

## 4. 変更する条件の全件

rootの`AGENTS.md`の全文を、利用者が示した本文に置き換える。本文は一字も変えない。ほかのファイル、TaskSpec、ケース、評価セット、採点は変えない。

## 5. 禁止行動、開放経路、閉じる境界

該当なし（2と同じ理由）。本文に含まれる「計画だけを出し、承認があるまで書き換えない」は、新しい操作（確認を取って止まる）を求める文である。STD14は対話のない単発の作業で、承認は届かないため、変更を求めるF課題とA02では、変更せずに止まる経路が増える見込みである。この見込みは本文の調整理由にせず、計測した結果として記録する。

## 6. 維持する正常経路

課題文、作業ツリー、階層ごとの指示（`src/`・`tests/`などの`AGENTS.md`）、`docs/`、`prompts/`はFreeと同じで、エージェントが読める範囲も同じ。

## 7. 新しく増える判断と、変更対象外への影響

依頼が「作成・修正・書き換え」と「監査・確認・照合」のどちらに当たるかの判断が増える。前者なら計画を出して止まり、後者ならそのまま実施する。課題文に変更と確認が両方書かれている場合の扱いは、本文からは決まらない。

## 8. 評価ケース、比較単位、比較条件、記録する項目

- 評価セットはSTD14（`the-caption-standard14-r1`）、各セルN=5（70件）。
- セルはClaude Code Opus 5.5 low（`opus`）とSonnet 5.5 low（`sonnet`）。プロファイルは計測の道具（`campaign-tools/single-prompt-r1/campaign.py`）が、Sonnet lowの基準プロファイルからプロンプトの識別子だけを置き換えて作る。両セルを一つの待ち行列で流す。
- 記録する項目は、品質（点数の分布とケースごとの失点）、費用、経過時間の中央値と5反復の幅、参考の生のトークン。保存済みのFreeとC319とは、同じ単価表で数え直して並べる。測った日が違うことを併記する。

## 9. 停止条件

- 実行前確認（preflight）の不一致、無効なrun、採点不能、互換条件の不一致で止める。
- 品質と費用には達成目標を置かず、計測として記録する。品質が下がっても、それを理由に計測を止めない。

## 判断の限界

- この計測は、利用者が示したプロンプトがSTD14でどう表れるかを示すだけで、対話の中で承認を受けながら進める実際の使い方での品質は示さない。
- STD14では承認が届かないため、計画を出して止まることは、多くの課題で求める成果の欠落として採点される。
