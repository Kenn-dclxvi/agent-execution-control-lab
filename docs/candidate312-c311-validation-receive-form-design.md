# Candidate312 確認のコマンドを、終了コードと判断に必要な出力だけを受け取る形で実行する

2026-10-12。C311でも、確認コマンドを出力そのままで実行し、終了コードを確かめずに報告するrunが残ったため、許可の文を、させたい形を書く文に置き換える設計記録。Candidate本文の作成前に固定する。[設計原則](prompt-control-design-principles.md)の全文を読み、「Candidateを作成する前の確認事項」の項目1〜9と「処理方法を指定できる条件」に対応させた。計測と記録は[計測と記録の基準r2](shared-instruction-evaluation-criteria-r2.md)に従う。この記録ではbundleを作成しない。

## 目的と役割

- 系列：実行環境を切り離し、負荷を見て次のrunを始める発行の条件（CPU使用率70%以下、間隔1秒）で測る系列。プールは実効互換の規則（`effective-v1`）で作る。
- ベースと直接の親：C311（`the-caption-3ce91a4-final-check-unit-output-trim-generic-r2`）。比較の基準は、同じ条件のC309・C310・C311のSonnet low。
- 計測の順序：Sonnet lowで確かめてから、Sol Lowを測る。
- 評価は計測であり、達成目標を置かない（r2）。
- 変更対象：C311のroot `AGENTS.md`のうち、出力を絞ってよいとする一文だけを置き換える。他の項目と他の18対象はC311とバイト一致を保つ。

## この一文で何をさせたいか

確認のコマンドについて、次の二つを満たすこと。

1. 確認コマンド自身の終了コードを、必ず受け取る。
2. 判断に使わない大量の出力を受け取らない。

C307〜C311の一文（「出力を絞って実行してよい」）は許可の形で、モデルが出力の大きさを予想しないまま実行すると、どちらも満たせない。

## 1. 比較の基準と、正常な最短経路

[C309の設計記録](candidate309-c307-final-check-unit-design.md)の項目1のとおり。確認では、各コマンドの終了コードと、成否の判断に必要な出力（テストの要約など、末尾に出る部分）を受け取れば足りる。

## 2. 保存traceで確認した問題

`main_verify.sh`を出力そのままで実行したrun（各20〜21件）：

| C301 | C309 | C310 | C311 |
| --- | --- | --- | --- |
| F07で4件 | F07で3件 | F07で5件、F03で4件、F01で2件 | F07で5件、F01で2件 |

- F07は、出力を絞ってよいとする一文があってもなくても、そのまま実行していた。`bash -n run.sh`のように出力がほとんどない確認が先にあり、同じ書き方を続けたと見られる。
- C311のF07では、出力が退避されて終了コードが見えなくなった後、退避されたファイルの末尾を読み直したrun（反復3・4）と、読み直さずに「終了コードはこの実行では取得していません」「pytestの最終行が失敗なしだったことで判断しています」と報告したrun（反復1・5）があった。後者は、確認の成否を、コマンド自身の終了コードではなく出力からの推測で報告している。

## 3. 開いている記述

許可の文は、出力を絞らずに実行することも、終了コードを受け取らない形で実行することも禁じない。確認コマンドの受け取り方の定めがないため、終了コードの見えない実行と、大量の出力の受け取りが開いている。

## 4. 追加・変更する条件の全件

C311の一文を、次に置き換える。

> - 確認のコマンドは、そのコマンド自身の終了コードと、判断に必要な部分の出力（末尾など）だけを受け取る形で実行する。

- 確認コマンドの書き方を決める処理方法の指定で、新しい操作の発行を求めない。
- 「そのコマンド自身の終了コード」は、C307〜C311の二文目（確かめる終了コードはそのコマンド自身のものとする）を含む。

## 5. 禁止行動、開放経路、閉じる境界、反証

| 項目 | 内容 |
| --- | --- |
| 閉じる経路 | 確認コマンドを、終了コードの見えない形、または判断に使わない大量の出力をそのまま受け取る形で実行する |
| 現在の開放経路 | 許可の文だけで、受け取り方の定めがない |
| 閉じる境界 | 確認コマンドの実行の形。終了コードの表示（`echo "exit=$?"`、`${PIPESTATUS[0]}`など）と、出力の絞り込み（`tail`、ファイルへの書き出しなど）の有無で、保存traceから判定できる |
| 正常な処理の保持 | 確認が失敗した場合も、テストの失敗の要約は出力の末尾に出る。さらに必要なら、書き出したファイルを読める |
| 反証する構成 | 出力が小さいと見込んで絞らずに実行する構成は、指定に反する。`tail`の終了コードを確かめる構成は、「そのコマンド自身の終了コード」に反する |

## 処理方法を指定できる条件との対応

| 条件 | 満たし方 |
| --- | --- |
| 1. 無条件である | 確認のコマンドすべてに当てはまり、出力の大きさの見込みなど、モデルの判断を介さない |
| 2. 遵守を観測できる | コマンドの文字列で、終了コードの表示と出力の絞り込みの有無を判定できる |
| 3. 遵守率を実証している | 未確認。この計測で最初に確かめる |
| 4. 正常経路を保持する | 項目5のとおり |
| 5. 汎用の形で書く | 個別のコマンド名、ケース、期待値を書いていない |

## 6. 維持する正常経路

- Claude Codeは、課題文の指定どおり、確認のコマンドを1コマンドずつ個別の`Bash`呼び出しで実行する。出力を`tail`で絞る形とファイルへの書き出しは、評価の仕組みで必須の確認として受け付けられている（C309で課題文の指定に反する実行は0件）。
- Codexの経路では、出力の上限（`max_output_tokens`）の指定がすでにあり、終了コードは結果に含まれる。

## 7. 新しく増える判断と、変更対象外への影響

- 新しい判断：どこまでが判断に必要な出力か。末尾の行数などは、モデルが選ぶ実装方法である。
- 危険1：出力の小さい確認（`bash -n`、`git diff --check`など）にも終了コードの表示が付き、コマンドの文字列が長くなる。費用への影響は小さい。
- 危険2：絞りすぎて失敗の内容が見えず、追加の読み取りが増える。全件が成功した場合は起きない。
- 固定分：一文の長さの差。

## 8. 評価ケース、比較単位、比較条件、記録する項目

- セル：Sonnet low、続けてSol Low。各Standard14の全14ケースN=5の計70件。
- 比較条件：C311の同じセルのプロファイルと同じで、prompt identityだけを変える。
- 記録する項目（r2）：品質、処理の適切さ（確認の成否をコマンド自身の終了コードで確かめてから報告したか）、費用、経過時間、生のトークン（参考）。
- 機序の診断（合否にしない）：遵守率（確認コマンドのうち、終了コードの表示と出力の絞り込みがある割合）、`main_verify.sh`を出力そのままで実行した件数、出力が退避された回数、終了コードを確かめずに報告したrun、状態の確認の置き場所の遵守率、状態を確かめずに報告したrun、F06とF07の`git diff --check`の成功件数。
