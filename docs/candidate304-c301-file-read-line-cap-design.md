# Candidate304 1回の取得で一つのファイルから300行を超えて受け取らない

2026-10-09。[Sol Lowの費用を要素に分ける（r1）](sol-cost-element-decomposition-r1.md)で、プロンプトで減らせる最大の要素とした「指示ファイル以外のファイルの全文取得」を、禁止する一文としてC301へ加える設計記録。利用者の依頼（Solだけの効果でも費用を下げる要素を取り出す。同じ文を入れることは目的にしない）に基づく。[設計原則](prompt-control-design-principles.md)の全文を読み、「Candidateを作成する前の確認事項」の項目1〜9に対応させた。計測と記録は[計測と記録の基準r2](shared-instruction-evaluation-criteria-r2.md)に従う。この記録ではbundleを作成しない。

## 目的と役割

- 系列：実行環境を切り離した系列。比較の基準かつ直接の親はC301（`the-caption-3ce91a4-outcome-binding-uniform-markdown-r1`）の[一つの待ち行列での計測](../evaluations/results/c301-onequeue-sol61-low-sonnet55-low-standard14-n5_2026-10-09.md)。
- 文の出所：C288の「ファイル名の指定だけでは全文を取得しない」という制限。C288の文は、取得を求める部分（「定義・節まで取得する」）や、開始時のまとめ読みと同じ変更単位だった。この記録ではそれらを引き継がず、禁止だけを、保存traceで判定できる行数の上限として書き直す。C288は親ではない。
- 評価は計測であり、達成目標を置かない（r2）。
- 変更対象：root `AGENTS.md`の末尾に一項目を加えるだけ。C301の本文と他の18対象はC301とバイト一致を保つ。

## 1. 比較の基準と、正常な最短経路

基準はC301。変更を伴うケースの正常な最短経路は、開始時の確認と読み取り → 変更 → 必須の確認 → 報告である。読み取りでは、変更する箇所と、その判断に必要な定義や参照先を取得する。長いファイルでは、検索で位置を確かめてから、その周辺の範囲を取得すれば足りる。C301のSonnet lowは、この形で全件4点だった。

## 2. 保存traceで確認した問題経路

C301の保存trace（各70件）で、一つのファイルの本文を1回の取得で300行を超えて受け取った件数を数えた。行数は、作業開始時点（`HEAD`）のファイルで数えた。

| セル | 300行を超える取得 | 該当run | 主な対象 |
| --- | ---: | ---: | --- |
| Sol Low | 20件 | 14 / 70 | `App.tsx`（1,101行、F04の全5件）、`system.md`（637行、F08の全5件）、F02の`v4_engine.py`ほか3ファイル |
| Sonnet low | 1件 | 1 / 70 | F02の`collection_history_updater.py`（316行） |

- Sonnet lowは、範囲を指定した読み取りが最大125行、範囲を指定しない`Read`は最大288行のファイルだった。Sol Lowは、範囲を指定した`sed -n`の90%が260行以内で、300行を超えたのは1件だった。
- Sol Lowで300行を超えた部分は、1反復あたり約63KBだった。ただし、Codexは呼び出しごとに出力の上限を指定するため、実際に文脈へ入った量はこれより少ない。
- 対象のファイルは、どれも課題文が名指しし、そのrunで変更したファイルである。読む必要のないファイルを読んでいたのではなく、変更する箇所のほかに、ファイル全体を一度に受け取っていた。Sonnet lowは同じケースで、検索で位置を確かめて範囲を読んでいた。

## 3. 開いている記述と、TaskSpec・正本で防げない理由

C301もTaskSpecも、読み取りの量を定めていない。C301の「事前調査は、対象と実施方法を一つに決めるために不足している情報だけに絞る」は、読む対象を絞るが、名指しされたファイルを一度に全部受け取ることを禁止しない。名指しされたファイルを読むことは正常な処理なので、TaskSpecやリポジトリの正本からは、全体を受け取る経路を閉じられない。

## 4. 追加する条件の全件

C301の末尾に、次の一項目を加える。

> - 1回のツール呼び出しで、一つのファイルの本文を300行を超えて受け取らない。

- 既存の操作（ファイルの本文の取得）の範囲を限定する文であり、新しい操作の発行を求めない。検索や範囲の取得を求める文は加えない。
- 「本文」は、`cat`、`nl`、`sed -n`、`head`、`git show <commit>:<path>`、`Read`などで、ファイルの内容をそのまま受け取ることを指す。検索の一致行、差分、テストの出力は含まない。
- 指示ファイル（`AGENTS.md`）は、このリポジトリでは6〜16行で、例外を置く必要がない。
- 300は、C301のSonnet lowの読み取りがすべて収まり、Sol Lowの範囲指定の読み取りの90%以上が収まる値として選んだ。個別のケースやファイルの値ではない。

## 5. 禁止行動、開放経路、閉じる境界、反証

| 項目 | 内容 |
| --- | --- |
| 禁止する行動 | rootが、1回のツール呼び出しで、一つのファイルの本文を300行を超えて受け取る |
| 現在の開放経路 | 読み取りの量の定めがなく、名指しされた長いファイルを`cat`などで一度に受け取れる |
| 閉じる境界 | 結果の受け取り。対象は、1回の呼び出しで受け取った一つのファイルの本文の行数という、保存traceのコマンドと対象ファイルの行数から機械的に判定できる事実で定める。読む目的や必要性では定めない |
| 正常な処理の保持 | 300行以内のファイルは全体を受け取れる。長いファイルは、検索の一致行や、300行以内の範囲で必要な箇所を受け取れる。変更、必須の確認、報告は妨げない |
| 反証する構成 | 一つの呼び出しの中で範囲を分けて合計300行を超えて受け取る構成は、同じ呼び出しで同じファイルから受け取るので禁止に当たる。複数のファイルを一つの呼び出しで読むことは、ファイルごとに数えるので妨げない。呼び出しを分けて300行ずつ順に受け取る構成は禁止に当たらない。これは閉じた経路ではなく、呼び出しの回数が増える別の経路として残り、その費用はKPIに現れる |

この一項目は「処理方法の指定」ではなく、受け取る量の上限である。ただし、遵守を新しく確かめる必要があるため、この計測で遵守率（300行を超える取得の件数）を記録する。

## 6. 維持する正常経路

- 変更する箇所の取得：長いファイルは、検索（`rg -n`など）で位置を確かめてから、その周辺を範囲で取得する。C301のSonnet lowが全件4点で行っていた経路である。
- 小さいファイル（300行以内）：これまでどおり全体を受け取れる。
- Claude Codeの`Read`：300行を超えるファイルでは`limit`を指定して読む。C301のSonnet lowで該当したのは70件中1件だけである。
- Codex：出力の上限を指定する既存の書き方は変えない。

## 7. 新しく増える判断と、変更対象外への影響

- 新しい判断：取得するファイルが300行を超えるかどうか。行数は、検索の結果や`wc -l`、範囲を指定した取得で確かめられる事実である。分からないまま取得する場合は、範囲を指定すれば違反にならない。
- 危険1：Sol Lowで、長いファイルの読み取りが、検索と範囲の取得の2回以上の呼び出しに分かれ、リクエストが増える。費用では、増えるリクエストの多くはキャッシュ読み取りで、減る全文の取得はキャッシュに乗らない入力なので、差し引きは計測で確かめる。
- 危険2：レビューのケース（F10の2件）で、対象ファイルを範囲で読み、必要な箇所を見落とす。F10の対象ファイルはC301で300行以内だったため、影響は小さいと見込むが、品質で観測する。
- 危険3：Sonnet lowで、`limit`の指定や範囲の取得を増やし、読み取りの回数が増える。C301で該当したのは1件だけなので、影響は固定分に近いと見込む。
- 固定分：109バイト。Sonnet lowでは、指示文の固定分はキャッシュ読み取りの単価で、費用ではごく小さい。
- 見込み：Sol Lowで、300行を超えた部分（1反復あたり約63KB、出力の上限で切られる分を含む）の一部が、範囲の取得に置き換わる。上限側で費用の約4%に当たる。基準の幅（Sol Low $0.8704〜$0.9324）に対して小さく、幅の中に収まる可能性がある。

## 8. 評価ケース、比較単位、比較条件、記録する項目

- セル：Sol LowとSonnet low、各Standard14の全14ケースN=5の計70件。
- 比較条件：C301の`-20261009-r3`プロファイルと同じで、prompt identityだけを変える。両セルの全スロットを一つの待ち行列（合計24本）で発行する。準備・実行・登録は`campaign-tools/single-prompt-r1/campaign.py`で行う。
- 記録する項目（r2）：品質、処理の適切さ、費用（基準の幅と比べた位置）、経過時間、生のトークン（参考）、使用量の内訳。
- 機序の診断（合否にしない）：
  - 1回の取得で300行を超えて受け取った件数（遵守率）。数え方は項目2と同じ。
  - 300行を超えるファイルを読んだrunで、検索と範囲の取得へ置き換わったか。そのrunの呼び出し（要求）の数。
  - Sol Lowのキャッシュに乗らない入力のうち、本文の読み取りに割り当てた量（[分析](sol-cost-element-decomposition-r1.md)と同じ数え方）。

## 9. 停止条件

- 発行前の確認が通らなければ、一件も発行しない。
- invalid、採点不能は記録の対象にしない。外部失敗だけ、同じ枠で固定上限内に再試行する。有効な4点未満は削除、相殺、再実行しない。
- 各セル70件で記録し、自動で追加反復しない。結果に合わせてこの記録と案文を書き換えない。

## 判断の限界

- 項目2の観測はC301のN=5の一系列で、行数は作業開始時点のファイルによる。
- 300行を超えた部分の量は、Codexの出力の上限で切られる分を含む上限側の値である。
- この記録は採用、release、本体反映を決めない。
