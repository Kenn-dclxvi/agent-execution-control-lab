# Candidate273: Astra N=5のトークン増加原因

## 結論

大幅増加の主因は、必須試験の増加ではなく、検証の途中結果を受け取るたびにモデルの推論を再開し、蓄積した会話履歴を入力として繰り返し処理したことである。C147では一つの外側呼び出しの内部で検証と待機を終えたのに対し、C273では検証開始、待機、次の検証、差分確認を別の外側呼び出しへ分けた。

F01・F02・F04の計15runでは、C147の変更後の外側呼び出しは15 / 15で1回、C273は15 / 15で5〜9回だった。C273全15runで、モデルが個別に待機呼び出しを発行する形が現れた。C147にも待機はあるが外側呼び出しの内部で処理され、追加のモデル推論を必要としなかった。

これはC273で削除した`VALIDATION_CLOSURE`と、`VALIDATION_PLAN`から削除した検証中のモデル再入を閉じる記述に直接対応する。変更前の増分には`DECISION_BOUNDARY`削除による開始状態と対象readの分割も対応する。複数条項を同時に削ったため、各条項を一つずつ除いた実験による独立効果の証明ではないが、保存traceでは検証の分割が主要な増加機序を説明する。

## 調査仕様と境界

利用者の依頼は、増加した試験の原因調査である。実行者はroot。対象は[既存の6ケースN=5結果](../evaluations/results/candidate273-c147-astra-medium-six-case-n5_2026-09-05.md)に含まれるC147とC273の計60run。必要な観測は、各runの全エージェントusage、root rolloutの呼び出しとusage増分、必須試験の実行回数、最初の変更前後の差である。

保存済みのbinding、usage、rollout、commandイベントを読み取り専用で調べた。新しい試験、Candidate、採点の変更、外部executorの変更は行っていない。モデル・環境・fixture・TaskSpecの互換性は先行計測の実行前receiptへ結び付く。[調査数値とrun ID・rollout SHA-256](candidate273-astra-n5-token-increase-causal-audit.json)を保存した。生ログ・ソース本文はこの診断JSONへ含めない。

## トークン増分が生じた位置

以下は6ケース各5件、30runずつの単純合計による分解であり、先行結果の「selection sampleごとの合計の中央値」とは集約方法が異なる。公式比較の+110.84%を置き換えない。

| 区分 | C147 | C273 | 差 |
| --- | ---: | ---: | ---: |
| 全トークン | 3,484,757 | 7,226,428 | +3,741,671 |
| 最初の変更発行まで | 1,685,882 | 1,936,897 | +251,015 |
| 最初の変更発行後 | 1,704,588 | 5,164,534 | +3,459,946 |
| 変更しないA01 | 94,287 | 124,997 | +30,710 |

増分の92.47%が最初の変更発行後にある。この区間は検証だけでなく最終差分確認と最終応答も含む。したがって92.47%を「待機呼び出しだけの厳密な寄与率」とは扱わない。

| usage内訳 | C147 | C273 | 差 |
| --- | ---: | ---: | ---: |
| 入力トークン | 3,455,761 | 7,189,190 | +3,733,429 |
| うちキャッシュ済み入力 | 2,584,320 | 6,352,128 | +3,767,808 |
| キャッシュされていない入力 | 871,441 | 837,062 | -34,379 |
| 出力トークン | 28,996 | 37,238 | +8,242 |

キャッシュ済み入力は入力トークンの内数であり、再加算しない。増分は長い回答を書くことや新規の非キャッシュ入力ではなく、主にキャッシュ済み履歴を再度入力として数える形で発生した。これはこの評価が定めるtotal_tokensの増加であり、料金や利用枠消費の同率増加を主張するものではない。

## 具体的な実行経路

### F01

中央値runはC147 `b193b226fbb64d388bedd912cb5b29d7`（117,762 token）、C273 `220b7f9ccdcb4f4b87143f8cc3e65f68`（301,281 token）。

C147は開始状態と本文取得を同じ外側呼び出しで発行し、変更後は一つの外側呼び出し内でfocused pytest、full gate、差分、状態確認を実行した。終了していないコマンドの待機も同じ呼び出し内に収まる。

C273は開始状態の取得と本文取得を別にした。変更後はfocused pytest → 待機 → full gate → 待機 → 待機 → 差分・状態確認へ分割した。推論は4回から10回へ増えた。このC273 runでは変更後の各推論に約27,000〜38,000 tokenの入力があり、短い待機指示でも履歴入力の再処理が積み重なる。

### F02

中央値runはC147 `221033bc9dd24e989c296b917cc70ebf`（165,408 token）、C273 `28781a0470ac41bab38f99d8673fec9d`（428,116 token）。

C147は変更後のfocused pytest、full gate、差分・状態確認と途中待機を一つの外側呼び出し内で完了した。C273はfocused pytest、その待機、full gate、3回の待機、差分確認を別呼び出しへ分割した。開始状態の取得と本文取得の分割もあり、推論回数は5回から12回へ増えた。

### F04

中央値runはC147 `1f485833e6f94ba8b6c6b30bb21eb178`（158,751 token）、C273 `e5ee99d20fa9414eb9fea5705952183f`（410,998 token）。

C147は変更後の差分・状態確認、npm ci、lint、build、最終状態確認を一つの外側呼び出し内で処理した。C273はnpm ci → 待機 → lint → 待機 → build → 3回の待機 → 最終確認へ分割した。このrunは14回の推論、ケース全体の中央値は14回である。C147の中央値は5回だった。

### A02・A01と増加しなかったF07 dependency

A02でも検証・待機・最終確認の分割があり、推論中央値は5回から7回へ増えた。開始後から最初の変更までのトークン中央値はむしろ減っており、主要な増加位置は変更後である。

A01はC147が全5runで一回の確認応答だったのに対し、C273の2run（`ac1217c5b64a4049837e014ef8a2c401`、`82c526d0b0e14d63a92af941c0bf838a`）で許可された開始状態の取得を挟み、2回の推論になった。C273の中央値は低下しているが合計と経過時間は増えた。要求成果を勝手に決めたり、sourceの変更・試験へ進んだものではない。

F07 dependencyは推論中央値が4回のままで、トークンも91,936から87,741へ減った。本文が短くなっただけで全ケースが増加するわけではなく、実行の分割が増えたケースに大きな退行が集中するという対照になる。

## 解釈

C273の作成時に「委任の細かな管理や検証を一括実行する指定」とまとめて外した部分には、会話履歴を再びモデルへ渡す回数を抑える制御が含まれていた。推測禁止と不要探索の制限を保持しても、それだけではC147の低コスト動作を維持できなかった。

判断順を変えただけでは不要な検証途中のモデル再入が許可されないというC147の境界と、必要な検証を完了できる経路を分けて理解する必要がある。成功runの個別コマンド列や待機回数をそのまま新しい義務として転記する根拠にはしない。本調査は原因の特定までであり、新Candidateの作成・再評価は行っていない。
