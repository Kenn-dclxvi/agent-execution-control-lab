## 要旨

Baselineは失敗したpromptではない。人間だけで行っていた開発プロセス（依頼の指示書化、実装、監査、レビュー、完了判定、PR作成）を、役割と工程として`AGENTS.md`とロールプロンプトへ書き下したものである`[R1-1]`。当時のprompt設計記録は、この分業を「人間の組織図の写し取りではなく、AI固有の失敗様式へ向けて作り直した統治の形」と位置づけていた`[R1-3]`。

**Baselineは、当時の拡張12課題評価で`58 / 60`件が4点・2件が3点・品質中央値`100.000`を示し、研究開始時点では品質確保の初期解として扱われていた**（「実務利用されていた」は著者提供の歴史的前提であり、本リポジトリの一次資料では検証していない`[R1-7]`）。その後、評価範囲をStandard14へ拡張すると、未確定値の確認停止、正本からの一意解決、必須検証の非省略に残余欠陥が見つかった`[R1-4]`、`[R5-1]`。

本研究の問いは、その品質を維持したまま、AI実行として不要な経路を除去できるかである`[R2-1]`。

そのために、成果の点数・all-agent token・所要時間を固定条件で比較できる4 Layerの基盤を作った`[R4-1]`。あわせて本論文は、Baseline本文から品質責務を9項目として抽出し、既存の評価課題集合Standard14の各課題がそのどの責務を観測するかを**事後的に対応づける**`[R3-1]`。この対応表は研究過程を再解釈するための分析枠組みであり、case作成時に同じ分類が設計正本として存在したことを示すものではない。

測定の結果は次のとおりである。Baselineは、同じ土俵の7条件中でtokenと所要時間が最大であり、点数分布も最も悪かった（A01が4件、A02が2件、F07依存関係が1件の減点）`[R5-1]`。拡張12課題・推論`high`の保存結果では、all-agent token中央値とroot-only中央値の差が、all-agent中央値の56.4%に相当した`[R5-3]`。一方、root指示書だけを0バイトにするとtokenは`-70.80%`になったが、確認停止の課題は5回中5回落ちた`[R6-1]`。削除では閉じない品質欠陥が残る`[R6-3]`。

最終到達点C125には、**探索過程で識別・精緻化された複数の実行境界**が継承・統合されている。研究過程で識別された境界ファミリーは**9件**（仕様確定、validation closure、発行単位、evidence admission、成果値と実装方法の分離、実装確定の終端、判定条件と実行方法の分離、変更前証拠の一括取得、条件を覆う追加取得）、C125のroot本文に載っているlabelは**13件**、`synthesis`がC81以降の寄与として記録しているのは**7件**である（7.5節、7.7節）。**この3つの数は別の集合を指すため、常にどれを指すか明示する。** 各境界の追加が単独でall-agent tokenを低下させたとは限らず、C118ではtoken増加（`+7.44%`）・所要時間低下（`-14.37%`）・実装確定後の再入減少（`5 / 20 → 0 / 20`）が同時に観測された`[R7-1]`。

これらに共通するのは、**擬人的な工程全体の保持ではなく、モデルが実行時に観測できる条件として書かれている**ことである。この再構成の過程で、擬人的な工程仕様7ファイル（約59KB）が空ファイルへ置換された。**C35のmanifestは、保存済み観測で当該7 targetへの参照が成功実行に現れなかったことを置換の設計理由として記録している。対応するraw command evidenceは本リポジトリに保存されていないため、本論文はこれを歴史的な設計記録として扱う**`[R7-5]`。

効かなかったのは、表面の圧縮`[R8-1]`、委譲条件の細分化`[R8-2]`、実行環境側の挙動の指定`[R8-3]`、抽象的なmeta判断の追加`[R8-4]`、量による証拠の打ち切り`[R8-5]`である。

**品質制約下でall-agent tokenが低下し、かつ同一比較内の診断値またはtraceが整合する比較では、その低下を不要な実行経路の減少として解釈した**`[R11-3]`。費用削減の主張としては扱わない。**本研究の主要な実行量KPIはall-agent tokenであり、`elapsed_seconds`は外部負荷を統制していない記述的副指標である**（4.3節）。したがって「KPIが低下した」と一括せず、tokenと所要時間を常に別記する。品質制約を維持したままKPIの方向が分かれた機構成立（C116→C118: token`+7.44%`、所要時間`-14.37%`）は別扱いとする（11.3節の表B）。ただし**どの境界が必要か、境界の集合が最小か、追加順序に必要性があるかは、ablationと順序入れ替えを測っていないため示していない**`[R7-14]`。

適用範囲は狭い。単一のmodel系列と単一の実行環境`[R10-1]`、繰り返し使ってきた14課題`[R12-1]`、単発作業だけである`[R12-4]`。同じ指示書でもmodelを変えると品質とコストは維持されなかった`[R10-2]`。C125の長期反復（B20）は未実施である`[R12-3]`。

## 1. 背景：Baseline以前とBaselineの到達点

> **節の目的**: Baselineを「研究前の到達点」として説明し、失敗作として扱わない。
> **中心主張**: Baselineは人間の開発工程をprompt化し、当時の拡張12課題評価で一定品質を示したため、研究開始時点では品質確保の初期解として扱われていた。その実行効率とAI固有の最適性は未計測だった。
> **使用する証拠**: Baseline bundle本文（root `AGENTS.md`、`docs/orchestration-process.md`、`prompts/{plan,implement,audit,review}.md`、`docs/prompt-guide.md`）、baseline manifest、初期比較result。

### 1.1 AI駆動開発へ人間の工程を移植した理由

Baselineが固定した実行モデルは、人間の開発プロセスの工程と成果物をそのまま持っている`[R1-1]`。

| 人間の工程 | Baselineでの対応 | 正本 |
| --- | --- | --- |
| 依頼の要件定義 → 実装指示書 | プランSAが草案を作る。草案は実行許可ではない | `prompts/plan.md`、`docs/orchestration-process.md` ケースE |
| 実装担当が作業する | 実装SAが承認済み指示書の`target / scope / done / tests / stop`だけを扱う | `prompts/implement.md` |
| 契約準拠の検査（受入検査） | 監査SAが非破壊で照合し、停止指摘 / 任意指摘 / 範囲外指摘へ分類する | `prompts/audit.md` |
| PRレビュー | レビューSAが監査通過後に非破壊で品質確認し、重大指摘 / 改善指摘 / 補足 / 範囲外指摘へ分類する | `prompts/review.md` |
| 差し戻しと再作業 | 親が自動修正ループを最大5回まで管理する | root `AGENTS.md` §停止と自動再修正 |
| 完了判定 | 実装・テスト・監査・レビューが揃い、停止指摘0件かつ重大指摘0件のときだけ成立 | root `AGENTS.md` §完了判定 |
| PR作成 | 親が言語規約とテンプレートに従って作成する | root `AGENTS.md` §PR作成 |

親エージェントは実装・修正・テスト実行・監査・レビュー相当の品質確認・指示書作成を直接行わない`[R1-2]`。すなわちBaselineは、**人間の職能分担と工程順序を、そのままエージェント間の役割と関所として写している**。

### 1.2 Baselineの設計記録が主張していたこと

ただし、Baselineを素朴な「組織図の写し取り」として扱うことはできない。設計理由の正本である`docs/prompt-guide.md`は、この分業を明示的に次のように位置づけていた`[R1-3]`。

> この分業は、人間の組織図の写し取りではない。（中略）AI にはその制約がなく、別の失敗様式を持つ。

同文書が挙げる7つの設計理由は、人間の管理慣行ではなくAI固有の病理を対象としている。失敗様式で役割を分ける、主張ではなく成果物（テスト結果・差分）で照合する、情報の非対称性を制御レバーにする（監査SAへ実装経緯を渡さない）、確証バイアス・迎合・reward hackingへ敵対的に防御する、直列の年功ではなく並列の多様性で検証する、親の希少資源はコンテキストと信頼である、検証は安いので前倒しする。

したがって本研究の出発点は、次のように精確に述べる必要がある`[R1-4]`。

> Baselineは、人間の開発プロセスの**工程・成果物・関所の構造**をpromptへ移植し、その各工程の**目的をAI固有の失敗様式へ向けて再設計した**初期解である。移植されたのは工程構造であり、その工程構造そのものがAIの実行特性に対して最適かどうかは、当時は測定されていなかった。

### 1.3 Baselineが実現した品質

Baselineが守ろうとした品質責務は、prompt本文から限定列挙として取り出せる`[R1-5]`。

1. **推測の禁止**: 問題・条件・境界項目（対象・範囲・完了条件・品質基準・実行許可）をAIが補完しない。推論を実行許可へ変換しない。
2. **停止の義務**: 境界項目が未定義なら停止する。テスト条件が未定義でテスト実行が必要なら停止する。
3. **範囲逸脱の禁止**: 指示書外改善、便乗リファクタ、仕様変更混入、対象外変更を禁じる。
4. **必須検証の非省略**: コード変更を含む作業単位ではテストコマンドを必須とする。明示テスト未実行・失敗の無視・期待値変更を停止指摘とする。
5. **reward hackingの禁止**: `# noqa`・skip・xfail追加、失敗パスのmock握りつぶし、assertion緩和を停止指摘とする。
6. **完了偽装の禁止**: 完了条件の達成扱いが差分・テスト結果・関連仕様で支えられない場合を停止指摘とする。
7. **情報境界の維持**: 監査SA・レビューSAへ実装経緯・事前評価・他SAの判断を渡さない。
8. **対象外操作の拒否**: `commit` / `push` / `deploy` / 外部送信を条件付き事前承認に含めない。
9. **ループの有界性**: 自動再修正を最大5回、同一指摘の連続2回再発で停止する。

**この9項目は本論文がBaseline本文から抽出した整理であり、当時のartifactにこの分類として記録されているものではない。** また、この9項目からStandard14を導出したという履歴も一次資料から確認できない。Standard14の正本から確認できるのは、旧12項目へA01とA02を加えて14項目とし、版と評価境界を固定したことである。3節では、既存のStandard14の各課題がこの9責務のどれを観測するかを**事後的に対応づける**（3.1節）。

### 1.4 未計測だった効率と実行経路

**研究開始前と研究開始後を分けて記述する。**

**研究開始前**: 著者は対象リポジトリでの利用経験からBaselineを品質確保の初期解として扱っていた。**この位置づけは著者提供の歴史的前提であり、本リポジトリの一次資料では検証していない**`[R1-7]`。「AI実行として最適か」という疑問はこの認識から生じた（2節）。

**研究開始後**: 評価基盤と評価課題集合を構築して測定した（4節）。拡張12課題・`N=5`（60回）では score `4 / 3 = 58 / 2`、`quality_score`中央値`100.000`である`[R1-6]`。**この初期測定は研究開始前の認識を部分的に支持したが、本論文が2.1節で定義する「全課題で減点なし」という品質制約は満たしていなかった**（2件の減点がある）`[R1-4]`。

**したがって、拡張12課題の結果を「研究開始時点でBaselineを初期解と考えていた根拠」としては使わない。** それは研究の中で得た証拠であり、研究前の認識とは別である。

一方、当時保存していたtoken値は**root agentのusageだけ**であり、委譲先の子セッションの消費が集計に入っていなかった`[R4-4]`。この計上のまま読むと、Baselineは中央値`3,888,115`でCandidate5（`4,503,816`）より少なく見えていた。all-agentへ再集計すると順序が逆転した（4.4節、5.3節）。

**そして、その品質を得るために消費していた実行量が観測できていなかった。** これが研究の出発点である。評価範囲をStandard14へ拡張したあとに見つかった残余欠陥は5.1節で扱う。

## 2. 研究疑問

> **節の目的**: 中心問いを「人間向け工程のAI実行上の最適性」として定義する。
> **中心主張**: 品質を制約条件として固定したうえで、AI固有の不要な実行経路を除去できるかを問う。
> **使用する証拠**: 本節は問いの定義であり、数値主張を持たない。

### 2.1 中心問い

> 人間向け開発プロセスのprompt化によって得た品質を維持しながら、AI固有の不要な実行経路を除去できるか`[R2-1]`。

「維持」は「品質中央値が同じ」ではなく、「**各品質責務に対応する課題で減点が発生しない**」と定義する（3節、4.3節）。

### 2.2 副問い

| 副問い | 対応する節 |
| --- | --- |
| 静的なprompt量（バイト数・label数）と動的な実行量（実行時token）は一致するか`[R2-2]` | 6.4節、8.1節 |
| 何を削除すると品質が壊れるか`[R2-3]` | 6.2節 |
| どの実行境界を残せば品質制約を維持できるか`[R2-4]` | 7節 |
| promptとexecutorの責務はどこで分かれるか`[R2-5]` | 8.3節、9節、11.5節 |

**最小性は副問いに含めない。** ablationを実施していないため、境界集合の最小性も各境界の単独の必要性も本研究では判定できない（7.6節、12.5節）`[R7-14]`。第4の副問いは「どの境界を残せば品質制約を維持できるか」であり、「どの境界が不可欠か」ではない。

### 2.3 この問いが前提としないこと

- Baselineが冗長・無駄・失敗だったという前提を置かない（1節）。
- all-agent tokenの最小化を目的関数としない。`quality_score`は最適化対象ではなく維持すべき制約であり、`elapsed_seconds`は記述的副指標である（4.3節）。
- 「短くすること」を改善の定義としない（2.2節の第1副問いは、両者が逆方向になり得るかを問うている）。

## 3. 評価設計：何を品質として守るか

> **節の目的**: 評価課題集合を、品質制約を定義する中心要素として提示する。
> **中心主張**: Standard14は「ベンチマーク問題集」ではなく、品質責務を実行時に観測可能な条件として表した**品質制約の観測集合**である。
> **使用する証拠**: `evaluations/sets/the-caption-standard14-r1/README.md`、各case revisionの`README.md`と`trial-prompt-input.json`、rating contract v13 / v14、`evaluations/README.md`、`evaluations/AGENTS.md`。
>
> **本節の対応づけは事後的である。** Standard14は9責務から導出されたのではなく、旧12項目へA01とA02を加えて固定された既存の評価課題集合である。本節が示すのは、**その既存集合の各課題がBaselineの9責務のどれを観測するか**という分析枠組みであり、case作成時の設計正本ではない`[R3-1]`。

### 3.1 観測可能条件としてのcase定義

Baselineの品質責務（1.3節）は、prompt本文の中では「〜してはならない」「〜の場合は停止する」という自然言語の禁止と義務だった。一方、Standard14の各caseは同種の責務を次の形で表している`[R3-1]`。

- 実行役へ渡すのは`trial-prompt-input.json`だけとする（model-visible）。
- 正解、期待diff、seed patch、grader、確認コマンドはmodel-invisibleとする`[R3-4]`。
- 各caseは`[C1] [C2] [C3]`のような**成果条件**、編集可能pathの閉じた列挙、禁止変更、必須検証条件、権限、制約を持つ。
- 有効な実行はすべて0〜4で採点し、「採点不能」を認めない`[R3-5]`。

すなわち、**Baselineが「推測しない」「範囲を超えない」という一般的な注意として書いていた責務は、case側では「何が未確定か」「どのpathが許可されているか」という観測可能な条件として表されている。** この形式の一致は、後の実行制御への移行（7節）と同じ方向を向いている。

**ただしこれを「Baselineの責務をcaseへ変換した」という歴史的因果として読まない。** 一次資料から確認できるのは両者の形式が同種であることであり、変換の履歴ではない。本論文の貢献はむしろ逆向きである。9責務を明示化することで、**既存の評価課題集合がそのどこを測っており、どの責務を測っていないか**を点検できるようにした（3.5節）。

### 3.2 品質責務と評価課題の対応表（主表）

**この表の「対応づけた責務」列は本論文が事後的に作った対応であり、case作成時の設計正本ではない**（3節冒頭、`[R3-1]`）。失敗方向は次の2種に分けて記載する。

- **under-execution**: 必要な行動・成果・根拠が欠落する（必須検証の未実行、成果条件の未達、読めるのに「もう無い」と誤判定して止まる誤停止を含む）
- **over-execution**: 不要な探索・変更・確認・質問・停止へ進む

## 4. 測定基盤

> **節の目的**: 3 KPIの役割を分けて定義する。
> **中心主張**: 基盤は優劣を出力しない。`quality_score`は**制約**、all-agent tokenは**主要な実行量KPI**、`elapsed_seconds`は**記述的な副指標**、その他は診断値である。
> **使用する証拠**: `evaluations/AGENTS.md`、`docs/prompt-comparison-workflow.md`、各resultの固定条件節、`v3-all-agent-token-reaccounting_2026-07-16.md`。

### 4.1 4つのLayer

評価は4 Layerに限定し、各Layerは自分の出力だけを作り、前段のartifactを変更しない`[R4-1]`。

1. **Evaluation set** — どの課題で測るかを固定する
2. **Execution** — 固定条件で指示書を実行し一次結果を保存する
3. **Quality rating** — 成果を0〜4で採点する
4. **KPI comparison** — 保存済み結果から比較viewを作る

基盤は`winner`、改善・悪化の断定、KPIの優先順位、採用可否、release判断、projection判断を**出力しない**`[R4-6]`。

### 4.2 互換条件

2つの結果を比べてよいのは、課題集合の版、対象リポジトリのref、model、実行環境、作業指示、権限、fixture、実行パラメータ、課題、反復条件、token集計版、採点契約が**すべて一致する**ときだけである`[R4-2]`。この一致を互換キー（compatibility key）で表す。

この規律の帰結として、**採点契約・推論の深さ・実行環境の版が異なる測定は連結できない。** 本文が層を分けるのはこのためであり、層をまたいだ削減率の掛け算は示さない`[R4-3]`。

| --- | --- | --- | --- | --- | --- | --- |
| 層A | 0バイト対照と静的量・動的量の乖離 | v9〜v12 | `high` | 0.144.0 | 拡張12課題ほか | 5.3, 6.4, 8.1 |

### 4.3 KPIの意味

| 指標 | 位置づけ |
| --- | --- |
| `quality_score` | **最適化対象ではなく、維持すべき品質制約。** `評価集合内のcase score合計 ÷ (4 × 評価集合のcase数) × 100`を1反復ぶんとして算出し、反復間で中央値化する。Standard14を`N=5`で実行した条件では14課題 × 5反復 = 70回、拡張12課題の`N=5`では12課題 × 5反復 = 60回となる |
| all-agent token | **親と全子エージェントの合計使用量。主要な実行量KPIであり、本研究が「実行経路が減ったか」を判定する量である。** 子1体の消費は総量へ丸ごと乗る |
| `elapsed_seconds` | 実測の所要時間。**実行順と外部負荷を統制していないため記述的な副指標として扱い、最適化対象にしない**（12.8節） |
| worker数、model再入、tool call、read、コマンドの出し方、1回で出し切れた率、誤停止件数 | **診断値。** KPI差を説明するために使い、指標へ昇格しない |

**標本の単位**: 1条件70回は「14種の異質な課題 × 5反復」であり、同一母集団からの70独立標本ではない。3指標の中央値はいずれも「14課題1周ぶんの合計（`quality_score`は得点率）を`N`回の反復間で中央値化した値」であり、中央値の実効標本数は`N`である`[R4-5]`。

### 4.4 all-agent集計が結論を反転させた事例

KPIの定義が結論を左右した実例がある`[R4-4]`。

保存していた`total_tokens`は当初root agentのusageだけだった。同じrunのrolloutからroot agentと全descendant sessionの最終usageを合算して再集計すると、拡張12課題`N=5`の中央値は次のようになった。

| 条件 | root-only中央値 | all-agent中央値 | 差 | 差 ÷ all-agent中央値 |
| --- | ---: | ---: | ---: | ---: |
| Baseline | 3,888,115 | 8,925,798 | 5,037,683 | **56.4%** |
| Candidate2（実装SAへ必須委任） | 3,841,478 | 7,381,355 | 3,539,877 | 48.0% |
| Candidate5（実装は親直接） | 4,503,816 | 5,740,441 | 1,236,625 | 21.5% |

**右端列の読み方には限定が必要である。** これは中央値同士の差をall-agent中央値で割った値であり、2つの中央値が同じiterationから来ている保証はない。したがって**「典型的なrunにおける子セッションの消費比率」としては読めない。** 言えるのは「拡張12課題・推論`high`の保存結果では、all-agent中央値とroot-only中央値の差がall-agent中央値の56.4%に相当した」ことである`[R4-4]`。run単位の`descendant_tokens / all_agent_tokens`を算出していないため、比率としての主張はしない（第12節、evidence mapの再検証候補12）。

集計範囲の誤りは方向として明確である。root-only値ではBaselineがCandidate5より`615,701`少なく見えていたが、all-agent値ではBaselineが`3,185,357`多い。**「委譲を使う条件のほうがtokenが少ない」という読みは、集計範囲の誤りだった**`[R4-4]`。

この一件は、本研究のKPI定義が「擬人的な工程がどこで実行量を生むか」を見るために必要だったことを示す。**委譲によるroot usageの低下は、all-agent総量の低下を意味しない。** この比較では、委譲先を含めるとBaselineの総量がCandidate5を上回った。**ただし「委譲は常に総量を増やす」とは言えない。** 指定の子セッションを使うD01ではWorker利用による局所的なtoken低下が観測されている（8.2節のC87）。

### 4.5 model-visible / private境界

課題は、実行役へ提示する情報（model-visible）と、採点用の正解・期待diff・確認コマンド（private）を厳密に分離する`[R3-4]`。**privateに確認コマンドが存在することと、それが実行役へ課された必須試験であることは別である**（8.6節）。

### 4.6 採点者の条件

採点者にはprompt identityとA / Bの名称を見せない（blind）。ただし**独立した第三者の採点者ではなく、固定した契約による監査である**`[R12-7]`。契約と集計側の欠陥が結論へ影響し得る（8.6節がその実例である）。

### 7.3 閉じた境界（層B）

**(1) 仕様の境界（C43）**`[R7-7]`

### 8.2 仮説B: 委譲の起動条件を細分化すれば重複作業が減る → 反証

C82〜C89は、producer規則の重複削除、Worker価値判定、実行計画、内部batching、same-wave admission、dispatch-time admissionを試した`[R8-2]`。

- 保存記録では、rootが同じ判定条件を処理しているのに独立した子セッションを起動する重複が確認された。起動の時刻条件を細かくしても、**誤って二つに分けた工程の同一性は変わらなかった**。
- C87は指定の子セッションを使うD01で親候補比token`-51.06%`を示したが、標準14項目全体ではC81比token`+6.09%`、所要時間`+1.35%`だった。**局所経路の改善を全体コスト改善へ一般化できない。**

残る規則: 子セッションの起動そのものを失敗条件にしない。先に工程の同一性と結果の消費者を確定する。rootと子が同じ判定条件を消費するなら、起動条件ではなく工程分解を疑う。

### 8.3 仮説C: 実行環境の振る舞いを指示書に書けば制御できる → 反証

C90〜C93、C96、C97は、tool出力の投影、バイト上限、結果の分類、成功後の締めを指示書で指定した`[R8-3]`。

- C96は成功した検証結果を識別子・コマンド・終了コードだけへ投影しようとしたが、成功時の標準出力は**全5件でモデルへ返った**。
- C97は検証成功後の追加判断を閉じようとしたが、**全5件で成功後に別の`git status`を発行**した（completion closure `0 / 5`）。

結論: **モデルが選べる行動と、実行環境がモデルへ返すeventを混同してはならない。** **本研究で試した条件では、指示書単独で安定して制御できたのは、返された結果の分類と後続行動の選択までだった。** 出力の変換、返却の時機、外側の待ち、adapterの原子性は、**試したprompt条件だけでは保証できなかった**`[R11-6]`。「原理的に不可能」とは述べない。

### 8.4 仮説D: 抽象的なmeta判断を足せば適切に振る舞う → 反証

C94 / C95は、担当者・risk・判断の必要性を一つのmeta判定条件へまとめた`[R8-4]`。

- C94はA02の正規な正本経路を質問へ置換した。
- C95は`N=5`を通過した。しかしB20（1,400回）では`4 / 2 / 1 = 1,398 / 1 / 1`で、score `1`はA02で不要な確認を返して未実行停止、score `2`はF06で担当者の具体的主体を質問して必須変更とtestを実行しなかった。コストもC81比でtoken中央値`+4.49%`、所要時間`+5.53%`だった。対応batchの両側正確Wilcoxon符号付順位検定をHolm補正した結果、tokenは`p=0.002325`、所要時間は`p=0.000019`で**両指標ともC81より有意に悪化**していた。この試験でC81側は`1,400 / 1,400`件が4点だった。
- 診断値では、command protocol violationがC95のみ19件 / 10 runで観測された（run単位の両側正確McNemar検定`p=0.001953`）。

**`N=5`の通過は長期安定性ではない。** これはC125にも同じ基準で適用される（12.3節）。

### 8.5 仮説E: 証拠の取得は回数や行数で打ち切れる → 反証

- C123は結果の往復回数に上限を置き、正常な状態を未確定と誤分類した`[R8-5]`。
- C124は同じ対象への追加読み取りを1回だけ許したが、取得範囲が条件を覆わずF04の誤停止を2件出し、F02の一括取得も崩した。

結論: **バイト数、行数、対象数、呼び出し数、往復回数は完了の代理値にすぎない。** 完了は「どの判定条件が必要とするどの条件を観測済みか」で決まる（C125、7.4節）。

### 8.6 仮説F: 採点契約は測定に影響しない → 反証

効率研究では、採点契約の欠陥が結論を反転させ得る`[R8-6]`。

A02は、一見あいまいだが実はリポジトリ規則で一意に決まる正しい手順を、質問せず解決して実装できるかを測る課題である。

- 実行役へ提示した成果条件は「shell構文、作業指示または適用される規則が要求する既存試験、最終差分の確認」という**抽象表現**であり、特定のコマンド名を含まない。
- 一方、採点側（private）には`git diff --check`という**特定コマンド**が置かれていた。
- 採点器はこの抽象条件を「そのコマンドの実行必須」と読み替え、未実行を欠落として減点した。
- しかしそのコマンドは末尾空白や競合markerの検査であり、A02の主眼である手順の解決とは別物である。

C71のB18でA02のscore 3は4件あり、意味確認により3件がこのずれ、1件が別の採点偽陰性と分かれた。v13がこのずれを塞ぎ、v14の`not_required_unless_model_visible`と`abstract_condition_evidence`として明文化されている。

**このずれは、当時の採用判断そのものへ影響していた**`[R8-8]`。B18（v12）の公式点数分布はC69が`4 / 3 / 2 / 1 = 1,257 / 1 / 1 / 1`、C71が`4 / 3 / 0 = 1,255 / 4 / 1`で、当時の意味確認では実質欠落がC69 1件・C71 4件、すなわち「C71側で実質的な低得点が3件多い」と分類された。これがC71の`stopped`判定の根拠の一つである。

しかし一次資料を突き合わせると、**C69の実質欠落1件もC71の3件と同じ`git diff --check`未実行である**。したがって後続のv13解釈を当てると、両者ともこの分は「要求と採点のずれ」へ再分類され、提示条件に照らした実質的な低下として残るのはC71のA01 1件だけになる。**「C71はC69比で実質的な低得点が3件多い」という当時の分類は、現在の解釈では維持されない**（正本: [`a02-rating-divergence.md`](a02-rating-divergence.md)）。

**ただし当時の判定と保存済みresultはin-placeで書き換えない。** C71の評価状態は`standard14_b18_evaluated / stopped`のままであり、release artifactに保存された当時の未解決risk 2件（A02の`3 / 90`、A01の`1 / 90`）もそのまま保持する。本論文が述べるのは、**この系列を「効率改善が品質低下を伴った例」として引用できない**ということである（13節#9）。

**一般的含意**: 抽象的な成果条件を採点側で特定手段へ具体化すれば、手段を変えた条件は実体のない減点を受ける。**効率化の測定では、効率化された側が「省略した」ように見えやすいため、この偏りは方向性を持つ。** 同型の事例は公開target側でも1件出た（10.3節）。

### 8.7 失敗候補を直系で継承しない

C121・C123・C124の規則を積み重ねず、最後に成立した親（C122）へ戻り、成功した判定条件だけを別軸として再検証した`[R8-7]`。C125がC122を直接の親にしたことがその具体例で、manifestの`baseline_identity`から確認できる。

**これは系列管理上の採用方針になったという記述にとどめる。** 直系継承した場合との比較を測っていないため、「指示書の中身と同じくらい結果に効いた」とは書かない`[R8-7]`。

## 11. 考察

> **節の目的**: 擬人的プロセスから実行制御への変換が何だったかを述べ、all-agent token低下の意味を確定する。
> **中心主張**: 変換過程では、Baselineの工程と責務を分解し、**root predicateへ移したもの、評価制約として維持確認したもの、現行構成から削除され未測定となったもの**を区別した。全責務がruntimeの観測可能条件へ変換されたわけではない。
> **使用する証拠**: 1節〜10節の各主張。

### 11.1 何が変換されたのか

Baselineの工程と、変換後に残ったものを並べる。**runtimeで残った制御と、評価課題集合で維持確認する品質責務を別の列として扱う**`[R11-1]`。評価課題集合は実行時の工程を代替しない（11.2節）。

| Baselineの工程（擬人的） | Baselineが守ろうとした責務 | runtimeで残った制御（root predicate） | 評価課題集合で維持確認する品質責務 | 変換の性質 |
| --- | --- | --- | --- | --- |
| プランSAが指示書草案を作る。草案は実行許可ではない | 境界項目をAIが補完しない | `SPEC` / `spec_ready`（成果値が明示入力または一意な正本へbind済みか。falseの間は着手しない） | A01（未確定値の停止）、F05 clarify（1回の明確化） | 常設工程を削除し、責務をroot predicateへ移した |
| 実装SAへ委任する | 実装者と判定者を分離する | `PRODUCER`（工程ごとにproducer実行identityを1つbindする） | F01〜F08の実装系case（成果条件と許可pathの遵守） | 役割の分離を、工程identityのbindへ置換した。**ただし「実装者と判定者を別主体にする」ことは保証していない**（下記） |
| 監査SAが契約準拠を判定する | 完了偽装・範囲逸脱・reward hackingの検出 | `VALIDATION_CLOSURE` / `VALIDATION_PLAN` / `TERMINAL`（必須検証の発行、結果のbind、terminal状態の判定） | F01 / F02 / F03 / F04 / F06 / F07×2（必須検証の非省略、test弱体化の禁止）、F01 / F03 / F06（reward hacking禁止）、全case（許可path外driftの禁止） | **常設の独立監査工程を削除した。runtimeに残ったのは機械的なvalidation closureであり、独立した契約準拠監査ではない**（下記） |
| レビューSAが品質確認する | テスト妥当性・周辺影響の確認 | **対応する常設制御を持たない**（rootにレビュー工程の起動predicateは存在しない） | F10×2（非破壊レビューを正しく実施できること、severity / 根拠 / 影響の提示） | **常設工程を削除した。責務のうち「レビュー作業を正しく実行できること」は評価範囲に残したが、実装runごとのレビュー実施は保証していない**（11.2節） |
| 親が監査・レビュー指摘に基づく自動再修正を最大5回まで管理する | ループの有界性、差し戻しによる欠陥修復 | **対応する常設ループを持たない**（rootに監査・レビュー指摘を起点とする再修正ループのpredicateは存在しない） | F01 / F02 / F03（`machine_rework_max=1`の遵守。**これは評価caseのTaskSpec契約であり、実行時の自動再修正ループの代替ではない**） | **常設の監査・レビュー工程とともに削除した。実装runごとの再修正はTaskSpecとruntime側の責務である** |
| 環境起因の実行失敗からの復旧 | 実行不能時の扱い | `RECOVERY`（`environment-only repair + same required command rerun`に限定。組の開始時だけ`environment_recovery_max`を消費する） | F01 / F02 / F03（`environment_recovery_max=0`の遵守） | **Baselineの自動再修正ループの置換ではなく、別種の境界である。** 回数上限そのものによる制御はC123で反証された |
| 完了判定は4者の結果が揃い指摘0件のとき | 完了偽装の禁止 | `TERMINAL`（全predicateにbind済みproducerのterminal resultがある場合だけterminal） | 全case（score 4 = 成果条件・禁止境界・明示必須試験のすべて充足） | 合意による完了を、**結果のbind状態**による完了へ置換した。4主体の合意という要件は残していない |
| 監査SAへ実装経緯を渡さない | 確証バイアスの防止（情報の非対称性） | `CONTEXT`（packetとallowed readで判定可能なら`fork_turns=none`） | F10×2（限定read範囲の直接根拠だけでレビューする） | **継承範囲を制御するpredicateは残ったが、独立した監査主体が存在しないため、監査SAが持っていた情報非対称性そのものを再現するものではない**（下記） |

**この表で最も誤読されやすい4行について、限定を明示する**`[R11-1]`。

**(1) 監査工程**: `VALIDATION_CLOSURE` / `VALIDATION_PLAN` / `TERMINAL`が担うのは、必須検証の発行、結果のbind、terminal状態の判定である。これらは、実装者から独立した契約準拠監査、reward hackingの敵対的検出、範囲逸脱の第三者判定、実装経緯を遮断した状態での完了偽装検査と**同じものではない**。正確には次のように述べる。

> 監査SAを常設する独立監査工程は削除された。runtimeに残ったのは、必須検証の発行、結果のbind、terminal状態の判定である。範囲逸脱、reward hacking、完了偽装を検出できることは固定評価課題で確認しているが、**個々の実装runにおいて独立監査が実施されることは保証していない。**

**(2) 情報の非対称性**: `CONTEXT`は継承範囲を制御するpredicateであり、**独立した監査主体が存在しない場合、Baselineの監査SAが持っていた情報非対称性そのものを再現するものではない。** 「実装経緯を見ていない主体が判定する」という構造自体は残っていない。

**(3) 実装者と判定者の分離**: `PRODUCER`は工程ごとにproducer実行identityを1つbindするが、rootが実装と検証の双方のproducerになる経路を禁止していない。**別主体による判定という要件は、常設制御としては残っていない。**

**(4) 自動再修正ループ**: Baselineの自動再修正は、監査SAの停止指摘とレビューSAの重大指摘を起点として実装SAへ差し戻す、最大5回のループだった。C125の`RECOVERY`が扱うのは`environment-only repair + same required command rerun`だけであり、**監査・レビュー指摘に基づく実装修正ループではない。** したがって両者は置換の関係ではなく、「監査・レビュー駆動の自動再修正ループが削除され、別種の環境recovery境界が残った」という関係である。

そのうえで、変換の全体像は次のように整理できる`[R11-1]`。

| 分類 | 該当する責務 |
| --- | --- |
| **(a) root predicateへ移った責務** | 仕様確定（`SPEC` / `spec_ready`）、完了判定（`TERMINAL`）、必須検証の発行と完了判定（`VALIDATION_CLOSURE` / `VALIDATION_PLAN`）、継承範囲の制御（`CONTEXT`）、環境起因の復旧（`RECOVERY`） |
| **(b) runtimeから削除されたが、評価課題集合で能力または禁止境界を確認している責務** | 非破壊レビュー（F10×2）、範囲逸脱・reward hacking・完了偽装の防止（F01 / F03 / F06、全caseの許可path境界） |
| **(c) runtimeから削除され、現行評価集合でも同等能力を直接確認していない責務** | **監査・レビュー指摘に基づく自動再修正ループ**（差し戻し、再監査、再レビューを最大5回まで回す能力）。`machine_rework_max=1`は評価caseのTaskSpec契約であり、同じ責務ではない |

**(c)は「評価集合側へ移った」とは言えない。** runtimeにも評価課題集合にも同等形が残っておらず、**削除されたまま能力が未測定である**。これは本論文が特定した未解決の境界であり、再検証候補として分離した（12.12節、evidence mapの再検証候補17）。

**残った工程の残り方**: (a)は擬人的な担当者としてではなく、発行単位と結果のbind状態として残った。

**この対応表は本論文が構成した解釈である。** 各行が「意図的な置換」として記録されているのは、C35（7 targetの置換）、C43（`SPEC`の置換）、C118（terminal化）などの個別manifestに限られ、全体を1つの変換として設計した記録はない`[R11-1]`。

### 11.2 評価課題集合はruntime制御を代替しない

11.1節の表で最も誤読されやすいのは、**レビューSAの行と監査SAの行**である。**F10を評価課題集合へ置いたことは通常の実装runにおけるレビュー工程を代替せず、同様に、F01〜F07で必須検証の非省略とtest弱体化の禁止を確認していることは、実装runごとの独立監査を代替しない**`[R11-1]`。

両者は別の問いに答えている。

| | 評価課題集合（F10、およびF01〜F07の禁止境界） | 実行時のレビュー／独立監査責務 |
| --- | --- | --- |
| 問い | 候補promptがレビュー作業を正しく実行できるか。範囲逸脱・reward hacking・完了偽装をしないか。何を品質として測るか | TaskSpecでレビューまたは独立監査が要求されたか。runtimeでその工程が起動されたか。実装runごとに独立した判定結果が得られたか |
| 単位 | 固定されたcaseに対する0〜4のscore | 個々の実装runにおける工程の実施 |
| 判定主体 | 固定契約による採点（実行後） | 実行中の独立した監査主体 |
| Layer | Evaluation set / Quality rating | Execution |

評価基盤自身が、Evaluation set、Execution、Quality rating、KPI comparisonを**別Layer**として定義している（4.1節）。**評価課題集合はruntime mechanismではない。**

したがって正確には次のように述べる。

> レビューSAと監査SAを常設する実行工程は削除された。一方、非破壊レビューを正しく実施できること、および範囲逸脱・reward hacking・完了偽装をしないことは、固定評価課題（F10×2、F01 / F03 / F06、全caseの許可path境界）を通じて評価範囲に残した。**評価課題集合は実行時のレビューや独立監査を代替するものではなく、候補promptが満たすべき品質制約を定義する。** 実装runごとのレビューまたは独立監査が必要な場合は、TaskSpecがそれを要求し、runtimeがその工程を起動する必要がある。

**runtimeに残っているのは、必須検証の発行・結果のbind・terminal判定という機械的なvalidation closureである**（11.1節の限定(1)）。これは検証が実行され結果が揃うことを閉じるが、「実装した主体とは別の主体が契約準拠を敵対的に判定する」という構造を持たない。

### 11.2.1 品質責務と工程の分離が必要だった理由

Baselineは、品質責務と工程を同じ文章の中で表現していた。「監査SAが停止指摘を出すまで完了しない」は、責務（完了偽装の禁止）と工程（監査SAの起動）を一体で述べている`[R11-2]`。

この一体化には2つの帰結があった。

1. **工程への経路を外すと責務も落ちる。** `ControlFreeRepository`は工程文書を残したまま、rootからその工程へ入る経路を外した結果、A01（責務1・2）を`5 / 5`で落とした。C35は工程仕様7ファイルの内容自体を空へ置換し、やはりA01を`5 / 5`で落とした（6.2節）。**前者は経路の非活性化、後者は静的artifactの除去であり、両者は別の操作である**`[R6-2]`。
2. **責務を守るために不要な工程を払い続ける。** 拡張12課題の保存結果では、Baselineのall-agent中央値とroot-only中央値の差がall-agent中央値の56.4%に相当した（5.3節）。実装目的の委譲は、選択可能にすると`0 / 40`件しか選ばれなかった（5.3節）。

**分離が必要だったのは、削るべき工程と守るべき責務を別々に扱えるようにするためである。** 評価課題集合は品質制約の観測側の受け皿であり（3節）、rootのpredicate集合が実行制御側である（7節）。**両者は同じ責務の別側面を担っており、一方が他方を代替するわけではない。**

### 11.3 all-agent token低下が意味するもの

**本節が扱うのはall-agent tokenの低下である。** 3 KPIのうち`quality_score`は制約、`elapsed_seconds`は記述的な副指標であり（4.3節）、11.3節の表で「低下」として示す列はすべてall-agent token中央値である。**「KPIが低下した」と一括しない。** 解釈は次に限定する`[R11-3]`。

**token低下を「費用削減」として扱わない理由**: 目的関数はAPI料金の削減ではない。C81の採用根拠は効率改善ではなく検証の発行経路の安定化であり、C118はtokenが`+7.44%`でも機構成立として記録され、C125の採用根拠は品質の回復と目標到達である。

**all-agent token低下を「不要な実行経路の減少」として読める条件**（4.3節の定義に対応）:

1. 比較可能な条件（互換キー）が一致している。
2. case scoreの分布を確認している（中央値の一致を品質の一致と読み替えない）。
3. 必要な品質責務が欠落していない。
4. token低下が検証省略・推測・過剰停止によるものではない。
5. 診断値またはtraceが、不要経路の減少という解釈に整合する。

**5条件は2段に分かれている。** 条件1〜3は「品質制約下でall-agent tokenが下がった」ことを判定し、条件4〜5は「その低下を不要経路の減少として解釈できる」ことを判定する。**この2段を1つの表へまとめない。**

#### 表A: 品質制約下でall-agent tokenが低下した比較（条件1〜3を満たす）

### 11.4 収支の式（解釈モデル）

次の式は、**観測されたtoken差を解釈するための概念モデルとして用いる。各項を独立に計装したものではない**`[R11-5]`。

```text
正味token差
= 制御文の読解cost
 + 追加された判断・確認cost
 - 回避できた探索・context継承・再読・再試行・手戻りcost
```

第3項が第1項・第2項を上回るときだけ、制御は正味で効く、という読み方をする。C69 / C71等の診断値（tool callとモデルステップの減少）は、回避されたモデル再入が差へ寄与したという解釈に整合する。表面圧縮系（8.1節）は第1項だけを減らして第3項を動かせなかったという解釈に整合し、C94 / C95は第2項を増やしたという解釈に整合する。

**ただし「どの項が支配的だったか」は測定結果ではない。** 3項はいずれも独立に計装しておらず、項別の寄与を算出していない。

### 11.5 promptで強制できる範囲と、runtime機構へ移すべき制御

**本研究で試した条件では、指示書単独で安定して制御できたのは、返された結果の分類と後続行動の選択までだった**`[R11-6]`。tool output変換、return timing、outer wait、adapter atomicityは、**試したprompt条件だけでは保証できなかった**（8.3節のC90〜C97、C105〜C111）。**「原理的に不可能」とは述べない。**

安定して効果が確認された機械的な制御を自然言語の指示書へ積み増し続けない、という方針は固定されている。型付きの作業指示、権限gate、scheduler、検証の依存グラフ、終端状態などの機構へ移す候補として扱う。**ただしその移行の実装はこのリポジトリの作業範囲ではない。** 本論文はこれを未解決の境界として記述するにとどめる。

### 11.6 実務での保守費用

制御を維持する費用は小さくない`[R11-7]`。

| 何が変わったか | 何が起きたか |
| --- | --- |
| Codex CLI `0.144.0 → 0.146.0` | 公開target側でC81とC125の互換キーが一致しなくなり、**tokenと所要時間の比較そのものが成立しなくなった**（10.2節） |
| model `Sol → Terra / Luna` | 同じ本文で品質とコストが維持されなかった（10.1節） |

壊れ方には型エラーのような即時の失敗がない。**比較が静かに無効化されるか、特定課題で低頻度の誤停止・探索拡大として現れる。** 後者の実例がC95で、`N=5`は通過しB20（1,400回）で2件だけ落ちた（8.4節）。

この壊れ方を検出するには反復測定が必要である。C125条件の70回が公開API単価換算で`$15.5472`だったので、同じ課題構成を仮定した線形外挿では標準14項目B20（1条件1,400回）が約`$311`、2条件比較で約`$622`である。**これは換算値の外挿であり、実請求額でも実測値でもない。** 設計、事前チェック、採点監査、結果登録にかかる人間の時間も含まない`[R12-11]`。

そして本研究は、制御の便益（確認して止まる、誤停止しない、手戻りが減る、待ち時間が短い）を**利用者側の価値として測っていない**`[R12-12]`。したがって「保守の手間に見合うか」という問いへ数値で答えられない。答えられるのは、どの制御が何を変えたかまでである。

## 13. 結論

> **節の目的**: 最終KPI値ではなく、観測されたこととその限定を結論として述べる。
> **中心主張**: 品質制約を維持しながら**all-agent token**を小さくした候補に共通していたのは、擬人的な工程全体の保持ではなく、仕様・証拠・実装・検証・停止を実行時に観測可能な条件として表した境界である。

**中心的な結論**`[R13-1]`:

> 人間中心の開発工程をpromptへ移植した初期解から出発し、その品質責務を明示化して既存の評価課題集合と対応づけ、実行経路をall-agent単位で測定した。**観測した評価範囲では、擬人的な工程仕様全体を保持しないbundleでも品質制約を満たした。** 品質制約を維持しながら**all-agent token**を小さくした候補に共通していたのは、仕様、証拠、実装、検証、停止を実行時に観測可能な条件として表した境界である。**所要時間は外部負荷を統制していない記述的副指標であり、この主張へ含めない。**

**この結論が述べていないこと**: どの境界が不可欠か、境界の集合が最小か、境界の追加順序に必要性があるか。ablationと順序入れ替えを測っていないため、いずれも判定できない`[R7-14]`。また品質を支える要素には、境界以外にmodelの既定能力、TaskSpec、path別`AGENTS.md`、repository authority、fixtureと対象リポジトリの状態、executorの挙動が残っている。

この結論を支える観測を列挙する。

1. **Baselineは、当時の拡張12課題評価において一定品質を示し、研究開始時点では品質確保の初期解として扱われていた。** 拡張12課題60回で`4 / 3 = 58 / 2`、品質中央値`100.000`。**ただし2件の減点があり、2.1節の「全課題で減点なし」という品質制約を完全に満たしていたわけではない。**保存された失敗内容の分類に、範囲逸脱・reward hacking・完了偽装・対象外操作は現れていない`[R1-6]`、`[R5-2]`。
2. **評価範囲をStandard14へ拡張すると、未確定値の確認停止、正本からの一意解決、必須検証の非省略に残余欠陥が見つかった。** 層B 70回でA01が4件、A02が2件、F07依存関係が1件`[R5-1]`。
3. **拡張12課題・推論`high`の保存結果では、Baselineのall-agent中央値とroot-only中央値の差がall-agent中央値の56.4%に相当した。** 委譲を選択可能にすると、実装目的の委譲は`0 / 40`件しか選ばれなかった。**この56.4%は中央値同士の差から算出した割合であり、run単位の子セッション消費比率ではない**`[R5-3]`、`[R5-4]`。
4. **rootの制御文だけを外すとtoken中央値は`-70.80%`（層B）／`-74.06%`（層A）になったが、A01は`5 / 5`落ちた。** 「lean」の最適点は0ではない`[R6-1]`、`[R6-3]`。
5. **静的量の減少は動的tokenの減少へ一貫して対応しなかった。** 表面量を操作した8件（圧縮を主目的とした7件＋全文重複の対照C64 1件）のうち7件で実行時tokenが増加または実質不変だった。**この系列が示すのは、静的なバイト数を動的実行量の代理指標として使用できないことである。** 集計軸が候補間で異なるため効果量の横断比較は行わない`[R8-1]`、`[R12-8]`。
6. **擬人的な工程仕様7ファイル（約59KB）が空ファイルへ置換された。** C35のmanifestは、保存済み観測で当該7 targetへの参照が成功実行に現れなかったことを置換の設計理由として記録している。**対応するraw command evidenceは本リポジトリに保存されていないため、本論文はこれを歴史的な設計記録として扱う。** byte数と0バイト化はbundle実体から確認できる`[R7-5]`。
7. **最終到達点C125には、探索過程で識別・精緻化された複数の実行境界が継承・統合されている。** 研究過程で識別された境界ファミリーは9件、C125のroot本文のlabelは13件、`synthesis`がC81以降の寄与として記録しているのは7件であり、**この3つは別の集合である**（7.5節、7.7節）。いずれもモデルが実行時に観測できる条件として書かれている`[R7-1]`。**各境界の追加が単独でKPIを低下させたとは限らない**（C81は所要時間`+5.78%`、C118はtoken`+7.44%`、C122は品質`69 / 70`）。**順序の入れ替え・同時追加・ablationは測っておらず、各境界の必要性も集合の最小性も示していない**`[R7-14]`。
8. **効かなかったのは、表面圧縮、委譲条件の細分化、実行環境側の挙動の指定、抽象的なmeta判断、量による証拠の打ち切りである**`[R8-1]`〜`[R8-5]`。
9. **少数反復の通過は分布の裾にある低頻度欠陥を除外しない。** C95は`N=5`を通過したが、B20（1,400回）で2件の品質未達とcommand protocol violation（19件 / 10 run）が観測された`[R8-4]`。**C95はC81比でtoken`+4.49%`・所要時間`+5.53%`であり、効率を改善した候補ではない。** また、C69 / C71のv12評価ではC71側の公式点数分布に追加の低得点が観測されたが、**後続分析によりA02の3件は「要求と採点のずれ」へ再分類された。したがってこの結果を実質的な品質低下の代償としては扱わない**`[R8-8]`。**本研究は「効率改善が品質低下を伴った」比較を確立していない。**
10. **採点契約そのものが結論を歪め得る。** 抽象的な成果条件を採点側で特定コマンドへ具体化する欠陥を検出し、v13で塞いだ。この偏りは効率化された側を不利にする方向を持つ`[R8-6]`。
11. **同じ指示書でもmodelを変えると品質とコストは維持されなかった。** LunaではC43が閉じたA01の失敗形（未解決値のまま試験へ進行）が再び現れた。**指示書とmodelの組を評価・採用の単位とする**`[R10-2]`。
12. **常設のレビュー工程と独立監査工程は削除された。** runtimeに残ったのは、必須検証の発行・結果のbind・terminal判定という機械的なvalidation closureである。レビュー作業を正しく実施できること、範囲逸脱・reward hacking・完了偽装をしないことは固定評価課題で確認しているが、**評価課題集合はruntime mechanismではなく、実装runごとのレビューまたは独立監査の実施を保証しない**`[R11-1]`。
13. **C125は終点ではなく、後続探索における現在の設計到達点である。** B20未実施、`N=100`未着手、長期・部分曖昧タスク未測定`[R9-2]`、`[R12-3]`、`[R12-4]`。

最後に、本基盤が一貫して分離してきた区別を再掲する。**評価は観測であり、採用は判断である。** 基盤は勝者も採否も出力しない。C71が評価上`stopped`のまま反映され、C125の一次結果が`adoption_not_decided`のまま別状態で採用・反映されている事実は、この分離が運用上も維持されていることを示す`[R4-6]`。
