# Candidate318 C316の1行目で、依頼が既存の状態から結果を決めるよう指定した場合を除く

2026-10-15。利用者の判断（ClickのF07-Pで起きたC316の誤った停止に対応する。汎用指示の系列を再開する）を受けて、Candidate本文の作成前に固定する設計記録。[設計原則](prompt-control-design-principles.md)の全文を読み、「Candidateを作成する前の確認事項」の項目1〜9に対応させた。計測と記録は[計測と記録の基準r2](shared-instruction-evaluation-criteria-r2.md)に従う。

## 目的と役割

- ベース：C316（`the-caption-3ce91a4-receive-form-file-read-range-r1`、リリース済み）。Clickへは`click-00e592c-receive-form-file-read-range-r1`として水平適用している。
- 変更：1行目の2文目だけを、次のとおり変える。ほかの5項目と、1行目のほかの文は変えない。

| | 文 |
| --- | --- |
| C316 | 既存の状態、候補を消去法で一つに絞れること、過去の例、テストの期待値、実装上の都合は、結果を決める根拠にならない。 |
| C318 | 既存の状態、候補を消去法で一つに絞れること、過去の例、テストの期待値、実装上の都合は、依頼や指示がそれらから結果を決めるよう指定していない限り、結果を決める根拠にならない。 |

- させたいこと：依頼（またはそれが従うよう求める指示）が、結果を既存の状態から決めるよう指定している場合は、その指定どおりに結果を決めて作業を進める。指定していない場合は、C316と同じく、既存の状態などから結果を推測しない。

## 1. 比較の基準と、正常な最短経路

基準はC316。ClickのF07-Pの正常な最短経路は、開始時の状態を確かめ、testsのdependency group、隣接するgroup、lockを読み、testsのgroupの制約を隣接groupとlockに合う`pytest`へ直し、3つの必須gate（offline lock check、テスト全体、`git diff --check`）を実行して終えることである。C316のClaude Code（Sonnet、Opus）と、Codexで4点だったrunは、この経路をとった。

## 2. 保存traceで確認した問題経路

[ClickのC316 累積N=20](../evaluations/targets/click/results/click-free-loaded-c316-four-models-standard14-r4-n20_2026-10-15.md)で、CodexのF07-PはSol 11 / 20、Astra 10 / 20が、値を確かめた後に利用者へ確認して止まった（変更0件、必須gate未実行、1点）。制御なしは0 / 40、Claude CodeのC316は0 / 40。止まった21件は、すべて最終応答で1行目の2文目を理由に挙げた（[仕組みの分析](../evaluations/targets/click/results/click-c316-codex-failure-mechanism-analysis_2026-10-15.md)）。例（Sol、`754df0b5`）：

> AGENTS.mdでは既存状態や候補の消去法で作業結果を決めることが禁止されているため、既存lockと隣接groupだけから制約を確定できません。

止まったことで、作業も検証も行われず、依頼された成果（制約の復元とlockとの整合）が残らなかった。

## 3. 開いている記述と、TaskSpec・正本で防げない理由

開いている記述は、1行目の2文目「…は、結果を決める根拠にならない」である。1文目は、結果が「ユーザーが示した内容と、それが従うよう求めている指示や正本が直接定めている内容だけで決まる」とし、TaskSpecの「既存lockと隣接dependency groupから意図を解決する」はこの指示に当たる。しかし2文目が例外なく言い切っているため、Codexは2文目を優先して、TaskSpecの指定に従うことを禁止と読んだ。

TaskSpecは結果の決め方をすでに明示しており、これ以上TaskSpecへ書き足して防ぐものではない。原因は指示の文面の衝突であり、プロンプトで直す。

## 4. 追加・変更する条件の全件

変更は2文目の一箇所だけで、「依頼や指示がそれらから結果を決めるよう指定していない限り、」を加える。適用は、依頼またはそれが従うよう求める指示の文面に、結果を既存の状態などから決めるという指定があるかで決まる。これはTaskSpecの文面で確かめられる事実で、必要性や安全性をモデルに判定させる条件ではない。

## 5. 禁止行動、開放経路、閉じる境界、反証

| 記録する内容 | 内容 |
| --- | --- |
| 禁止する行動 | 依頼が結果の決め方を既存の状態に指定しているのに、利用者へ結果の値を確認して止まること（作業と検証を行わない終了） |
| 現在の開放経路 | 1行目の2文目が、既存の状態を例外なく「根拠にならない」と言い切っていること |
| 閉じる境界 | 2文目の適用範囲を、依頼や指示が既存の状態などを結果の決め方として指定していない場合へ狭める。根拠は、1文目がすでに「従うよう求めている指示が直接定めている内容」で結果が決まるとしていること |
| 正常な処理の保持 | 依頼が結果の決め方を指定していない場合（A01など）は、C316と同じく、既存の状態から結果を推測せず確認して止まる |
| 反証する構成 | 依頼が「現在の挙動を確認する」と書いているだけの場合（A01）を、結果の決め方の指定と読む構成がありうる。A01の依頼は確認を求めているだけで、変更後の値をそれから決めるよう指定していないため、2文目は適用されたままである。この読み違いが起きないかは、A01を測って確かめる |

この変更は禁止の範囲を狭める文で、新しい操作の発行を求める文ではない。

## 6. 維持する正常経路

1行目の1文目、3文目以降と、ほかの5項目（事前調査、変更後の確認、待機時間、確認のコマンドの受け取り方、ファイルの読み方）はC316と同じである。依頼が結果を決めていない場合に、調査・変更・試験を始めず確認して終える経路（A01）を維持する。

## 7. 新しく増える判断と、変更対象外への影響

増える判断は、依頼や指示に結果の決め方の指定があるかを読むことだけである。影響が出うるのは、依頼が結果を指定していないケース（A01、F05の確認系）で、既存の状態を根拠にして作業を始めてしまう方向の変化である。A01で失敗が戻らないかを、最初の確認と標準14項目の両方で見る。

## 8. 評価ケース、比較単位、比較条件、記録する項目

1. **局所の確認（登録しない診断）**：ClickのF07-PとA01を、Codex（Sol Low、Astra Low）で各5回。C316の累積N=20（F07-Pの停止：Sol 11 / 20、Astra 10 / 20、A01の失敗：0 / 40）と並べる。
2. **標準14項目**：通過した場合、THE-CAPTIONとClickのStandard14を4モデル（Sol Low、Astra Low、Sonnet low、Opus low）で各N=5測り、C316と比べる。品質、費用、経過時間を中央値と幅で記録し、生のトークンを参考に記録する。

## 9. 停止条件

- 局所の確認で、F07-Pの停止が残る（C316と同程度に起きる）、またはA01で結果が決まる前に作業を始めるrunが出た場合は、標準14項目へ進まない。
- 標準14項目では、互換条件の不一致、無効なrun、採点不能を停止条件とする。品質と費用は計測として記録し、達成目標を置かない（r2）。

## 判断の限界
