# Candidate306 C302の成功後の一項目を、TaskSpecが求める確認で区切る

2026-10-09。ベースをC302に決め、その弱点を潰す作業の一つとして、Candidate本文の作成前に固定する設計記録。[設計原則](prompt-control-design-principles.md)の全文を読み、「Candidateを作成する前の確認事項」の項目1〜9に対応させた。計測と記録は[計測と記録の基準r2](shared-instruction-evaluation-criteria-r2.md)に従う。この記録ではbundleを作成しない。

## 目的と役割

- 系列：実行環境を切り離し、負荷を見て次のrunを始める発行の条件（CPU使用率70%以下、間隔1秒）で測る系列。
- ベースと直接の親：C302（`the-caption-3ce91a4-uniform-success-closure-and-wait-time-r1`）。比較の基準は、同じ条件で測ったC302のSonnet low（`-r2`）。
- 利用者の指示により、Sonnet lowで確立するまでSolは測らない。
- 評価は計測であり、達成目標を置かない（r2）。
- 変更対象：C302のroot `AGENTS.md`の、C298の一項目だけを置き換える。C299の一項目、C301の本文、他の18対象はC302とバイト一致を保つ。

## 1. 比較の基準と、正常な最短経路

基準はC302（`-r2`）。変更を伴うケースの正常な最短経路は、開始時の確認と読み取り → 変更 → TaskSpecが求める確認（すべて） → 報告である。TaskSpecは、ケースによって、必須のテストに加えて`git diff --check`や変更pathの確認を求める（例：F07の`F07-C3`は「`bash scripts/dev/main_verify.sh`、`git diff --check`、変更path確認で判定する」）。

## 2. 保存traceで確認した問題経路

C302のSonnet low（`-r2`、70件）で、次を確認した。

- F07（反復4、run `6d3a5577…`）は、`main_verify.sh`の成功を受けた後、TaskSpecが`F07-C3`で求める`git diff --check`と変更path確認を実行せずに報告した。報告には「確認コマンドが成功した後はコマンドを発行せず報告する、というCLAUDE.mdの指示に従ったため」と書かれ、`F07-C3`が未完了であることを自ら述べている。F06とF07で`git diff --check`が成功した件数は、C302が10件中9件、C301 `-r5`とC304は10件中10件だった。
- 同じrunとF01（反復3、run `c6d0e449…`）は、`main_verify.sh`の出力が退避されて終了コードが見えないまま、退避された出力を読まずに報告した。

C298の一項目「必須の確認コマンドがすべて成功した結果を受け取った後は、コマンドを発行せずに報告する。」の「必須の確認コマンド」に何が含まれるかを、モデルが決めている。最初の大きな確認が通った時点で「すべて成功した後」に当たると判断し、TaskSpecが求める残りの確認まで止めていた。

## 3. 開いている記述と、TaskSpec・正本で防げない理由

TaskSpecは求める確認を列挙しているが、C298の一項目は、その列挙と結びついていない。一項目が「必須の確認」をTaskSpecと別の言葉で指すため、どの確認の後に発行を止めるかの判断がモデルに残り、TaskSpecの列挙では防げない。

## 4. 追加・変更する条件の全件

C302のC298の一項目を、次の一文に置き換える。

> - TaskSpecが求める確認がすべて成功した後は、TaskSpecが求めていないコマンドを発行せずに報告する。

- 止める時点を「TaskSpecが求める確認がすべて成功した後」とし、何が求められているかの根拠をTaskSpecの列挙にそろえた。
- 禁止する対象を「TaskSpecが求めていないコマンド」に限った。TaskSpecが求める確認（`git diff --check`、変更path確認など）は、この文では止まらない。
- 既存の操作の発行を禁止する文であり、新しい操作の発行を求めない。

## 5. 禁止行動、開放経路、閉じる境界、反証

| 項目 | 内容 |
| --- | --- |
| 禁止する行動 | rootが、TaskSpecが求める確認がすべて成功した後に、TaskSpecが求めていないコマンドを発行する |
| 現在の開放経路（C302） | 「必須の確認」の範囲をモデルが決めるため、求められていない状態確認を続ける経路と、求められた確認まで止める経路の両方が開いている |
| 閉じる境界 | 操作の発行。止める時点も、禁止の対象も、TaskSpecの列挙という、モデルに見える入力から決まる事実で定める |
| 正常な処理の保持 | TaskSpecが求める確認は、すべて実行できる。確認が失敗した場合の修正と再実行は「すべて成功した後」に当たらず、妨げない。退避された出力の読み取りなど、成功を確かめる前の操作も妨げない |
| 反証する構成 | 求められていない状態確認を「完了の確認」と位置づけても、TaskSpecが求めていないので禁止に当たる。TaskSpecが求める確認を一部だけ実行した段階では「すべて成功した後」に当たらない |

## 6. 維持する正常経路

- Claude Codeは、課題文の指定どおり、求められた確認を個別の`Bash`呼び出しで実行する。この文はその指定に触れない。
- Codexの経路では、C298の一項目と同じく成功後のコマンドを止める。TaskSpecが求める確認を含めた後に止まる点だけが変わる。

## 7. 新しく増える判断と、変更対象外への影響

- 新しい判断：コマンドがTaskSpecの求める確認に当たるか。TaskSpecは確認を具体的なコマンドや判定の言葉で列挙しており、確定した入力から決まる。
- 危険1：TaskSpecが「変更path確認」のように操作を言葉で求める場合、`git status`や`git diff --name-only`などがそれに当たると判断され、C302より成功後のコマンドが増える。TaskSpecが求める確認なので、正常な処理である。
- 危険2：Sonnet lowの出力の形（C302の弱点2）は、この変更の対象ではない。C305で切り分ける。
- 固定分：置き換える文の差（改行を除き、C298の文は131バイト、新しい文は135バイト）。

## 8. 評価ケース、比較単位、比較条件、記録する項目

- セル：Sonnet lowのStandard14の全14ケースN=5の計70件。
- 比較条件：C302のSonnet low `-r2`と同じで、prompt identityだけを変える。
- 記録する項目（r2）：品質、処理の適切さ（TaskSpecが求める確認をすべて成功させてから報告したか）、費用、経過時間（内訳を含む）、生のトークン（参考）。
- 機序の診断（合否にしない）：F06とF07の`git diff --check`の成功件数、TaskSpecが求める確認を実行せずに終えたrunの件数、退避された出力を読まずに終えたrunの件数、最後に成功したfull gateより後のコマンドの回数（C302の診断と同じ数え方）。
